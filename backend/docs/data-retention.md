# 업무 데이터 삭제·보관 작업 명세

Jira: [S15P31D109-157](https://ssafy.atlassian.net/browse/S15P31D109-157). 변경 범위는 backend 내부다. 계획 → 구현 → 검증 순으로 진행하며, 기존 001~044는 변경하지 않고 045 하나를 적용한다. 운영 DB에서 migration·폐기는 실행하지 않는다.

## 보관 기준과 삭제 의미

| 대상 | 일반 삭제 | 실제 폐기 기준 |
|---|---|---|
| 통화, 분석, AI 이벤트, 미답변, 연결 요청, STT, 녹취, 연결 PBX 수신 | 통화 deleted_at으로 함께 숨김 | 최초 incoming_at + 5년 |
| 주문, 상세, 배송, 결제 요청·청구 상세 | 주문 deleted_at으로 함께 숨김 | 최초 완료/취소 시각 + 5년, 미완료는 생성 시각 + 5년 |
| 관리자, 기업, 부서, 소속, 개인/기업 PIN, FAQ | deleted_at, 원본·논리 참조 유지 | deleted_at + 5년 |
| 삭제한 고객 정보 | deleted_at으로 숨김, 남은 주문 FK가 필요하면 식별자만 보존 | deleted_at + 5년 후 이름·전화번호·주소 폐기. 기존 WITHDRAWN 상태 전환은 별도이며 그 동작은 유지 |
| 감사 로그, 전송 완료한 알림 기록 | 사용자 삭제 API 없음 | 발생/완료 후 7일 |
| 미연결 PBX 수신 | 기존 방식 유지 | 수신 후 30분 |

기간은 PostgreSQL 달력 기준 5년이며 읽기·수정·재전송·soft delete가 원래 기준을 연장하지 않는다. 통화 수신 시각이 없는 과거 행은 실제 PBX 시작 등 확인 가능한 원본으로만 보완한다. 확인 불가능한 행은 별도 점검 대상으로 남기며 임의로 현재 시각을 넣지 않는다. 운영 중인 결제 승인·접수·녹취 업로드와 충돌하는 폐기는 중단하고 다음 주기에 재시도한다.

기존 취소 주문은 성공한 최초 취소 감사 기록을 사용한다. 기록이 없으면 생성 시각을 보수적으로 사용하여 수정 시각 때문에 보관이 연장되지 않게 한다. 기존 접수 완료 주문은 dver_received_at을 사용한다. 고객·PIN의 신규 DELETE API는 추가하지 않으며 기존 상태 변경은 삭제로 바꾸지 않는다.

## 구현 범위와 순서

1. 045에서 deleted_at, 주문 완료 시각, 주문 생성자·페르소나 작성자 이름 스냅샷을 추가한다. 기존 감사 기록으로 확인 가능한 값만 보완한다. 활성 행에만 적용하는 UNIQUE 인덱스로 같은 로그인·사원번호·FAQ의 재등록을 지원한다. 미답변 삭제는 원문을 남기도록 제약과 쓰기를 함께 바꾼다.
2. 기존 관리자·기업·부서·소속·FAQ 삭제를 UPDATE로 전환한다. 관리자 세션은 즉시 폐기한다. 기업 삭제는 기존 advisory lock → 고객 → 기업·부서 순서를 유지하고 하나의 트랜잭션으로 소속·부서·PIN을 함께 숨긴다.
3. 주문/통화 관리자 DELETE를 추가한다. 인증·Origin 검증·감사 기록을 유지하고 처리 중인 업무는 409로 막는다. 정상 204, 없거나 삭제된 대상 404다. 일반 조회·검색·건수·AI 입력·PIN/결제 자격·녹취 URL 발급에서 삭제된 루트를 제외한다. 과거 청구 총액은 soft delete로 변경하지 않는다.
4. bounded batch와 DB advisory lock/행 잠금을 사용하는 정리 워커를 추가한다. FK 순서에 따라 자식부터 폐기하며 승인 결과가 미확정인 결제는 먼저 복구해야 한다. 기존 주문 상세 불변 트리거는 만료가 확인된 정리 트랜잭션에만 물리 삭제를 허용한다.
5. 녹취 객체는 DB 키를 보존한 채 외부에서 삭제하고 성공을 확인한 후 DB에서 제거한다. 버전 관리 버킷의 과거 버전·delete marker까지 처리한다. 실패 시 키를 남겨 재시도하며, 외부 요청 동안 DB 트랜잭션을 열어 두지 않는다. PBX 업로드 lease와 경쟁하지 않는다.

세션 로그아웃·만료 정리, 확정한 페르소나 임시 초안 소비, 30분 미연결 수신 정리, 보관 만료 후 실제 폐기는 물리 삭제를 유지한다. 삭제 복원 API/UI는 이번 범위에 포함하지 않는다.

## 영향 확인과 검증 계획

- 새 DB 전체 migration과 044까지 데이터가 있는 DB의 045 적용·롤백 검증. 기존 값·버전·FK·결제 금액 보존 확인.
- 관리자 삭제 후 세션 무효화와 같은 로그인 재가입, 기업·부서·소속 삭제 후 고객/주문/통화/청구 이력 보존 및 재등록 확인.
- FAQ 단건/복수 삭제, AI 조회/알림, 미답변 원문 보존과 재전송 방어 확인.
- 주문·통화 DELETE 인증/Origin/역할/진행 중 차단, 목록·총건수·상세·주소 이력·재생·AI 입력 차단 확인.
- 최초 수신/완료 시각의 5년 경계와 7일 로그 경계, 늦은 AI/PBX 재전송, 두 워커의 동시 실행, 외부 저장소 실패 재시도, FK 삭제 순서 확인.
- 기존 인증·회원·청구·결제 승인/복구·취소·접수·실시간 통화 수 회귀 및 전체 Linux 검증 실행.

## 운영 적용 전 필요한 작업

기존 앱 중지 → DB/녹취 백업 → 045 한 번 적용 → 새 앱 시작 순서다. 구버전 앱과 혼용하면 숨긴 데이터를 다시 노출할 수 있어 금지한다. 운영 Docker/호스트 로그의 7일 보관, 백업·복제본·외부 AI 및 PBX 원본의 5년 폐기, S3 삭제 권한·Object Lock·복제 버킷 정책은 backend 코드만으로 보장할 수 없다. 필요한 설정은 구현 결과와 함께 별도로 보고한다.

## 검증 결과

- 1차 스키마 검증: 격리 PostgreSQL 17에서 기존 데이터가 있는 044 → 045 적용/전체 롤백, 원본 버전·시각·작성자 보완, 활성 UNIQUE 재등록, FK 25개·업무 트리거 10개 보존 및 실제 배포 검증문을 포함한 14개 테스트 통과.
- API·워커·전체 회귀 결과는 해당 구현 검증 후 추가한다.
