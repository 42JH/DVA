# 백엔드 최적화 작업 기록

- 기준: `develop-backend` / `f20206a3947dcf6467c9a1674aee76d280940252`
- 브랜치: `refactor/backend-optimization`
- 변경 범위: `backend/`, `infra/`, 루트 Jenkinsfile. 프론트·AI 코드는 수정하지 않는다.
- API URL·요청·응답·인증·오류 코드·정확한 total_count·일괄 등록의 원자성을 유지한다.
- 각 작업은 계획 → 구현 → 검증 → 채택 또는 복구 순으로 진행하고 독립 커밋으로 기록한다.
- 실제 서비스 DB와 배포 작업은 이 기록의 로컬 적용·격리 검증과 구분한다.

## 변경하지 않는 설계

- Redis는 실측 필요성이 확인될 때 검토한다. 현재 PostgreSQL inbox/outbox와 멱등 처리를 유지한다.
- 모듈 내부 FK, 주문 주소·청구 명칭·결제 원본 등 이력 스냅샷은 유지한다.
- 모듈 간 FK 제거와 PIN 부서명 정규화는 소유권·삭제 정책·검색 조건 변경이 필요하므로 일괄 적용하지 않는다.
- 적용된 SQL migration은 고치지 않고 필요한 새 migration만 추가한다.
- 배송상세 수 제한, AI 알림 JSON 변경, 프론트 변경을 최적화에 포함하지 않는다.

## 검증 환경과 결과

- 변경 전 Node.js 24.22.1에서 lint·format·컴파일·단위 101개·결제 샘플 21개가 통과했다.
- 로컬 Docker daemon은 실행 중이지 않아 PostgreSQL 통합 검증은 별도 로컬 PostgreSQL 18과 최종 Linux Docker CI로 구분한다.
- 단계별 변경과 실제 검증 결과는 아래에 추가한다.

### 1. CI 경로와 검증 선택

- 계획: DB·관측·결제 데모 인프라 경로 누락을 보완하고 마지막 성공 커밋 이후 전체 변경을 비교한다.
- 작업: 삭제·이동의 이전 경로도 포함한다. 불명확한 이력·공통 코드·배포는 전체 검사하며, 백엔드 모듈 변경은 호출자까지 포함한 기존 전체 백엔드 회귀를 유지한다.
- 검증: 변경 전 로컬 DB 회귀 499개/156,090ms. 변경 후 기본 검사·122개 테스트, 경로·실제 임시 Git 저장소 검증 3개 통과. 패치 적용 가능 검사 통과.
- 판정: 로컬 검증본 채택. Git Bash의 `flock` 부재로 배포 셸 회귀와 Docker 실행은 Linux CI에서 추가 확인한다. 실제 Jenkins Job 설정과 서비스 배포는 실행하지 않는다.

### 1. Docker 중복 컴파일 제거

- 계획/작업: `test:compiled`에 기존 테스트 선택을 그대로 옮겨 Docker builder의 컴파일 결과를 재사용한다. 로컬 `npm test`는 컴파일부터 실행한다.
- 검증: 기존 테스트 명령과 새 compiled 명령의 선택이 같음을 검사했고, 변경 후 lint·format·컴파일·단위 101개·결제 샘플 21개가 통과했다.
- 판정: 채택. Docker 실행 경로는 같은 단계의 Linux CI에서 검증한다.

- Linux CI #63에서 `JsonSlurperClassic` 생성이 Jenkins sandbox에 차단됨을 확인했다. 관리자 허용 목록을 바꾸지 않고 엄격한 3개 boolean·사유 문자열을 전달하도록 수정했다. CLI 전달 형식 회귀 검증을 추가하고 CI 재검증 전까지 다음 단계를 적용하지 않는다.

- Linux CI #64: 경로 판정·배포 셸 fixture·백엔드 기본 122개·DB 499개·운영 이미지/Nginx 17개 통과. 관측 fixture의 Nginx 시작 직후 `nginx -t`와 master의 listen이 겹치며 포트 충돌이 발생했다. 임시 컨테이너의 실제 HTTP 준비를 기다린 후 설정을 검사하도록 바꿨다. 백엔드 Docker 검증도 같은 시작 경쟁을 피하고 실제 HTTP 계약 검사는 유지한다. 최종 CI 재검증 전까지 다음 단계를 채택하지 않는다.

- Linux CI #65 재검증: 기본 122개·DB 499개·운영 이미지/Nginx 17개와 관측 실제 수집·알림·결제 인프라 검증 통과. 패키징·SSH·배포 단계는 건너뛰었다. 단계 1 채택.

### 2. 테스트 준비 정리

- 계획: 주문 fixture의 앱 3개를 2개로 줄인다. 다른 역할의 세션은 기존 앱으로 인증하며 실제 인스턴스 간 경쟁 검증은 유지한다. 문서의 정확한 문구·언어·업무 번호에 결합된 단언만 제거하고 스키마·보안·응답 검증은 유지한다.
- 변경 전: 주문 95개/9,806ms, 통화·AI 설정 48개/6,469ms 통과(로컬 PostgreSQL 18, 단일 측정).
- 검증/판정: 변경 후 같은 143개 통과/14,687ms, format·diff 검사 통과. 준비용 앱 3→2개 채택. 전후 실행 구성이 다르고 단일 측정이므로 시간 차이를 성능 보장으로 사용하지 않는다.

### 3-1. 녹취 워커 연결 반납

- 계획: 전역 세션 잠금과 장시간 점유 연결을 수신 건별 UUID·5분 lease로 바꾼다. 선점·통화 매칭·완료만 짧게 DB에서 처리하며 다운로드/S3 중에는 연결을 반납한다. 기존 최초 1분 대기·재시도 간격·S3 멱등성은 유지한다.
- 검증 기준: 두 앱의 동일 수신 중복 방지, 다른 수신 진행, I/O 중 pool 가용성, 만료 후 재선점·이전 작업자의 완료 차단, S3/DB 실패 복구.
- 검증/판정: lint·컴파일·format, 녹취/PBX 18개 통과. 저장소 대기 중 사용 중인 pool 연결 0개, 다른 수신의 진행, 재선점 뒤 오래된 완료·실패·해제 무효화를 실제 DB에서 확인했다. 신규 031 migration과 함께 채택. 실제 서비스 DB 적용은 하지 않았다. 장애 시 앱을 이전 버전으로 복구하고 추가 컬럼은 보존한다.

### 3-2. FAQ 알림 순차 배치

- 계획: 5초마다 1개이던 알림을 한 번에 최대 10개 순차 처리한다. 알림 JSON은 그대로이며 첫 실패·선행 lease·backoff에서 중단해 순서를 보존한다. 종료 요청 이후 다음 알림은 선점하지 않는다.
- 검증/판정: 컴파일·format, FAQ/초기등록/알림 31개 통과. 12건을 10+2건으로 처리하고 실패·재선점·감사 롤백·종료 후 미선점을 검증했다. 최초 분리 실행은 빈 DB의 스키마 준비 누락으로 실패했으며 실제 migration 전체를 적용한 뒤 재검증했다. 채택.

### 3-3. 인라인 직원 일괄 SQL

- 계획: 직원별 고객·소속 쓰기를 집합 SQL로 줄인다. 고객 쓰기는 CustomersService를 통해 고객 모듈이 담당한다. 전화번호·사번 충돌과 전역 소속 잠금·역할·상태·부서 생략/명시 null·전체 롤백·감사 규칙은 유지한다. 고객 번호로 등록하는 기존 경로도 유지한다.
- 검증/판정: lint·컴파일·format, 직원·고객·초기 컨텍스트 51개 통과. 1,000명 신규 등록과 이름 수정에서 고객+소속 쓰기 각각 2문장으로 검증(기존 신규 등록은 2,000문장). 1,000명 전원의 전화번호·사번·이름 매핑과 total_count를 검사했다. 기존 상태/역할·부서 선택·경쟁·감사 실패 롤백도 통과해 채택.

### 3-4. 주문 상세 일괄 추가

- 계획: 신규 배송상세를 JSON recordset으로 모아 추가한다. 행 트리거 비용과 문장별 시간 제한을 고려해 한 문장에 최대 200행만 보내되, 전체 요청은 기존 한 트랜잭션에서 처리한다. 배송상세 수 제한은 추가하지 않는다. 실제 트리거 버전·위치·null·숫자·실패 시 전체 롤백을 유지한다.
- 검증/판정: lint·컴파일·format, 주문/수기 주문 109개 통과. 2,500개 배송상세를 13문장으로 저장하며 위치·수량·실제 버전 2,501을 검증했다. 두 번째 배치 직후 실패를 주입해 첫 배치·주문·요청 키가 모두 롤백됨을 확인했다. 분리 테스트 스키마 준비를 공통 실행기에 반영한 후 전체 대상 재검증해 채택.

### 3-5. 유지보수 트랜잭션 분할

- 계획: 미결제 만료는 기존 최대 100건/실행을 유지하되 10건씩 커밋한다. 월 청구 초기화는 기존 대상 전체를 조회한 후 10개월 레코드씩 짧게 처리한다. 주문/월별 감사와 금액·요청 갱신은 같은 트랜잭션에 유지한다. 앞 배치 성공은 뒤 배치 장애로 되돌리지 않으며 실패한 배치는 다음 실행에서 재시도한다.
- 검증/판정: lint·컴파일·format, 청구·실결제·기업 삭제 46개 통과. 만료 25건의 11번째 감사에서 실패시켜 첫 10건만 확정되고 다음 실행에서 나머지 15건을 중복 감사 없이 복구함을 확인했다. 기업 25개의 월 초기화도 트랜잭션당 최대 10건과 감사 50개를 검증했다. 채택.

### 3-6. 최적화 관측 근거

- 계획: HTTP 지연 histogram, 프로세스의 DB 연결/대기 수, 트랜잭션 횟수·실패·합계/최장 시간·연결 대기 합계를 기존 내부 metrics에 더한다. 업무 식별자·SQL·본문을 라벨에 넣지 않고 추가 DB 조회 없이 수집한다. 내부 지표는 프론트·AI API 계약에 포함하지 않는다.
- 검증/판정: lint·format·컴파일·기본 123개, DB/관측 6개 통과. HTTP 누적 bucket·count·sum과 DB 성공/롤백 통계, 풀 반납, 기존 지표 실패 구분·공개 Swagger 제외를 검증했다. 최초 기본 검사는 제한 실행 환경의 localhost 접속(EACCES)으로 실패했으며 네트워크가 허용된 격리 테스트로 재검증해 채택.
- 확인 예: `histogram_quantile(0.95, sum by (le, route, method) (rate(dva_http_request_duration_seconds_bucket[5m])))`. bucket 범위 밖의 지연은 상한 bucket 때문에 정밀도가 제한된다. DB duration 합계는 연결 획득 뒤부터 COMMIT/ROLLBACK까지, max는 프로세스 시작 이후 최장 값이다. 연결 대기는 별도 누적 counter와 현재 대기 gauge로 본다.

### 4. 조회 실행 계획 비교

- 계획: 격리 DB에 통화·주문 각각 100,000건을 만들고 실제 저장소의 total_count 포함 SQL을 비교한다. 통화 시작 내림차순과 고객별 주문 최신순 인덱스는 EXPLAIN ANALYZE·BUFFERS에서 이득이 확인된 것만 새 migration으로 채택한다. 인덱스 전후 응답·검색 총건수는 같아야 한다.
- 측정: PostgreSQL 18.4, 통화·주문 각 100,000건, 고객 100명. 캐시 준비 1회 뒤 같은 SQL을 5회 실행한 중앙값. 결과 전체를 deepEqual로 비교했다. `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`의 실제 버퍼 접근과 인덱스 사용을 확인했다.

| 실제 저장소 조회 | 총건수 | 이전 → 이후(ms) | shared hit blocks 이전 → 이후 |
|---|---:|---:|---:|
| 통화 최신 20건 | 100,000 | 674.634 → 9.825 | 53,118 → 1,094 |
| 통화 기간 20건 | 17,280 | 128.714 → 2.693 | 11,758 → 389 |
| 고객별 주문 20건 | 1,000 | 5.066 → 1.159 | 1,178 → 1,031 |
| 고객별 주문 offset 500 | 1,000 | 11.186 → 3.542 | 2,274 → 2,014 |

- 후보 채택: 032에 `call_sessions(started_at DESC NULLS LAST,call_session_seq DESC)`와 `orders(customer_seq,created_at DESC,order_seq DESC)`만 추가한다. 10만 건에서 인덱스 크기는 각각 3,178,496/4,079,616바이트였다. 디스크·추가 쓰기 비용이 있으므로 다른 검색 인덱스를 추측으로 늘리지 않는다. 측정은 격리 환경의 캐시가 준비된 조회이며 운영 성능·쓰기 부하를 보장하지 않는다. total_count는 정확한 count를 계속 수행한다.
- 검증/판정: 새 032를 포함한 빈 DB 구성·통화/주문/주소 이력/페이징 144개 통과. 응답·기간·동률 정렬·빈 페이지·필터 총건수 회귀를 확인해 채택. 실제 서비스 DB 적용은 하지 않았다.

### 5-1. 통화 데이터 소유권

- 계획: 통화 생성·CALL_STARTED 감사·주문 연결·녹취 매칭 시각 저장을 consultations 모듈에서 제공한다. 고객/주문/PBX가 통화 Repository를 가져오거나 call_sessions를 직접 수정하지 않게 한다. 호출자가 연 공유 트랜잭션·기존 잠금·오류 코드는 유지한다.
