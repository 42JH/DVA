# 백엔드 테스트 정리 결과

이 문서는 최초 선택 실행 도입 당시 결과다. 현재 전체 검증은 874개이며, 구형·중복 제거와 시간 비교는 [후속 정리 기록](ci-test-cleanup.md)을 따른다.

기준: develop-backend `f7f492c1`, 작업 브랜치 `ci/backend-test-scope`. 2026-11-08~09 로컬 Linux Docker의 임시 DB에서 검증했다. 저장소의 CI·테스트·관련 문서만 변경했으며 운영 Jenkins 설정·운영 DB·프론트·AI 소스는 변경하지 않았다.

## 정리한 부분

- 기존 CJS 테스트 103개 파일을 조사했다. 동일 제목·본문의 테스트와 진입점에서 참조하지 않는 하위 테스트/fixture는 발견하지 못했다. DTO·HTTP·DB의 비슷한 사례는 검증 경계가 달라 보존한다. 이전 API의 404·금지 입력과 이전 통화의 주문 호환성도 현재 계약 검증이므로 유지한다.
- 공통 업무·주문·수기 주문 fixture의 반복 비밀번호 해시/로그인을 임시 DB 세션 준비로 교체했다. 실제 guard와 권한 검사는 그대로 통과한다. 인증 전용·운영 이미지 테스트는 실제 로그인을 유지한다.
- 운영 검증 계정 준비를 인증 테스트에서 `runtime-fixture.integration.test.cjs`로 옮겼다. 이 fixture가 활성 페르소나(없을 경우)와 접수 완료 주소 스냅샷도 준비하므로 관련 없는 인증 전체·주소 이력 테스트가 선행될 필요가 없다.
- DB 통합 테스트 838개는 전체 회귀용으로 보존한다. 일반 변경은 아래 15개 영향 범위의 합집합을 기존 순서로 한 번씩 실행한다. 모든 단위 테스트와 production/Nginx/HTTPS 23개는 매번 실행한다.
- 전체 단위·DB 실행 목록의 누락/중복을 검사한다. 새 테스트를 목록에 연결하지 않으면 검증이 실패한다. 새 하위 등록 파일은 기존 진입점의 require 연결도 필요하다.
- 배포 mock 회귀 3종은 CI/배포·공유 설정·migration 변경, 비교 기준 누락 또는 수동 전체 실행에서 검사한다. 일반 기능 변경은 반복하지 않는다. 실제 배포의 브랜치·웹훅 판정·체크섬·SSH·migration·readiness·복구 조건은 유지한다.

## 검증 중 발견해 해결한 의존성

1. 기존 운영 검증은 인증 테스트가 남긴 계정과 주소 이력 테스트의 주문을 사용했다. 운영 전용 fixture로 분리했고, 인증/주소 이력 그룹 없이 FAQ DB 175개와 운영 23개가 통과했다. 이후 최소 active 범위의 운영 검증에서 활성 페르소나가 없어 404가 나는 의존성도 확인했다. 활성 페르소나가 없는 경우에만 전용 fixture가 정상 ACTIVE 버전을 준비하도록 보완했다. 운영 테스트의 200·APPLIED 재전송 기대값은 유지한다.
2. 고객 범위 최초 실행에서 주문 접수 테스트의 전송 횟수가 `6 != 1`로 실패했다. 실제 복구 워커가 앞선 주문 테스트의 PAID 주문 5건까지 처리한 것이 원인이었다. 기존 복구 테스트와 같은 방식으로 접수 suite 시작 시 확인된 임시 DB의 주문을 비워 격리했다. 전송 1회 기대값과 실제 워커 실행은 유지하며, 수정 후 고객 범위 350개가 통과했다.
3. Linux 배포 회귀 최초 실행에서 Windows CRLF인 Jenkinsfile의 `fi`를 찾지 못해 추출 블록이 닫히지 않았다. 테스트에서 줄바꿈을 정규화한 뒤 실제 조건 블록의 실행/생략을 검증한다. 수정 후 Linux 배포·복구·이미지 재사용·체크섬·SSH 회귀가 통과했다.

- 최신 checks 이미지: lint·format 검사와 CJS 단위 **199개**·결제 단위 **21개**, 합계 **220개** 통과. source/의존성이 동일한 컴파일 레이어는 빌드 캐시를 사용했다.
- CI 선택/Git 이력 **11개**, Linux 배포·복구·체크섬·SSH·이미지 재사용 mock 회귀, 관측 설정·결제 데모의 실제 Docker/Compose/Nginx/권한/잠금 검증이 통과했다.
- 마지막 신규 테스트 분류 경계 보완은 실제 회귀가 먼저 실패함을 확인하고 수정했다. 전체 목록뿐 아니라 변경한 통합 진입점이 선택 명령에도 포함되는지 검사하며, 선택기에만 한 수정은 단위/CI 11개와 최신 checks 이미지에서 추가 검증했다. 업무 소스와 DB 실행 명령은 전체 검증과 동일하다.
- 전체·최소·선택 범위의 최종 성공 실행에서 fail/cancelled/skipped/todo는 모두 0이다. 앞선 실패 로그는 원인 확인용으로 별도 보존했다. 업무 src·migration·프론트·AI·MSA diff는 없다.
- 운영 Jenkins 재실행·Job 변경·실제 배포는 하지 않았다. 로컬 수치만으로 실제 Jenkins 빌드 시간을 보장하지 않는다.

## 재현과 적용

저장소 루트에서 기본 전체 실행:

```sh
node backend/scripts/check.cjs
```

Linux 선택 실행과 혼합 실행:

```sh
BACKEND_TEST_PROFILE=pins node backend/scripts/check.cjs
BACKEND_TEST_PROFILE=faq+dashboard node backend/scripts/check.cjs
```

PowerShell 선택 실행 후 기본값 복원:

```powershell
$env:BACKEND_TEST_PROFILE = 'pins'
node backend/scripts/check.cjs
Remove-Item Env:BACKEND_TEST_PROFILE
```

Jenkins에서 `FULL_BACKEND_TESTS=true`를 선택하면 전체 백엔드·관측·결제 데모·배포 mock 회귀를 강제한다. 실제 배포 여부는 기존 `DEPLOY_LIGHTSAIL`·웹훅·보호 브랜치 판정을 따른다. 기본 단위/통합 명령과 Docker checks CMD는 전체 실행이다.

이 변경을 처음 반영하는 빌드는 CI/실행기 변경이므로 전체 검증 대상이다. 이후 해당 기능만 바꾸는 빌드부터 선택 범위가 적용된다. 실제 Jenkins 시간은 서버의 동시 빌드 부하·이미지 캐시에도 영향을 받으므로 로컬 측정을 단축률로 단정하지 않는다.
