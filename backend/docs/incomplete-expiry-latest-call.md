# 미완료 24시간·최신 확정 통화 정책

사용자 확정: 2026-11-09. 브랜치 `feature/complaint-draft-follow-up`. 이전 문서의 ‘미완료는 5년 동안 재개 가능’ 설명보다 이 문서를 우선한다. 7일·재개 1시간 유예 제안은 채택하지 않았다.

## 확정 규칙

- 원본 초안의 retentionStartedAt부터 **24시간 이상이면 만료**다. 조회·수정·재개로 기한을 연장하지 않으며 유예도 없다. 재개 사본은 기존처럼 원본 시각·예약번호를 상속한다.
- 고객별로 **통화 종료와 주문 입력 결과 확정이 모두 완료된 최신 통화**에서 남은 미완료만 유효하다. 최신 통화의 여러 INCOMPLETE 배송은 모두 대상이다. 고객별 초안 한 개로 줄이는 정책은 아니다.
- FAQ·주문 조회·미완료 없이 전부 접수한 통화·빈 배송 집합의 NO_ORDER도 동일하다. backend에 등록된 통화에 기존 order-intake 완료 통보와 PBX 종료가 모두 있어야 한다. 시작만 했거나 한쪽만 도착한 통화는 이전 건을 만료시키지 않는다.
- 최신 여부는 incomingAt → startedAt → registeredAt의 사용 가능한 통화 시각과 통화 번호 순으로 비교한다. 처리 완료·재전송 시각 순으로 비교하지 않아 늦은 옛 결과가 이전 미완료를 다시 살리지 않는다.
- 고객 번호가 있으면 같은 고객 번호를 사용한다. 고객 번호 없는 미완료는 같은 최초 발신번호로 범위를 제한한다. 다른 고객·번호의 새 통화는 영향을 주지 않는다.

## 이어가기와 동시성

새 통화가 진행 중일 때는 아직 유효한 이전 미완료를 재개할 수 있다. 원본은 RESUMED, 새 통화 사본은 EDITING/READY가 되는 기존 흐름을 유지한다. 새 통화가 확정되면 그 통화에 남은 미완료만 유지한다.

관리자 단독 재개 사본도 원본 통화를 기준으로 최신 여부를 판단한다. 24시간이 지나거나 더 최신 통화가 확정되면 저장·접수할 수 없다. 새 UUID나 수정 시각으로 기한을 다시 시작하지 않는다.

재개·수정·관리자 접수·통화 완료/확정은 고객 및 미등록 발신번호별 transaction advisory lock을 같은 순서로 획득한다. 새 통화 확정이 먼저 끝났으면 오래된 관리자 사본 접수는 404다. 유효한 접수가 먼저 완료됐으면 생성된 실제 주문은 유지한다. 잠금 대기 후에는 DB 현재 시각으로 기한을 다시 검사한다.

통화 확정은 만료된 재개 사본을 실제 주문으로 전환하지 않는다. 유효한 다른 READY 배송은 기존 방식으로 처리하고, 남은 유효 배송이 없으면 NO_ORDER로 확정한다. 이미 CONVERTED된 주문의 정상 재전송·결제/접수 복구는 이 만료 정책으로 취소하거나 재생성하지 않는다.

## API와 건수

만료 초안은 업무상 없는 리소스로 처리한다.

- GET /api/parcel-drafts: 기본 INCOMPLETE와 status=ALL 모두에서 제외. 기존 검색·기간·기업·페이지 조건도 동일 적용.
- GET /api/parcel-drafts/{id}, 만료 원본 재개, PATCH, 관리자 초안 최종 접수: 기존 NOT_FOUND 404. 이미 사용한 생성 키의 재전송은 기존 키 보호 규칙에 따라 409일 수 있다.
- GET /api/admin/orders: 전체 및 COLLECTING 목록·total_count·statusCounts.all/incomplete에서 제외.
- GET /api/dashboard/home: pendingWork.incomplete와 incompleteDrafts에서 제외.
- AI 이어가기 후보: 같은 INCOMPLETE API로 조회하므로 동일하게 제외. 목록 조회 후 경계 시각이 지났다면 상세·재개 404를 처리하고 최신 목록을 다시 확인한다.

EXPIRED 초안 상태·탭·새 입력 필드·새 오류 코드·새 endpoint는 추가하지 않는다. 실제 주문의 CANCELLED 건수나 결제 상태를 바꾸지 않는다. 최신 통화가 FAQ/조회여도 기존 AI가 보내는 빈 COMPLETE 통보를 그대로 사용한다. AI 자동 이어가기 활성화 설정은 이번 작업에서 켜지 않는다.

## 기존 데이터와 보관

기존 행에도 같은 최초 시각·최신 통화 조건을 즉시 적용한다. 배포일부터 시간을 다시 주거나 기존 데이터의 시각·상태·고객 연결을 일괄 수정하지 않는다. 만료 판정은 공통 조회·쓰기 조건이므로 별도 정리 배치나 타이머를 기다리지 않는다.

내부 사본은 기존 최초 보관 시작부터 5년 후 물리 삭제한다. 최신 통화가 soft delete돼도 이전 미완료가 다시 나타나지 않는다. 이관 원본 주문의 제외 조건도 유지한다. 예약번호는 보존하고 만료 번호를 재사용하지 않는다.

059 migration은 최신 확정 통화를 고객/발신번호와 실제 통화 시각으로 찾는 partial index 두 개만 추가한다. 기존 행 변경·만료 backfill·새 상태 컬럼·새 환경변수는 없다. 이 브랜치 전체 배포에는 057·058·059가 필요하다.

## 검증 기록

구현 전 신규 회귀 4개에서 기존 미완료가 200으로 남는 실패를 재현했다. 기존 동시 재개 검증은 1년 된 ‘유효 초안’을 사용하므로 24시간 안의 1시간 전 데이터로 조정했고, 원본 시각·예약번호 보존과 중복 재개 방지 기대는 유지했다.

관련 intake profile은 단위 214·결제 21·DB/API 179·runtime 13 = 427개 통과, 실패·취소·skip 0, 로컬 132,544ms였다. 이후 종료/결과 각각만 받은 상태 및 경합 테스트의 실패 종료 경로도 보강하고 최종 full profile에서 다시 검증한다.

최종 `BACKEND_TEST_PROFILE=full node backend/scripts/check.cjs` 종료 코드 0. 컴파일·ESLint·Prettier, 단위 214·결제 21·DB/API 653·운영 이미지/Nginx/HTTPS 13 = **901개**, 실패·취소·skip 0, 로컬 235,739ms(약 3분 56초). 직전 897개에서 회귀 4개를 추가했으며 기존 테스트 정리를 되돌리지 않았다. 이번 full 실행의 단위·결제도 실제 재실행했다.

추가로 Linux Jenkins/Git 선택 회귀 8개, 배포 trigger/deploy/Linux release mock 3종과 실제 스크립트 bash 문법 검사가 통과했다. 실제 Jenkins job 설정 전용 Python 검사는 로컬 컨테이너에 서버 설정 경로가 없어 실행되지 않았으며 원격 CI 검증으로 간주하지 않는다. 실제 운영 배포·외부 AI/결제/디버 호출·실제 프론트 화면은 미검증이다.

## 적용 시 조회 기준

만료는 조회 시점에 계산한다. 기존 시각과 상태를 일괄 변경하지 않는다. 신·구 정책의 백엔드를 동시에 운영하지 않는다.
