# 백엔드 내부 구조 및 테스트 정리

- 기준: `develop-backend`의 `17d86ce`, 작업 브랜치: `refactor/backend-internals`
- 절차: 각 단계의 계획 → 수정 → 검증을 완료한 뒤 다음 단계로 진행한다.

## 유지할 계약과 검증 기준

API 경로·메서드·상태 코드·요청/응답 DTO·Swagger·인증·오류 메시지는 유지한다.
AI·프론트 연동 명세, DB 마이그레이션·테이블·컬럼·FK, 운영 설정과 데이터는 변경하지 않는다.
변경 범위는 `backend/`와 `infra/`의 내부 구현·테스트·검증 도구다.

수정 전후 Swagger JSON을 동일 환경에서 비교하고 Controller·DTO·Guard·마이그레이션의
Git 차이를 확인한다. 공유 DB의 순차 실행, 여러 앱 인스턴스의 동시성 검증,
동일 PoolClient·잠금 순서·감사 로그 원자성·외부 요청의 트랜잭션 분리를 보존한다.
이벤트 정규화는 기존 JSON 필드 순서와 해시를 유지해야 한다.

## 진행 결과

### 1단계: DB 검증 정리

- 변경 전 `test-monolith.ps1`을 실행해 결제수단 없는 주문의 `SUBMITTING` 전환이
  `orders_payment_method_required_check`에서 실패하는 것을 재현했다.
- fixture의 결제수단을 명시하고, 최신 migration 수는 파일 목록에서 계산한다.
  009 업그레이드 보존 비교는 이관 전의 실제 컬럼 목록을 사용해 이후 추가된 컬럼 때문에
  실패하지 않도록 했다. 명시적으로 제거된 좌표·end_reason만 비교에서 제외한다.
  기존 ledger 행의 체크섬·적용 시각도 그대로 비교한다.
- 수정 후 `infra/database/test-monolith.ps1` 전체 통과:
  새 DB·과거 버전 업그레이드·원본 데이터 보존·반복 적용·체크섬 변경 거부·신규 SQL 전체 롤백·백업 복원.
- 마이그레이션 SQL과 운영 스키마/데이터는 변경하지 않았다.
- API 비교 기준을 실제 Swagger 생성 경로에서 확보했다: 60개 경로, 82개 operation, 148개 schema.

### 2단계: 미사용 테스트 선언 제거

### 3단계: 공통 테스트 준비 분리

- `helpers/application.cjs`에 격리 DB Pool, 앱 시작/종료, 관리자 역할별 로그인,
  HTTP 요청과 공통 오류 검사를 모았다. FAQ helper에는 FAQ 조작·집계·검증용 marker만 남겼다.
- FAQ가 필요 없는 통화 조회·보관 기간 테스트는 공통 fixture를 직접 사용한다.
  고객·기업 테스트의 앱 시작과 Pool, 수기 주문 fixture의 Pool도 공통 코드를 재사용한다.
- FAQ 관리자 이름을 검증하는 기존 감사 로그 테스트는 이름과 검증문을 그대로 유지했다.
  새 fixture는 자체적으로 격리 테스트 스키마를 준비/검사한다.
- 영향받는 통합 테스트 13개 파일을 실제로 순차 실행해 통과했다.

- 보조 실행기의 첫 실행은 통합 테스트 stdin 전달 누락으로 검증 집계에서 제외했다.
  전달 방법을 수정한 재실행에서 파일별 RUN, 13개 테스트 집계, 실패/skip 0을 확인했다.

### 4단계 실행 구조

공유 fixture와 순차 실행을 보존하기 위해 주문·AI 설정의 기존 `.integration.test.cjs`를
명시적 진입점으로 유지하고, 각각 책임별 시나리오 등록 파일과 fixture로 나눈다.
과거 migration 사례도 별도 등록 파일로 이동하며 원래 위치에서 등록한다.
새 테스트 프로세스나 병렬 실행을 추가하지 않는다. package.json의 기존 진입점 연결과
분할 파일의 require 연결을 검증하고, 시나리오 이름·순서·본문을 AST로 비교한다.

### 4단계: 대형 통합 테스트 분리 결과

- 주문을 생성·조회·수정·접수·결제·동시성·통화 문맥·관리자 화면 등록 파일과 공통 fixture로 분리했다.
  AI 설정은 관리·적용·게시·초안 등록 파일과 fixture로 분리했다.
- 주문 037, 페르소나 034/035/036/039, 통화 분석 025/042의 과거 migration 검증은 별도 파일로 옮겼다.
  기존 package.json 진입점과 공유 DB, 복수 앱 인스턴스 수는 그대로 유지했다.
- 최초 실행에서 반복문으로 등록되던 동시성 테스트 5건이 fixture로 먼저 이동해
  월 정산을 일찍 초기화하는 순서 오류를 발견했다. 이동 전 테스트 99개가 같은 새 DB에서
  통과하는 것을 비교 확인하고, 반복문을 원래 등록 위치로 복원했다. 기대값은 변경하지 않았다.
- 직접 등록 165건과 반복문 2개의 본문·등록 순서를 AST로 비교했다.
  fixture 참조 변경 및 포맷을 제외한 코드가 같고, 22개 관련 파일의 Node 구문 검사도 통과했다.
- 수정 후 실제 PostgreSQL 순차 실행: 주문 99 + AI 설정 51 + 통화 이벤트 20 = 170개 통과, 실패/skip 0.

### 5단계: 주문 조회 기간 검증 재사용

- 관리자 목록·일반 목록·이전 주소 조회의 동일한 조건을 OrdersService의 private 함수 하나로 옮겼다.
  통화 헤더 검사와 날짜 검사 순서, 상태 코드·오류 코드·메시지, 읽기 트랜잭션과 쿼리는 유지했다.
- 실제 PostgreSQL에서 주문 99 + 주소 이력 14 = 113개 통과, 실패/skip 0.
  날짜 역전·같은 시각·잘못된 시간대·KST/UTC 경계·관리자/AI 권한·동시 읽기 검증을 포함한다.
- 6단계 변경 전에 기존 CallEventsService를 실행해 4종 payload의 정규화 결과와 저장 해시를
  확보했다. 분리 후 동일한 값인지 단위 테스트에서 비교한다.

### 6단계: 통화 이벤트 입력 정규화 분리

- `call-event-input.ts`의 순수 함수로 DB 접근 전 정규화와 요청 내 중복 검사를 옮겼다.
  기존 CallEventsService는 정규화 후 같은 트랜잭션·UUID 잠금 순서·해시 계산·참조 검사·저장·감사 기록을 수행한다.
- 변경 전 실제 서비스에서 확보한 UTTERANCE, AI_ACTION, BUSINESS_RESULT, FAQ_ANSWERED의
  정규화 결과 및 저장 해시 4개가 분리 후에도 일치한다.
- 단위 테스트 4개를 추가해 기존 해시, 수신 순서, 원문/개행, 시간대, 0/null,
  입력 불변성, 잘못된 시각, 대소문자 UUID/순번 중복, FAQ 참조 규칙과 오류 상태를 검증했다.
