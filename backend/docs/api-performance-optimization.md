# API 성능 개선 — S15P31D109-174

## 진행 원칙

기준은 feature/frontend-qa의 a7988bf9이다. 기존 3개 API 작업은 커밋·푸시되어 있고 작업 트리는 깨끗한 상태에서 시작했다. 같은 브랜치에서 API 하나씩 계획 → 작업 → 테스트 → 적용 또는 복구를 수행한다. 성능 개선이 확인된 변경만 단계별 커밋한다.

응답 필드·타입·값·null·정렬·페이지·전체 건수·상태 그룹·검색·보관·삭제·권한·오류 의미를 유지한다. 기능 추가, 새 필터, 기존 필드 제거, 페이지 방식 교체는 이번 성능 개선에 섞지 않는다. 요청 식별자·발급 시각처럼 요청마다 달라지는 값은 기존 생성 규칙을 유지한다.

검증은 임시 PostgreSQL 17에만 합성 데이터를 만든다. 기존 SQL과 수정 SQL을 같은 REPEATABLE READ 스냅샷에서 대조하고 EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)의 실행 횟수·스캔량과 번갈아 실행한 지연을 기록한다. 시간만으로 CI 성공을 판단하지 않고 결과 일치와 실행 계획의 작업량을 확인한다. 운영 부하 개선으로 확대 해석하지 않는다.

## 순서와 계획

1. 관리자 주문 목록: 페이지에 포함할 주문을 먼저 선택한 뒤 배송상세 JSON을 구성하는 후보를 검증한다. 첫·중간·깊은·빈 페이지와 검색·기간·기업·상태 필터 결과를 기존 SQL과 비교한다. 개선이 없거나 결과가 다르면 후보만 복구한다.
2. 통화 목록·타임라인: 기존 정렬과 페이지를 유지하면서 현재 페이지 밖의 녹취·발화·분석 조회가 반복되는지 측정하고 해당 SQL만 개선한다.
3. 통계: 각 통계의 공통 대상 스캔·집계 비용을 측정한다. 기존 분모·null·현재/직전 버전·소수값을 보존하는 후보만 적용한다.
4. 페르소나: 공개 필드·프롬프트를 그대로 반환하면서 중복 DB 조회·JSON 생성만 줄일 수 있는지 측정한다.
5. 부분 검색·녹취·CSV: 동일 결과·오류·보관·URL 발급 규칙을 지킬 수 있는 내부 개선을 검토한다. 응답 축소·지연 발급·새 페이지 API가 필요한 후보는 계약 보존 조건에서 제외하고 근거를 기록한다. 인덱스는 조회 효과와 쓰기 비용을 확인한 뒤 판단한다.

## 1. 관리자 주문 목록

계획: GET /api/admin/orders의 저장소 조회만 대상으로 한다. 상태별 건수·초안 조회·서비스 트랜잭션·Controller·DTO는 유지한다. 이전 SQL을 회귀 비교용 fixture로 고정하고 전체 배송상세 배열을 포함한 결과를 대조한다. 수정 전후의 깊은 페이지에서 실제 JSON 집계 횟수가 페이지 크기에 비례하는지 확인한다.

작업: readPage에 현재 페이지에만 적용하는 고정 SELECT를 선택적으로 전달한다. 기본 SELECT는 기존 page.* 그대로이며 주문 목록에서만 배송상세 JSON 계산을 페이지 뒤로 옮겼다. 필터·전체 건수·정렬·limit+1 조회·페이지 메타데이터 제거·서비스 트랜잭션은 유지한다. SQL 1회와 동일 스냅샷을 보존한다.

테스트: 격리 PostgreSQL 17, 합성 주문 2,000개·주문당 상세 6개·limit=20·offset=1900. 이전 SQL과 현재 SQL을 같은 스냅샷에서 대조했다. 검색·특수문자·전화 하이픈·기간·비활성 기업/소속·상태 그룹·첫/깊은/빈 페이지·최대 안전 offset을 포함한 20가지 저장소 결과가 모든 필드·값·정렬·건수까지 일치했다. 관련 HTTP·공통 페이지·주문·집계·소속·홈 통합 테스트 130개가 통과했다.

| 같은 실행에서 측정한 항목 | 이전 SQL | 변경 SQL |
| --- | ---: | ---: |
| 배송상세 JSON 집계 횟수 | 1,921 | 21 |
| EXPLAIN 실행 시간 | 254.008 ms | 8.569 ms |
| 10회씩 교대 실행한 쿼리 중앙값 | 224.558 ms | 11.039 ms |

적용 판단: 결과 일치와 JSON 집계가 limit+1 안으로 제한되는 것을 확인했다. 약 20.3배의 중앙값 차이는 이 합성 데이터·깊은 페이지·격리 환경에 한정한다. 운영 부하·전체 HTTP 응답 속도 개선으로 해석하지 않는다. 기본 호출자를 포함한 공식 전체 회귀 검증 후 적용·커밋한다.

결정: 적용. 공식 `node backend/scripts/check.cjs` 종료 코드 0. 컴파일·lint·format, 단위 194개·결제 21개·PostgreSQL 통합 857개·운영 이미지/Nginx/HTTPS 23개, 합계 1,095개가 통과했다. 공통 readPage의 기존 기본 호출자와 주문 주소 이력을 포함했다. 전체 실행에서도 JSON 집계 1,921→21회, 교대 중앙값 324.369→12.023ms를 확인했다. DTO·서비스·공개 API·migration·환경변수는 변경하지 않았다.

## 2. 통화 목록

계획: GET /api/calls와 이를 재사용하는 홈의 recordedAt 계산만 대상으로 한다. 기존 SQL을 고정해 첫/중간/깊은/빈 페이지·페이지 크기·삭제·만료·동일 시작 시각·분석 완료/실패/미수신 데이터의 모든 SQL 결과를 대조한다. 상세 조회는 기존 recordedAt 계산을 유지하고 목록에서만 페이지 선택 뒤 min(recordings.created_at)을 구하는 후보를 측정한다. 각 통화의 분석 내용·현재 소속·정렬·전체 건수·필터는 바꾸지 않는다.

작업: 목록 SQL에서 recordedAt만 페이지 선택 뒤로 옮겼다. 통화 상세는 기존 SELECT와 같은 위치에서 계산한다. 분석 결과 변환·서비스·필터·정렬·전체 건수·DTO는 유지한다.

테스트: 격리 PostgreSQL 17, 합성 통화 2,000개·일부 녹취 없음/그 외 통화당 녹취 6개·limit=20·offset=1900. 첫/중간/깊은/빈/최대 안전 offset과 limit=1/100, 총 7가지 페이지의 모든 SQL 필드·타입·값이 이전 SQL과 일치했다. 상세의 분석 완료 우선순위·녹취 시각도 유지했다. 통화 상세·분석 상태·기업 소속·처리 결과·홈을 포함한 통합 테스트 64개와 컴파일·lint·format·단위 194개·결제 21개가 통과했다.
