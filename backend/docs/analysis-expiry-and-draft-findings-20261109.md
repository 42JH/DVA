# 분석 만료·미완료 흐름·미답변 고객명 확인

미완료는 후속 사용자 확정의 [24시간·최신 확정 통화 만료 정책](incomplete-expiry-latest-call.md)이 아래 최초 조사 설명보다 우선한다.

## 이번 작업 범위

- 사용자 확정: 분석 결과 없이 PBX 통화 종료 후 **10분**이면 EXPIRED. 시간만으로 COMPLETED 처리하지 않는다.
- 구현: 통화 공통 조회 SQL·Swagger 타입·관련 회귀·프론트/AI 전달 문서.
- 조사·설명: 이관 원본 제외, 미완료 확정·이어가기·보관, 미답변의 고객명 누락.
- 제외: PIN 및 AI 코드 수정, 운영 데이터 보정, 이어가기 정책 변경, 프론트 소스 수정, 배포·새 MR 생성·병합.

## 1. 분석 만료

목록 `GET /api/calls`의 data[], 상세 `GET /api/calls/{id}`의 data.call, 홈 `GET /api/dashboard/home`의 data.recentCalls[]에 동일한 analysisStatus를 반환한다. 우선순위는 다음과 같다.

1. 정상 분석 행이 실제 저장됨 → COMPLETED.
2. 정상 분석 없이 최종 실패 통보 시각이 있음 → FAILED.
3. 둘 다 없고 `call_sessions.ended_at <= transaction_timestamp() - interval '10 minutes'` → EXPIRED.
4. 그 외 → PENDING. 종료 시각이 없는 오래된 통화도 이 조건만으로 만료시키지 않는다.

EXPIRED는 조회 시 계산한다. 별도 배치·상태 UPDATE·migration·환경변수는 추가하지 않는다. 분석 결과, analysis_failed_at, 실패 감사 기록을 만들어내지 않으며 analysis는 null이다. AI 작업의 실제 실행 여부를 감시하거나 AI 재시도를 중단하는 기능은 아니다. 기존 정상 분석 수집 API가 실제 결과를 저장한 경우에만 COMPLETED가 된다. 실제 실패 통보가 뒤늦게 오면 FAILED로 표시한다.

**프론트 후속:** develop-fe의 통화 DTO 및 callState 타입에 EXPIRED를 추가하고 ‘분석 만료’ 분기를 넣어야 한다. 현재 코드 그대로라면 새 상태도 기본 ‘분석 중’으로 보인다. [상태 연동 명세](call-analysis-status-frontend-integration.md)에 변경 위치를 적었다. AI의 성공·실패 POST 경로·본문·인증은 변경 없다.

## 2. 이관 원본 제외 조건

055가 이전 COLLECTING 주문의 배송을 초안으로 복사하면서 `legacy_order_seq`에 원본 주문번호를 남겼다. 주문 조회 SQL은 아래 조건으로 이미 초안으로 이관된 원본 주문 행을 제외한다.

```sql
NOT EXISTS (
  SELECT 1 FROM order_parcel_drafts d
  WHERE d.legacy_order_seq = o.order_seq
)
```

이는 같은 내용을 원본 주문과 미완료 초안으로 두 번 표시·접수하지 않기 위한 조건이다. 원본 orders 행의 삭제를 뜻하지 않는다. 번호를 아는 원본 상세 조회는 가능하지만 변경·접수·취소는 409로 제한한다.

이 조건은 이관 초안의 status·deleted_at·보관 기간을 따로 검사하지 않는다. 해당 참조 행이 존재하는 동안 RESUMED 또는 soft delete 상태도 원본 제외 근거가 된다. 이번 작업에서 조건을 바꾸지 않았다. 새 통합 목록은 원본 대신 조회 가능한 INCOMPLETE 초안을 예약번호와 draftSeq로 표시한다.

## 3. 미완료가 만들어지고 이어지는 흐름

1. AI 통화에서 배송별 초안을 저장한다. 필수값이 부족하면 EDITING, 완료하면 READY다. 여러 배송 초안이 같은 통화에 있을 수 있다.
2. AI의 주문 입력 완료 통보와 PBX 종료가 모두 확인돼야 최종 확정한다. 통화가 끊겼다는 이유만으로 즉시 INCOMPLETE가 되지는 않는다.
3. 확정 시 READY는 기존대로 실제 주문 한 건에 묶여 CONVERTED가 되고, 남은 EDITING은 INCOMPLETE가 된다. READY가 없으면 실제 주문을 만들지 않고 미완료만 확정한다.
4. 완료 통보가 먼저 오면 종료를 기다리고, 종료가 먼저 와도 완료 통보를 기다린다. 확정 복구 대상은 완료 통보·종료가 모두 있고 아직 확정되지 않은 통화다. 완료 통보 자체가 없으면 복구 워커가 임의 확정하지 않는다. 분석 만료 10분은 이 주문 확정 조건을 바꾸지 않는다.
5. 이어가기는 원본 INCOMPLETE의 sourceDraftSeq와 새 clientParcelId로 새 초안을 생성한다. 원본은 RESUMED, 새 초안은 EDITING/READY가 된다. 원본 사본·보관 시작 시각을 유지하고 이번 예약번호 작업에서는 reservedOrderSeq도 유지한다. 동시 재개는 잠금으로 제어한다.
6. 새 초안을 보완해 관리자 단독 접수하거나 AI 통화의 다음 확정을 거친다. 접수하면 CONVERTED, 다시 미완성으로 확정하면 새 초안이 INCOMPLETE다. 예전 통화의 이미 생성된 주문에 배송을 자동 추가하지 않는다.

### 최신 1건과 만료는 별개

**backend는 고객별 최신 1건만 보관하지 않는다.** 삭제·보관 만료되지 않은 INCOMPLETE 전부가 목록 대상이다.

**보관 만료는 retentionStartedAt부터 5년이다.** 기간이 지나면 조회·재개 대상에서 제외하고 기존 retention worker가 물리 삭제한다. 재개할 때 이 시각을 복사하므로 5년을 다시 시작하지 않는다. 하루 뒤 취소되는 결제 대기 주문이나 분석 10분 만료와 다르다.

### AI 자동 이어가기의 현재 설정

최신 develop-ai의 `_resume_lookup`은 INCOMPLETE를 `limit=1`로 조회해 최신 1건을 후보로 쓴다. 제안에는 접수 의도·이번 통화에서 새 택배 정보를 받기 전·아직 제안하지 않음·후보 createdAt부터 설정 기한 이내 등의 조건이 있다. 조회 실패 시 새 접수로 진행한다.

자동 이어가기는 AI에서 기능과 제안 기한을 설정한 경우에만 동작한다. 이 설정은 백엔드의 초안 보관 기한과 독립적이다.

## 4. 미답변 문의의 이름 누락

미답변 API는 연결 주문 고객을 우선하고 없으면 통화의 `customer_seq`를 사용한다. 과거 고객 행을 찾지 못하면 고객명이 null일 수 있다. 전화번호 재사용으로 서로 다른 고객의 이력이 연결되지 않도록 현재 고객으로 자동 변경하지 않는다.

## 5. PIN 및 적용 상태

PIN은 사용자 지시대로 AI 담당 범위다. backend·AI·기존 PIN 데이터 모두 수정하지 않았다. 앞선 ‘보내는 곳’ 조사 결과만 기존 [운영 상태 기록](production-state-findings-20261109.md)에 유지한다.

현재 변경은 작업 브랜치 기준이며 운영 배포 결과가 아니다. 분석 만료를 화면에서 보려면 backend 배포와 프론트 EXPIRED 표시를 함께 반영해야 한다. 예약번호·통합 목록까지 배포할 때는 기존 안내대로 057·058 적용도 필요하다. 자동 이어가기 활성화 여부·기한은 별도 정책 변경 사항이다.

## 6. 검증 결과

- 구현 전 회귀에서 종료 11분 경과 통화가 PENDING으로 남아 EXPIRED 기대와 불일치함을 재현했다.
- 수정 후 analysis profile 종료 코드 0: 단위 214·결제 21·DB/API 161·운영 이미지/Nginx/HTTPS 13 = 409개, 실패·취소·skip 0. 컴파일·lint·format 포함.
- 최종 full profile 종료 코드 0: 같은 소스·테스트의 빌드/단위/결제 검증 레이어를 재사용하고 DB/API 648·운영 이미지 13을 다시 실행했다. 합계 검증 대상 896개, 실패·취소·skip 0, 로컬 204,484ms(약 3분 24초). 원격 Jenkins 측정은 아니다.
- 새 테스트 파일·테스트 케이스는 늘리지 않았다. 기존 상태 회귀를 종료 후 7분 PENDING·11분 EXPIRED·종료 없는 오래된 통화 PENDING·실제 실패 FAILED·실제 정상 결과 COMPLETED로 보강했다. EXPIRED 시 실패 타임스탬프·실패 감사 기록이 생성되지 않는 것도 검증했다.
- 기존 과거 통화 fixture는 새 계약에 맞는 EXPIRED 기대값으로 변경했으며, 통화 목록·상세·녹취·권한·홈·주문·초안 회귀를 유지했다.
- PIN·AI/프론트 코드·운영 데이터는 수정하지 않았다. 운영 데이터·AI 설정은 읽기만 했다. 실제 프론트 표시·외부 AI 호출·운영 배포 후 동작은 미검증이다.
