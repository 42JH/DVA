# 수기 주문 수령인 개인 PIN 자동 저장

작업 브랜치: `feature/complaint-draft-follow-up`. 요청 범위는 수기 주문의 수령인 자동 등록·중복 제외이며, 미완료 정책·AI 코드·운영 데이터 보정은 이번 수정에 포함하지 않는다.

## 적용 기준

- 전화 플로우의 수령인 저장 기준을 사용한다. 주문 고객의 개인 PIN으로 저장하며 별칭은 수령인 이름이다. 이름·전화번호·도로명·지번·상세주소·동명·우편번호를 보존한다.
- 기존 `pin_identity` 정규화 및 고객별 활성 PIN 고유 인덱스로 중복을 판단한다. 같은 고객의 같은 수령인·주소는 기존 행을 유지한다. 별칭·주소·version을 덮어쓰지 않는다. 상세주소나 수령인 정보가 다르면 별도 항목이다.
- 다른 고객의 같은 수령인은 각 고객 주소록에 따로 저장한다. soft delete PIN은 기존 인덱스 정책에 따라 활성 중복으로 취급하지 않는다.
- 발송인은 PIN에 자동 등록하지 않는다. 이번 수정에서 고객 기본 출발지·이름도 변경하지 않는다.

## 호출 경로와 저장 시점

`OrderSubmissionService.prepareSubmission`의 기존 검증을 통과한 ADMIN 출처 주문에만 적용한다. 신규 `POST /api/admin/orders`, 관리자 초안 최종 접수, 기존 관리자 임시 주문의 최종 접수가 같은 경로를 사용한다. AI 출처의 새 주문은 기존 전화 플로우의 PIN 등록을 유지한다.

개인카드는 결제 대기(notPaid)가 되더라도 등록한다. 월·그룹결제도 같은 기준이다. 외부 디버의 최종 ACCEPTED를 기다리지 않으며, 외부 접수 실패 후에도 저장된 주문·PIN은 남는다. 입력 중 초안·주문 수정만으로는 자동 등록하지 않는다.

PIN·생성 감사는 주문 내부 저장과 같은 트랜잭션이다. 검증·설정·결제 준비·감사 저장이 실패하면 함께 롤백한다. 실제 새 PIN에만 PERSONAL_PIN_CREATED를 기록하고 요청자의 관리자/AI 구분을 유지한다. 이름·전화·주소를 감사 metadata에 넣지 않는다.

같은 요청 키의 재전송은 기존 주문 결과를 반환한다. 서로 다른 주문이 같은 수령인을 동시에 저장해도 고유 인덱스와 ON CONFLICT DO NOTHING으로 한 건만 남긴다. 여러 주소는 중복 판정 값 순으로 삽입해 반대 순서의 동시 접수가 불필요하게 충돌하지 않도록 한다.

API 경로·본문·응답·인증·상태·결제 자격은 변경 없다. 프론트의 추가 PIN POST도 필요 없다. 추가 migration·환경변수·의존성은 없다. 과거 주문 143번 등을 소급 등록하지 않는다.

## 작업·검증 순서

1. 기존 미구현 상태에서 수령인 미생성(0건/기대 1건)과 PIN 감사 실패 주입이 적용되지 않는 실패를 재현했다.
2. 공통 접수 준비·주문 repository에 최소 저장을 추가했다.
3. 첫 회귀 실행에서 AI가 기존 관리자 임시 주문을 접수하는 경우 감사 actor를 ADMIN/null로 기록해 422가 발생했다. 기존 AI/관리자 구분으로 수정했으며 정상 경로 테스트 기대값은 변경하지 않았다.
4. 수기·전화·초안·결제 회귀와 최종 전체 검증을 확인한 뒤 커밋한다. 결과는 아래에 기록한다.

## 검증 결과

- `BACKEND_TEST_PROFILE=orders node backend/scripts/check.cjs` 종료 코드 0. 컴파일·ESLint·Prettier, 단위 214·결제 21·DB/API 306·운영 이미지/Nginx/HTTPS 13 = 554개, 실패·취소·skip 0, 로컬 201,381ms.
- 최종 full profile 종료 코드 0. 동일 소스·테스트의 빌드/단위/결제 레이어를 재사용하고 DB/API 649·운영 이미지 13을 재실행했다. 합계 검증 대상 **897개**(기존 896 + 신규 회귀 1), 실패·취소·skip 0, 로컬 222,899ms(약 3분 43초). 원격 Jenkins 측정은 아니다.
- 실제 HTTP·PostgreSQL로 동시 두 주문의 반대 배송 순서·동일 주문 내 중복 배송·상세주소 차이·고객별 분리·수령인 별칭·발송인 미등록·기존 PIN 전체 행 보존을 확인했다. 결제 대기 상태에서도 저장하고 외부 디버 호출을 만들지 않는 경로를 검증했다.
- 기존 관리자 재개 회귀에서 AI 출처 주문은 자동 PIN을 추가하지 않고 관리자 초안 접수·재전송은 PIN 한 건만 남기는 것도 확인했다. PIN 감사 실패와 결제 준비 감사 실패의 주문·고객·PIN 전체 롤백을 기존 실패 회귀에 보강했다.
- 기존 전화·결제·재요청·권한·PIN API·보관·목록·초안 회귀를 유지했고 기존 테스트를 삭제하거나 검사를 완화하지 않았다.
- 운영 데이터·AI 설정은 읽기만 했다. 운영의 구체적인 미완료 72건 현황은 [상세 보고](incomplete-draft-current-state-20261109.md)를 따른다. 실제 프론트 화면·외부 AI/결제/디버 실서비스·원격 Jenkins·운영 배포 후 동작은 미검증이다.
