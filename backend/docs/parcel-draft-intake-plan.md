# 통화별 주문 초안 전환 계획

범위: backend 모놀리식과 해당 infra 검증. AI·프론트 코드 및 운영 DB·배포는 변경하지 않는다. MR 생성 직전에 보고한다.

## 확정 동작

- 통화 중 배송 단건은 order_parcel_drafts에만 저장한다. READY·EDITING을 구분하고 수정 시작 시 이전 값을 비운다.
- PBX 종료와 AI order-intake/complete를 모두 확인한 후 READY만 실제 주문 하나로 변환한다. 미완료는 INCOMPLETE로 보존한다. 완성 상세가 없으면 NO_ORDER다.
- 개인 카드는 결제 안내 → notPaid → 승인 완료 PAID → 디버 일괄 전송. 월·그룹결제는 종료 확정 후 기존 자격·원장 처리와 디버 일괄 전송을 따른다.
- AI 완료 수신 뒤 초안을 잠근다. 종료 웹훅보다 늦은 정리 저장은 완료 수신 전까지만 받는다. 두 신호 중 하나가 없으면 결제·전송하지 않는다.
- 재개는 같은 고객의 INCOMPLETE를 새 초안으로 복사하고 source_draft_seq로 연결한다. version은 해당 행의 낙관적 잠금이며 과거 행 복사와 별개다.
- 새 참조는 논리 참조다. 고객·통화·주문·원본 초안의 삭제가 새 초안의 삭제나 NULL 변경을 유발하지 않는다. 주소·물품은 독립 스냅샷으로 조회한다. 소유권 확인 시 참조 대상이 없으면 쓰기를 거절한다.
- 초안은 soft delete, 최초 생성(과거 이관은 원래 주문 생성)부터 5년 보관한다. 재개 사본도 원본 보관 시작을 상속한다. 삭제·수정·재개로 기간을 연장하지 않는다.
- 기존 관리자 수기·보정 권한은 유지한다. 미완료 보완은 새 초안 API에서 별도 ADMIN 주문을 만든다. 기존 전송 주문에 상세를 붙이지 않는다.
- 기존 COLLECTING은 자동 접수하지 않고 초안으로 복사한다. 원본 주문·FK·시각·버전은 보존하며 활성 목록 중복과 원본 재접수를 막는다.
- 기존 통화는 레거시로 구분하고 신규 통화는 새 계약을 사용한다. 배포 시 진행 통화를 마친 뒤 AI·백엔드·프론트를 함께 전환한다.

## 커밋 5단계

1. 계획 → 055 단일 migration·논리 참조·기존 미완료 이관·배포 검증 → 이관/롤백/제약 테스트.
2. 계획 → 초안 생성·PATCH·목록/상세·재개·권한 → HTTP·동시성·소유권 테스트.
3. 계획 → AI 완료·종료 후 확정·결제·재시작 복구·레거시 우회 차단 → 양쪽 신호 순서·멱등성·원자성·결제/전송 테스트.
4. 계획 → 관리자 미완료 보완·조회 중복 제거·soft delete·5년 폐기 → 기존 관리자·보관·삭제 회귀.
5. 계획 → ERD·AI/프론트 개별 명세·전환 안내 → 전체 Docker 검증·최종 점검.

## 검증 원칙

각 단계에서 실제 검증 결과를 기록하고 통과 후 커밋한다. 운영 데이터는 사용하지 않는다. 지연·중복·동시 호출, 수정 중 단절, READY 없음, 고객/통화/주문 삭제 후 스냅샷 보존, 카드 승인 미확정과 재시도, 트랜잭션 롤백을 확인한다. 기존 정상 주문·관리자·결제·PBX 경로도 최종 전체 회귀에 포함한다.

## 실행 기록

- 시작 기준: origin/develop-backend 5c10eed, feature/parcel-draft-intake. 기존 작업 트리 변경 없음.

- 1단계 검증: 임시 PostgreSQL 17에서 055 이관·실패 롤백·원본 시각/버전 보존·논리 참조 원본 삭제 후 스냅샷 보존 1개 통과. 배포 스키마 회귀 21개 통과. 초기 테스트 접속/필수 상태 fixture 오류는 보완 후 재검증했다. 운영 적용 없음.
