# 디버 접수 10초 응답 제한과 10분 자동 재시도

## 확정한 동작

- 실제 디버 요청은 최대 10초 기다린다. 응답 오류·시간 초과는 `SUBMITTING_FAILED`로 저장한다.
- 첫 디버 전송부터 10분 동안, 마지막 전송 시작에서 최소 1분 간격으로 같은 주문을 재신청한다. 성공하면 `ACCEPTED`로 종료한다.
- 10분이 끝나면 `SUBMISSION_FAILED`로 전환하고 자동 재신청에서 제외한다. 서버 재시작·재호출·주문 수정으로 기한을 연장하지 않는다.
- 요청 결과 저장 실패나 프로세스 중단으로 남은 `SUBMITTING`도 백그라운드에서 복구한다. 읽기 API나 프론트 재호출을 기다리지 않는다.
- 기존 관리자 `POST /api/admin/orders/{id}/retry`는 명시적인 수동 시도로 유지한다. 최종 실패 후 수동 시도도 자동 재시도 기한을 새로 열지 않는다.
- 결제·청구·수거 시각을 다시 처리하지 않는다. 동시에 실행한 작업과 늦게 도착한 이전 시도 결과는 같은 주문의 최신 시도를 덮어쓸 수 없다.

## DB와 API 영향

새 migration `046-order-submission-retry-window.sql` 한 파일에 주문 상태 제약과 두 nullable `timestamptz` 컬럼을 추가한다. 기존 001~045는 변경하지 않는다.

| 컬럼 | 의미 |
|---|---|
| orders.submission_first_attempt_at | 첫 전송 시각. 자동 재시도 마감은 이 시각 + 10분 |
| orders.submission_last_attempt_at | 마지막 전송 시작 시각. 응답 제한·재시도 간격·이전 응답 차단에 사용 |

이전 접수의 첫 시각은 기존 성공 감사 기록을 우선 사용하고, 없으면 결제·생성 시각으로 보수적으로 보완한다. 주문의 기존 버전·생성/갱신 시각은 보완 작업 때문에 바꾸지 않는다.

기존 URL·권한·요청 본문은 유지한다. 주문 상태 응답·필터에 `SUBMITTING_FAILED`를 추가한다. 관리자 목록의 기존 `SUBMISSION_FAILED` 탭은 재시도 중 실패와 최종 실패를 함께 보여주며 개별 `status`로 구분한다. `SUBMITTING`은 기존처럼 처리 중 응답이다. AI·프론트는 `ACCEPTED`만 접수 성공으로 안내한다.

5년 보관 기한이 지난 주문은 정상 재접수 배치에서 제외한다. 과거 미확정 결제는 자동 폐기하거나 재결제하지 않고 별도 확인 대상으로 남긴다.

## 검증 계획

- 실제 무응답 HTTP의 10초 제한과 중간 실패 저장.
- 최초 시각 고정, 1분 재시도 간격, 성공 시 중단, 10분 경계 후 자동 종료.
- 재호출 없는 중단 복구, 서버 재시작, 다중 작업·관리자 경합, 이전 응답 차단.
- 기존 결제·청구·배송 중복 방지, 오래된 주문의 배치 선점 방지.
- populated 045에서 046 적용·롤백과 기존 FK·트리거·원본 시각 보존.

디버의 멱등키·접수 결과 조회 계약은 아직 없다. 응답이 유실된 요청을 재전송할 때 외부 디버에서 발생할 수 있는 중복 접수까지 이 백엔드만으로 보장하지는 않는다.

## 검증 결과

`node backend/scripts/check.cjs` 종료 코드 0. lint·format·Linux 컴파일, 단위 118개·결제 시뮬레이터 21개·PostgreSQL 통합 641개·운영 이미지/nginx·HTTPS 실행 20개, 합계 800개 통과(실패·skip 0).

새 무응답 테스트는 변경 전 최종 실패로 저장되어 실패했고 변경 후 중간 실패로 통과했다. 접수 회귀 17개에서 10초 무응답, 재호출 없는 복구, 1분 간격, 10분 경계, 재시작, 마감 직전 요청 제한, 동시 재시도·이전 응답 차단과 결제·배송 중복 방지를 확인했다. 045 데이터가 있는 046 적용·전체 롤백과 배포 검증문 누락 거절도 확인했다. 운영 DB·실제 디버 호출은 이 검증에 포함하지 않는다.
