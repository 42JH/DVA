# 기업·개인 등록 카드 배포 및 결제 복구

## 적용 범위

`063-member-payment-policy.sql`은 기업 신규 등록의 월결제 기본값을 true로 바꾸고 직원별 월결제·기업 카드 허용을 추가한다. 기존 기업의 false는 유지하며 기존 부서별 그룹결제 허용을 직원별 값으로 복사한다.

`064-payment-cards.sql`은 개인 또는 기업 소유의 등록 카드와 결제 요청의 카드·PG 주문 ID를 추가한다. 과거 결제 요청은 카드 참조가 null이므로 기존 링크를 유지한다. 이미 결제된 주문을 다시 승인하지 않는다.

## 운영 설정과 배포

1. 기존 백엔드 쓰기·워커를 중지하고 DB를 백업한다. 배포 스크립트는 최초 064 적용에서 이 절차를 수행한다.
2. 기존 `~/dva-deploy/shared/.env`에 `TOSS_BILLING_SECRET_KEY`와 `PAYMENT_CARD_ENCRYPTION_KEY`를 추가한다. 기존 결제창용 키, MM URL, 인증 토큰은 보존한다.
3. 빌링 시크릿 키는 **API 개별 연동·자동결제 계약 상점**의 `test_sk_...` 또는 `live_sk_...`다. 기존 결제창용 `test_gsk_...`로 대체하지 않는다.
4. 암호화 키는 `openssl rand -hex 32`로 최초 한 번 생성하는 64자리 hex다. 서버 비밀 저장소에 백업하며 이후 재생성하지 않는다. 임의 변경하면 기존 카드 키를 복호화할 수 없다.
5. 063·064를 순서대로 적용하고 `infra/database/verify.sql`을 통과한 새 이미지를 배포한다. Compose가 새 변수 두 개를 backend에 전달한다. 기존 컨테이너 restart만으로는 환경변수가 갱신되지 않는다.
6. 호스트 HTTPS Nginx의 `infra/https/https.conf`도 반영·검증·reload한다. 등록 카드 승인은 최대 65초, 이어지는 디버 요청은 최대 10초이므로 API 읽기 제한은 양쪽 Nginx 모두 85초다. 프론트 요청 제한도 이 경로에서 85초 이상 허용하거나 동일 요청 키로 조회·복구한다.

새 변수는 프론트나 AI에 전달하지 않는다. 미설정 상태에서도 기존 결제 링크는 유지되며 카드 등록만 503이다. 자동 승인은 기존 `ORDER_PAYMENTS_ENABLED` 설정을 따른다.

토스의 [자동결제 API 연동 가이드](https://docs.tosspayments.com/guides/v2/billing/integration-api)에 따른 카드 정보 발급 방식이다. 실제 상점의 자동결제 계약과 구매자 본인인증 절차는 운영 전 확인한다. 저장하는 값은 암호화된 PG 빌링키·무작위 customerKey·마스킹 정보이며 카드번호·소유자 확인번호·비밀번호는 저장하지 않는다.

## 승인과 복구

- 주문 확정 트랜잭션은 먼저 결제 대기와 사용할 카드를 저장한다. 외부 승인은 DB 트랜잭션 밖에서 실행한다.
- 개인 `billing`은 카드가 없으면 기존 MM 링크, 카드가 있으면 자동 승인이다. `groupBilling`은 기업 카드와 직원 허용을 확인하고 실제 승인 후에만 디버로 보낸다.
- 같은 주문의 승인·조회는 DB 처리권으로 직렬화한다. 승인 시 PG 주문 ID를 멱등키로 사용한다.
- 승인 응답 유실·프로세스 종료 후에는 해당 PG 주문 ID로 조회하며 새 승인으로 바꾸지 않는다. 조회 404·인증 오류·응답 불명확은 결제 완료나 확정 실패로 처리하지 않는다.
- 명시적 승인 거절은 `cardPaymentFailed=true`로 보존하고 자동 재승인을 중단한다. 카드 교체 후 기존 `POST /api/payments/requests/{id}/reconcile`로 명시적으로 다시 처리할 수 있다. 같은 거절 카드로는 재승인하지 않는다.
- 결제 완료와 최초 청구액·완료 안내 대기를 같은 DB 트랜잭션에 기록하고 디버 접수를 시도한다. 디버 실패 재시도는 기존 로직을 사용하며 결제를 반복하지 않는다.
- 그룹 카드 원장은 실제 승인 후 기업 청구로 기록한다. 기업 월결제 `credit`과 개인 월결제 조회의 기존 구분은 유지한다.
- 카드 해제·교체·고객/기업 삭제는 soft delete와 감사를 같은 트랜잭션으로 저장한다. 진행 중 승인 결과 확인이 끝난 뒤 워커가 PG 빌링키를 해제하며, 삭제 행은 기존 정책과 같이 5년 뒤 폐기한다.

## 복귀 제한

064 적용 뒤에는 이미지 단독으로 이전 앱에 복귀하지 않는다. 구버전은 새 직원 권한과 등록 카드 승인을 모르므로 결제를 건너뛰거나 링크를 중복 제공할 수 있다. 배포 스크립트가 호환되지 않는 수동·자동 복귀를 차단한다. 호환 이미지로 수정 배포하거나 쓰기를 중지한 상태에서 백업 복구를 별도로 결정한다.

## 검증 범위

격리 PostgreSQL과 로컬 PG·MM·디버 모형으로 API·금전 처리·기존 경로를 검증한다. 실제 상점의 카드 등록·카드사 승인과 운영 배포는 별도 확인 대상이다.
