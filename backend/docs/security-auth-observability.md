# S10 인증 보안 기록·탐지 운영

로그인 성공·실패와 관리자 세션, AI 업무·페르소나·통화 기록 인증 실패를 응답 완료 시 한 번 기록한다. S04의 차단 횟수, 비밀번호 검증, 쿠키, Origin, 응답 코드·본문은 유지한다. 기존 DB 감사 기록과 별도로 stdout → Alloy → Loki → Grafana 경로를 사용하며 새 테이블은 없다.

## 백엔드 키 설정

변수 이름은 `SECURITY_LOG_HMAC_KEY`다. 32바이트 난수를 64자리 16진수로 표현한다. AI 토큰과 다른 키를 사용하며 AI·프론트에 전달하지 않는다.

```bash
openssl rand -hex 32
```

Node.js에서도 생성할 수 있다.

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

생성한 값을 백엔드 배포 환경에 주입한다. 환경 파일 경로 예시는 `/path/to/deploy/shared/.env`다. 개발에서 Node를 직접 실행하면 `backend/.env.development`, 개발 Compose는 저장소 루트의 `.env`를 사용한다. 실제 파일이나 생성한 값은 Git·채팅·빌드 산출물에 넣지 않는다.

```dotenv
SECURITY_LOG_HMAC_KEY=<생성한 64자리 16진수>
```

production에서는 누락·잘못된 형식이면 시작을 거절하고 변수 이름만 오류에 남긴다. development/test의 미설정은 프로세스 임시 키를 사용하므로 재시작 간 식별값 연계는 보장하지 않는다. 운영 키를 교체하면 이전·이후 표시값이 달라져 기존 탐지 창의 계정·출처별 연계가 끊긴다.

같은 운영 환경의 백엔드 인스턴스는 같은 키를 사용해야 로그가 연결된다. AI·프론트와의 키 공유를 뜻하지 않는다.

## 기록과 개인정보

- 이벤트: `authentication_success`, `authentication_failure`.
- 고정 인증 종류: `admin_login`, `admin_session`, `ai_business`, `ai_persona`, `ai_insights`.
- 실패 사유는 잘못된 인증 정보·세션·서비스 토큰, 비활성/승인 대기, 접근 거절, 요청 제한, 잘못된 입력, 서비스 설정 누락으로 구분한다. 비밀번호 불일치와 존재하지 않는 ID는 같은 `invalid_credentials`다.
- `accountKey`는 유효한 ID 형식으로 주장된 로그인 계정의 HMAC이다. 실제 계정 존재·로그인 성공의 증거가 아니다. 기존 대소문자 구분을 보존한다. 잘못된 입력에는 계정 표시값을 붙이지 않는다.
- `sourceKey`는 기존 `AUTH_PROXY_HOPS`와 동일한 신뢰 프록시 경로에서 얻은 출처의 HMAC이다. 백엔드 포트 비공개·edge 헤더 덮어쓰기 조건은 S04와 같다. IP로 해석할 수 없으면 생략한다.
- 계정과 출처는 서로 다른 HMAC 입력 영역을 사용한다. 비밀번호·토큰·쿠키·원문 IP·로그인 ID·본문·전달 헤더는 기록하지 않는다.
- 요청 ID로 기존 HTTP 로그와 연결한다. 계정·출처·요청 ID를 Prometheus나 Loki의 저장 라벨로 추가하지 않는다. Loki 라벨은 기존 `service`, `environment`만 사용한다.
- Alloy도 인증 종류와 64자리 소문자 16진수 표시값만 허용한다. 기존 비밀값 제거는 유지한다.

가명값도 접근을 제한한다. 중앙 Loki는 기존 168시간 보관 및 삭제 지연 정책을 따른다. Docker 원본 로그는 기존 용량 회전 정책이 별도 적용되므로 7일 만료와 동일하게 취급하지 않는다.

## 탐지 규칙

| 규칙 | 조건 |
| --- | --- |
| 동일 계정 반복 실패 | 같은 `accountKey`의 `invalid_credentials`가 최근 15분 5회 이상 |
| 한 출처의 다수 계정 시도 | 같은 `sourceKey`에서 최근 5분 서로 다른 계정 10개 이상의 `invalid_credentials` |
| 전체 실패 증가 | 최근 5분 `invalid_credentials` 30회 이상 |
| AI 인증 실패 반복 | AI 인증 종류별 최근 5분 `invalid_service_token` 5회 이상 |

429·비활성·승인 대기·Origin 거절·잘못된 입력·서비스 토큰 미설정·로그인 성공은 위 실패 횟수에 더하지 않는다. 같은 계정의 여러 출처 시도는 계정 규칙에서 합산한다. 한 출처의 같은 계정 반복은 서로 다른 계정 수로 중복 계산하지 않는다.

LogQL은 표시값을 조회 시에만 분석하고 최종 결과를 단일 집계로 만든다. 저장 라벨은 기존 두 개로 유지한다. Loki는 집계 중간에도 조회 시계열 한도를 적용하므로 기존 기본 500 대신 단일 백엔드의 로그인 추적 상한을 기준으로 `max_query_series: 10000`을 명시한다. 메모리·CPU·동시 조회 상한은 늘리지 않는다. 출처/계정 조합 증가·재시작·향후 복제본 등으로 예산을 넘을 수 있으며, 이를 무제한으로 처리한다고 주장하지 않는다.

보안 규칙의 조회 실패는 `DatasourceError`로 알린다. 이 경우 횟수 조건을 충족했다고 표시하지 않고 고정된 탐지 조회 실패 안내만 보낸다. 원문 오류·쿼리 응답·계정·출처를 메시지에 직렬화하지 않는다. Grafana 알림 라벨은 고정된 서비스·사건 종류이며 기존 30초 평가·그룹 대기와 반복 정책을 유지한다. 이 규칙은 확인이 필요한 징후이며 실제 공격을 확정하지 않는다.

## 적용 순서

1. 백엔드 키를 먼저 운영 env에 추가한다.
2. 새 백엔드 이미지와 Compose로 배포해 컨테이너 환경을 다시 주입한다. 파일 저장이나 단순 `restart`만으로 새 환경이 반영되지는 않는다. 기존 DB migration 절차는 그대로다.
3. 관측 파일을 별도로 반영하고 갱신된 관측 `deploy.sh`로 적용한다. Loki·Alloy·Grafana를 재시작해 파일 설정을 다시 읽으며 업무 앱은 재시작하지 않는다. 일반 백엔드 배포에는 관측 설정이 포함되지 않는다.
4. Grafana 기존 `DVA BE 운영 상태` 대시보드의 인증 보안 기록 패널과 요청 ID를 확인한다. 계정·출처 분석은 `accountKey`·`sourceKey`를 이용한다.
5. `MATTERMOST_WEBHOOK_URL`이 없는 관측 환경에서는 새 규칙도 일시 정지 상태다. 기존 운영 설정을 사용한다. 실제 채널 테스트 메시지 발송과 운영 배포는 코드 검증과 별개다.

AI·프론트 변경, DB 이행, 새 인증 정책은 필요하지 않다. 로거 출력 지연 시 제한된 로그 유실을 허용하며 수집기·Grafana·서버 전체 장애 중 탐지를 보장하지 않는다. 보안 기록 실패가 업무 응답을 실패시키지 않는다.
