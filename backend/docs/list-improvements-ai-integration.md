# AI 전달 명세 — 통화 분석 실패·목록 개선·수거 시간

작성일: 2026-11-08. 이번 프론트 요청 1~6번의 **모놀리식 backend** 연동 변경이다. 기존 주문 초안·FAQ·미답변 등의 전체 계약을 대체하지 않는다. 이 문서 작성만으로 운영 배포나 AI 구현이 완료된 것은 아니다.

## AI가 변경할 부분

새로 호출할 API는 **분석 단계의 최종 실패 통보 한 개**다. 정상 분석 전송은 기존 API를 그대로 사용한다. 기업명·결제 가능 수단·관리자 검색은 백엔드가 기존 관계를 조회하므로 AI가 추가 필드를 보내지 않는다.

| 상황 | 호출 |
| --- | --- |
| 정상 통화 분석 결과 저장 | 기존 `POST /api/ai/calls/{callSessionSeq}/analysis` |
| 분석 단계가 최종 실패로 확정 | 신규 `POST /api/ai/calls/{callSessionSeq}/analysis/failure` |
| 분석은 성공했으나 FAQ·미답변·녹취 등 다른 전송 단계만 실패 | 분석 실패 API를 호출하지 않고 해당 단계 복구 |

## 분석 최종 실패 통보

```http
POST /api/ai/calls/123/analysis/failure
Authorization: Bearer <AI_INSIGHTS_TOKEN>
Content-Type: application/json
```

```json
{
  "providerCallId": "rtc_example"
}
```

- 경로: 백엔드가 발급한 `callSessionSeq`. 본문: 해당 통화의 **OpenAI 통화 식별자**인 `providerCallId`. PBX 녹취 번호와 다르다.
- `providerCallId`는 기존 정상 분석과 같은 1~200자 비공백·NUL 없는 문자열이다.
- 인증은 기존 **AI_INSIGHTS_TOKEN**이다. 고객·주문 API의 AI_BUSINESS_TOKEN이나 관리자 세션으로 대체하지 않는다. 새 환경변수는 없다.
- 본문은 위 필드 하나만 받는다. 실패 시각·오류 원문·실패 사유·카운터나 `call_session_seq` 헤더를 추가하지 않는다. 알 수 없는 본문 필드는 400이다.
- 성공은 **204, 응답 본문 없음**이다. 최초 수신 시각만 서버가 저장한다. 같은 요청을 다시 보내도 204이며 최초 시각은 바뀌지 않는다.

| HTTP | 처리 기준 |
| --- | --- |
| 204 | 기록 성공, 중복 또는 이미 정상 분석이 저장된 통화 |
| 400 | 경로·본문 형식이나 미허용 필드 확인 |
| 401 | insights 토큰 누락·오류 확인 |
| 403 | 통화 번호와 providerCallId 불일치 또는 기존 Origin 제한 확인 |
| 404 | 없는 통화, 삭제되었거나 보관 기한이 만료된 통화 |
| 503 | 백엔드 insights 인증 설정 확인 |
| 기타 5xx·타임아웃 | 같은 통화·같은 본문으로 전송 재시도 |

오류는 기존 `{ "error": { "code": "...", "message": "...", "details": [] }, "meta": { "requestId": "..." } }` 구조다. 204를 JSON으로 파싱하지 않는다.

## AI 전송 시점과 재시도

1. 기존 정상 분석 단계를 실행하고 기존 성공 API로 전송한다.
2. 분석 자체가 최종 실패한 경우에만 새 실패 통보를 영속 전송/재전송 경로에 넣는다. 분석을 계속 시도하는 동안의 일시 장애를 최종 실패로 보내지 않는다.
3. outbox 전체 FAILED에는 다른 단계 실패도 포함될 수 있다. 전체 상태만 보고 분석 실패를 통보하지 않는다.
4. 실패 통보의 타임아웃은 미저장을 뜻하지 않는다. 같은 요청을 다시 보낸다. 400/401/403/404는 식별자·인증·본문·수명 문제를 먼저 확인한다.
5. 분석 복구 후에는 정상 결과를 기존 성공 API로 보낸다. 백엔드는 정상 결과를 우선한다. 가짜 0건·빈 분석으로 실패를 표현하지 않는다.

백엔드는 이 API로 통화를 만들거나 PBX 종료·주문·녹취를 변경하지 않는다. PBX 종료 웹훅보다 먼저 실패 통보가 도착해도 기존 통화와 식별자가 맞으면 저장할 수 있다.

## 프론트에 보이는 분석 상태

`GET /api/calls`의 `data[]`, `GET /api/calls/{id}`의 `data.call`에 다음 상태가 반환된다.

| 상태 | 기준 |
| --- | --- |
| COMPLETED | 정상 분석 저장. 과거·늦은 실패 통보보다 우선 |
| FAILED | 정상 분석은 없고 최종 실패 통보를 수신 |
| PENDING | 둘 다 없음. 시간 경과만으로 실패로 바꾸지 않음 |

실패 통보가 누락되면 PENDING으로 남는다. 과거 통화도 AI가 실제 분석 단계 실패를 확인한 보관 기간 내 건만 재통보한다. 종료 후 5분 같은 자동 실패 기준이나 과거 데이터 일괄 실패 처리는 없다.

`recordedAt`은 기존 녹취 참조의 최초 **DB 저장 시각**이며 AI가 새로 보낼 필드는 아니다. 실제 녹음 시작 시각과 다르다.

## 수거 시각 — 기존 계약 유지

- 운영 시간 기준은 **한국 시간 09:00~17:00, 정확히 17:00 포함**이다. 현재 AI `workflow.toml`도 이 설정이다.
- AI가 보낸 수거 희망 시각은 기존 주문 API로 시간대가 포함된 ISO 8601 값으로 보낸다. 이번 작업에서 백엔드는 AI 입력에 새 영업시간 차단을 추가하지 않는다.
- 요청 시각이 결제 시각과 같거나 나중이면 원래 요청 시각을 유지한다. 결제 1시간 전 여부와 무관하다.
- 요청 시각이 이미 지났거나 없으면 결제 시각+1시간으로 보정한다. 보정 결과가 09:00 전이면 당일 09:00, 17:00을 넘으면 다음 **달력 날짜** 09:00이다. 정확히 17:00은 당일 유지한다.
- 프론트팀에는 수기 입력에 09:00부터 17:00까지와 현재 시각+1시간부터 +72시간까지의 검사를 함께 적용하도록 요청한다. 이 프론트 제한을 AI의 기존 API 거부 규칙으로 해석하지 않는다. 이번 backend MR에 프론트·AI 소스 변경은 없다.

## 적용 순서와 확인

1. 기존 DB runner로 `056-call-analysis-failure.sql` 적용 및 DB 검증.
2. 이번 backend 배포. `call_sessions.analysis_failed_at` nullable timestamptz 하나가 추가되며 신규 테이블·FK·과거 실패 backfill은 없다.
3. AI 실패 통보 경로 연결. 새 통화에서 PENDING → FAILED → 정상 분석 복구 후 COMPLETED를 확인하고 정상 분석 후 늦은 실패가 완료 상태를 내리지 않는지 확인한다.
4. 프론트가 서버 상태를 사용하도록 반영. 분석 내용·카운터·기존 성공 전송은 유지한다.

실패 기록은 기존 통화의 soft delete·최초 수신 기준 5년 보관 정책을 따른다. 재통보나 7일 로그 정리로 기한이 바뀌지 않는다. MSA 별도 consultation DB/API는 이번 모놀리식 migration으로 변경되지 않으므로 별도 전환 시 동등 계약을 확인해야 한다.
