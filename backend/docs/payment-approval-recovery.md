# S05 결제 실패 판정과 복구

## 변경과 적용 범위

최초 승인에서 결제가 없거나 세션이 만료되었다고 확인한 경우까지 키를 고정하던 경로를 수정한다. `PaymentsService`의 실패 판정과 백엔드 소유 고객 결제 페이지 `checkout.js`를 변경한다. 기존 승인·취소 잠금, 45초 처리권, 승인 기록 보호와 멱등키를 재사용한다.

| 외부 결과 | 서버 처리 | 고객 페이지 |
| --- | --- | --- |
| 최초 승인 POST의 HTTP 404 + `NOT_FOUND_PAYMENT` 또는 `NOT_FOUND_PAYMENT_SESSION` | 조건부 키 해제, 기존 422 `PAYMENT_FAILED` | 기한 내 `PENDING`, 같은 링크에서 새 결제 시도 |
| 최초 승인 POST의 기존 카드 거절 | 기존 조건부 키 해제·422 유지 | 같은 링크 재시도 |
| 조회 GET의 404·인증 오류·5xx·타임아웃·불일치 | 키 보존, 기존 502 `PAYMENT_RESULT_UNKNOWN` | `REVIEW_REQUIRED`, 결과 확인 유지 |
| `ALREADY_PROCESSED_PAYMENT` 후 조회 오류 | 최초 승인 결과와 구분하여 키 보존 | 재결제 차단 |
| 동일 주문·결제 키·금액·KRW의 `ABORTED`·`EXPIRED` 조회 | 기존 조건부 해제·422 유지 | 기한 내 같은 링크 재시도, 기한 후 `EXPIRED` |
| 동일 주문·결제 키·금액·KRW와 유효 승인 시각의 `DONE` | 기존 결제 저장·디버 접수 | 결제 완료와 택배 접수 완료를 구분 |

조건부 해제는 현재 DB 처리권이 유효하고 해당 요청에 승인·완료·무효화 기록이 없을 때만 성공한다. 이 조건을 만족하지 못하면 422로 단정하지 않고 502를 반환한다. 기존 24시간 결제 기한을 연장하거나 새 링크를 발급하지 않는다.

판정은 [토스 공식 승인 오류 코드](https://docs.tosspayments.com/reference/error-codes)의 두 404 코드를 최초 승인 거절에 한정해 적용한다. 과거 승인이 불명확한 건의 조회 404까지 미승인 증거로 확대하지 않는다. `ALREADY_PROCESSED_PAYMENT` 이후의 응답은 조회 결과이므로 카드 거절 코드가 오더라도 직접 승인 거절로 분류하지 않는다.

결과 확인 요청이 422로 끝나면 페이지는 GET으로 현재 서버 상태를 다시 읽는다. `PENDING`이면 기존 결제 화면으로 돌아가는 링크를 보여 준다. 처음부터 확인 대기였던 페이지에는 토스 위젯이 초기화되지 않았으므로, 그 페이지의 결제 버튼만 활성화하지 않는다. `PAID`·확인 대기·만료·취소 상태에서는 재결제를 안내하지 않는다.

## AI·프론트·DB·환경변수 영향

- **AI 수정 없음:** 주문 API URL, 요청·응답 필드, `paymentRequest`, 주문 상태, Bearer 인증, 호출 순서를 유지한다. AI에 승인·재조회·복구 API 호출을 추가하지 않는다.
- **관리자 프론트 필수 수정 없음:** 기존 공개 결제 상태 `PENDING`, `REVIEW_REQUIRED`, `PAID`, `EXPIRED`, `CANCELLED`와 오류 봉투를 유지한다. 이미 사용하던 422·502의 적용 대상만 명확하게 구분한다. 별도 클라이언트가 모든 결제 실패를 502로 가정한다면 기존 422 처리 여부는 확인해야 한다.
- **고객 결제 화면 수정:** 백엔드 이미지에 포함된 JavaScript가 갱신된다. 별도 프론트 저장소 수정·빌드가 필요하지 않다.
- **환경변수 추가 없음:** 토스·Mattermost·AI 설정을 변경하지 않는다. 결제 기본 비활성·테스트 키 전용 정책도 유지한다.
- **추가 migration 없음:** 이미 제공된 migration 051의 다음 확인 시각과 처리권을 사용한다. 배포 DB는 기존 전체 migration 기준을 충족해야 하며 이 작업에서 운영 DB를 변경하지 않는다.
- **멱등키 유지:** 결제 요청 ID·금액·토스 결제 키의 SHA-256을 그대로 사용한다. 같은 실패 키의 응답이 재사용되어도 새 결제 키의 정상 시도는 다른 멱등키를 사용한다.

신규 링크나 AI 추가 호출을 요구하는 변경은 도입하지 않았다. 실제 AI·관리자 프론트 소스는 사용자 지정 제외 범위이므로 해당 구현·실통화까지 검증한 결론은 아니다.

## 기존 미확정 결제의 운영 확인

1. 기존 고객 링크 또는 `GET /api/payments/requests/{paymentRequestId}`에서 현재 상태를 확인한다. 링크 ID와 토스 결제 키는 공개 로그·메신저에 남기지 않는다.
2. `REVIEW_REQUIRED`는 재결제·취소로 우회하지 않는다. 고객 페이지의 결과 확인 또는 같은 Origin에서 기존 `POST /api/payments/requests/{paymentRequestId}/reconcile`에 `{}`를 전송한다. 이 요청은 DB의 기존 키로 조회하며 승인을 다시 POST하지 않는다.
3. 인증 오류라면 운영 담당자가 키 종류·상점·테스트 환경의 일치를 확인한 후 같은 건을 재조회한다. 잘못된 설정을 결제 실패로 간주해 키를 지우지 않는다.
4. 조회가 동일 결제의 `DONE`을 확인하면 결제 저장을 복구한다. 동일 결제의 `ABORTED`·`EXPIRED`를 확인하면 조건부 해제하고, 기한 내 같은 링크의 새 시도를 허용한다. 422 뒤에는 상태를 다시 조회한다.
5. 조회 404·계속 처리 중·계속되는 장애는 사업자 관리 화면·지원 창구에서 승인 여부를 확인한다. 단순 미조회·담당자 추정만으로 DB 키 삭제, 강제 결제 완료, 신규 결제를 실행하지 않는다. 서버가 확인할 수 있는 확정 결과가 없으면 확인 대기를 유지한다. 강제 초기화 API는 추가하지 않았다.

배포 전 이미 404를 받고 확인 대기가 된 건에는 최초 응답이 저장되어 있지 않으므로 일괄 해제하지 않는다. 이번 수정은 새 최초 승인 응답을 안전하게 분류하며, 과거 불명확 기록을 미승인으로 소급 판정하지 않는다. 워커의 기존 20건 순환 선정·1분 뒤 재조회 예약은 유지되므로 오래된 미확정 건이 새로운 건을 계속 독점하지 않는다.

토스 [코어 API](https://docs.tosspayments.com/reference)의 주문번호 조회는 주문서형 키(`test_gsk`)를 지원하지 않으므로 해당 조회를 추가하거나 운영 키 교체를 요구하지 않는다. 실제 테스트 카드·실제 상점에서 같은 링크의 새 시도를 검증하는 일은 배포 전 별도 확인 항목이다.

## 검증

`test/payment-recovery.test.cjs`는 실패 분류·조회 응답 출처·처리권 해제 실패와 실제 배포 결제 JavaScript를 검사한다. `test/order-payments.integration.test.cjs`는 격리 PostgreSQL과 모의 토스·디버로 같은 링크의 새 시도, 실패 응답 멱등성, 기한 보존, 취소·만료 정리를 검사한다. 기존 응답 유실·재시작·중복 승인·21건 순환 조회·승인 기록 보호 검사도 유지한다.

실행 명령은 `npm run build`, `node --test test/payment-input.test.cjs test/payment-recovery.test.cjs`, `npm run check:docker`다. 실행 결과는 작업 완료 시 별도 검증 기록에 남긴다. 이 문서 자체는 운영 배포·실제 토스 승인·AI 실통화 성공을 증명하지 않는다.
