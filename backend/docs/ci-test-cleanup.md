# Jenkins 백엔드 테스트 정리

기준은 MR !388의 `9dec7f85`, 정리 브랜치는 `ci/backend-test-prune`이다.
Jira는 [S15P31D109-174](https://ssafy.atlassian.net/browse/S15P31D109-174)이며 기존 홈 화면·연동 문서·빌드별 체크아웃 수정도 함께 유지한다.
이번 정리는 업무 src, API 응답, migration, 실제 배포 설정을 바꾸지 않는다.

## 실행 건수

`BACKEND_TEST_PROFILE=full`의 실제 `node:test` 결과를 합산했다. `test()` 선언 개수와 반복문으로 생성되는 사례 수는 다르다.

| 검증 | 이전 | 정리 후 | 감소 |
| --- | ---: | ---: | ---: |
| 백엔드 단위 | 201 | 200 | 1 |
| 결제 데모 단위 | 21 | 21 | 0 |
| 격리 PostgreSQL·API | 866 | 640 | 226 |
| 운영 이미지·Nginx·HTTPS | 23 | 13 | 10 |
| 합계 | **1,111** | **874** | **237 (21.3%)** |

삭제한 사례를 다른 실행 명령으로 옮기거나 skip으로 숨기지 않았다. DB 실행 프로세스 묶음은 56개에서 47개로 줄였다.
Jenkins/Git 회귀 8개와 Linux 배포 mock 3종은 위 백엔드 건수에 포함하지 않는다.

보관 만료, 데이터 격리, 금액·결제 중복 방지, 외부 전송 실패/재시도, 트랜잭션 rollback, 감사 실패, 다중 인스턴스 검증은 현재 업무 경로에서 유지한다.
과거 데이터의 특정 버전별 변환 재현과 대량 데이터 실행계획/시간 비교는 정리 후 자동 회귀 범위에서 제외된다. 해당 검증이 필요한 DB 전환·성능 작업에서는 이전 커밋의 시나리오와 당시 측정 기록을 참고한다.

## 반복 준비 비용

- 업무 테스트에서 Swagger를 기본 생성하지 않고 스키마를 확인하는 home에서만 활성화한다. 운영 이미지의 Swagger 비공개 검사는 유지한다.
- 14개 업무 테스트 파일의 비밀번호 해시·로그인 준비를 기존 `createTestSession`으로 바꾼다. 임시 DB에 정상 세션을 준비하고 실제 HTTP 인증 guard·권한·상태·Origin 검사를 통과한다.
- 실제 비밀번호 검증, 쿠키 발급·만료·로그아웃·세션 폐기, 로그인 제한은 auth/auth-limits와 운영 이미지 검증에서 실제 로그인으로 검사한다. 새 의존성이나 실행 생략 설정은 추가하지 않는다.
- 실행 목록에서 삭제된 파일 참조를 제거하고 영향 범위 선택기를 갱신한다. 미등록/누락/중복, 알 수 없는 변경의 전체 검증 전환은 기존 단위 검증으로 계속 확인한다.

## 검증 기록

1. `a2a0b73`: 1차 삭제 후 전체 Docker 검증 통과. 874개, 실패·취소·skip 0, 총 244,214ms.
2. `f033019`: 로그인 준비 정리 후 전체 Docker 검증 통과. 874개, 실패·취소·skip 0. 컴파일·lint·format, 격리 DB·운영 이미지·Nginx/HTTPS 검증 포함.
3. Windows와 Linux의 Jenkins/Git 8개 통과. Linux 배포 trigger/deploy/package mock 3종과 셸 문법 검사 통과. 실제 배포는 실행하지 않았다.
4. `dashboard` 선택 실행도 빈 격리 DB에서 통과했다. DB·API 파일 10개, 검증 총 53,625ms이며 누락된 선행 fixture 없이 홈·통계와 운영 이미지 검증을 실행했다.

초기 삭제 검증에서 기업 역할 테스트가 쓰는 두 번째 앱/세션 fixture를 함께 지운 오류가 발생했다. 해당 fixture를 복구하고 권한 assertion을 유지한 상태로 위 전체 검증을 다시 통과했다.

| 로컬 전체 검증 | 이전 | 1차 정리 | 로그인 준비 정리 후 |
| --- | ---: | ---: | ---: |
| 총시간 | 289,232ms (4분 49초) | 244,214ms | **205,846ms (3분 26초)** |

로컬 총시간은 약 28.8% 감소했다. 이전 로컬 실행은 checks 단계의 단위/결제 결과를 Docker 캐시로 재사용했고, 정리 후 실행에서는 221개를 새로 실행했다. 설치/이미지 캐시와 호스트 부하가 달라질 수 있으므로 고정 성능 보장은 아니다.

실제 Jenkins #114의 backend 검증은 1,300,602ms(21분 41초), DB·API는 972,632ms(16분 13초)였다. 전체 Job은 26분 16초였다. #115는 Checkout의 HEAD.lock 오류로 테스트에 진입하지 않았다.
동일 Jenkins 에이전트·빌드 전용 Docker에서 `f033019`를 새 전용 디렉터리로 실행한 전체 검증도 종료 코드 0으로 통과했다. 단위 200·결제 데모 21·DB/API 640·운영 이미지 13개, 총 **874개를 새로 실행**했고 실패·취소·skip은 0이었다.

정리 후 측정은 Jenkins 에이전트에서 `BACKEND_TEST_PROFILE=full node backend/scripts/check.cjs`를 직접 실행한 값이다. 바깥 프로세스는 Docker 자원 정리까지 544.837초였다. 번호가 붙는 Jenkins Job의 Checkout·산출물 패키징·배포 단계는 실행하지 않았다. #114는 `58134403`, 정리 후는 기존 !388 변경까지 포함한 `f033019`이며, 동일 시점의 고정 부하 A/B 실험은 아니다. 서버 자원 제한을 바꾸거나 기존 공유 checkout·Git 잠금·다른 작업의 컨테이너를 삭제하지 않았다.
