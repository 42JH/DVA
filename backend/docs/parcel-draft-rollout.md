# 055 배송 초안 전환·배포·복구

코드 범위는 backend 모놀리식과 그 infra다. AI·프론트 소스, MSA 서비스/라우팅, 실제 운영 DB·컨테이너는 이번 작업에서 변경하지 않는다.

## DB 변경

- 새 테이블 1개: order_parcel_drafts. 배송 단건 스냅샷·수집/미완료/재개/변환 이력, 생성 UUID 원문 비교, version, 삭제·최초 보관 시각을 저장한다.
- customer_seq·call_session_seq·created_by_admin_user_seq·source_draft_seq·order_seq·order_parcel_seq·legacy_order_seq·legacy_order_parcel_seq는 모두 논리 참조다. 이 테이블의 실제 FK와 연쇄 삭제는 없다. caller_phone_number·parcel_data는 원본 삭제와 독립적인 최소 업무 사본이다.
- call_sessions에 order_intake_enabled/version, order_completion_received_at/payload, order_finalized_at/result, order_finalization_error_code/attempted_at의 8개 컬럼과 완료 짝 검증·복구 인덱스를 추가한다. 기존 행 enabled=false, 이후 등록 true다.
- 기존 COLLECTING을 초안 INCOMPLETE/기존 취소 상세 CANCELLED로 복사한다. 상세 없는 원본도 부분 초안 1개로 보존한다. 원본의 고객/행/시각/version/실제 FK/감사/결제 상태는 바꾸지 않는다. 여러 통화가 한 원본에 연결돼 있으면 초안의 통화·발신번호를 임의로 하나 선택하지 않고 null로 둔다.
- 실제 결제 대기·결제 완료·디버 접수/실패 주문은 이관 대상이 아니다. 미완료를 자동 READY로 승격하거나 결제·디버 전송하지 않는다.
- public 테이블 30개, FK 25개, 업무 트리거 10개다. pbx_webhooks는 기존 별도 스키마다. 배포 원본은 단일 `055-parcel-draft-intake.sql`이며 이전 적용 migration은 변경하지 않았다.

## 전환 순서

1. AI·프론트에 개별 명세를 전달하고 새 초안/완료 신호 계약 준비를 확인한다. 신규 통화의 기존 AI 주문 생성·수정·취소·최종 접수 쓰기는 409가 된다.
2. 새 유입을 잠시 중지하고 기존 진행 통화와 AI outbox 전송을 마친다. 남은 PBX·결제 승인·디버 처리권을 점검한다. 실제 결제 미확정 결과를 임의 실패로 바꾸지 않는다.
3. 기존 backend 쓰기를 중지하고 백업한다. 기존 runner로 미적용 migration 전체를 한 트랜잭션에서 적용하고 verify.sql을 통과시킨다. 이 작업에서는 운영 runner를 실행하지 않았다.
4. 055 호환 backend와 새 AI·프론트를 전환한 뒤 신규 통화를 연다. 계정·AI_BUSINESS_TOKEN·기존 결제·디버 설정을 유지한다. 신규 환경변수나 별도 메시지 브로커는 없다.
5. 새 통화 등록 → EDITING/READY 단건 저장 → PBX·AI 완료 → 카드 대기 또는 월·그룹 접수 → 후속 실제 번호 이벤트를 확인한다. 이관 미완료 목록·관리자 보완·삭제/보관도 점검한다.

기존 deploy.sh는 055 최초 전환에서 stop → 백업 → migration/verify → 새 앱 순서를 적용한다. 이후 같은 스키마의 배포는 기존 무중단 범위를 유지한다. 통화 유입 차단·AI/프론트 전환은 운영 협업으로 수행한다.

## 복구

완료 신호·초안·최종 결과는 DB에 보존한다. PBX가 늦게 온 건은 기존 10초 유지보수 워커에서 처리한다. 로컬 확정 실패는 오류 코드와 마지막 시도를 저장하고 1분 뒤 다시 시도한다. 같은 완료 본문을 재호출해도 된다. 누락된 PBX/AI 신호를 추정하거나 미완료를 임의 접수하지 않는다.

FAILED는 원인별로 확인한다. 활성 고객/결제 자격·PIN이 없어졌으면 업무 상태를 확인하고, DEPENDENCY_UNAVAILABLE은 기존 디버 설정을 확인한다. DB/감사 저장 실패는 전체 로컬 변환을 롤백한다. 봉인은 유지되므로 확정 본문을 바꿔 덮어쓰지 않는다. 데이터 수정이 필요하면 운영 검토를 거쳐야 하며 자동으로 다른 결제수단을 선택하지 않는다.

디버 요청은 로컬 트랜잭션 밖이다. PAID 이후 프로세스가 중단되면 기존 워커가 전송을 이어간다. 디버 실패는 결제와 별개로 기존 10초 제한·최초 10분/1분 재시도를 따른다. 결제를 다시 받지 않는다. 느린 디버 호출은 최대 20개 복구 배치를 병렬 처리해 기존 결제/재시도 유지보수 앞에 직렬 누적시키지 않는다.

055 적용 뒤 호환되지 않는 구버전 배포·수동 rollback·자동 복귀는 차단한다. 구버전 앱이 이관 원본을 다시 접수하면 중복 결제가 생길 수 있기 때문이다. 호환 앱으로 전진 복구하거나 쓰기 중지 상태에서 백업을 별도 DB로 복원·검증한 후 전환한다. 이미지 단독 복귀로 DB를 되돌리지 않는다.

## 보관·삭제

초안·생성 비교 사본·발신번호는 최초 수집부터 5년, 과거 이관은 원래 주문 생성부터 5년이다. 재개 사본은 원본 보관 시작을 상속한다. 삭제일·수정일·재개일로 연장하지 않는다. 삭제·만료는 서버 조회에서 제외하고 기존 retention 워커가 100개씩 실제 폐기한다. 주간 감사/전송 로그 정리와 분리된다.

원본 고객/통화/주문/초안이 없어져도 남은 초안의 번호·텍스트를 NULL 처리하거나 연쇄 삭제하지 않는다. 소유권 없는 쓰기·만료 데이터 재개는 거절한다. 실제 주문/결제/배송의 기존 내부 FK와 트랜잭션 경계는 유지한다. 신규 주문의 실제 접수 이후 보관 정책은 기존 orders 정책을 따른다.
