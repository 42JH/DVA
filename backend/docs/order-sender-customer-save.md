# 주문 보내는 분 수정과 고객정보 선택 저장

프론트 주문 상세의 **보내는 분 수정** 연동 명세. 2026-11-01 합의 기준이다.

기존 주문 수정 API와 고객 수정 API를 순서대로 사용한다. 신규 API·DB migration·백엔드 동의 필드는 추가하지 않는다. 노티와 동의 상태는 프론트에서 처리한다.

## 1. 화면 동작

보내는 분의 이름·주소를 변경할 때 다음 내용을 확인한다.

> 변경한 이름과 주소를 고객정보에도 저장할까요?
>
> 고객정보에 저장하면 해당 고객의 기본 정보도 변경됩니다. 다른 주문의 배송정보와 PIN은 변경되지 않습니다.

| 선택               | 저장 동작                                 |
| ------------------ | ----------------------------------------- |
| 이번 주문에만 저장 | 주문 수정 API만 호출                      |
| 고객정보에도 저장  | 주문 수정 성공 후 고객 수정 API 추가 호출 |

전화번호는 해당 주문의 보내는 분 정보에서만 변경할 수 있다. 고객 원본 전화번호 변경은 지원하지 않는다. 전화번호만 바꾼 경우에는 고객 저장 대상으로 안내하지 않고 고객 PATCH도 호출하지 않는다.

이 기능은 주문을 다른 고객으로 옮기는 기능이 아니다. 주문 상세의 `customerSeq`를 유지한다.

## 2. 호출 순서

1. `GET /api/orders/{orderSeq}`로 `customerSeq`, `version`, `parcels[].orderParcelSeq`와 현재 보내는 분을 읽는다.
2. 고객 기본 정보가 필요한 경우 `GET /api/customers/{customerSeq}`로 조회한다.
3. 폼에 입력한 보내는 분과 고객정보 저장 동의 여부를 프론트에 보관한다. 동의 플래그를 API 본문에 추가하지 않는다.
4. 아래 주문 PATCH를 먼저 호출한다.
5. 주문 저장이 성공하면 응답의 실제 `version`을 반영한다.
6. 고객 저장에 동의했고 저장할 이름 또는 주소 변경이 있을 때만 고객 PATCH를 호출한다.
7. 성공 후 주문 상세와, 고객 저장을 시도한 경우 고객 상세를 다시 조회해 화면을 갱신한다.

**주문 저장이 실패하면 고객 수정 API는 호출하지 않는다.**

## 3. 주문의 보내는 분 저장

```http
PATCH /api/orders/123
Content-Type: application/json
```

```json
{
  "expectedVersion": 4,
  "parcels": [
    {
      "orderParcelSeq": 101,
      "origin": {
        "name": "홍길동",
        "phoneNumber": "01012345678",
        "roadAddress": "서울시 예시로 1",
        "jibunAddress": "서울시 예시동 1",
        "detailAddress": "101호",
        "dongName": "예시동",
        "postalCode": "01234",
        "latitude": 37.5,
        "longitude": 127
      }
    }
  ]
}
```

- 예시 번호는 실제 주문 번호·상세 번호·조회 버전으로 바꾼다.
- **기존 상세 수정에는 `orderParcelSeq`를 반드시 보낸다.** 생략하면 상세 추가로 처리된다.
- `origin`에는 수정한 하위 필드만 보낼 수 있다. 생략한 값과 다른 상세는 유지된다.
- 주문 고객·고객 원본·원본 PIN·다른 주문은 자동 변경하지 않는다.
- 허용되지 않는 `customerSeq`, `saveCustomerInfo` 등의 추가 필드를 주문 PATCH에 보내지 않는다.
- 수정 후 주문을 자동 재접수하거나 디버에 변경 전송하지 않는다.

성공은 HTTP **200**이다.

```json
{
  "data": { "version": 6 },
  "meta": { "requestId": "00000000-0000-4000-8000-000000000001" }
}
```

위 버전은 예시다. DB 처리 결과를 사용하며 프론트에서 `기존 version + 1`로 계산하지 않는다.

## 4. 동의한 경우 고객 원본 저장

```http
PATCH /api/customers/456
Content-Type: application/json
```

경로의 번호는 주문 상세에서 받은 `customerSeq`다.

```json
{
  "name": "홍길동",
  "address": {
    "roadAddress": "서울시 예시로 1",
    "jibunAddress": "서울시 예시동 1",
    "detailAddress": "101호",
    "dongName": "예시동",
    "postalCode": "01234",
    "latitude": 37.5,
    "longitude": 127
  }
}
```

성공은 HTTP **204**, 응답 본문은 없다. 이 응답에서 `response.json()`을 호출하지 않는다.

| 주문의 보내는 분       | 고객 PATCH 필드         | 규칙                                      |
| ---------------------- | ----------------------- | ----------------------------------------- |
| `origin.name`          | `name`                  | 변경한 경우에만 전달. 빈 이름·null 불가   |
| `origin.roadAddress`   | `address.roadAddress`   | 주소 저장 시 필수                         |
| `origin.jibunAddress`  | `address.jibunAddress`  | 주소 저장 시 필수                         |
| `origin.detailAddress` | `address.detailAddress` | 선택. 생략 또는 빈 문자열 허용, null 불가 |
| `origin.dongName`      | `address.dongName`      | 주소 저장 시 필수                         |
| `origin.postalCode`    | `address.postalCode`    | 숫자 5자리 문자열                         |
| `origin.latitude`      | `address.latitude`      | 숫자 -90~90                               |
| `origin.longitude`     | `address.longitude`     | 숫자 -180~180                             |
| `origin.phoneNumber`   | 전달하지 않음           | 고객 원본 전화번호는 변경 불가            |

- 고객에게 반영할 **변경 필드만** 보낸다. 이름만 바뀌었다면 `name`만 보내고, 주소만 바뀌었다면 `address`만 보낸다.
- `address` 객체를 보낼 때는 위 필수 주소값을 모두 포함한 **전체 주소 객체로 교체**한다. 주문 PATCH의 주소 부분 수정과 다르다.
- `origin` 객체를 그대로 `address`에 복사하면 이름·전화번호 등의 추가 필드 때문에 거절된다.
- 불완전한 주문 주소는 고객 주소로 저장할 수 없다. 임의 좌표·주소를 채우지 말고 주소 완성 또는 이번 주문만 저장하도록 안내한다.
- `address` 생략은 기존 주소 유지, `address: null`은 고객 주소 삭제다. 이 수정 플로우에서 불완전한 주소를 null로 바꿔 보내지 않는다.
- `status`, `monthlyBillingEnabled`, 회원 소속 등은 이 화면의 저장 대상이 아니다.
- 주문의 여러 상세에서 서로 다른 보내는 분을 수정했다면, 고객 원본에 반영할 상세를 사용자가 선택해야 한다. 첫 상세를 자동 선택하거나 모든 상세로 고객 PATCH를 반복하지 않는다.

## 5. 실패와 재시도

두 API는 **별도 트랜잭션**이다.

| 결과                             | 프론트 처리                                                                                                       |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 주문 저장 성공, 고객 저장 미선택 | 주문 수정 완료 안내                                                                                               |
| 주문·고객 저장 모두 성공         | 주문과 고객정보 수정 완료 안내                                                                                    |
| 주문 PATCH 실패                  | 고객 PATCH 호출 금지. 기존 오류에 맞게 재조회·수정 안내                                                           |
| 주문 성공 후 고객 PATCH 실패     | “주문은 수정됐지만 고객정보 저장에 실패했습니다.” 안내. 주문 성공 상태는 유지                                     |
| 고객 저장 재시도                 | 고객 PATCH만 재시도. 주문 PATCH를 다시 실행하지 않음                                                              |
| 주문 응답 유실                   | 주문 GET으로 변경값·버전을 확인. 저장 여부를 모른 채 고객 PATCH를 진행하거나 오래된 버전을 무조건 재전송하지 않음 |
| 고객 응답 유실                   | 고객 GET으로 저장 여부 확인. 204 본문 없음은 실패가 아님                                                          |

고객 PATCH는 현재 버전 비교가 없다. 재시도 전에 최신 고객정보를 확인하고, 그동안 다른 관리자가 수정했다면 덮어쓰기 여부를 다시 확인한다. 무제한 자동 재시도를 하지 않는다.

## 6. 권한과 기존 제한

- ACTIVE `OPERATOR`·`SUPERVISOR`·`SYSTEM_ADMIN`이 사용한다. 두 API 모두 같은 관리자 세션을 전달해 관리자 감사 기록을 남긴다.
- 관리자 브라우저 요청은 허용된 Origin에서 보내고 세션 쿠키를 포함한다. 다른 Origin으로 직접 요청한다면 프론트 HTTP 클라이언트의 credentials 설정도 확인한다.
- 주문 수정에는 AI용 `call_session_seq` 헤더가 필요하지 않다.
- 관리자는 전체 주문 상태에서 수정할 수 있으나, 활성 고객 조건·PIN 접근 검사·현재 버전 검사는 유지한다.
- 결제 승인 처리 중에는 주소 수정도 409 `REQUEST_IN_PROGRESS`로 거절된다.
- 버전 충돌은 409 `VERSION_CONFLICT`다. 최신 주문을 다시 읽고 변경 내용을 재확인한다.
- 주소 필드·타입 오류는 400이며 고객 PATCH의 전화번호 변경도 400이다.
- 주문 배송비를 바꾸지 않는 보내는 분 수정은 주문 금액·기존 결제 요청을 유지한다.
- 고객 원본 수정은 해당 고객을 조회하는 다른 화면의 현재 정보에도 반영된다. 다른 주문의 저장된 배송정보와 PIN을 일괄 변경하지 않는다.

## 7. 이번 검증

앱 코드·API 입력 계약·마이그레이션은 변경하지 않았다. 새 백엔드 빌드 후 격리 PostgreSQL과 실제 HTTP 요청으로 다음 **4개 시나리오 × 관리자 3개 역할 = 12개 시나리오**를 확인했다.

1. 주문 보내는 분 이름·전화번호·주소만 저장하면 고객 원본은 그대로 유지된다.
2. 고객 이름·주소를 추가 저장해도 고객 전화번호·원본 PIN·다른 주문·현재 주문 금액과 결제 요청은 유지된다.
3. 주문 저장 후 고객 검증이 실패해도 주문 수정은 유지되며, 고객 저장만 재시도해도 주문 버전은 다시 바뀌지 않는다.
4. 오래된 주문 버전과 고객 전화번호를 포함한 잘못된 PATCH가 거절되고 부분 저장되지 않는다.

12개 모두 통과했다. 이번 조합 검증은 결제 대기 주문을 대상으로 했으며, 프론트 노티·분기 화면 구현과 실제 서버 연동 검증은 프론트 작업에서 진행한다.
