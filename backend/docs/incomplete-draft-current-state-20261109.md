# 미완료 배송 초안 현재 현황 — 2026-11-09

아래는 정책 변경 전 운영의 읽기 전용 스냅샷이다. 이후 확정·구현한 [24시간·최신 확정 통화 만료 정책](incomplete-expiry-latest-call.md)이 업무상 유효기간 설명보다 우선한다. 아래 72건을 새 정책 적용 후의 유효 건수로 해석하지 않는다.

운영 backend `dva-backend:d61b900d3ee3-117`과 READ ONLY PostgreSQL 조회 기준이다. 쿼리는 5초 제한을 사용했고 개인정보 본문은 출력하지 않았다. 아래는 조회 당시 스냅샷이며 초안·고객·주문·AI 설정을 변경하지 않았다.

| INCOMPLETE | 72 | 이어가기 대상인 미완료 배송 단건 |
| RESUMED | 2 | 이미 새 초안으로 재개된 원본 기록 |
| CONVERTED | 3 | 실제 주문·배송상세로 전환된 기록 |

## 3. 통화 종료 후 미완료 확정

통화 초안은 수집 중 EDITING, 완성 시 READY다. **AI의 입력 완료 통보와 PBX 종료가 모두 있어야 최종 확정**한다. READY 여러 개는 기존대로 실제 주문 한 건으로 묶어 CONVERTED, 나머지 EDITING은 INCOMPLETE가 된다. READY가 없으면 실제 주문을 만들지 않고 NO_ORDER로 확정하며 미완료는 남을 수 있다.

현재 미삭제 초안이 남은 신규 방식 통화 10건은 모두 확정됐다. 실제 주문을 만든 통화 3건, NO_ORDER 통화 7건이며 확정되지 않은 대상은 0건이다. 즉, 조회 시점에는 EDITING/READY가 종료 후 확정 대기 상태로 남은 사례가 없었다. 초안 없는 통화까지 모두 검사한 수치로 확대하지 않는다.

완료 통보가 없으면 WAITING_AI, 종료가 없으면 WAITING_PBX이며 둘 다 없으면 COLLECTING이다. 둘 다 받은 뒤 확정 중이면 FINALIZING, 확정 오류가 있으면 FAILED다. 복구 워커는 완료 통보·종료가 모두 있고 미확정인 통화를 재시도한다. 완료 통보 자체를 임의 생성하지 않는다. 통화 분석의 10분 EXPIRED는 이 주문 확정 흐름과 별개다.

## 4. 이어가기의 정확한 동작

1. 삭제·5년 만료되지 않은 INCOMPLETE를 고른다.
2. 새 clientParcelId와 sourceDraftSeq로 새 초안을 만든다. 원본 고객이 있으면 그대로 유지하고, 없으면 활성 고객을 지정한다.
3. 원본은 RESUMED가 되고 새 초안이 EDITING/READY로 이어받는다. 원본 주소·물품 사본과 retentionStartedAt을 유지한다. 원본 번호는 이력으로 남는다.
4. 새 초안을 READY로 보완한 뒤 관리자가 단독 접수하거나 다음 AI 통화에서 확정한다. 접수 성공 경로에서는 CONVERTED, 다시 미완성으로 확정하면 새 초안이 INCOMPLETE다.
5. 이전에 이미 생성된 주문에 배송을 자동 추가하지 않는다. 같은 원본의 중복 재개·접수는 잠금·버전·멱등성으로 제어한다.

고객 50번의 실제 예시는 `56(RESUMED) → 69(RESUMED) → 72(INCOMPLETE)`다. 같은 체인의 현재 미완료는 72 한 건이지만, 별도 건인 55·71도 INCOMPLETE로 남아 현재 총 3건이다. 같은 체인의 보관 시작은 11월 6일로 유지됐다. 재개 초안 createdAt은 새 생성 시각이므로 보관 시작 시각과 다를 수 있다.

## 5. 만료와 AI 자동 이어가기

INCOMPLETE는 retentionStartedAt부터 5년까지 조회·재개할 수 있다. 이후 목록에서 제외하고 기존 retention worker가 물리 삭제한다. 재개해도 보관 기한을 다시 시작하지 않는다. 개인카드 결제 대기의 24시간 취소와 통화 분석의 10분 만료를 적용하지 않는다.

운영 AI의 `/app/config/server.toml`은 `backend.parcel_draft_intake=true`, **`call.resume_window_sec=0.0`**이다. 현재 자동 이어가기 제안은 비활성이다. 최신 코드의 INCOMPLETE `limit=1` 조회는 활성화했을 때의 후보 선택 기준이며 backend가 한 건만 보관한다는 뜻이 아니다.

활성화할 경우에도 접수 의도, 새 배송 정보를 말하기 전, 아직 제안하지 않은 통화, 후보 createdAt부터 설정 기한 이내라는 조건을 사용한다. AI 제안 기한과 backend의 5년 보관은 다른 기준이다. 설정·AI 코드는 변경하지 않았다.

## 6. 운영과 작업 브랜치의 차이

운영 DB에는 아직 reserved_order_seq 열이 없다. 따라서 신규 초안 7건은 예약 주문번호가 없는 기존 동작이다. 운영 관리자 전체 목록도 이번 작업 브랜치의 주문+초안 통합 목록을 아직 적용하지 않았다.

`feature/complaint-draft-follow-up`에는 058 예약번호와 통합 목록 구현·검증·커밋이 있다. 적용 후에는 기존 초안에도 새 예약번호가 생기고, 관리자 전체·미완료 탭에서 draftSeq로 구분해 같은 목록을 사용한다. 원본 legacyOrderSeq는 보존하며 원본 주문을 다시 접수하지 않는다. 배포 시 057·058과 프론트 분기가 필요하다.

이번 수기 PIN 수정은 관리자 초안이 최종 접수될 때의 수령인 자동 등록도 포함한다. 미완료 보관 건수·만료·확정·재개·자동 이어가기 설정 자체는 변경하지 않았다.
