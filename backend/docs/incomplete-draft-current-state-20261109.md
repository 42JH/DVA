# 미완료 배송 초안 처리 기준

[24시간·최신 확정 통화 만료 정책](incomplete-expiry-latest-call.md)을 우선 적용한다.

## 1. 보관 기준

서로 다른 미완료 초안은 각각 보관한다. 초안 한 건은 배송 한 개이며 활성 고객과 연결되기 전에는 `customerSeq`가 비어 있을 수 있다.

## 2. 입력값 검증

READY로 보완할 때 필수값과 전화번호·우편번호·가액·수량·배송비를 검증한다. 접수할 때 결제 자격을 다시 확인한다.

## 3. 통화 종료 후 미완료 확정

통화 초안은 수집 중 EDITING, 완성 시 READY다. **AI의 입력 완료 통보와 PBX 종료가 모두 있어야 최종 확정**한다. READY 여러 개는 기존대로 실제 주문 한 건으로 묶어 CONVERTED, 나머지 EDITING은 INCOMPLETE가 된다. READY가 없으면 실제 주문을 만들지 않고 NO_ORDER로 확정하며 미완료는 남을 수 있다.

완료 통보가 없으면 WAITING_AI, 종료가 없으면 WAITING_PBX이며 둘 다 없으면 COLLECTING이다. 둘 다 받은 뒤 확정 중이면 FINALIZING, 확정 오류가 있으면 FAILED다. 복구 워커는 완료 통보·종료가 모두 있고 미확정인 통화를 재시도한다. 완료 통보 자체를 임의 생성하지 않는다. 통화 분석의 10분 EXPIRED는 이 주문 확정 흐름과 별개다.

## 4. 이어가기의 정확한 동작

1. 삭제·5년 만료되지 않은 INCOMPLETE를 고른다.
2. 새 clientParcelId와 sourceDraftSeq로 새 초안을 만든다. 원본 고객이 있으면 그대로 유지하고, 없으면 활성 고객을 지정한다.
3. 원본은 RESUMED가 되고 새 초안이 EDITING/READY로 이어받는다. 원본 주소·물품 사본과 retentionStartedAt을 유지한다. 원본 번호는 이력으로 남는다.
4. 새 초안을 READY로 보완한 뒤 관리자가 단독 접수하거나 다음 AI 통화에서 확정한다. 접수 성공 경로에서는 CONVERTED, 다시 미완성으로 확정하면 새 초안이 INCOMPLETE다.
5. 이전에 이미 생성된 주문에 배송을 자동 추가하지 않는다. 같은 원본의 중복 재개·접수는 잠금·버전·멱등성으로 제어한다.

## 5. 만료와 AI 자동 이어가기

INCOMPLETE의 물리적 보관 기한은 retentionStartedAt부터 5년이다. 조회·재개 자격에는 [별도 만료 정책](incomplete-expiry-latest-call.md)을 적용한다. 재개해도 보관 기한은 기존 보관 시작 시각을 기준으로 계산한다.

AI 자동 이어가기 사용 여부와 제안 기한은 AI 설정으로 결정한다. 활성화하면 최근 미완료 한 건을 후보로 조회한다.

활성화할 경우에도 접수 의도, 새 배송 정보를 말하기 전, 아직 제안하지 않은 통화, 후보 createdAt부터 설정 기한 이내라는 조건을 사용한다. AI 제안 기한과 backend의 5년 보관은 다른 기준이다. 설정·AI 코드는 변경하지 않았다.

## 6. 예약번호와 통합 목록

058을 적용하면 기존 초안에도 예약번호가 생긴다. 관리자 전체·미완료 탭은 `draftSeq`와 예약번호를 반환한다. `legacyOrderSeq`는 이관 원본을 추적하는 데 사용한다. 관리자 초안의 최종 접수에서는 수령인도 개인 PIN에 등록한다.
