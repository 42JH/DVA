# AI 통화 후속 연동 변경

2026-11-04 사용자 확정 사항. 기준 `develop-backend` `e5dc008`, 작업 브랜치 `feature/ai-call-updates`.

## 계획과 범위

1. 수거 요청 시각 보존·결제 시 조정, 결제 안내·Swagger·AI 명세 반영 → 결제/청구/재접수 검증 → 커밋.
2. 기존 통화 분석에 콜백 요청 여부 추가, 통화 목록·상세 제공 → 입력·멱등·삭제/보관·migration 검증 → 커밋.
3. AI 고객 기본 주소 수정은 진행 중 본인 통화로 제한, 개인 PIN 추가·수정은 종료 후에도 허용 → 소유권·관리자·감사/롤백·동시 처리 검증 → 커밋.
4. 전체 백엔드·PostgreSQL·실제 nginx/HTTPS 회귀 검증, AI·프론트 전달 사항 정리.

수정 범위는 `backend/`와 필요한 `infra/` 검증이다. AI·프론트 코드, 실제 PBX 전환, 운영 DB 적용·배포, PR 생성은 포함하지 않는다. 기존 관리자 세션·Origin·고객 소유권·soft delete·보관 기간 검사를 유지한다. 새로운 개인정보나 콜백 처리 완료 업무는 추가하지 않는다.

## 확정한 수거 시각 정책

- 시간대는 `Asia/Seoul`, 백엔드가 계산하는 수거 시각의 범위는 09:00~17:00이다.
- AI가 보낸 `pickupRequestedAt`은 시간대가 포함된 ISO 8601 형식만 확인하며 별도 영업시간·예약 가능 일수 제한을 추가하지 않는다.
- 결제 대기 중에도 전달받은 시각을 보존한다.
- 실제 결제 완료 시각이 요청 시각 이전 또는 같으면 요청 시각을 유지한다.
- 요청 시각 이후에 결제되거나 요청 시각이 없으면 결제 완료 + 1시간으로 정한다. 계산값이 결제일 09시 이전이면 당일 09시, 결제일 17시를 넘으면 다음날 09시로 정한다. 정확히 17시는 허용한다.
- 개인 카드·월결제·부서 그룹결제에 같은 규칙을 적용한다. 재접수·동일 결제 재전송은 확정 시각을 다시 계산하지 않는다.
- 주말·공휴일 보정은 추가하지 않는다.

## 콜백과 주소 정책

- 콜백은 기존 분석의 `hasCallbackRequest` 선택 boolean으로 요청 여부만 저장·조회한다. 콜백 번호·이름은 기존 통화·고객 정보로 표시하며 별도 연락처, 사유, 완료 상태는 추가하지 않는다. 과거·미수집 값은 null로 구분한다.
- 고객 기본 주소는 고객 동의를 받은 AI가 진행 중인 본인 통화에서 기존 고객 PATCH로 수정한다. 관리자 수정은 기존 계약을 유지한다.
- 개인 PIN은 같은 통화 고객에 한해 종료 후에도 추가·수정한다. PIN 목록 조회는 진행 중 통화 기준을 유지한다. 삭제·보관 만료 통화와 다른 고객 접근은 허용하지 않는다.
- 주문 저장은 고객 기본 주소나 PIN을 자동 갱신하지 않는다. 주소 저장 실패 때문에 이미 저장된 주문을 실패로 되돌리지 않는다.

## 콜백 AI·프론트 계약

기존 `POST /api/ai/calls/{callSessionSeq}/analysis`의 완성된 최종 분석 본문에 `hasCallbackRequest: true | false | null`을 추가한다. 기존 `Authorization: Bearer <AI_INSIGHTS_TOKEN>`을 사용하고 별도 콜백 경로·Idempotency-Key는 추가하지 않는다. 최초·동일 재전송은 204, 이미 확정한 값 변경은 409 `EVENT_PAYLOAD_CONFLICT`다. 종료된 통화는 수신 가능하지만 삭제·보관 만료 통화는 404다. `hasHandoffRequest`와 독립이며 연결 요구로 콜백을 추정하지 않는다.

- DB: `call_analyses.has_callback_request boolean NULL`, 기본값 없음. `048-call-callback-request.sql` 하나를 새 앱 전에 적용한다. 기존 행·해시·분석 시각과 FK는 변경하지 않는다. 생략/null을 해시에서 제외해 기존 AI 재전송을 유지한다.
- 프론트: 목록 `data[].analysis.hasCallbackRequest`, 상세 `data.analysis.hasCallbackRequest`. true는 요청, false는 요청 없음, null은 미수집이다. `analysis=null`은 분석 미수신이다. 연락처는 기존 통화의 발신번호, 이름은 기존 고객 이름(없으면 null)을 사용한다.
- 콜백은 통화 분석과 같은 업무 이력이다. 통화 soft delete 시 조회에서 숨기고, 최초 수신부터 5년인 기존 통화 폐기 흐름에서 같이 삭제한다. 로그 7일 TTL 대상이 아니다.
- 콜백 전환: 백업 → 048 적용 → 새 백엔드 배포 → AI 콜백 필드 전송·프론트 표시 연결 순서다. 구버전 백엔드는 새 입력 필드를 거절하므로 콜백 필드 전송을 먼저 시작하지 않는다. 기본 주소의 통화 헤더 전송은 아래처럼 새 백엔드보다 먼저 반영한다. 실제 운영 적용은 이번 작업에 포함하지 않는다.

## 기본 주소·PIN AI 계약

| 작업                     | AI 호출                                                 | 통화 조건                                   | 성공 |
| ------------------------ | ------------------------------------------------------- | ------------------------------------------- | ---- |
| 고객 기본 주소 수정/삭제 | `PATCH /api/customers/{id}`, `address`                  | 진행 중 본인 통화의 `call_session_seq` 필수 | 204  |
| 개인 PIN 추가            | `POST /api/customers/{id}/pins`, 완성 `addressData`     | 종료 후에도 해당 통화 고객만 허용           | 201  |
| 개인 PIN 수정            | `PATCH /api/pins/{id}`, `label` 또는 완성 `addressData` | 종료 후에도 해당 통화 고객만 허용           | 200  |
| 개인 PIN 목록            | `GET /api/customers/{id}/pins`                          | 기존 진행 중 본인 통화 조건 유지            | 200  |

- 고객 주소는 객체 전체 교체, null은 삭제, 생략은 유지다. AI 이름 단독 수정·고객 등록/상세와 관리자 수정 계약은 유지한다. 고객 동의는 AI가 확인하며 새로운 동의 필드·이력 테이블은 추가하지 않는다.
- 기본 주소 수정의 통화 종료 기준은 기존 통화 권한과 같은 `call_sessions.ended_at`(PBX 종료 반영)이다. 통화를 먼저 잠그고 고객을 잠가 종료·삭제와 경합 시 재검증하며 성공 감사까지 같은 트랜잭션으로 처리한다.
- PIN 추가/수정도 발신번호·활성 고객·통화의 기존 고객 연결을 확인한다. 고객 연결이 이미 저장된 통화는 그 번호까지 일치해야 하므로 삭제된 고객의 전화번호를 다른 고객이 재사용해도 이전 통화로 접근할 수 없다. 기존 고객 미연결 통화의 발신번호 검사와 nullable 호환은 유지한다.
- 삭제·보관 만료 통화/고객/PIN은 계속 거절한다. 잘못된 관리자 쿠키를 AI로 전환하지 않는다. MVP 서비스 인증 미적용은 기존 제한이며 통화 번호 자체는 인증 토큰이 아니다.
- 배포 전에 AI 기본 주소 PATCH에 통화 헤더를 먼저 추가한다. 구버전 BE는 헤더를 무시하므로 이 순서가 가능하다. 새 BE 반영 후에는 헤더 없는 기본 주소 변경이 400이며, 통화 종료 후에는 409이므로 기본 주소 저장은 통화 중 완료한다. PIN 후처리만 종료 뒤 실행한다.
- PIN 기존 중복·주소 전체 교체·버전 규칙을 유지한다. 주소/PIN 저장은 주문과 별도 트랜잭션이며 실패해도 주문 성공을 되돌리거나 주문 결과를 재전송하지 않는다.

## 진행 기록

- 1단계 구현: 기존 `orders.pickup_requested_at`을 결제 대기 중 보존하고 공통 결제 SQL에서 확정한다. 새 테이블·컬럼·migration은 없다. 결제 전 안내/페이지는 요청 시각과 지연 결제 규칙을 보여 주고, 승인/재조회 후에는 확정된 시각을 표시한다. 완료 안내는 기존 절대 시각 표시를 유지한다.
- 1단계 검증: 새 DB 경계 테스트가 기존 코드의 요청 시각 삭제·영업시간 미조정에서 실제 실패함을 먼저 확인했다. 수정 후 lint·포맷·컴파일, 단위 129개, 결제 시뮬레이터 21개, 실제 PostgreSQL 주문 99개·청구 11개·결제 36개·접수 복구 17개가 모두 통과했다. 통합 합계 163개, 실패·skip·cancelled·todo 0.
- 1단계 회귀 보완: 기존 주문 잠금 테스트가 수거 시각 덮어쓰기에 따른 버전 증가를 전제로 했다. 실제 `touch_order_header` 트리거를 확인하고, 미래 시각 보존 시 수거 시각과 버전이 모두 유지되는지 검사하도록 변경했다. HTTP 중 잠금 해제와 동시 재호출 검증은 유지했다.
- 2단계 구현: `hasCallbackRequest` 입력·정규화·저장·통화 목록/상세·Swagger를 기존 분석 계약에 추가했다. 생략/null은 기존 해시를 유지하고, true/false 변경은 기존 최종 분석 충돌 규칙을 적용한다. AI·프론트 전달 문서와 048 배포 검증을 함께 갱신했다.
- 2단계 검증: 기존 DTO에서 새 정상 boolean 입력이 실패함을 먼저 확인했다. 변경 후 lint·포맷·컴파일·단위 129개·결제 시뮬레이터 21개, 실제 PostgreSQL 분석 14개·분석 조회 15개·통화 24개·배포 스키마 16개·soft delete 12개·보관 8개(통합 합계 89개)가 모두 통과했다. 새 필드의 true/false/null, 이전 해시 재전송, 048 업그레이드의 행/해시/시각 보존, 삭제 후 콜백 보존·숨김과 5년 폐기를 검증했다.
- 2단계 DB 검증: 기존 `infra/database/test-monolith.ps1`의 신규·이전 버전 업그레이드, 전체 048까지의 반복 적용, 체크섬 변조 거부, 최초/후속 실패 롤백, 백업 복원 검사가 모두 통과했다. 28 public 테이블·24 FK·10 트리거 수는 유지된다.
- 3단계 구현: AI의 기본 주소 수정/삭제에 진행 중 통화 헤더·발신번호·기존 고객 연결 검사를 추가했다. PIN은 추가·수정만 종료 후 허용하고 목록의 종료 차단을 유지한다. 관리자 세션/Origin과 기본 이름 단독 수정은 기존 계약을 유지한다. 추가 DB 변경은 없다.
- 3단계 검증: 기존 코드에서 통화 헤더 누락·다른 고객 연결 주소 수정이 성공하는 것을 새 HTTP 테스트로 먼저 확인했다. 수정 후 lint·포맷·컴파일·단위 129개·결제 시뮬레이터 21개, 실제 PostgreSQL 고객 16개·PIN 18개·주문 99개·고객 초기 조회 13개·기업 주소 검색 15개·soft delete 12개(통합 합계 173개)가 모두 통과했다. 종료 경합 시 재검증, 삭제/만료 차단, 전화번호 재사용 시 고객 연결 보호, 종료 후 PIN의 중복·감사 실패 롤백을 확인했다.
- 전체 1차 검증에서 과거 025·042 migration 테스트가 최신 콜백 분석까지 과거 규격으로 다시 해시하는 문제를 발견했다. 운영 migration 파일은 수정하지 않았다. 해당 테스트의 트랜잭션에서 기존 행을 임시 보관하고 과거 fixture에만 migration을 실행한 뒤 기존 행을 복원하도록 격리했다. 기존 행 전체·해시·시각 보존 및 과거 결과의 API 재전송/충돌 검사는 모두 유지했다.
- 격리 보완 검증: 콜백 분석을 먼저 저장한 뒤 분석 14개 → 이벤트/과거 migration 20개 → 분석 조회 15개(통합 합계 49개)를 연속 실행해 모두 통과했다. lint·포맷·컴파일·단위 129개·결제 시뮬레이터 21개도 통과했다.
- 전체 회귀 검증은 보완한 코드로 다시 진행한다. 운영 DB·실제 토스/디버·브라우저 수동 결제·배포는 실행하지 않았다.
