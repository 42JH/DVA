# S04 관리자 인증 요청 제한

단일 모놀리식 백엔드 프로세스의 초기 운영 기준이다. 기존 관리자 세션·Origin 검사·역할·가입 승인·비밀번호 초기화 방식·scrypt 강도는 유지한다. AI 고객·주문·통화·PBX API에는 이 요청량 제한을 적용하지 않는다.

## 적용값

| 항목 | 값 | 범위 |
| --- | --- | --- |
| 로그인 IP | Nginx 평균 30회/분, `burst=5 nodelay` | 성공·실패·입력 오류를 포함한 POST. 처음에는 기본 요청 1개와 초과 5개를 즉시 허용한다. |
| 가입 IP | 최근 10분 5회, 최근 24시간 20회 | 두 이동 시간창 모두 충족해야 한다. DTO 오류·중복 가입·처리 여유 부족도 횟수에 포함한다. 이미 차단한 요청은 시간을 연장하지 않는다. |
| 로그인 ID | 최근 15분 비밀번호 오류 5회 → 5분 제한 | 미등록 ID도 동일. ID 대소문자는 기존대로 구분한다. 차단 중 요청·뒤늦게 끝난 실패로 제한을 연장하지 않는다. |
| 비밀번호 처리 | 프로세스 전체 2개, 대기열 0개 | 로그인·가입·본인 변경·관리자 초기화가 슬롯을 공유한다. DB 트랜잭션 전에 확보하고 성공·실패 모두 반환한다. |
| 가입 이름 | 최대 유니코드 코드 포인트 50자 | 기존 공백만 있는 이름 거절·입력 공백 보존을 유지한다. |
| 새 비밀번호 | 최대 유니코드 코드 포인트 256자 | 가입·변경·변경 확인에 적용한다. 기존 로그인과 현재 비밀번호 확인의 길이 정책은 유지한다. 잘라 저장하거나 공백을 제거하지 않는다. |
| 승인 대기 검토 | 가입 30일 경과 | 아래 수동 검토 절차를 따른다. 자동 상태 변경·자동 삭제는 추가하지 않는다. |

로그인 제한은 매분 초기화하는 고정 횟수가 아니라 Nginx의 평균 요청률과 순간 초과 허용량이다. 계정 제한은 다섯 번째 실패까지 401이고 다음 시도부터 429다. 5분이 지나면 새로운 실패 횟수를 계산하며, 정상 로그인 커밋이 성공하면 해당 ID의 실패 기록을 지운다. 서버 오류와 올바른 비밀번호의 PENDING·INACTIVE 응답은 비밀번호 실패로 계산하지 않는다.

## 오류와 프론트 전달

제한 응답은 기존 `{error:{code,message,details},meta:{requestId}}`, HTTP 429, `error.code=RATE_LIMITED`, `Cache-Control: no-store`를 사용한다. `X-Request-Id`와 `meta.requestId`가 일치한다. `Retry-After`는 초 단위 정수다.

- 로그인 IP 초과: 2초. 계속 요청이 몰리면 재시도도 다시 제한될 수 있다.
- 가입 IP·로그인 ID: 허용 가능 시각까지 남은 초. 두 가입 한도가 겹치면 더 긴 대기 시간을 반환한다.
- 처리 슬롯 부족: 1초. 비밀번호 검증·가입 저장·세션 교체를 시작하지 않는다.
- 카운터 저장 공간 부족: 60초. 살아 있는 카운터를 지워 제한을 우회시키지 않는다.

프론트는 429를 잘못된 비밀번호와 구분하고 `Retry-After` 동안 재제출을 제어한다. 자동 반복 요청은 하지 않는다. 가입 이름 50자·새 비밀번호 256자를 안내하고, 로그인과 현재 비밀번호 입력에는 새 256자 상한을 강제하지 않는다. 문자열 길이는 자바스크립트의 `[...value].length` 기준으로 맞춘다. 성공 응답과 쿠키 형식은 그대로다. 현재 체크아웃에는 실제 프론트 구현이 없어 화면 반영은 프론트 담당 작업이다.

프록시가 거절한 로그인은 `X-Dva-Auth-Limited: 1`로 본문 없이 기존 로그인 경로에 전달한다. 앱의 제한 guard가 DTO·인증 전에 429를 반환하므로 HTML 오류와 별도 CORS 설정이 필요 없다. 이 헤더는 클라이언트가 보낼 필요가 없으며, 임의로 보내도 자기 요청이 거절될 뿐 인증·제한을 우회하지 못한다.

429는 HTTP 요청 로그와 상태 코드 지표에 남긴다. 이 제한 예외마다 DB 감사 행을 추가하면 DB 풀 보호가 무효화되므로 DB 실패 감사에서는 제외한다. 기존 401·403 및 다른 오류의 감사 동작은 유지한다.

## IP 신뢰와 배포

`AUTH_PROXY_HOPS`는 인증 제한에서만 사용하는 전달 IP 선택 값이며 Express 전체의 프록시 신뢰 설정은 변경하지 않는다.

| 실행 경로 | 값 | 조건 |
| --- | --- | --- |
| Node 직접 실행 | `0` (기본) | 소켓 IP만 사용하고 전달 헤더는 무시한다. |
| 개발 Compose → 컨테이너 Nginx → backend | `1` | Compose가 주입한다. 개발 Nginx가 외부 X-Forwarded-For를 소켓 IP로 덮어쓴다. |
| 호스트 HTTPS Nginx → 컨테이너 Nginx → backend | `2` | 운영 Compose가 주입한다. 호스트가 외부 전달 헤더를 실제 IP로 덮어쓰고 내부 Nginx가 한 홉을 추가한다. |

선택한 우측 전달 체인이 부족하거나 IP 형식이 잘못되면 소켓 IP로 묶어 처리한다. backend 포트는 외부에 공개하지 않고 운영 컨테이너 Nginx는 기존 `127.0.0.1:8082` 바인딩을 유지한다. 짧은 우회 경로를 외부에 열거나 프록시 수를 바꾸면 이 신뢰 조건이 깨지므로 함께 재설계해야 한다. 단독 Node 실행에는 Nginx 로그인 IP 제한이 없으며 계정·처리 슬롯 제한은 적용된다.

배포 순서:

1. 새 backend와 해당 Compose를 적용한다. 새 비밀 환경변수나 DB migration은 필요 없다.
2. 호스트 `infra/https/https.conf`를 운영 Nginx 설정에 반영하고 `nginx -t` 성공 후 reload한다. 일반 앱 배포가 호스트 설정을 자동 교체하지 않는다.
3. 격리한 테스트 IP에서 429·Retry-After·JSON·CORS와 정상 로그인 회복을 확인한다. 공유 사무실 IP의 정상 사용자는 같은 IP 한도를 소비한다.

카운터는 메모리에 최대 10,000개이고 각 가입 IP는 최대 20개·각 로그인 ID는 최대 5개의 실패 시각을 보유한다. 만료 항목을 요청 시 정리한다. 재시작하면 기록이 초기화되며 복제본·Node worker를 추가하기 전에 공유 저장소로 바꿔야 한다. 현재 변경은 Redis·새 의존성·업무 테이블을 추가하지 않는다. 서버 처리량을 실측한 결과가 아니므로 인증 지연·429 빈도·CPU·메모리·DB 대기를 보고 운영값을 조정한다.

## 30일 지난 승인 대기 계정 검토

SYSTEM_ADMIN이 기존 관리자 목록에서 `status=PENDING`과 `createdAt`을 확인한다. 필요한 경우 승인된 운영 DB의 읽기 전용 세션에서 아래 목록을 조회한다. 이 문서 작성·자동 검증에서 운영 DB를 조회하거나 계정을 삭제하지 않는다.

```sql
SELECT admin_user_seq, login_id, name, created_at
FROM admin_users
WHERE status = 'PENDING'
  AND deleted_at IS NULL
  AND created_at <= statement_timestamp() - interval '30 days'
ORDER BY created_at, admin_user_seq;
```

운영자가 신청 유효성을 확인한 뒤 기존 승인 또는 관리자 soft delete API로 처리한다. 삭제된 계정은 기존 5년 보관 계약을 따른다. 30일을 즉시 물리 삭제 기간으로 사용하지 않는다.
