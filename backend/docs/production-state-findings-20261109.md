# 운영 상태 확인 — 2026-11-09

아래는 최초 조사 시점 기록이다. 후속 사용자 확정의 분석 만료 10분 구현, 이관 원본 조건, 미완료의 다건·5년 보관·운영 AI 자동 이어가기 비활성화, 미답변 고객명 누락 3건은 [추가 보고](analysis-expiry-and-draft-findings-20261109.md)를 따른다. PIN은 AI에서 수정하기로 했으며 이 작업에서는 변경하지 않는다.

운영 PostgreSQL은 READ ONLY 트랜잭션과 5초 statement timeout으로 조회했다. 주소·전화번호·발화 본문은 출력하지 않았다. 아래 수치는 조회 시점의 스냅샷이며 실시간 데이터는 이후 달라질 수 있다. 상태·PIN·주문을 직접 수정하지 않았다.

확인 당시 운영 backend 이미지: `dva-backend:319de6fb0464-116`. 본 작업 브랜치의 057·058과 통합 목록은 아직 운영 배포하지 않았다.

## 번호가 건너뛰는 이유

- orders와 call_sessions의 sequence increment는 모두 1, cache도 1이다. 잘못된 증가 간격 설정은 아니다.
- 통화 등록의 `CallSessionRepository.ensureCall`은 INSERT ... ON CONFLICT(provider_call_id) DO NOTHING 뒤 기존 행을 조회한다. 중복 수신에서도 기본 identity 값이 배정될 수 있다. 트랜잭션 롤백도 PostgreSQL sequence를 되돌리지 않는다.
- 조회 시 전체 call_sessions는 171행·최대 번호 403, orders는 99행·최대 번호 141이며 두 테이블의 soft delete 행은 0개였다. 행 번호와 수신/생성 시도 번호는 같지 않다. 각 빈 번호의 과거 발생 원인을 모두 개별 추적한 것은 아니다.
- 주문 136·137·139는 실제로 존재하는 COLLECTING 원본이고 각각 이관 초안이 1개 있다. 기존 관리자 전체 목록은 이 원본 중복을 제외해 번호가 더 건너뛴 것처럼 보인다.
- 화면 정렬은 업무 시각·생성 시각 기준이며 PK의 연속성을 보장하지 않는다. 새 예약번호도 삭제·취소·여러 초안 묶음 때문에 미사용 번호가 생기는 사용자 확정 방식이다. 기존 PK를 재정렬하지 않는다.

- 최신 실제 주문 140·141은 notPaid다. 모든 주문을 CANCELLED로 일괄 변환하는 조회 코드는 없었다. 프론트의 상태 매핑은 notPaid를 결제 대기로 매핑하며, 취소된 배송상세는 해당 줄만 CANCELLED로 표시한다.

## 미완료 이어가기

원본은 삭제·만료되지 않은 INCOMPLETE여야 한다. 관리자와 새로운 AI 통화는 새 clientParcelId·sourceDraftSeq로 새 초안을 만든다. 원본은 RESUMED로 바뀌며 같은 원본의 동시 재개는 잠금으로 직렬화된다. 같은 생성 UUID 재전송은 기존 새 초안을 반환한다.

원본 고객이 있으면 그대로 유지하고 없으면 활성 고객을 지정한다. 주소·물품 사본과 보관 시작 시각을 복사하며, 이어가기로 5년 보관 기한을 연장하지 않는다. 필수값을 채워 READY로 저장한 뒤 관리자 초안 submit으로 별도 ADMIN 주문을 만든다. 원본 통화의 이미 확정된 주문에 상세를 덧붙이지 않는다.

기존 운영 버전은 이 최종 접수 시 새 orderSeq를 배정한다. 작업 브랜치는 source의 reservedOrderSeq를 새 초안으로 이어 받아 같은 번호로 접수한다. 진행 중인 통화의 READY/EDITING을 관리자가 직접 이어가는 것은 허용하지 않는다.

## 개인 PIN의 ‘보내는 곳’ — 고객 50번

- 화면의 두 항목은 실제 personal_pins 행이다. 프론트가 기본 주소를 합성한 것이 아니다.
- PIN 30: label=`보내는 곳`, 활성, AI가 한국시간 2026-11-06 11:55:32에 생성. 고객 기본 주소와 도로명·상세주소가 같고 실제 주문의 출발지 주소와 일치한다.
- PIN 34: 활성, AI가 한국시간 2026-11-09 10:21:26에 생성. 기본 주소와 다른 위치이며 실제 주문의 도착지 주소와 일치한다. 개인정보 이름·번호·주소는 이 기록에 복제하지 않는다.
- 같은 ‘보내는 곳’ 라벨의 활성 PIN은 확인 당시 10개 고객에 10개였다.

고객 기본 출발지는 `customers.address_data` 한 객체다. 개인 주소록은 별도 `personal_pins`의 여러 행이다. backend 주문 저장 자체가 고객 기본 주소나 PIN을 자동 갱신하지는 않는다. AI의 일반 저장 정책(`ai/app/domain/address_book.py`)은 택배를 담을 때 변경된 발송 주소를 고객 기본 주소에 덮어쓰고, 새 수령 주소는 개인 PIN으로 추가한다.

그런데 최신 develop-ai `6e4dd14c`의 `ai/app/calls/results.py` register 경로는 신규 고객을 주소와 함께 등록한 후 다시 `create_pin(..., role="sender", label="보내는 곳")`을 호출한다. 이 별도 경로가 출발지를 개인 PIN에 한 번 더 넣는다. 해당 AI 테스트도 보내는 곳 PIN 생성을 기대하고 있어 정책 변경 시 함께 수정해야 한다.

요구한 ‘출발지는 최신 개인 주소 하나’와 맞추려면 이 신규 등록의 sender PIN 생성 호출을 제거하고 기본 주소 저장을 유지해야 한다. 수령지 PIN은 별개다. 기존 10행의 삭제·교정과 AI 코드는 아직 변경하지 않았다. backend PIN API는 주소의 출발/도착 용도를 별도 필드로 저장하지 않으므로 라벨 문자열만 보고 자동 삭제하지 않았다.

추가로 AI 출발지 후보는 기본 주소가 없으면 과거 접수 출발지를 대체 후보로 사용한다(`ai/app/calls/service.py`). 기본 주소만 쓰는 정책을 엄격히 적용한다면 이 대체 경로도 AI에서 함께 확인해야 한다.
