선언 일치는 기능·DB 동등성의 완료 판정이 아니다. 기존 구현에도 이후 API/인증/DTO/SQL 변경이 있으므로 함께 대조한다.

## 실행 순서

각 작업 단위는 **대조 → 계획 → 작업 → 검증 → 커밋** 순서로 진행한다.

1. 최신 기준·계약 목록과 056~060 소유 DB 구조를 반영한다.
2. 기존 인증·고객/기업/PIN·페르소나·녹취/진행 통화 수의 변경을 작은 단위로 동기화한다.
3. 상담 이벤트/조회/분석 실패·통계·미답변/FAQ를 소유 서비스와 연결한다.
4. 주문 쓰기·초안·통화 완료를 고객/상담의 인증 이벤트와 연결한다.
5. 결제·접수·배송·청구 처리와 해당 워커/복구를 연결한다.
6. 소유자별 보관·삭제와 교차 소유자 이벤트를 연결하고 전체 차이를 다시 검증한다.

검증은 수정 범위의 기존 검사부터 실행한다. 공통 변경이나 최종 통합에서는 영향받는 기존 정상 경로도 확인한다.
시간·금액·상태·권한 기대값을 느슨하게 바꾸거나 검사를 생략해 동등성으로 판정하지 않는다.
마지막에는 같은 입력에 대한 응답·DB·감사·외부 호출과 워커/복구 결과를 원본과 대조하고 미검증 범위를 구분한다.

## 작업 기록

### 0. 기준 대조와 계획

- 대조: 새 기준 109개 API/59개 SQL/7개 자동 처리 진입점과 MSA 선언을 기존 inventory/coverage 함수로 수집했다.
- 계획: 위의 순서로 기존 계약 변경과 누락 기능을 나누고, 수정 경로를 msa/infra로 제한한다.
- 작업: 새 작업 브랜치와 이 보고서를 준비했다. 구현 변경은 아직 없다.
- 검증: 기존 소스에서 70개 일치/39개 누락을 확인했다. 원문 목록은 Git 제외 경로 `msa/liquibase/verification-logs/current-parity/contrast.json`에 보관했다.

### 1. 공용 주문·PIN·AI FAQ 인증

- 대조: 최신 원본은 Bearer 없는 AI 요청을 401로 거절하지만 기존 MSA의 세 메서드 표식은 인증 없이 통과했다. 수정 전 동일 요청으로 차이를 재현했다.
- 계획: 원본의 공용 AI/관리자 세션 분기와 주문 guard를 적용하되 기존 내부 이벤트 인증은 보존한다. 배포 환경과 기존 검사 호출자도 함께 맞춘다.
- 작업: 공용 표식을 Bearer/관리자 세션 정책에 연결하고 order 환경 검증 및 order/operations의 기존 `msa-ai-business` Secret 참조를 추가했다. 기존 정상 업무/장애 검사는 유효한 시험용 토큰으로 업무 경로까지 도달하도록 요청 fixture를 갱신했다.
- 검증: 원본 guard와 30개 조건(누락/오류/중복 Bearer, 잘못된 cookie, 관리자 Origin, 미설정 토큰 포함)을 대조해 일치했다. order/customer/operations 빌드, order 린트, 기존 HTTP E2E 6/9/9개가 통과했다. 테스트 파일 추가는 없다. DB를 포함한 전체 비교는 후속 통합 검증에서 수행한다.

### 2. 최신 기준과 056~060 소유 DB 구조

- 대조: 055 뒤의 분석 실패 시각, 불만 판정 재시도 필드/인덱스, 초안 예약번호, 최종 통화 인덱스, 페르소나 분리 필드가 MSA에 없었다. 현재 원본 helper에는 과거 fixture patch 내용이 이미 포함되어 있어 그대로 재적용할 수 없었다.
- 계획: 기존 SQL/changeset checksum을 보존하고 해당 소유자에만 새 migration을 추가한다. 055 이관 검사는 명시적으로 055까지만 적용하고 최신 스키마 전체 비교도 유지한다.
- 작업: consultation 009~011, order 005, operations 011에 원본 SQL을 그대로 추가했다. baseline은 `864ccde5`의 109개 API/59개 SQL/7개 자동 처리 진입점으로 갱신했다. 중복 fixture patch를 삭제해 원본 테스트 helper도 변경 없이 사용한다.
- 검증: 기존 계약 검사 10개, 원본 격리 회귀 5개, PostgreSQL 17.11/Liquibase 5.0.4 검증 206단계가 통과했다. 새 주문/배송 스키마·함수와 추가 컬럼/인덱스·페르소나 불변 이력을 원본과 비교했다. 기존 055 데이터 이관·재적용·후반 실패 원자성 및 pending/stale fingerprint 보호도 통과했다. 테스트 파일 집합은 최초와 동일한 69개다.

### 3. 고객 조회·일괄 삭제와 기업 구성원 검색

- 대조: 고객 목록의 부분 전화번호 검색·결제 수단, 다건 삭제, 구성원 목록의 q 검색 계약이 최신 원본과 달랐다.
- 계획: 고객 소유 DB의 원본 SQL·검증·잠금 순서를 적용하고, 감사 이벤트 수신자가 다건 삭제의 개별 감사도 처리하도록 연결한다.
- 작업: 고객 다건 삭제의 전체 검증·원자적 soft delete·소속/PIN 정리·감사를 추가했다. 목록 결제 수단과 검색, 구성원 q 검색 및 OpenAPI를 원본과 맞췄다. 기존 대조 파일의 입력만 확장했다.
- 검증: 실제 PostgreSQL과 원본/분리 서비스에서 조회·인증 111개 및 쓰기·인증 81개 요청의 HTTP·업무 DB·감사 결과가 일치했다. 감사 실패 시 고객/소속/PIN 롤백과 중복·누락 ID를 검증했다. 기존 대조 8개 및 customer 빌드·린트·HTTP E2E 9개가 통과했다. 테스트 파일은 69개로 동일하다. DDL 변경이 없어 전체 DB migration 검사는 반복하지 않았다.

### 4. 회사·개인 PIN 일괄 삭제

- 대조: 최신 원본의 DELETE /api/companies 및 /api/pins가 빠져 있었다. 기존 단건 기업·부서 삭제와 PIN의 고객 잠금 순서도 함께 확인했다.
- 계획: 원본 검증·정렬 잠금·전체 soft delete·개별 감사를 기존 소유 DB와 감사 이벤트에 연결한다.
- 작업: 두 다건 삭제와 DTO를 추가하고 감사 수신 동작을 연결했다. 기존 고객 대조의 입력만 확장했다.
- 검증: 조회 111개·쓰기 103개 요청의 응답·업무 DB·감사가 원본과 일치했다. 두 회사의 부서/소속 및 여러 고객의 PIN 삭제, 누락/중복 ID, 인증, 감사 실패 전체 롤백을 포함한다. customer/operations Docker 빌드의 린트·E2E·기존 단위 검사가 통과했다. DDL 변경 및 테스트 파일 추가는 없다.

### 5. 페르소나 분리 입력과 관리자 검색

- 대조: 원본의 페르소나 여섯 입력·조합 프롬프트·버전/초안 저장·AI 공개 필드 및 관리자 q 검색이 MSA와 달랐다. 페이지 조회의 상세 투영 인자도 필요했다.
- 계획: operations 소유 로직·DTO·OpenAPI를 현재 원본과 맞추고, 상담 버전 참조 프로토콜과 기존 알림/복구는 유지한다.
- 작업: 원본 필드와 프롬프트 조합, 이력/초안·AI 응답 필터, 관리자 NFC/부분 검색을 적용했다. 원본 인증 테스트의 다른 소유자 테이블 count는 이 DB에 해당 테이블이 없음을 검증하도록 복사본에서만 맞췄으며, 관리자/세션/감사 불변 비교는 유지했다. migration 개수 11개와 새 컬럼 존재도 엄격히 확인한다. 복구 검사에도 현재 업무 Bearer를 전달한다.
- 검증: operations 전체 기존 파이프라인이 통과했다. 원본 인증/관리자 54개·페르소나 49개·FAQ 35개 검사, 페르소나 HTTP 96개 요청·10개 선언·23개 스키마 및 DB/AI 전달, 실제 SIGKILL 뒤 페르소나/FAQ 알림 복구와 배포 준비 검사를 포함한다. DDL 변경과 테스트 파일 추가는 없다.
- 검사 시간: 동일한 관리자 HTTP 대조의 반복 비밀번호 해시 검증을 입력/해시가 바뀔 때만 수행해 145.2초에서 16.2초로 줄였다. 로그인·비밀번호 변경·모든 HTTP/DB 기대값은 유지하고, 알려지지 않은 비밀번호도 거절한다.

### 6. 통화 분석 실패 통보와 진행 통화 수

- 대조: 분석 최종 실패 API가 없고, 진행 통화 수에서 정상 AI 종료 분석을 제외하는 최신 원본 조건이 빠져 있었다. PIN의 인증 동작과 OpenAPI 보안 표기도 달랐다.
- 계획: 원본의 최초 실패 기록·잠금·중복/완료 우선 처리와 감사를 이식하고, 진행 통화 수의 SQL·설명을 맞춘다. 기존 검사에 입력을 추가하고 연결된 PIN 계약도 함께 확인한다.
- 작업: POST /api/ai/calls/:id/analysis/failure와 감사 수신 허용을 연결했다. 진행 통화 수는 PBX 종료 또는 정상 AI 종료 분석이 있으면 제외하며 실패 통보만으로 제외하지 않는다. PIN 보안 문서에 실제 Bearer 계약을 표시했다.
