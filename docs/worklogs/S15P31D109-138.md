## 1. 가변 배송비와 취소 감사

계획: 기존 상세 금액·취소 API를 재사용한다. 상세별 배송비와 주문 총액을 저장·검증하고 부분 취소 후 금액을 다시 계산한다. AI 취소 이력과 금액 변경 로그를 요청 주체에 맞춰 기록한다. 적용된 migration은 수정하지 않는다.

영향: 주문 생성·미완료 보완·수기 생성·접수 검증·조회·취소, 감사 조회, 배송 이력 제약, 관련 DTO·테스트.

검증 전 기준: 수정 전 lint·format·build 및 단위 테스트 67개 통과. 첫 sandbox 검사는 로컬 HTTP 연결 EACCES로 실패했으며 같은 검사를 정상 통신 환경에서 재실행해 통과했다.

구현: 016 migration, 상세 배송비와 총액 DTO·저장·조회·접수 검증, 미완료 보완 필드, 취소 후 합계 재계산, AI 배송 이력, 공개 가능한 금액 감사 메타데이터를 반영했다.

검증: lint·format·build와 단위 테스트 69개 통과. 임시 PostgreSQL 실제 API에서 12,000원 중 5,000원 부분 취소 → 7,000원, 원래 상세 가격 보존, AI 감사, 중복 요청의 무변경, 전체 취소 → 0원을 확인했다. 테스트 준비의 ACTIVE 누락 및 설정 로딩 순서는 fixture에서 수정했다.

DB 검증: 전체 monolith runner 통과. 스키마·이력·PBX 보존, 재실행·체크섬 변조 차단·실패 롤백·백업 복원·기존 upgrade 검증을 확인했다. 과거 스키마 비교에는 신규 total_amount 열을 명시적으로 제외하고 migration 이력 기대값을 15개로 갱신했다.

## 2. 부서와 결제 자격

계획: 기업별 부서, 구성원 부서 배정, 개인·기업 월결제 및 부서 그룹결제 설정을 추가한다. 소속과 기업이 일치하는지 DB·API에서 검증하고 고객 확인 응답에 자격을 제공한다. 기존 구성원 이관에는 실제 팀 배정이 필요하며 임의 기본 팀을 만들지 않는다.

구현: 017 migration, 부서 등록·조회·수정, 구성원 부서 필수값과 이동·CSV 배정, 개인·기업 월결제 boolean, 고객 확인의 부서·결제 자격을 반영했다. 월결제 자격은 관리자만 설정하고 주문의 고객 입력으로는 변경할 수 없다. 기존 구성원이 있으면 실제 배정표를 받아야 이관된다.

검증: lint·format·build와 단위 70개 통과. 실제 API에서 기본 false·명시적 true/false, 다른 기업 부서 거절, 동시 월/그룹 자격, AI의 자격 변경 거절을 확인했다. 전체 DB runner에서 기업·부서 FK와 실제 배정표를 통한 기존 데이터 보존·이관·롤백을 확인했다.

## 3. 주문 결제와 디버 접수

계획: 주문 status를 기준으로 결제 대기·완료·디버 접수중·완료·실패를 연결한다. 개인 카드만 결제를 기다리고 월결제·그룹결제는 자격 확인 후 즉시 완료한다. 부분 취소 시 결제 요청을 교체하고 오래된 요청의 결제 완료를 차단한다. 재접수는 같은 주문에서 재결제·중복 집계 없이 처리한다.

구현: 018 migration, notPaid/PAID/SUBMISSION_FAILED와 기존 SUBMITTING/ACCEPTED 연결, 카드 결제 요청 교체·승인 선점·내부 완료 함수, 관리자 재접수 endpoint를 추가했다. 결제사 성공 자가신고 HTTP API는 만들지 않았다. 접수 결과 이력은 SYSTEM으로 기록한다.

검증: lint·format·build 및 단위 70개, 실제 API 통합 6개 통과. 개인 카드 대기·수정 금지·부분 취소의 요청 교체와 동일 만료 시각·오래된 금액 거절·승인/취소 경합·결제 완료 중복 처리 방지·남은 상세만 디버 전송·기업/개인의 결제 자격·동일 주문 재접수를 확인했다. 실제 외부 결제와 발송은 미연동이다.

DB 전체 runner도 통과했다. 현재 public 테이블 21개, FK 19개이며 신규 요청의 유일성·기존 데이터 보존·전체 롤백과 백업 복원을 확인했다.

## 4. 자동 만료·월별 집계와 상담 조회

계획: 최초 24시간 뒤 미결제 주문을 취소하고 새 KST 월을 0원으로 시작한다. 이력은 보존하며 자동 작업은 SYSTEM으로 기록한다. 상담 조회에서 연결된 주문의 결제·접수 상태를 확인한다.

구현: 019 migration의 주문별 기업 결제 원장·월별 사용액, 분 경계 자동 작업, PAID 전송 복구, 미결제 만료·승인 중 보호, 기업 사용액 조회, 상담의 연결 주문 상태·금액 및 감사 주체 필터·담당자 표시를 반영했다. 신규 월과 지난 월을 별도 행으로 보존한다.

검증: 정적 검사·단위 70개 및 통합 8개 통과. KST 월 경계 직전/직후 0원 시작·이전 월 보존·중복 reset 방지, 원장 1회 집계, 감사 실패 시 결제·집계 전체 롤백, 만료 주문·녹취 보존·SYSTEM 감사, 승인 중 만료 보호와 해제 후 만료를 확인했다. 전체 monolith DB 검증도 통과했으며 public 테이블 23개·FK 22개다.

## 5. 회귀 검증과 인계

계획: 전체 정적 검사·단위·통합·DB 검증을 실행하고 변경된 계약을 갱신한다. AI 연동 규격은 `docs/api/ai-order-billing-integration.md`에 별도로 작성한다. AI 경로 변경이 없는지 확인하고 MR 제목·본문·검증 결과를 준비한 뒤 생성 전에 사용자에게 보고한다.

구현: 기존 API 회귀 fixture에 실제 테스트 부서를 배정하고 4열 CSV·명시적 배송비·결제 자격을 반영했다. 취소 회귀는 접수된 미결제 배송을 취소하던 이전 계약에서 notPaid 주문의 부분 취소로 전환했다. 접근 범위·동시 요청·감사 실패 롤백·1MiB 경계 검증은 유지했다. 서로 다른 운영자의 감사가 섞이는 통합 테스트는 작업자 ID로 범위를 지정했다.

회귀 과정에서 최초 AI CANCELLED 저장의 총액을 0원으로 정리하고 원래 상세 가격·AI 감사는 보존했다. 오래된 SUBMITTING을 기존 submit 재호출에서도 실패로 전환해 수동 재접수로 이어지도록 보완했다. 운영 지표·알림은 SUBMISSION_FAILED로 통일하고 백엔드 자동 작업의 구조화 로그를 허용했다. 부서·감사 금액 응답의 Swagger 스키마와 기존 API 문서를 갱신했다.

배포 검토: 017~019 이후에는 구버전 앱이 필수 부서·결제 상태를 지원하지 못한다. 기존 배포 스크립트에 최초 전환의 백엔드 중지 → 백업 → migration → 앱 시작을 추가하고, 전환 뒤 호환되지 않는 수동·자동 복귀를 차단했다. SQL 실패로 전환이 롤백되면 기존 앱 복귀를 허용한다. 모의 Docker/curl 검증으로 정상 전환·실패·호환 복귀·비호환 차단을 확인했다. 실제 배포는 실행하지 않았다.

최종 검증:

- `npm run check`: ESLint·Prettier·TypeScript·단위 70개 통과. sandbox의 로컬 HTTP EACCES는 정상 통신 환경에서 재실행해 통과했다.
- `npm run check:docker`: Linux에서 단위 70개 + API 통합 344개 + 운영 이미지·실제 Nginx 17개, 총 431개 통과. 모의 디버/S3와 임시 PostgreSQL만 사용했다. 이미지에서 테스트·개발 도구·환경 파일 제외, FAQ 자료 포함도 확인했다.
- `infra/database/test-monolith.ps1`: 전체 통과. public 테이블 23개·FK 22개·트리거 10개, migration 18개 파일, 데이터 보존·실제 부서 이관·체크섬·중복 실행·실패 롤백·백업 복원을 확인했다.
- `infra/deploy/test-deploy.sh`: 임시 Linux 컨테이너의 모의 Docker/curl 검증 통과. 008/010/019 최초 전환 순서와 비호환 복귀 차단을 포함한다.
- `node infra/observability/test.mjs`: 임시 Grafana·Prometheus·Loki·Nginx에서 전체 통과. 접수 실패 알림·1분 DB 장애·개인정보 제거·AI 관측 제외·재시작 로그 복구·복구 메시지/중복 알림 억제를 검증했다. 외부 알림은 발송하지 않았다.
- 변경 문서 JSON 예시 27개 파싱 통과. 별도 AI 규격의 COMPLETE 예시는 실제 DTO·배송비 합계 검증 통과. 변경 문서의 상대 링크 85개도 확인했다.

검증 중 기존 계약의 기본 요금·이전 상태·접수 후 취소·3열 CSV 및 신규 응답 필드 기대값을 갱신했다. 검사 삭제나 예외 삼키기로 실패를 숨기지 않았다. 최종 명령의 성공 출력을 확인한 뒤 마지막 커밋으로 진행한다.
