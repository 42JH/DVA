## 1. 성능 · 네트워크

### 1. JS · CSS가 압축 없이 나감 (11/12, !594)
- **문제:** Lighthouse(데스크톱, 첫 방문) 성능이 주문 88, FAQ 85. 1순위 지적이 "텍스트 압축"으로, 화면마다 400~600KB를 더 받고 있었다.
- **원인:** 서버 `nginx.conf`에 `gzip on`은 있지만 `gzip_types`가 주석이라 nginx 기본값대로 `text/html`만 압축했다. 무게 대부분인 `/assets/*.js` · `*.css`는 원본 크기.
- **사용한 기술:** nginx `gzip_types` · `gzip_vary` · `gzip_comp_level 5`. 서버 공용 파일이라 관리자 웹 location 두 곳에만 적용(백엔드 · AI · Jenkins 경로는 그대로).
- **조치:** 백업 → 수정 → `nginx -t` 통과 시에만 reload. 첫 시도는 셸 변수가 글자 그대로 들어가 `nginx -t`가 막았고, reload 전이라 운영 영향 없이 되돌린 뒤 다시 넣음.
- **결과:** 메인 JS 258,982B → 81,890B(-68%), CSS 52,095B → 10,907B(-79%). 8화면 성능 85~98 → 95~99, FCP 화면마다 0.25~0.5초 단축.
- **근거:** `docs/fe-gzip-results.md`, `docs/fe-gzip-results/*.json`

### 2. 홈 요청 12번, 주문 탭 건수 5번 (11/09, !421)
- **문제:** 홈이 카드마다 따로 요청해 약 12번, 주문 상태 탭 건수는 탭마다 1번씩 5번. 카드마다 조회 시점이 달라 숫자가 서로 안 맞을 수 있었다.
- **원인:** 화면이 먼저 만들어지고 집계 API가 나중에 생김.
- **사용한 기술:** 백엔드 통합 API로 교체 — `GET /dashboard/home`(모든 칸 같은 `observedAt`), 목록 응답의 `statusCounts`.
- **조치:** 기업 여러 곳 삭제도 한 곳씩(중간 실패 시 일부만 지워짐) → `DELETE /companies` 한 번(실패하면 서버가 전체 되돌림).
- **결과:** 홈 요청 12 → 1, 탭 건수 요청 5 → 1, 기업 삭제는 전부 되거나 전부 안 됨.

### 3. 로그인 그림 · 로고 (11/12, !596)
- **문제:** Lighthouse "이미지 92KB 줄일 수 있음", 가장 큰 화면 요소(LCP)인 그림을 늦게 받음, 로고 크기 미지정(화면 밀림 위험).
- **사용한 기술:** WebP 변환(새 라이브러리 없이 Chrome canvas 인코더로), `fetchpriority="high"`, `width`/`height`, 표시 폭의 2배(72px)로 줄인 로고는 4KB 아래라 빌드 때 JS에 인라인(요청 0).
- **결과:** 그림 3장 113KB → 25KB(-78%), 로고 7.6KB → 2.4KB. 로그인 LCP 0.87 → 0.79초, 받는 양 478 → 395KB(1회 측정).
- **남은 것:** 그림이 JS로 들어가서 HTML만 보고는 미리 못 찾는다는 지적은 남음(로그인 화면 한 곳이라 둠).

### 4. 목록 화면 강제 리플로우 (11/12, !596)

- **원인:** `useScrollable`이 그린 직후 `scrollHeight`를 읽음.
- **사용한 기술:** 첫 판정도 `ResizeObserver`에 맡김(관찰을 시작하면 한 번 불림).
- **결과:** 6화면 → 2화면. 남은 통화 목록(칩 칸 폭을 그리기 전에 재야 깜빡임이 없음) · FAQ(펼침 높이 측정)는 의도한 측정이라 둠.

### 5. 숨긴 탭 요청 · 녹음 끊김 (11/02, !196)

### 26. 글꼴 직접 내려주기를 시도했다가 되돌림 — 렌더링 차단을 없앴더니 LCP가 나빠짐 (11/12, !623 → 되돌림)
- **문제:** Lighthouse "렌더링 차단 요청" — 모든 화면에서 Pretendard 글꼴 CSS(53KB, jsdelivr)를 받는 동안 약 220ms 화면이 그려지지 않음. 미리 연결(preconnect, !596)을 걸었지만 그대로였음.
- **원인(차단):** `<head>`의 외부 스타일시트는 받을 때까지 그리기를 막음. preconnect는 연결 시간만 줄일 뿐 막는 것 자체는 못 없앰.
- **시도(!623):** 글꼴 직접 내려주기(self-host) — 같은 판(v1.3.9) 동적 서브셋 woff2 92개와 @font-face를 우리 CSS에 합침(`unicode-range`, `font-display: swap` 그대로).
- **배포 뒤 측정(16화면, 1회씩):** 첫 화면 FCP 평균 454 → 311ms, 렌더링 차단 233 → 92ms로 좋아졌지만 **LCP는 16화면 중 15화면에서 늘어 평균 886 → 987ms**, 성능 점수가 1점씩 내려간 화면이 생김.
- **원인 확인(같은 시각 A/B):** 측정 사이가 6시간이라 서버 상태 탓일 수도 있어, 같은 코드를 글꼴만 다르게 두 벌 빌드해 이 PC에서 번갈아 3회씩 잼(목 빌드, 가운데 값). 글꼴 파일을 막는 방식은 브라우저가 글꼴을 기다리는 동작이 끼어 비교가 안 돼 버림.

  | 화면 | HTTP/1.1 LCP (우리 서버 / CDN) | HTTP/2 LCP (우리 서버 / CDN) |
  |---|---|---|
  | 홈 | 2,072 / 788ms | 846 / 472ms |
  | 통화 목록 | 1,054 / 725ms | 737 / 460ms |
  | 통계 | 1,292 / 657ms | 792 / 492ms |

  - 우리 서버 쪽은 FCP가 빠르지만(258~463ms) 기본 글꼴로 먼저 그린 뒤 Pretendard가 오면 글자를 다시 그리고, 그 시점이 LCP가 됨. HTTP/1.1에서는 글꼴 조각 10여 개가 연결 6개를 JS · API와 나눠 써 더 늦어짐.
  - 성능 점수는 LCP(25%)가 FCP(10%)보다 무거워 CDN 쪽이 높음(홈 86 대 77).
- **조치:** 되돌림 — CDN 스타일시트 · preconnect 복구, 저장소의 글꼴 파일 삭제.
- **배운 것:** 지표 하나(렌더링 차단)만 보고 고치면 다른 지표가 나빠질 수 있음. 바꾸기 전후를 같은 시각 · 같은 조건 A/B로 재야 원인을 가를 수 있음. 같은 A/B에서 HTTP/2만 켜도 CDN 쪽 홈 LCP 788 → 472ms, 성능 86 → 97 — HTTP/2가 더 큰 개선 후보.
- **근거:** A/B 수치 `docs/troubleshooting/font-ab.json`

### 42. AI 상담가 화면이 같은 API를 두 번 부름 (11/13)
- **문제:** AI 상담가 3화면(상담가 · 시나리오 시험 · 시험 상세)의 Lighthouse는 성능 99 · 접근성 100 · 권장사항 100이라 점수로는 고칠 것이 안 보였다. 요청 목록을 보니 화면을 열 때 같은 API를 두 번 부르고 있었다 — `/auth/me`는 잰 13화면 모두 2번, 시나리오 시험 화면은 상담가 목록 · 상세 · 버전 기록까지 다시 불러 14번 중 4번이 중복. 시험 화면은 표에 쓸 시험 결과를 상담가 자료가 온 뒤에야 부르기 시작해 한 박자 늦게 그려졌다.
- **원인:** React Query 기본값(`staleTime` 0)에서는 부품이 붙을 때마다 0.1초 전에 받은 자료도 낡았다고 보고 다시 받는다. 로그인 가드가 `/auth/me`를 받은 뒤에야 화면 틀이 붙고, 표 · 띠는 상담가 자료가 온 뒤에 붙으므로 늦게 붙는 부품마다 한 번씩 더 불렀다. 39 · 40번 수정에서 표가 '통화에 쓰는 상담가의 버전 기록'도 보게 되면서 시험 화면의 중복이 2개 늘었다(12번 → 14번).
- **사용한 기술:** 로컬 측정 틀 — 빌드본을 실서버 nginx와 같은 조건(gzip 5단계 · 30일 캐시)으로 내주고, API는 가짜 서버(mock)의 응답을 받아 적어 80ms 뒤에 돌려준다. 로그인 없이, 같은 자료로, 빌드 두 벌을 같은 시각에 번갈아 잴 수 있다(실서버는 로그인 · 배포가 필요하고 자료가 그새 바뀜 — 24번). Playwright로 첫 화면의 API 요청을 순서대로 적어 중복과 박자(앞 응답을 기다렸다가 부르는 묶음)를 셈.
- **조치:** 내 정보는 30초, 상담가 목록 · 버전 기록 · 시험 결과는 5초 동안 방금 받은 것으로 봄(`staleTime`) — 저장 · 반영 · 시험 시작 뒤에는 전처럼 invalidate로 바로 다시 받는다. 시험 화면은 시험 결과를 상담가 자료와 같이 받기 시작(`usePrefetchQuery`). AI 상담가 화면에서도 미리 받게 해 봤지만, 띠가 없는 평소엔 쓰지 않는 요청 2개가 늘어 되돌리고 띠가 뜰 때만 같이 받게 함(43번).
- **결과:** 첫 화면 요청 — AI 상담가 12 → 11번(4박자 → 3박자), 시나리오 시험 14 → 10번(3박자 → 2박자), 시험 상세 17 → 14번. 중복 1 · 4 · 3개 → 0. `/auth/me`는 잰 13화면 모두 2 → 1번. Lighthouse 5회 중앙값(같은 시각 전후) LCP 948 → 834ms · 979 → 791ms · 990 → 871ms, 성능 99 · 99 · 99 → 99 · 100 · 99. 접근성 · 권장사항 100, CLS 0, TBT 0은 그대로. 여기까지는 API 지연을 80ms로 둔 로컬 값. 배포 뒤 실서버(11/14, 3회 중앙값)는 AI 상담가 성능 100 · 접근성 100 · 권장사항 100 · LCP 757ms(11/12 옛 화면은 99 · 95 · 100 · 990ms), 시나리오 시험 100 · 100 · 100 · 743ms, 시험 상세 99 · 100 · 100 · 889ms.
- **근거:** `docs/troubleshooting/persona-lighthouse/` — 측정 틀(`record.cjs` · `serve.mjs` · `audit.mjs` · `reqs.cjs`), 전후 요청 목록(`requests-*.txt` · `auth-me-count.txt`), Lighthouse 회차별 값(`lighthouse-*.json`).

### 6. 검색칸 한글 조합이 끊김 (10/30, !102)
- **문제:** 검색칸에 한글을 치면 조합이 끊기고, 가운데를 고치면 커서가 끝으로 튐.
- **원인:** 검색어를 URL 쿼리에 두는데, 라우터가 주소 변경을 `startTransition`으로 늦게 반영 → 입력칸이 이전 값으로 되돌아갔다 다시 바뀜.
- **사용한 기술:** 목록 공용 훅 `useListParams`의 `setSearchParams`에 `flushSync: true`.
- **결과:** 공용 훅 한 곳 수정으로 모든 목록 화면 검색칸이 함께 해결. 같이 넣은 것: 초성 검색('ㄱㄷㅇ' → 강도윤), 띄어쓰기 무시, 한글 조합 중 Enter 무시(`search.test.ts`).

### 7. 크롬 자동 완성 뒤 첫 클릭 무시 (11/01, !144)
- **문제:** 크롬이 아이디 · 비밀번호를 채워도 [로그인] 첫 클릭이 먹지 않음.
- **원인:** 크롬 자동 완성 값은 사용자가 화면을 누르기 전엔 입력 이벤트가 없어 React 상태가 빈 채 → 버튼이 진짜 `disabled`라 첫 클릭이 버려짐.
- **사용한 기술:** 버튼은 회색으로 보이되 `aria-disabled`(누를 수 있음), 누른 순간 입력칸 DOM 값을 직접 읽어 로그인. 로그인 중에만 진짜 `disabled`로 두 번 눌림 방지.
- **결과:** 수치 없음(실서버 크롬 저장 비밀번호로 확인).

### 8. 모달 배경이 스크롤과 함께 밀림 (11/01, !161)
- **문제:** 모달을 열고 스크롤하면 어두운 배경이 화면을 다 덮지 못하고 밀림.
- **원인:** 페이지 등장 애니메이션(`translateY`)이 `fill: both`로 끝난 뒤에도 남아, 그 래퍼가 `position: fixed` 자손의 기준 상자가 됨(transform이 있는 조상은 fixed의 기준이 되는 CSS 규칙).
- **사용한 기술:** 등장 애니메이션을 전부 `backwards`로(끝나면 transform이 빠짐). 디자인 토큰에 규칙으로 적어 팀원 모달까지 공통 적용.
- **결과:** 애니메이션 끝난 뒤 배경이 화면 전체를 덮음. 수치 없음.

### 9. 창 안에서 끌다 놓으면 창이 닫힘 (11/01, !135)
- **문제:** FAQ 입력 중 글을 드래그해 선택하다 배경에서 놓으면 창이 닫혀 입력이 사라짐.
- **원인:** 배경 `click`은 누른 곳과 뗀 곳이 달라도 뗀 곳 기준으로 발생.
- **사용한 기술:** 배경에서 누르고(`mousedown`) 배경에서 뗄 때만 닫음. 같이: 첫 입력칸 포커스, Tab 순환, 닫으면 연 버튼으로 포커스 복귀, 겹친 창은 맨 위만 Esc.
- **결과:** 수치 없음.

### 10. 스크롤바가 생겼다 사라지며 화면 출렁 (11/09 !373, 11/11 !495)
- **문제:** 메뉴를 옮길 때마다 0.25초쯤 창 스크롤바가 생겨 화면 폭이 출렁. 표에서 쪽을 넘겨 행 수가 바뀔 때도 같음.
- **원인:** 새 화면이 6px 아래에서 떠오르는 동안 본문이 창보다 6px 길어짐. 표는 행 수에 따라 막대가 생겼다 없어짐.
- **사용한 기술:** 본문 `overflow-hidden`(스크롤은 안쪽 상자), 스크롤 상자 전체에 `scrollbar-gutter: stable`(global.css 한 규칙).
- **결과:** 메뉴 11개를 차례로 눌러 매 프레임 넘침 기록 — 화면마다 약 25프레임 동안 6px 넘침 → 0(1440×900 · 1440×780).

### 11. 탭 건수가 탭마다 다르고 탭이 울렁임 (11/09, !409 · !403)
- **문제:** 주문 상태 탭을 누를 때마다 '전체' 건수가 바뀜(26 → 25 → 24). 건수가 하나씩 도착하며 탭이 밀려 흔들림.
- **원인:** 쪽을 넘겨도 줄이 밀리지 않게 고정하는 목록 기준 시각을 **탭 조건까지 넣어** 정함 → 주문 취소 탭이면 마지막 취소 주문 시각이 기준이 되어 그 뒤 주문이 모든 탭 건수에서 빠짐.
- **사용한 기술:** 기준 시각은 검색 · 기간만으로(`useSnapshotList`의 `anchorQuery`), 탭 건수 자리를 받기 전에 잡아 두고 새로 받는 동안 옛 숫자 유지.
- **결과:** 탭 6개를 차례로 눌러 기록 — 전체 건수 490 · 485 · 489 · 490 · 475 · 489 → 모든 탭 490. 마지막 탭 위치 이동 열 때 3번 · 기간 바꿀 때 4~5번 → 0번.

### 12. 끝난 통화가 '통화 중'으로 남음 (11/09, !415)
- **문제:** 목록을 열 때 '통화 중'이던 통화가 끝나도 새로고침 전까지 '통화 중'.
- **원인:** 쪽 고정(기준 시각) 때문에 이미 보이는 줄의 상태를 다시 받지 않음. 서버 값은 정상이었음(실서버 확인).
- **사용한 기술:** 보고 있는 쪽을 15초마다 같은 기준 시각으로 다시 받음 → 줄 · 순서는 그대로, 상태만 새로.
- **결과:** 수치 없음(실서버에서 15초 주기 재요청 · 줄 순서 유지 확인).

### 13. 뒤로 오면 목록이 맨 위로, 2쪽에서 열면 1쪽으로 (11/09 !387, 11/11 !534)
- **문제:** 통화 상세에서 ‹ 를 누르면 목록이 맨 위. 주문 2쪽에서 상세를 열면 1쪽으로.
- **원인:** 화면이 창이 아니라 안쪽 상자로 스크롤해 브라우저 기본 복원이 안 됨, ‹ 가 링크라 새 기록을 쌓음. 상세를 주소(`o`)에 쓸 때 목록 훅이 필터 변경으로 보고 쪽을 1로.
- **사용한 기술:** 기록(`location.key`)마다 상자 위치를 기억해 목록이 다 올 때까지(최대 약 5초) 다시 맞춤, 바로 전 기록이 그 목록이면 ‹ 를 뒤로가기로. 상세를 열고 닫을 때 지금 쪽을 같이 넘김.
- **결과:** 통화 목록 300px 굴림 → 상세 → ‹ → 300px, 브라우저 뒤로 · 앞으로도 300px. 기업 목록 199px 그대로.

- **사용한 기술 · 결과:** `singleTilde: false` — 물결표 두 개(`~~글자~~`)만 취소선. 수치 없음.

### 15. 배포 뒤 열어 둔 탭이 오류 화면 (11/09, !402)
- **문제:** 배포 전에 열어 둔 탭에서 안 열어 본 화면으로 가면 "화면을 그리지 못했어요".
- **원인:** 배포가 파일 묶음을 통째로 바꿔 옛 해시 이름 JS가 사라짐 → `Failed to fetch dynamically imported module`.
- **사용한 기술:** 라우트 오류 화면에서 이 오류(크롬 · 파이어폭스 · 사파리 문구)면 새로고침 한 번. 1분 안에 또 나면(정말 없는 파일) 안내 화면 — `sessionStorage`에 마지막 새로고침 시각을 두어 무한 새로고침 방지.
- **결과:** 운영 빌드에서 화면 파일을 한 번만 404 → 새로고침 1번 뒤 정상, 파일을 지움 → 1번 뒤 안내 화면, 반복 없음.

### 16. 엑셀이 CSV 전화번호 · 사번 앞 0을 지움 (11/06, !356)
- **문제:** 엑셀로 CSV를 열었다 저장하면 `01012345678` → `1012345678`, 사번 `00134` → `134` → 사원 등록 실패 또는 중복 사원.
- **사용한 기술:** 국내 번호는 늘 0 하나로 시작하고 다음 자리가 0이 아니라는 규칙으로, 0을 붙였을 때 국내 번호 모양일 때만 복원. 앞자리별 자릿수 검사(02 9~10, 010 11 등), 백엔드 11자리 규칙과 맞춰 보내기 전에 이유를 밝혀 막음, `1.01E+10` 지수 표기는 복원 불가라 안내.
- **결과:** 수치 없음(서버 400 대신 화면에서 이유와 함께 거절).

### 34. 통화 상세에서 말을 누르면 그 말을 놓침 (11/13)
- **문제:** 대화 줄을 누르면 녹취가 그 말보다 늦게 시작 — 짧은 고객 말('네')은 아예 안 들림.
- **원인:** 발화 시각(`offsetSeconds`)은 AI 통화 시작부터 세는데, 녹취(PBX WAV)는 그보다 늦게 시작. 실서버 녹취를 내려받아 0.5초 단위 음량(RMS)으로 말 구간을 찾아 대조: #596은 AI 말이 시각보다 1~2초, 고객 말이 2.5~3초 일찍 녹취에 있음. 녹취 길이 349.8초 · 통화 길이 352초 → 빈 칸 2.2초가 녹취 앞쪽(#590도 330 − 328.16 = 1.8초, 첫 인사 시각 3초 · 녹취 2.0초).
- **사용한 기술:** 녹취 위치 = 통화 시각 − (통화 길이 − 녹취 길이). 누를 때 · 재생 위치로 줄을 칠할 때 · 불만 눈금 위치 모두 같은 식. 재생 줄 시각도 통화 시각으로 보여 대화 줄 시각과 같은 숫자.
- **결과:** #596 '네'(시각 14초) 이전 12초 → 9.8초부터(녹취 속 '네'는 11초), AI 첫 인사 4초 → 1.8초(녹취 2.0초). 고객 말 2초 앞당김은 그대로.

### 35. 주문 탭이 '전체 0 · 미완료 3' (11/13)
- **문제:** 기간 '오늘'에 주문이 없는데 미완료만 3건 — 전체보다 큰 숫자.
- **원인:** 다른 탭은 기간 안에서 세는데(서버 statusCounts는 미완료 초안도 기간 안만 전체에 더함), 미완료 탭은 초안 목록(`/parcel-drafts`)을 기간 없이 셈.
- **사용한 기술 · 조치:** 초안 목록 · 건수 요청에도 같은 `from`을 넘기고, 미완료 탭에서도 기간 버튼을 보임.
- **결과:** 실서버 오늘 기준 초안 기간 없이 3건 → `from` 넣고 0건, statusCounts all 0 · incomplete 0과 같음.

### 36. 프롬프트를 저장해도 [취소][저장]이 남고 [통화에 반영]이 꺼짐 (11/13, !692)
- **문제:** AI 상담가 프롬프트를 [저장]해도 [취소][저장]이 그대로 남고, 반영 전 띠의 [통화에 반영]이 꺼진 채 '고친 내용 저장' 안내가 나옴.
- **원인:** 저장 뒤 상담가 목록(현재 버전 번호)이 버전 기록보다 먼저 도착 → 입력 칸이 새 현재 버전 기준으로 다시 떴는데 맨 위 버전은 아직 옛 글이라 '고친 게 있음'으로 남음.
- **사용한 기술:** `usePersonaPage`의 편집 대상 계산에 최신 여부 검사 — 남은 초안이 없으면 버전 기록 맨 위 번호가 목록의 현재 버전과 같을 때만 입력 칸을 띄움.
- **결과:** 저장 직후 입력 칸이 새 글로 뜨고 [통화에 반영]이 바로 켜짐(저장 → 반영 전 띠 → 시험 → 반영까지 mock에서 확인). 수치 없음.

### 37. 목소리가 기본 음성인 상담가가 늘 '선택'으로 보임 (11/13, !696)
- **문제:** 목소리가 '기본 음성'인 상담가는 목소리 칸이 늘 회색 '선택'으로 보이고 기본 음성이 안 보임.
- **원인:** 기본 음성 값이 ''(서버 voiceId null)인데, 공용 SelectField가 value='' 자리에 '선택' 빈 선택지(disabled)를 먼저 둬서 그쪽이 골라짐.
- **사용한 기술:** `VoiceFields`가 SelectField 대신 select를 직접 그림 — 빈 선택지를 없애고 '' = 기본 음성 하나만 둠(카드는 작은 칸, 등록 화면은 이름 칸과 같은 모양).
- **결과:** 기본 음성 상담가가 '목소리 기본 음성'으로 보이고, 등록 → 남성 1 선택 → 저장 뒤에도 '남성 1' 유지(1440 mock). 수치 없음.

### 38. 가짜 서버(mock)에서 상담가 [삭제] · [등록]을 누르면 로그아웃 (11/13, !694 · !696)
- **문제:** mock 모드에서 상담가 [삭제]나 [등록]을 누르면 화면이 로그아웃됨 → 삭제 · 등록 흐름을 끝까지 확인할 수 없음.
- **원인:** MSW에 DELETE · POST `/personas` 받기가 없어 요청이 실서버로 넘어가 401.
- **사용한 기술:** `mocks/handlers/personas.ts`에 받기 추가 — 삭제는 204로 목록에서 빼고 사용 중 · 적용 대기면 409, 없는 번호면 404(서버와 같게). 등록은 v1 사용 안 함으로 넣고 201 `{ aiPersonaSeq }`.
- **결과:** 로그아웃 없이 삭제 뒤 사용 중 상담가로, 등록 뒤 새 상담가 탭으로 돌아옴. 수치 없음.

### 39. '모두 통과하면 바로 반영'이 AI 상담가 화면을 열어 둔 동안에만 됨 (11/13)
- **문제:** 띠의 [시험하고 반영]을 누른 뒤 다른 메뉴로 가면, 시험이 모두 통과해도 반영되지 않다가 다음에 AI 상담가 화면을 열 때 반영됨. 실제 시험은 통화 10건이라 10~25분 — 그동안 화면을 떠나는 것이 보통이고, 담당자는 반영된 줄 아는데 통화는 예전 내용으로 받음.
- **원인:** 통과하면 반영하는 처리가 상담가 카드 안의 effect에 있어 카드가 떠 있을 때만 돎. 가짜 서버의 시험은 15초라 화면을 떠날 일이 없어 줄별 확인에서 드러나지 않음.
- **사용한 기술:** 약속(상담가 · 버전 · 시작 전 시험 시각)을 localStorage에 남기고, 앱 틀(`AppLayout`)이 `useSyncExternalStore`로 약속이 있는지만 보다가 있을 때만 지켜보는 코드(`useApplyAfterTest`)를 `lazy`로 불러옴 — 시험 창구 코드가 첫 화면 묶음에 들어가지 않게(틀에서 바로 부르면 첫 화면 JS가 gzip 129.8 → 132.3KB, 나눠 불러 129.5KB). 무엇을 할지(기다림 · 버림 · 반영)는 순수 함수 `pledgeStep` + 테스트 4개. 탭이 여러 개면 약속을 꺼낸 탭만 요청을 보냄. 방금 건 시험이 목록에 보이기 전에 약속이 지워지던 틈도 '시작 전 시험 시각'과 비교해 막음.
- **결과:** 주문 화면에 가 있는 동안 시험이 끝나면 반영 요청이 1번 가고, 돌아오면 반영 중 → 사용 중(가짜 서버 자동 점검). 브라우저가 닫혀 있으면 다음에 열 때 반영 — 서버가 약속을 맡기 전까지의 한계. 수치 없음.

### 40. 상담가 이름만 바꿔도 '반영 전' 띠가 생김 (11/13)
- **문제:** 통화에 쓰는 상담가의 이름을 연필로 바꾸면 '반영 전 · 고친 내용' 띠가 생기고, 없애려면 [통화에 반영] → 시험(실제 통화 10건, 요금)을 돌려야 함. 시안은 이름만 바뀌고 띠가 없음.
- **원인:** 서버에서 이름은 버전에 딸린 값이라 이름 저장 = 새 버전. 통화에 쓰는 버전과 번호가 달라져 '반영 전'으로 보임.
- **사용한 기술:** 이름 저장 뒤 바로 적용 요청(프롬프트 · 목소리가 그대로라 시험할 것이 없음). 띠의 [통화에 반영]도 내용이 통화에 쓰는 것과 같으면 시험 없이 묻고 반영. 그렇게 반영된 버전은 시험한 적이 없으므로, 시험 결과 표 · 상세의 비교 기준을 내용이 같은 앞 버전에서 찾는 순수 함수 `baseOf` + 테스트.
- **결과:** 이름을 바꾸면 반영 중 → 사용 중, 띠 없음. 이름 한 번 바꾸는 데 드는 시험 통화 10건 → 0건. 시험 결과 표의 '통화에 쓰는 내용' 칸도 '결과 없음'으로 비지 않음.

### 41. 눈으로는 '시안과 같음'이던 화면이 수치로는 다름 (11/13)
- **문제:** AI 상담가 10개 흐름을 세션 10개가 나눠 만들고 저마다 '시안과 같음'으로 보고했지만, 띠 글자(16 · 14)가 15 · 13, 토글 회색 받침 없음, [상담가 등록]이 28px 어긋남, 프롬프트 글 15가 14 등 차이가 남아 있었음.
- **원인:** 한 줄 전체를 담은 시안 그림(화면 하나가 350px 폭으로 줄어듦)을 눈으로 비교 → 글자 1px · 간격 몇 px 차이가 안 보임. Figma에서 뽑은 그림은 글꼴 렌더링도 달라 폭으로 글자 크기를 가릴 수 없음.
- **사용한 기술:** 시안을 만든 원본 HTML을 실제 화면과 같은 헤드리스 Chrome으로 그려, 23개 상태마다 요소별 computed style(글자 크기 · 굵기 · 색 · 바탕 · 테두리 · 여백)과 위치를 뽑아 실제 화면의 같은 요소와 자동 비교(요소 짝 표 = 이름 · 시안 쪽 찾기 · 화면 쪽 찾기). 흐름 점검(누르기 · 새로고침 · 뒤로 가기 · 화면 크기 5종 108개)과 한 번에 돎.
- **결과:** 모양 차이 156 → 42곳, 6px 넘는 자리 차이 293 → 156곳(같은 부품이 여러 상태에 되풀이되면 그만큼 셈). 남은 모양 차이는 일부러 둔 것(공용 창 · 공용 입력 칸, 접근성 대비로 더 진하게 한 회색)과 짝이 어긋난 측정, 자리 차이는 가짜 자료의 글 · 날짜 길이가 시안과 다른 것과 스크롤 자리 10px.
- **근거:** `docs/troubleshooting/persona-design-check/` — 시안 원본 생성기 · 요소 짝 표 · 흐름 점검 · 전후 비교 기록(before.txt · after.txt). 같은 흐름 점검 108개를 고치기 전 코드에 돌리면 10개 실패, 고친 뒤 0개.

### 43. 시험 중에 AI 상담가 화면을 새로 열면 '반영 전' 띠가 잠깐 보임 (11/13)
- **문제:** 고친 내용을 시험하는 중이거나, 시험에 실패가 있어 확인이 필요한 상태에서 AI 상담가 화면을 새로 열면 약 0.1초 동안 '반영 전' 띠 · [통화에 반영] · 고칠 수 있는 입력 칸이 보였다가 '시험 중'(잠김) · '확인 필요'로 바뀐다. 시험 창구가 느리면 그만큼 길어진다.
- **원인:** 띠의 상태는 시험 결과가 있어야 정해지는데, 결과를 아직 못 받은 동안을 '시험 전'과 똑같이 그렸다. 게다가 시험 결과는 버전 기록이 온 뒤에야 부르기 시작해(띠의 대상이 버전 기록에서 나옴) 늘 한 박자 늦게 왔다. 전에는 다른 코드([통화에 사용하기] 관문)가 시험 결과를 먼저 받아 둬서 드러나지 않다가, 39 · 40번에서 그 코드를 지우며 생겼다 — QA 흐름은 화면을 연 채로 누르는 것만 봐서 못 잡음.
- **사용한 기술:** `requestAnimationFrame`마다 띠 글과 입력 칸 잠김을 읽어 달라질 때만 적는 스크립트 — 눈과 스크린샷으로는 놓치는 0.1초를 기록. 받아 적은 응답에서 시험 상태만 바꾼 사본(시험 중 · 실패 있음)으로 재현.
- **조치:** 띠가 뜰 상담가인지는 목록만으로 알 수 있으므로(반영 전 내용이 있음 · 통화에 안 쓰는 상담가) 시험 결과를 버전 기록과 같이 받기 시작하고, 둘 다 온 뒤에 카드를 그림. 시험 창구가 답하지 않으면 첫 요청이 실패할 때까지만(최대 10초) 기다리고 시험 전으로 그림. 카드를 한 번 그린 뒤 띠가 생길 때(저장 직후)는 기다리지 않음 — 처음엔 이때도 카드를 가려서, 띠가 없는 상태에서 저장하면 카드가 한 번 깜빡였다(가짜 서버에서 약 20ms, 같은 방식의 스크립트로 발견).
- **결과:** 시험 중 · 실패 있음 상태에서 첫 화면이 바뀐 횟수 6회 중 6회 → 0회. 맞는 띠가 처음 뜨는 때는 약 0.3초로 틀린 띠가 뜨던 때와 같다(전에는 맞는 띠가 약 0.4초). 띠가 없는 평소 상태는 시험 결과 요청 0번 그대로.
- **남은 것:** 저장 직후 목록이 버전 기록보다 먼저 오는 한두 프레임(가짜 서버에서 약 10ms) 동안 띠에 앞 내용의 저장 시각이 보이고 입력 칸이 읽기 전용으로 바뀐다(36번의 '버전 기록이 따라올 때까지 입력 칸을 띄우지 않음'과 같은 틈). 이번 수정 전에도 같았고, 없애려면 저장 · 반영 뒤 목록과 버전 기록을 한 번에 갈아 끼워야 한다.

### 46. 시험을 중단한 뒤 다시 시작하면 중단 확인 창이 저절로 뜸 (11/14)
- **문제:** 시나리오 시험 화면에서 [시험 중단]으로 멈춘 뒤 그 화면에서 다시 시험을 시작하면, 누르지도 않았는데 '시험을 중단할까요?' 창이 뜬다. 창의 [중단]에 초점이 가 있어 Enter 한 번이면 방금 건 시험이 멈춘다(실서버 시험은 실제 통화라 요금이 든다). 같은 화면에 두 가지가 더 있었다 — 시작하자마자 멈추면 [남은 10개 시험]과 [전체 10개 시험]이 같이 떠 같은 일을 하는 버튼이 둘, 중단 요청이 실패한 뒤 창을 닫았다 다시 열면 지난 실패 문구가 먼저 보임.
- **원인:** 창을 여는 상태를 [취소]에서만 껐다. 중단이 되면 '시험 중'이 아니라서 창이 안 보일 뿐 상태는 켜진 채 남고, 다음 시험이 시작되는 순간 다시 보였다. 실서버에는 백엔드 중계가 없어(11/14에 생김) 중단이 늘 실패했으므로 '중단 성공 → 다시 시작'을 밟을 수 없었고, 가짜 서버 점검은 시험 화면에서 중단한 뒤 바로 앞 화면으로 돌아가 같은 화면에서 다시 시작하는 순서가 없었다. 남은 것 버튼은 '결과 없음 + 연결 실패'로만 정해(33번), 끝난 것이 하나도 없으면 전체와 같아지는 경우를 보지 않았다.
- **사용한 기술:** 실서버에 중계가 배포됐는지는 이미 끝난 묶음에 멈춤을 보내 확인 — 창구는 돌고 있는 묶음만 멈추므로 아무것도 바뀌지 않는다(202, 없는 묶음은 404, 전후 목록 동일). 그날 실서버에 생긴 실제 중단 묶음(끝난 시나리오 0개)을 읽기 전용으로 열어 본 것이 시작. 가짜 서버에서 '시험 → 중단 → 다시 시험'을 스크립트로 재현하고(`stop-restart.cjs`), 실패 응답은 `fetch`를 한 번 끊어 만듦.
- **조치:** 시험이 멈추거나 끝나면 창 상태를 끔. 창을 열 때 지난 실패는 지움. 남은 것이 전체와 같으면 [남은 N개 시험]을 두지 않음(`restOf` + 테스트) — 띠의 [다시 시험하고 반영] 확인 창도 '남은 10개를' 대신 '10개를 모두'가 됨.
- **결과:** 다시 시작한 뒤 저절로 뜨는 창 — 두 순서(몇 개 돈 뒤 중단 · 시작하자마자 중단) 모두 뜸 → 모두 안 뜸. 시작하자마자 멈춘 뒤 버튼 2 → 1개. 다시 연 창의 지난 실패 문구 있음 → 없음. AI 상담가 자동 점검 108개 통과.
- **근거:** `frontend/src/features/persona/components/ScenarioTest.tsx`, `hooks/scenarioTest.ts`(`restOf`), 재현 스크립트 `docs/troubleshooting/persona-design-check/stop-restart.cjs`.

### 45. knip이 깨끗하다고 한 뒤에도 남아 있던 안 쓰는 코드 (11/14)
- **문제:** 21번에서 knip으로 정리한 뒤 knip은 '안 쓰는 파일 · 의존성 0'이었지만, 화면을 여러 번 갈아엎으며 남은 코드가 그대로 있었다 — 테스트만 부르는 함수, 아무도 넘기지 않는 부품 옵션, 화면이 읽지 않는 훅 반환값.
- **원인:** knip은 어디선가 import하면 쓰는 것으로 본다. ① 테스트가 import해도 사용으로 침 — 달력 계산 5개 · 최근 조회 저장소처럼 화면은 없어지고 테스트만 남은 것 ② 옵션(props)과 반환 객체의 키는 보지 않음 — 확인 창의 끌어 옮기기, Button의 kind 6개 ③ 주석은 코드가 아니라서 없어진 이름을 계속 가리킴.
- **사용한 기술:** 검사 스크립트 넷 — `testonly.py`(테스트를 빼면 앱 어디에서도 안 쓰는 export), `props.py`(부품이 받는 값 이름과, 그 부품을 쓰는 JSX 태그의 속성 이름을 대조), `vmkeys.py`(훅이 돌려주는 키를 다른 파일 어디서도 읽지 않음 — 이름이 겹치면 쓰는 것으로 보는 보수적 판정), `comments.py`(주석 2,712개에서 코드에 없는 이름 · 주석 처리된 코드). 지운 뒤 동작이 그대로인지는 가짜 서버에서 화면 30개의 글과 그림을 전후로 남겨 대조(`snap.cjs` · `compare.cjs`)하고 AI 상담가 자동 점검 108개를 돌림.
- **조치:** 테스트만 쓰던 함수 14개와 그 테스트, 부품 12개의 옵션(Button kind 9 → 3, 확인 창의 끌어 옮기기 등 66줄, SelectField 옵션 5개 → 한 모양, Markdown 검색어 표시), 훅 7개의 반환값 10개, 두 군데 있던 관리자 탭 이름, 가짜 서버의 죽은 응답 2곳, 없어진 이름을 가리키던 주석 10여 곳을 지움. 가장 복잡하던 usePersonaPage는 띠 단계와 확인 창 문구를 순수 함수(`personaBand.ts`, 테스트 7개)로 떼어내고, 5단 · 4단으로 겹친 삼항 둘(통화 상세 녹취 문구 · 상담가 버전 상태)은 if로 풂.
- **결과:** 57파일 +466 −891줄(새 순수 함수 · 테스트 275줄 포함). 주석 처리된 코드는 처음부터 0개. usePersonaPage 470 → 362줄 · 복잡도 114 → 86, 겹친 삼항 104 → 84곳. 화면 30개의 글은 모두 같고 그림 차이는 시각 표시뿐, 자동 점검 108개 통과, 테스트 36 → 41개(지운 함수의 테스트 2파일을 빼고 7개 더함).
- **남은 것:** 복잡도 15를 넘는 함수는 43개 그대로 — useOrderForm(89) · useCallDetail(66) · useMemberForm(60) · useCompanyDetail(42)는 주문 · 기업 화면에 흐름 점검 스크립트가 없어 구조를 바꾸지 않았다. `?call=`로 미답변을 거르는 주소는 들어오는 링크가 없어졌지만 직접 치면 동작해 그대로 둠.

### 47. 이름 비교 검사가 못 본 안 쓰는 코드 (11/14)
- **문제:** 45번 정리 뒤 다시 확인하니 안 쓰는 코드가 남아 있었다. ① 화면 틀이 화면을 열 때마다 미완료 주문 건수를 받아 오는데 그 숫자를 읽는 곳이 없음(사이드바에서 숫자를 뺀 뒤 요청만 남음) ② 가짜 서버만 쓰는 주문 240줄(이름 · 주소 포함)이 실서버용 묶음에 실림 ③ 11/09 시연에 쓴 '시연 모드'가 상수 false로 꺼진 채 파일 하나와 분기 5곳으로 남음 ④ 서버 응답을 화면 모양으로 바꾸면서 계산해 놓고 아무도 안 읽는 값(버전마다 앞 버전과 다른 점, 통화 줄의 상담가 이름, 줄 비교의 줄 번호 등) ⑤ 미답변 목록을 날짜별로 묶은 뒤 화면이 그대로 다시 펴서 씀.
- **원인:** 45번의 검사는 이름 비교였다. `vmkeys.py`는 같은 이름이 다른 파일에 한 번이라도 나오면 쓰는 것으로 봐서 `incomplete` · `persona` · `status` · `customer`처럼 흔한 이름은 통째로 빠졌다. knip은 가짜 서버가 import하는 것(가짜 주문)과 상수로 꺼진 분기를 쓰는 것으로 보고, 타입의 칸은 어느 도구도 보지 않았다. '없다'고 한 근거가 검사 도구가 볼 수 있는 범위였다.
- **사용한 기술:** 타입스크립트 컴파일러 API로 '읽는 자리'에서 거꾸로 추적(`tsreads.cjs`) — 앱 코드의 모든 속성 읽기(`a.b` · 구조 분해 · `a['b']` · `T['b']`)가 가리키는 선언을 모으고, 한 번도 안 읽힌 선언(타입의 칸 · 훅 반환값)을 남김. 다른 타입 이름으로 넘겨받아 읽는 것(부품 props · 배열을 `.map`으로 그리기)은 따라가지 못하므로 결과는 후보로만 쓰고, 후보마다 그 값을 받는 화면 코드를 찾아 읽는지 확인. 지울 때는 타입에서 칸을 먼저 지워 읽는 곳이 하나라도 있으면 컴파일 오류가 나게 함. 테스트만 쓰는 export는 언어 서비스의 참조 찾기(`tsrefs.cjs`). 요청 수는 화면 10개를 새로 열며 셈(`shell-reqs.cjs`), 묶음은 지우기 전후 빌드를 조각 이름별로 대조.
- **조치:** 화면 틀의 미완료 건수 요청 삭제. 가짜 주문을 `src/mocks/handlers/orderData.ts`로 옮김(가짜 서버는 개발 모드에서만 받음). 시연 모드 파일 · 분기 · 안내 줄 삭제. 훅 9개의 반환값 14개, 화면 모양으로 바꾸며 만들기만 하던 값 17개와 그 계산, 테스트만 쓰던 `suggest` 삭제. 미답변 목록은 처음부터 줄 목록으로(날짜 순서는 그대로). 지운 값을 보던 테스트는 같은 내용을 남은 값으로 보게 고침.

### 27. 시나리오 시험 화면이 실제 창구 · 백엔드 모양에서만 깨짐 (11/12, !618 · !628)
- **문제:** 시나리오 시험 화면을 가짜 서버(MSW)로만 확인해 왔다. 실제 시험 창구에 붙였더니 (1) 통화가 중간에 멈춘 시나리오의 상세 화면이 "화면을 그리지 못했어요"로 깨졌고, (2) 백엔드 코드를 대조해 보니 백엔드가 넘겨줄 응답을 화면이 풀지 못해 목록이 비어 보일 상태였다.
- **원인:** (1) 판정과 대화 기록을 따로 받는데, 판정이 먼저 오면 대화 줄이 0개인 상태에서 "통화가 멈춘 곳"을 찾다가 없는 줄 번호(-1)를 돌려줬다. 가짜 서버는 둘을 늘 같은 순서로 줘서 드러나지 않았다. (2) 백엔드는 모든 JSON 응답을 `{ data, meta: { requestId } }`로 감싸는데(ResponseEnvelopeInterceptor), 화면은 `{ data }` 하나만 있을 때만 풀도록 되어 있었다.
- **사용한 기술:** 가짜 대신 진짜에 붙여 보는 확인. 시험 창구(FastAPI)를 로컬에서 띄우고 전에 돌린 실제 시험 결과를 복사해 읽히고(통화는 걸지 않음), 개발 서버 프록시가 토큰을 붙여 창구로 넘기게 했다. 백엔드 쪽은 `develop-backend`의 전역 인터셉터 · 예외 필터 코드를 읽어 응답 모양을 대조했다. 위치 찾기와 응답 풀기는 순수 함수로 빼서 테스트로 고정.
- **조치:** `failLine`이 대화 줄이 없으면 위치 없음(null)을 돌려주게 함. `unwrap`이 `{ data, meta }` · `{ data }` · 감싸지 않은 응답을 모두 받게 함. 가짜 창구도 실제 창구와 같은 주소 · 모양으로 바꿈.
- **결과:** 실제 창구에 붙인 브라우저 확인 18항목 통과(결과 표, 상세, 실제 녹음 10MB 재생과 위치 이동, 시나리오 보기). 가짜 모드 확인 18항목도 그대로 통과. 두 버그 모두 서버에 연결되기 전에 발견해 사용자에게 나간 적 없음. 속도 수치 없음.
- **근거:** !618(연결 · 위치 찾기 수정), !628(응답 풀기), `frontend/src/features/persona/hooks/scenarioTest.ts` · `api/scenarioTestMap.ts`와 각 테스트.

### 28. 요금이 드는 시험 시작 요청이 뜻과 다르게 실행될 수 있음 (11/12, !632)
- **문제:** 시나리오 시험의 시작 요청은 실제 통화를 걸어 요금이 나간다. 백엔드 중계를 만들기 전 계약을 검토하다가 세 가지 위험을 찾았다. (1) 시나리오 목록이 빈 배열이면 시험 창구가 "전체 실행"으로 받는다. (2) 페르소나 글이 빠지면 창구가 자기 기본 페르소나로 통화를 걸고, 그 결과에 이 버전의 표시가 붙는다. (3) 시작 요청이 시간 초과되면 화면이 "다시 시도해 주세요"를 보여 주는데, 창구는 이미 통화를 걸기 시작했을 수 있어 다시 누르면 통화가 두 번 걸린다.
- **원인:** 창구는 원래 개발자가 직접 부르는 도구라 빠진 값을 기본값으로 채운다(`scenarios or 전체`, 글이 없으면 기본 페르소나). 화면은 그 관대한 입력을 그대로 믿었고, 시작 요청은 같은 요청을 두 번 보내도 한 번만 실행된다는 보장(멱등성)이 없다.
- **사용한 기술:** 요금이 드는 요청은 보내기 전에 화면에서 한 번 더 검사(`runBody` 순수 함수 + 테스트). 실패했을 때는 다시 보내지 않고 묶음 목록을 다시 받아 "이미 시작됐는지"를 확인하는 방식(React Query `invalidateQueries` 뒤 캐시 확인). 백엔드 중계도 같은 조건을 필수로 받기로 합의.
- **조치:** 글이 비었거나 시나리오가 빈 배열이면 요청을 보내지 않음. 시작 요청이 실패하면 목록을 다시 받아, 이 버전이 시험 중이면 확인 창을 닫음. 오류 문구에서 "다시 시도"를 빼고 "표에 시험 중이 없을 때만 다시 시작"으로 바꿈.
- **결과:** 서버에 연결하기 전에 발견해 실제 요금 사고는 없음. 수치 없음.
- **근거:** !632, `frontend/src/features/persona/api/scenarioTestMap.ts`(`runBody`)와 테스트, `hooks/useScenarioTest.ts`.

### 31. 시험 통화가 전부 연결 실패여도 [통화에 사용하기]가 열림 (11/12)

### 32. 배포에는 시나리오 시험이 있는데 팀원이 받은 코드로 띄우면 없음 (11/12)

### 33. 시험이 중간에 끊기면 전체를 다시 돌려야 함 (11/12)
- **문제:** 시나리오 시험이 도는 중에 develop-ai가 머지되면 AI 배포가 시험 창구도 다시 띄워 통화가 끊긴다. 끝난 시나리오 결과는 남지만 못 끝낸 것은 "결과 없음"이 되는데, [다시 시험]은 연결 실패만 다시 돌려서 남은 것을 마저 하려면 [전체 시험]을 눌러야 했다. 이미 끝난 것까지 다시 걸려 요금이 두 번 나간다.

- **조치:** 버튼을 [남은 N개 시험]으로 바꾸고 "결과 없음 + 연결 실패"를 보냄. 일부만 시험한 이 버전의 결과일 때만 보임. 같은 정리에서 창구가 보내지 않는 판정 시각(`at`) 처리 코드도 지움.
- **결과:** 끊겨도 남은 것만 다시 걸림. 수치 없음.
- **근거:** `frontend/src/features/persona/hooks/scenarioTest.ts`(`restOf`)와 테스트, `hooks/useScenarioTest.ts`.

### 24. 측정이 틀리게 나옴
- **로그인이 안 이어짐:** Playwright `launch()` + `newContext()`는 따로 떨어진 컨텍스트라, Lighthouse가 같은 Chrome에 연 탭엔 쿠키가 없어 모든 화면이 로그인 화면으로 측정됨(전부 100점) → `launchPersistentContext`로 같은 프로필, 로그인 화면으로 넘어가면 측정 중단.

## 7. 서버 설정

### 29. HTTP/1.1이라 요청이 연결 6개에 줄을 섬 (11/12)
- **문제:** Lighthouse "Modern HTTP" — 모든 화면에서 0.2~0.5초 손해 추정. 화면 하나에 JS · CSS · API 요청이 20~40개인데 서버가 HTTP/1.1만 말함. 상단 '통화 중 N건'은 서버와 연결을 열어 두는 SSE라 탭을 여러 개 열면 6개 중 하나씩 계속 차지함.
- **원인:** nginx `listen 443 ssl`에 http2가 없음. 브라우저는 HTTP/1.1에서 서버마다 연결을 6개까지만 열고, 연결 하나는 한 번에 요청 하나.
- **사용한 기술:** HTTP/2(연결 하나로 요청 여러 개를 동시에, 헤더 압축). nginx 1.24라 `listen 443 ssl http2;`. http2는 포트 단위라 443을 쓰는 server 블록 3개(IP · 도메인 · sslip) 모두에 같이 적용됨 — 관리자 웹만 골라 켤 수 없음.
- **확인한 것:** 앞서 글꼴 A/B(26번)에서 HTTP/2만 켜도 홈 LCP 788 → 472ms가 나와 효과 근거가 있었음. 적용 전후 주요 경로 12곳(화면 · API · API 문서 · Jenkins · Grafana · 모니터 · PBX/OpenAI 웹훅 3곳 · IP · sslip) 응답 코드 동일. 실제 브라우저로 화면 · API · Jenkins · Grafana 모두 h2, '통화 중 N건' SSE 정상. 적용 전에 시작해 적용 뒤에 끝난 실제 통화(#585)의 종료 시각 · 분석 완료가 정상으로 들어와 통화 종료 웹훅도 확인. 백업 `dva-ip.bak-20261112114736`, 되돌리기는 `http2` 단어를 빼고 reload.
- **결과(16화면, 전 = CDN 글꼴 + HTTP/1.1 14:27, 후 = CDN 글꼴 + HTTP/2 20:51):** 성능 99~100 → **16화면 모두 100**, LCP 평균 886 → 660ms(-25%, 화면별 -61 ~ -338ms), FCP 평균 454 → 435ms. "Modern HTTP" 지적 해결.
- **근거:** `docs/troubleshooting/http2-16-screens.json`

### 30. CSP(허가 목록) 없음 — 알림 전용으로 먼저 (11/12)
- **문제:** Lighthouse 권장사항의 보안 항목 "CSP가 XSS를 막는지" — CSP 헤더가 없음. 입력값(고객 이름 · FAQ 답변 등)에 악성 스크립트가 숨어 들어와도 브라우저가 막을 장치가 React의 기본 이스케이프 하나뿐.
- **어려운 점:** 허가 목록에서 하나라도 빠지면 그 기능이 조용히 멈춤. 예: 녹음은 S3 서명 주소에서 재생, 글꼴은 jsdelivr.
- **사용한 기술:** `Content-Security-Policy-Report-Only` — 같은 목록을 걸되 막지 않고, 목록 밖 요청만 브라우저가 기록. 목록: 스크립트는 우리 서버만, 글꼴 · 스타일은 우리 서버 + jsdelivr, 녹음 · 이미지는 우리 서버 + S3 버킷, API는 우리 서버만, object 금지. 스타일은 React `style` 속성 때문에 `'unsafe-inline'` 허용(스크립트는 막음). 관리자 웹 location에만.
- **확인한 것:** 자동 브라우저로 화면 19곳(로그인 · 가입 · 홈 · 목록 12 · 통화 상세 · 주문 상세 · FAQ 펼침 · 기업 상세 · 고객 패널)과 실제 녹음 재생(통화 #584, S3에서 3.6초 재생)까지 돌며 `securitypolicyviolation` 이벤트 · 콘솔 기록을 모음 → **위반 0건**.
- **다음:** 실제 사용 며칠 뒤에도 기록이 없으면 헤더 이름을 `Content-Security-Policy`로 바꿔 실제 차단. 백업 `dva-routes.conf.bak-20261112114643`.
