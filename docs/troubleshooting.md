## 1. 성능 · 네트워크

### 1. JS · CSS가 압축 없이 나감 (11/12, !594)
- **문제:** Lighthouse(데스크톱, 첫 방문) 성능이 주문 88, FAQ 85. 1순위 지적이 "텍스트 압축"으로, 화면마다 400~600KB를 더 받고 있었다.
- **원인:** 서버 `nginx.conf`에 `gzip on`은 있지만 `gzip_types`가 주석이라 nginx 기본값대로 `text/html`만 압축했다. 무게 대부분인 `/assets/*.js` · `*.css`는 원본 크기.
- **사용한 기술:** nginx `gzip_types` · `gzip_vary` · `gzip_comp_level 5`. 서버 공용 파일이라 관리자 웹 location 두 곳에만 적용(백엔드 · AI · Jenkins 경로는 그대로).
- **조치:** 백업 → 수정 → `nginx -t` 통과 시에만 reload. 첫 시도는 셸 변수가 글자 그대로 들어가 `nginx -t`가 막았고, reload 전이라 운영 영향 없이 되돌린 뒤 다시 넣음.
- **결과:** 메인 JS 258,982B → 81,890B(-68%), CSS 52,095B → 10,907B(-79%). 8화면 성능 85~98 → 95~99, FCP 화면마다 0.25~0.5초 단축.
- **근거:** `docs/fe-gzip-results.md`, `docs/fe-gzip-results/*.json`

### 2. 홈 요청 12번, 주문 탭 건수 5번 (11/09, !421)
- **문제:** 홈이 카드마다 따로 요청해 약 12번, 주문 상태 탭 건수는 탭마다 1번씩 5번. 카드마다 조회 시점이 달라 숫자가 서로 안 맞을 수 있었다.
- **원인:** 화면이 먼저 만들어지고 집계 API가 나중에 생김.
- **사용한 기술:** 백엔드 통합 API로 교체 — `GET /dashboard/home`(모든 칸 같은 `observedAt`), 목록 응답의 `statusCounts`.
- **조치:** 기업 여러 곳 삭제도 한 곳씩(중간 실패 시 일부만 지워짐) → `DELETE /companies` 한 번(실패하면 서버가 전체 되돌림).
- **결과:** 홈 요청 12 → 1, 탭 건수 요청 5 → 1, 기업 삭제는 전부 되거나 전부 안 됨.

### 3. 로그인 그림 · 로고 (11/12, !596)
- **문제:** Lighthouse "이미지 92KB 줄일 수 있음", 가장 큰 화면 요소(LCP)인 그림을 늦게 받음, 로고 크기 미지정(화면 밀림 위험).
- **사용한 기술:** WebP 변환(새 라이브러리 없이 Chrome canvas 인코더로), `fetchpriority="high"`, `width`/`height`, 표시 폭의 2배(72px)로 줄인 로고는 4KB 아래라 빌드 때 JS에 인라인(요청 0).
- **결과:** 그림 3장 113KB → 25KB(-78%), 로고 7.6KB → 2.4KB. 로그인 LCP 0.87 → 0.79초, 받는 양 478 → 395KB(1회 측정).
- **남은 것:** 그림이 JS로 들어가서 HTML만 보고는 미리 못 찾는다는 지적은 남음(로그인 화면 한 곳이라 둠).

### 4. 목록 화면 강제 리플로우 (11/12, !596)
- **문제:** 목록 화면 6곳에서 "강제 리플로우" — 그리자마자 레이아웃을 다시 계산.
- **원인:** `useScrollable`이 그린 직후 `scrollHeight`를 읽음.
- **사용한 기술:** 첫 판정도 `ResizeObserver`에 맡김(관찰을 시작하면 한 번 불림).
- **결과:** 6화면 → 2화면. 남은 통화 목록(칩 칸 폭을 그리기 전에 재야 깜빡임이 없음) · FAQ(펼침 높이 측정)는 의도한 측정이라 둠.

### 5. 숨긴 탭 요청 · 녹음 끊김 (11/02, !196)
- **문제:** 통화 목록 · 상세를 5초마다 새로 받으면서 녹음 주소 글자가 바뀌어 재생이 끊길 수 있고, 안 보는 탭에서도 계속 요청.
- **사용한 기술:** 탭이 숨겨지면 멈추고 돌아오면 바로 받음, 녹음은 `recordingSeq`로 같은 녹음인지 판단(주소 글자가 바뀌어도 유지), 만료 · 재생 오류 때만 새 주소로 바꾸고 듣던 위치 복원. 상세 네 조회를 나눠 하나가 늦어도 나머지는 먼저 표시.
- **결과:** 숨김 동안 요청 0건, 재생 중 갱신에도 소리 그대로, 만료 뒤 같은 위치부터 이어 재생. 명세 완료 조건 8개 재현 확인.

### 26. 글꼴 직접 내려주기를 시도했다가 되돌림 — 렌더링 차단을 없앴더니 LCP가 나빠짐 (11/12, !623 → 되돌림)
- **문제:** Lighthouse "렌더링 차단 요청" — 모든 화면에서 Pretendard 글꼴 CSS(53KB, jsdelivr)를 받는 동안 약 220ms 화면이 그려지지 않음. 미리 연결(preconnect, !596)을 걸었지만 그대로였음.
- **원인(차단):** `<head>`의 외부 스타일시트는 받을 때까지 그리기를 막음. preconnect는 연결 시간만 줄일 뿐 막는 것 자체는 못 없앰.
- **시도(!623):** 글꼴 직접 내려주기(self-host) — 같은 판(v1.3.9) 동적 서브셋 woff2 92개와 @font-face를 우리 CSS에 합침(`unicode-range`, `font-display: swap` 그대로).
- **배포 뒤 측정(16화면, 1회씩):** 첫 화면 FCP 평균 454 → 311ms, 렌더링 차단 233 → 92ms로 좋아졌지만 **LCP는 16화면 중 15화면에서 늘어 평균 886 → 987ms**, 성능 점수가 1점씩 내려간 화면이 생김.
- **원인 확인(같은 시각 A/B):** 측정 사이가 6시간이라 서버 상태 탓일 수도 있어, 같은 코드를 글꼴만 다르게 두 벌 빌드해 이 PC에서 번갈아 3회씩 잼(목 빌드, 가운데 값). 글꼴 파일을 막는 방식은 브라우저가 글꼴을 기다리는 동작이 끼어 비교가 안 돼 버림.

  | 화면 | HTTP/1.1 LCP (우리 서버 / CDN) | HTTP/2 LCP (우리 서버 / CDN) |
  |---|---|---|
  | 홈 | 2,072 / 788ms | 846 / 472ms |
  | 통화 목록 | 1,054 / 725ms | 737 / 460ms |
  | 통계 | 1,292 / 657ms | 792 / 492ms |

  - 우리 서버 쪽은 FCP가 빠르지만(258~463ms) 기본 글꼴로 먼저 그린 뒤 Pretendard가 오면 글자를 다시 그리고, 그 시점이 LCP가 됨. HTTP/1.1에서는 글꼴 조각 10여 개가 연결 6개를 JS · API와 나눠 써 더 늦어짐.
  - 성능 점수는 LCP(25%)가 FCP(10%)보다 무거워 CDN 쪽이 높음(홈 86 대 77).
- **조치:** 되돌림 — CDN 스타일시트 · preconnect 복구, 저장소의 글꼴 파일 삭제.
- **배운 것:** 지표 하나(렌더링 차단)만 보고 고치면 다른 지표가 나빠질 수 있음. 바꾸기 전후를 같은 시각 · 같은 조건 A/B로 재야 원인을 가를 수 있음. 같은 A/B에서 HTTP/2만 켜도 CDN 쪽 홈 LCP 788 → 472ms, 성능 86 → 97 — HTTP/2가 더 큰 개선 후보.
- **근거:** A/B 수치 `docs/troubleshooting/font-ab.json`

## 2. 화면 버그

### 6. 검색칸 한글 조합이 끊김 (10/30, !102)
- **문제:** 검색칸에 한글을 치면 조합이 끊기고, 가운데를 고치면 커서가 끝으로 튐.
- **원인:** 검색어를 URL 쿼리에 두는데, 라우터가 주소 변경을 `startTransition`으로 늦게 반영 → 입력칸이 이전 값으로 되돌아갔다 다시 바뀜.
- **사용한 기술:** 목록 공용 훅 `useListParams`의 `setSearchParams`에 `flushSync: true`.
- **결과:** 공용 훅 한 곳 수정으로 모든 목록 화면 검색칸이 함께 해결. 같이 넣은 것: 초성 검색('ㄱㄷㅇ' → 강도윤), 띄어쓰기 무시, 한글 조합 중 Enter 무시(`search.test.ts`).

### 7. 크롬 자동 완성 뒤 첫 클릭 무시 (11/01, !144)
- **문제:** 크롬이 아이디 · 비밀번호를 채워도 [로그인] 첫 클릭이 먹지 않음.
- **원인:** 크롬 자동 완성 값은 사용자가 화면을 누르기 전엔 입력 이벤트가 없어 React 상태가 빈 채 → 버튼이 진짜 `disabled`라 첫 클릭이 버려짐.
- **사용한 기술:** 버튼은 회색으로 보이되 `aria-disabled`(누를 수 있음), 누른 순간 입력칸 DOM 값을 직접 읽어 로그인. 로그인 중에만 진짜 `disabled`로 두 번 눌림 방지.
- **결과:** 수치 없음(실서버 크롬 저장 비밀번호로 확인).

### 8. 모달 배경이 스크롤과 함께 밀림 (11/01, !161)
- **문제:** 모달을 열고 스크롤하면 어두운 배경이 화면을 다 덮지 못하고 밀림.
- **원인:** 페이지 등장 애니메이션(`translateY`)이 `fill: both`로 끝난 뒤에도 남아, 그 래퍼가 `position: fixed` 자손의 기준 상자가 됨(transform이 있는 조상은 fixed의 기준이 되는 CSS 규칙).
- **사용한 기술:** 등장 애니메이션을 전부 `backwards`로(끝나면 transform이 빠짐). 디자인 토큰에 규칙으로 적어 팀원 모달까지 공통 적용.
- **결과:** 애니메이션 끝난 뒤 배경이 화면 전체를 덮음. 수치 없음.

### 9. 창 안에서 끌다 놓으면 창이 닫힘 (11/01, !135)
- **문제:** FAQ 입력 중 글을 드래그해 선택하다 배경에서 놓으면 창이 닫혀 입력이 사라짐.
- **원인:** 배경 `click`은 누른 곳과 뗀 곳이 달라도 뗀 곳 기준으로 발생.
- **사용한 기술:** 배경에서 누르고(`mousedown`) 배경에서 뗄 때만 닫음. 같이: 첫 입력칸 포커스, Tab 순환, 닫으면 연 버튼으로 포커스 복귀, 겹친 창은 맨 위만 Esc.
- **결과:** 수치 없음.

### 10. 스크롤바가 생겼다 사라지며 화면 출렁 (11/09 !373, 11/11 !495)
- **문제:** 메뉴를 옮길 때마다 0.25초쯤 창 스크롤바가 생겨 화면 폭이 출렁. 표에서 쪽을 넘겨 행 수가 바뀔 때도 같음.

### 11. 탭 건수가 탭마다 다르고 탭이 울렁임 (11/09, !409 · !403)

- **결과:** 탭 6개를 차례로 눌러 기록 — 전체 건수 490 · 485 · 489 · 490 · 475 · 489 → 모든 탭 490. 마지막 탭 위치 이동 열 때 3번 · 기간 바꿀 때 4~5번 → 0번.

## 5. 측정 방법 자체의 문제 (11/12)

### 27. 시나리오 시험 화면이 실제 창구 · 백엔드 모양에서만 깨짐 (11/12, !618 · !628)
- **문제:** 시나리오 시험 화면을 가짜 서버(MSW)로만 확인해 왔다. 실제 시험 창구에 붙였더니 (1) 통화가 중간에 멈춘 시나리오의 상세 화면이 "화면을 그리지 못했어요"로 깨졌고, (2) 백엔드 코드를 대조해 보니 백엔드가 넘겨줄 응답을 화면이 풀지 못해 목록이 비어 보일 상태였다.
- **원인:** (1) 판정과 대화 기록을 따로 받는데, 판정이 먼저 오면 대화 줄이 0개인 상태에서 "통화가 멈춘 곳"을 찾다가 없는 줄 번호(-1)를 돌려줬다. 가짜 서버는 둘을 늘 같은 순서로 줘서 드러나지 않았다. (2) 백엔드는 모든 JSON 응답을 `{ data, meta: { requestId } }`로 감싸는데(ResponseEnvelopeInterceptor), 화면은 `{ data }` 하나만 있을 때만 풀도록 되어 있었다.
- **사용한 기술:** 가짜 대신 진짜에 붙여 보는 확인. 시험 창구(FastAPI)를 로컬에서 띄우고 전에 돌린 실제 시험 결과를 복사해 읽히고(통화는 걸지 않음), 개발 서버 프록시가 토큰을 붙여 창구로 넘기게 했다. 백엔드 쪽은 `develop-backend`의 전역 인터셉터 · 예외 필터 코드를 읽어 응답 모양을 대조했다. 위치 찾기와 응답 풀기는 순수 함수로 빼서 테스트로 고정.
- **조치:** `failLine`이 대화 줄이 없으면 위치 없음(null)을 돌려주게 함. `unwrap`이 `{ data, meta }` · `{ data }` · 감싸지 않은 응답을 모두 받게 함. 가짜 창구도 실제 창구와 같은 주소 · 모양으로 바꿈.
- **결과:** 실제 창구에 붙인 브라우저 확인 18항목 통과(결과 표, 상세, 실제 녹음 10MB 재생과 위치 이동, 시나리오 보기). 가짜 모드 확인 18항목도 그대로 통과. 두 버그 모두 서버에 연결되기 전에 발견해 사용자에게 나간 적 없음. 속도 수치 없음.
- **근거:** !618(연결 · 위치 찾기 수정), !628(응답 풀기), `frontend/src/features/persona/hooks/scenarioTest.ts` · `api/scenarioTestMap.ts`와 각 테스트.

### 28. 요금이 드는 시험 시작 요청이 뜻과 다르게 실행될 수 있음 (11/12, !632)
- **문제:** 시나리오 시험의 시작 요청은 실제 통화를 걸어 요금이 나간다. 백엔드 중계를 만들기 전 계약을 검토하다가 세 가지 위험을 찾았다. (1) 시나리오 목록이 빈 배열이면 시험 창구가 "전체 실행"으로 받는다. (2) 페르소나 글이 빠지면 창구가 자기 기본 페르소나로 통화를 걸고, 그 결과에 이 버전의 표시가 붙는다. (3) 시작 요청이 시간 초과되면 화면이 "다시 시도해 주세요"를 보여 주는데, 창구는 이미 통화를 걸기 시작했을 수 있어 다시 누르면 통화가 두 번 걸린다.
- **원인:** 창구는 원래 개발자가 직접 부르는 도구라 빠진 값을 기본값으로 채운다(`scenarios or 전체`, 글이 없으면 기본 페르소나). 화면은 그 관대한 입력을 그대로 믿었고, 시작 요청은 같은 요청을 두 번 보내도 한 번만 실행된다는 보장(멱등성)이 없다.
- **사용한 기술:** 요금이 드는 요청은 보내기 전에 화면에서 한 번 더 검사(`runBody` 순수 함수 + 테스트). 실패했을 때는 다시 보내지 않고 묶음 목록을 다시 받아 "이미 시작됐는지"를 확인하는 방식(React Query `invalidateQueries` 뒤 캐시 확인). 백엔드 중계도 같은 조건을 필수로 받기로 합의.
- **조치:** 글이 비었거나 시나리오가 빈 배열이면 요청을 보내지 않음. 시작 요청이 실패하면 목록을 다시 받아, 이 버전이 시험 중이면 확인 창을 닫음. 오류 문구에서 "다시 시도"를 빼고 "표에 시험 중이 없을 때만 다시 시작"으로 바꿈.
- **결과:** 서버에 연결하기 전에 발견해 실제 요금 사고는 없음. 수치 없음.
- **근거:** !632, `frontend/src/features/persona/api/scenarioTestMap.ts`(`runBody`)와 테스트, `hooks/useScenarioTest.ts`.

### 24. 측정이 틀리게 나옴
- **로그인이 안 이어짐:** Playwright `launch()` + `newContext()`는 따로 떨어진 컨텍스트라, Lighthouse가 같은 Chrome에 연 탭엔 쿠키가 없어 모든 화면이 로그인 화면으로 측정됨(전부 100점) → `launchPersistentContext`로 같은 프로필, 로그인 화면으로 넘어가면 측정 중단.

- **PageSpeed Insights:** 로그인을 못 해 `/calls`를 넣어도 로그인 화면을 잼 → 로그인한 상태로 화면마다 직접 측정.
- **화면 데이터가 바뀜:** 측정 사이에 통화 #530 · 기업 #10이 사라져 404 · 측정 누락 — 코드 문제 아님, 숫자 비교에서 그 화면은 따로 봄.

## 7. 서버 설정

### 27. HTTP/1.1이라 요청이 연결 6개에 줄을 섬 (11/12)
- **문제:** Lighthouse "Modern HTTP" — 모든 화면에서 0.2~0.5초 손해 추정. 화면 하나에 JS · CSS · API 요청이 20~40개인데 서버가 HTTP/1.1만 말함. 상단 '통화 중 N건'은 서버와 연결을 열어 두는 SSE라 탭을 여러 개 열면 6개 중 하나씩 계속 차지함.
- **원인:** nginx `listen 443 ssl`에 http2가 없음. 브라우저는 HTTP/1.1에서 서버마다 연결을 6개까지만 열고, 연결 하나는 한 번에 요청 하나.
- **사용한 기술:** HTTP/2(연결 하나로 요청 여러 개를 동시에, 헤더 압축). nginx 1.24라 `listen 443 ssl http2;`. http2는 포트 단위라 443을 쓰는 server 블록 3개(IP · 도메인 · sslip) 모두에 같이 적용됨 — 관리자 웹만 골라 켤 수 없음.
- **확인한 것:** 앞서 글꼴 A/B(26번)에서 HTTP/2만 켜도 홈 LCP 788 → 472ms가 나와 효과 근거가 있었음. 적용 전후 주요 경로 12곳(화면 · API · API 문서 · Jenkins · Grafana · 모니터 · PBX/OpenAI 웹훅 3곳 · IP · sslip) 응답 코드 동일. 실제 브라우저로 화면 · API · Jenkins · Grafana 모두 h2, '통화 중 N건' SSE 정상. 적용 전에 시작해 적용 뒤에 끝난 실제 통화(#585)의 종료 시각 · 분석 완료가 정상으로 들어와 통화 종료 웹훅도 확인. 백업 `dva-ip.bak-20261112114736`, 되돌리기는 `http2` 단어를 빼고 reload.
- **결과(16화면, 전 = CDN 글꼴 + HTTP/1.1 14:27, 후 = CDN 글꼴 + HTTP/2 20:51):** 성능 99~100 → **16화면 모두 100**, LCP 평균 886 → 660ms(-25%, 화면별 -61 ~ -338ms), FCP 평균 454 → 435ms. "Modern HTTP" 지적 해결.
- **근거:** `docs/troubleshooting/http2-16-screens.json`

### 28. CSP(허가 목록) 없음 — 알림 전용으로 먼저 (11/12)
- **문제:** Lighthouse 권장사항의 보안 항목 "CSP가 XSS를 막는지" — CSP 헤더가 없음. 입력값(고객 이름 · FAQ 답변 등)에 악성 스크립트가 숨어 들어와도 브라우저가 막을 장치가 React의 기본 이스케이프 하나뿐.
- **어려운 점:** 허가 목록에서 하나라도 빠지면 그 기능이 조용히 멈춤. 예: 녹음은 S3 서명 주소에서 재생, 글꼴은 jsdelivr.
- **사용한 기술:** `Content-Security-Policy-Report-Only` — 같은 목록을 걸되 막지 않고, 목록 밖 요청만 브라우저가 기록. 목록: 스크립트는 우리 서버만, 글꼴 · 스타일은 우리 서버 + jsdelivr, 녹음 · 이미지는 우리 서버 + S3 버킷, API는 우리 서버만, object 금지. 스타일은 React `style` 속성 때문에 `'unsafe-inline'` 허용(스크립트는 막음). 관리자 웹 location에만.
- **확인한 것:** 자동 브라우저로 화면 19곳(로그인 · 가입 · 홈 · 목록 12 · 통화 상세 · 주문 상세 · FAQ 펼침 · 기업 상세 · 고객 패널)과 실제 녹음 재생(통화 #584, S3에서 3.6초 재생)까지 돌며 `securitypolicyviolation` 이벤트 · 콘솔 기록을 모음 → **위반 0건**.
- **다음:** 실제 사용 며칠 뒤에도 기록이 없으면 헤더 이름을 `Content-Security-Policy`로 바꿔 실제 차단. 백업 `dva-routes.conf.bak-20261112114643`.
