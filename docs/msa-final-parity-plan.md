# 최초 기준 전체 동등성 검증

Jira: [S15P31D109-160](https://ssafy.atlassian.net/browse/S15P31D109-160)

## 기준과 범위

사용자 요청에 따라 이후 API 변경 이식은 보류한다. 처음 이 작업을 시작한 `develop-backend` **`6a141a0512b73837905f6154c4ff84bcf33f912b`**의 backend를 고정한다. 최초 계획 커밋 `7266964`의 `msa/parity/baseline.json`을 `initial-baseline.json`에 그대로 보존한다. HTTP 선언 95개(업무 92개·health/metrics 3개), SQL 파일 51개(마지막 번호 052), 워커 6개가 대상이다. 최신 backend를 따르는 기존 `baseline.json`/Jenkins inventory 검사는 유지한다.

검증 대상 MSA는 MR !363 병합 커밋 `06ce863beaf44320111df3d609dc2b79a1bd5db0`이다. 브랜치는 `test/msa-final-parity`다. backend/frontend/AI는 읽기 전용이며 추적 수정은 msa/docs에 한정한다. 원본은 `git archive`로 무변형 추출한 복사본으로 빌드한다. 기존 055 구현을 되돌리거나 후속 API를 추가하지 않는다. 최초 계약과 현재 구현이 달라진 부분은 누락·동작 차이로 기록한다.

## 검증 순서와 판정

1. 원본 archive의 API·SQL 해시·워커 전체 목록을 최초 baseline과 비교한다. 현재 MSA 소스에서 동일 경로의 선언을 모두 조사한다. 선언 존재만으로 실행 동등성을 인정하지 않는다.
2. 원본 Docker checks/production 이미지와 다섯 MSA checks/production 이미지, 기존 Liquibase 이미지를 빌드한다. 원본 자체의 전체 integration 명령을 전용 임시 PostgreSQL에서 실행한다. 테스트 파일·기대값은 바꾸지 않는다.
3. 원본 DB와 서비스별 다섯 DB를 독립적으로 생성한다. 동일 업무 초기 데이터와 관리자 세션을 준비하고 최초 95개 API의 실제 응답·헤더·OpenAPI 계약, 읽기 후 DB 상태를 대조한다. 인증·입력 실패의 일치만으로 정상 동작 통과를 인정하지 않는다. 누락 경로는 두 앱이 우연히 같은 404를 반환해도 실패다.
4. 정상 고객 등록·수정/조회, 고객 확인·통화 등록, PIN·FAQ·페르소나·주문 생성 등 원본 업무 흐름을 실행한다. 응답·응답 직후 업무 DB·감사와 외부 호출을 확인한다. 원본 성공/MSA 실패이면 차이를 기록하고 나머지 경로를 계속 조사한다. SSE·비JSON 자산·인프라 health/metrics는 별도 처리한다.
5. 워커/서비스 간 이벤트의 구현·실행 증거를 구분한다. 미구현·미실행 경로와 이후 계약 때문에 달라진 경로를 명시한다. 전체 판정은 누락/불일치/미검증 항목이 하나라도 있으면 실패다. 기존 부분 검증의 성공을 전체 완료 근거로 사용하지 않는다.

모든 런타임 자원은 고유 실행 ID/소유 라벨을 붙인 로컬 Docker 내부 네트워크·임시 DB로 제한한다. 운영 Jenkins·DB·k3s·외부 결제/디버/AI를 변경하거나 호출하지 않는다. 검사 산출물은 `msa/liquibase/verification-logs/final/`에 저장하고 종료 시 이번 실행 소유 자원만 정리한다. 운영 배포 검증과 실제 외부 시스템 결과는 포함하지 않는다.

## 커밋과 MR

기준/계획 → 실행 가능한 검증기/회귀 → 실제 결과/후속 범위로 작업 단위를 나눈다. 검증기가 미구현을 검출해 실패한 경우 그 실패를 문서화하며 성공으로 꾸미지 않는다. 같은 Task 160에 연결한 MR을 `develop-backend` 대상으로 생성하고 사용자 병합 확인을 기다린다. 이번 MR은 전체 동등성 검증이며 미구현 업무 전체를 임의로 확장하는 MR이 아니다.
