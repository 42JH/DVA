# 통화 내역 자동 갱신 프론트 연동 명세

2026-11-02. 백엔드 브랜치 `fix/call-history-before-recording` 기준이다. 프론트 확인 기준은 `develop-fe`의 `e50791d`다. 백엔드 수정은 구현·검증했고, 프론트 구현은 사용자 결정에 따라 이 문서로 인계한다. 운영 배포 여부와 화면 반영 여부는 별도 확인한다.

## 목표와 작업 구분

AI에서 받은 통화 정보·분석·대화·처리 내역을 먼저 표시하고, PBX 정보·녹취가 나중에 준비되면 같은 통화에 반영한다. 녹취가 없다는 이유로 통화 행이나 전체 상세 화면을 숨기지 않는다.

| 담당 | 작업 | 상태 |
| --- | --- | --- |
| 백엔드 | PBX 시각이 없어도 기간 목록·상세에서 조회, 이후 같은 통화 번호에 데이터 연결 | 이 브랜치에서 구현·검증 |
| 백엔드 | 기존 S3 비동기 업로드·실패 재시도·녹취 재생 URL 발급 | 기존 동작 유지 |
| 프론트 | 열린 목록·상세 재조회, 늦게 도착한 데이터 반영, 재생 중 URL 보존 | 이 명세로 인계 |

## 사용할 API

기존 활성 관리자 세션 쿠키 `dva_session`을 사용한다. 새 엔드포인트·업로드 API·프론트용 AI 토큰은 없다.

| 표시 영역 | 요청 | 응답에서 읽을 값 |
| --- | --- | --- |
| 통화 목록 | `GET /api/calls?from=...&to=...&limit=20&offset=0` | 각 `data[]`, `hasNext`, `total_count` |
| 통화 기본 정보·분석·녹취 | `GET /api/calls/{id}` | `data.call`, `data.analysis`, `data.aiActionCount`, `data.recordings` |
| 대화 | `GET /api/calls/{id}/transcript` | 발화 목록·순서·`offsetSeconds` |
| AI 동작 | `GET /api/calls/{id}/actions` | 동작 목록 |
| 처리 내역 | `GET /api/calls/{id}/processing-results` | 주문·FAQ·이관 등의 처리 결과 목록 |

`id`는 DB의 `callSessionSeq`다. `providerCallId`나 녹취 번호를 경로에 넣지 않는다. 단건은 `{ data, meta }`, 목록은 `{ data, hasNext, total_count }`다. 목록 API의 기존 페이지 순회를 유지해 첫 100개만 전체로 취급하지 않는다.

상세 필드·오류 계약은 [통화 조회](calls.md), 대화·AI 동작·처리 결과는 [분리 조회](call-events-read-spec.md)를 따른다.

## 시각과 기간 검색

- `startedAt`: PBX 시작 → AI 시작 → 수신 이벤트 시각 순으로 선택한다. 셋 다 없으면 null이다.
- `endedAt`: PBX 종료 → AI 종료 순이며, 둘 다 없으면 null이다.
- 기간 `from` 포함·`to` 미포함, 정렬, 응답 시작 시각은 같은 기준이다. 화면 날짜 선택의 KST 자정·종료 다음 날 변환은 유지한다.
- PBX가 나중에 오면 같은 통화의 표시 시각·통화 길이·목록 위치가 보정될 수 있다. 새 통화 행으로 추가하지 않는다.
- 프론트는 응답의 시각을 사용한다. 현재 시각이나 `analysedAt`·녹취 `createdAt`으로 통화 시각을 추정하지 않는다. `endedAt: null`만으로 실제 통화 진행 중이라고 단정하지 않는다.

## 데이터 도착 순서별 표시

아래 단계는 새 서버 상태 코드가 아니라 화면 처리 기준이다. 도착 순서는 고정되어 있지 않다.

| 현재 응답 | 화면 처리 |
| --- | --- |
| 통화 존재, `analysis: null`, `recordings: []` | 통화 기본 정보를 표시한다. 결과는 기존 '분석 전' 표현을 사용하고 대화·동작은 받은 만큼 표시한다. |
| `analysis` 있음, `recordings: []` | 분석·대화·처리 내역을 표시한다. 녹취 미수신 안내와 함께 재생만 비활성화한다. |
| `analysis: null`, 녹취 `url` 있음 | 녹취 재생은 허용하고 분석은 미수신 상태로 둔다. |
| 분석·녹취 모두 있음 | 모든 수신 정보를 표시하고 이후 갱신에도 같은 통화 번호를 유지한다. |
| 녹취 항목의 `url: null`, `playbackError` 있음 | 녹취 오류만 표시한다. 통화·분석·대화를 오류 화면으로 바꾸지 않는다. |

빈 녹취 배열은 아직 연결된 녹취가 없다는 뜻이다. 업로드 중·업로드 실패·무음 통화로 확정하지 않는다. `analysis: null`을 접수 성공·불만 없음·되묻기 0으로 변환하지 않는다. 불만·결과 필터를 선택하면 분석 미수신 통화가 조건에서 빠질 수 있으며 이는 정상 필터 동작이다.

## 갱신·캐시 처리

1. 화면 진입 시 현재 데이터를 즉시 조회한다. 녹취 수신을 기다린 뒤 나머지 요청을 시작하지 않는다.
2. 열린 화면의 목록·상세를 주기적으로 재조회한다. 권장 주기는 5초이며 실제 주기는 프론트 요청량에 맞춰 정한다. 이는 서버 푸시가 아니므로 백엔드에 데이터가 저장된 뒤 다음 성공한 조회에서 반영된다.
3. 상세의 무기한 캐시와 검색 결과의 5분 재사용 정책이 새 데이터 반영을 막지 않도록 한다. 일반 목록과 검색 결과용 `pool` 경로를 모두 확인한다. 기존 페이지 크기·검색 상한과 안내는 유지한다.
4. 갱신 중 기존 행·대화·분석을 유지한다. 화면 전체를 다시 로딩 상태로 만들거나 검색어·필터·페이지·선택 통화를 초기화하지 않는다.
5. 같은 쿼리의 요청이 중첩되지 않게 기존 쿼리 관리 기능을 사용한다. 화면 이탈·숨김 탭에서는 정기 조회를 멈추고 복귀 시 다시 조회한다. 늦게 끝난 이전 통화 요청을 현재 통화에 적용하지 않는다.
6. 재조회 결과로 해당 영역을 교체하거나 ID 기준으로 병합한다. 통화는 `callSessionSeq`, 녹취는 `recordingSeq`, 발화는 `callUtteranceSeq`, 동작·처리 결과는 `eventId`를 사용해 같은 항목을 중복 추가하지 않는다. 목록 건수는 서버 `total_count`를 따른다.
7. 후속 조회 실패 시 이미 받은 데이터와 오류 상태를 함께 유지한다. 401은 기존 세션 만료 처리, 통화 상세 404는 통화 없음 처리로 연결하고 해당 상세의 반복 조회를 중단한다. 빈 성공 응답과 요청 실패를 구분한다.

상세·대화·동작·처리 결과는 이미 별도 API다. 현재 네 요청을 묶는 조회가 한 영역의 지연·실패 때문에 다른 수신 정보 표시까지 막는지도 확인한다.

## 녹취 URL과 오디오 유지

- 재조회마다 서명 URL 문자열이 달라질 수 있다. 같은 통화·같은 `recordingSeq`이고 기존 URL이 유효하면 재생 중인 `<audio src>`를 새 URL로 바꾸지 않는다.
- 현재 프론트 `Recording` 화면 모델은 녹취 번호를 보존하지 않는다. 같은 녹취를 판별하는 데 필요하면 DTO 변환에서 `recordingSeq`를 유지한다. 백엔드에 새 필드를 요구할 필요는 없다.
- URL 유효 기간은 최대 5분이며 더 짧을 수 있다. `expiresAt`은 만료 시각이다. 만료·재생 오류로 새 URL이 필요하면 상세를 재조회하고 기존 재생 위치·재생 여부를 복원한다. 통화나 녹취가 바뀌면 이전 파일의 재생 상태를 넘기지 않는다.
- 녹취가 먼저 도착했어도 늦은 분석·대화 수집을 계속 반영한다. 재생 URL 하나를 받았다는 이유로 모든 갱신이 끝났다고 판단하지 않는다.
- 실제 URL·대화·연락처를 콘솔이나 영구 캐시에 남기지 않는다. S3 403은 파일 없음으로 단정하지 않으며 `NOT_FOUND`와 `DEPENDENCY_UNAVAILABLE`의 기존 구분을 유지한다.

## 완료 조건

- [ ] PBX 시각·녹취가 없는 통화가 오늘 목록에 보이고 상세를 열 수 있다.
- [ ] 페이지를 새로 열지 않아도 새 통화·늦은 분석·발화·동작·처리 내역이 다음 갱신에 보인다.
- [ ] 녹취를 지연시켜도 텍스트·분석이 보이고, 나중에 같은 통화에 재생 기능이 붙는다.
- [ ] 녹취가 분석보다 먼저 도착해도 이후 분석이 반영된다.
- [ ] 반복 갱신 후 통화·발화·녹취가 중복되지 않고 기존 페이지·검색 조건을 유지한다.
- [ ] 녹취 재생 중 갱신해도 소리·위치가 초기화되지 않는다. URL 만료 후 재발급·위치 복구도 동작한다.
- [ ] 재조회 실패나 녹취 오류만으로 기존 통화 상세가 사라지지 않는다.
- [ ] 탭 숨김·화면 이탈 시 조회를 멈추고 복귀 시 최신 상태를 받는다.

## 백엔드 검증과 한계

기본 검사 134개와 관련 통합 테스트 89개가 통과했다. 격리 PostgreSQL과 모의 저장소에서 업로드 대기 중 통화 조회, 완료 후 같은 통화에 녹취 연결, PBX 시각 우선순위·조회 권한·기간 경계·총건수를 확인했다. 세부 기록은 [백엔드 작업 인계](../../backend/docs/recording-independent-calls.md)를 따른다.

프론트 구현·브라우저 동작·운영 배포·실제 통화·실제 S3 업로드는 아직 검증하지 않았다. 현재 AI의 분석·이벤트 전송은 통화 종료 후 이루어지므로 이 변경이 통화 중 실시간 STT를 새로 제공하지는 않는다. 백엔드가 수신하기 전의 데이터를 프론트가 갱신만으로 가져올 수는 없다.
