# MSA CI 실행 비용 및 #40 배포 실패 수정

Jira: [S15P31D109-160](https://ssafy.atlassian.net/browse/S15P31D109-160)

기준: `06ce863beaf44320111df3d609dc2b79a1bd5db0` / `fix/msa-ci-runtime` → `develop-backend`.
변경 범위는 `msa/`, `infra/`, `docs/`로 제한한다. frontend/AI/backend와 이후 API 계약은 변경하지 않는다.
최초 052 전체 동등성 검증 MR !364는 별도로 보존하며, 이번 변경이 전체 업무 동등성 완료를 의미하지 않는다.

## 관찰한 원인

[Jenkins #40](https://13.209.59.180/jenkins/job/dva-msa/40/console): 총 3,629.724초.
Jenkins 단계 기록은 DB 1,265.613초, operations 945.336초, customer 148.035초,
consultation 477.306초, order 517.216초, 앱 빌드/패키징 131.356초다.
검증 5개가 전체 시간의 약 92%이며, DB 로그에 Liquibase 기동 173회,
동등성 검증기에 Docker build 호출 31회가 기록됐다. 일부 Docker 캐시는 정상 재사용됐다.
실제 빌드용 Docker 제한은 CPU 1개/2GiB이며, agent는 CPU 0.5개/1GiB다.

#40은 모든 CI 검증을 통과했다. DB 배포에서 055가 요구하는 두 서비스 중지 조건을
자동 배포 경로가 준비하지 않아 종료했다. 보호 검사를 제거하거나 실패를 성공으로 바꾸지 않는다.

## 계획

1. 앱 배포 대상과 회귀 검증 대상을 분리한다. 검증 파일 변경은 필요한 검증을 실행하되
   정상 앱 전체 재배포로 연결하지 않는다. 잘못되거나 없는 비교 기준은 전체 검증한다.
2. 같은 실행의 checks/production/Liquibase 이미지를 한 번씩 빌드해 이미지 ID로 공유한다.
   검증기는 기존 독립 DB와 실패/복구 검사를 유지한다. 소스/이미지 불일치는 차단한다.
   앱 패키지는 검증한 production 이미지에 릴리스 태그를 붙여 만든다.
3. 서비스 Docker 의존성 설치 레이어에서 이벤트 검증 스크립트와 테스트를 분리한다.
   CPU 1개 조건으로 Liquibase JVM 기동 설정을 비교하고 실제 개선이 확인된 설정만 적용한다.
   기존 DB 검증 항목과 changeset/SQL은 유지한다.
4. 055가 실제 pending일 때 두 DB의 동일 정지 시점을 준비한다. 실행 중 업무/이벤트 확인,
   두 서비스 중지와 잔여 Pod 확인, 접근 제한된 두 DB 백업과 무결성 확인을 연결한다.
   DDL 전 준비 실패는 이전 복제 수를 복원한다. DDL 시작 뒤에는 구형 앱 자동 복원을 금지한다.
   기존 pending fingerprint, 호스트 키, 배포 잠금, 이미지 검증은 유지한다.
5. 선택 규칙/공유 이미지/전환 실패 회귀 → 실제 Linux/Docker DB·이벤트·동등성 검증 →
   패키징/배포 fixture 검증 → 결과 기록 → 작업 단위 커밋/새 MR 생성 순서로 진행한다.
   운영 클러스터를 이 작업 중 중지하거나 마이그레이션하지 않는다.

## 결과 기록 원칙

시간은 해당 실행 환경과 명령을 함께 기록한다. 로컬 개선을 Jenkins 실제 개선으로 단정하지 않는다.
실패·제외·미검증을 남기며, 필요한 검증이나 기대값을 삭제/완화해 시간을 줄이지 않는다.
