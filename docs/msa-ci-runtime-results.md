# MSA CI 비용 정리와 #40 실패 수정 검증

Jira: [S15P31D109-160](https://ssafy.atlassian.net/browse/S15P31D109-160)

## 확인한 실패와 수정

[Jenkins #40](https://13.209.59.180/jenkins/job/dva-msa/40/console)은 3,629.724초(60분 30초)에 실패했다.
컴파일·DB·서비스 회귀는 통과했으며, 실제 실패는 Database Delivery의 055 전환 준비 누락이었다.
055는 order/consultation 쓰기 중지·이벤트 처리 완료·백업을 요구하지만 기존 배포 경로가 이를 준비하지 않았다.
앱 배포가 건너뛰어졌으므로 미배포 변경은 다음 실행에서도 계속 대상이다. 성공 이력을 임의로 기록해 범위를 줄이지 않고 실패 경로를 고쳤다.

수정 후에는 모든 앱 이미지를 먼저 전송·검증하고, 모든 DB 미리보기와 pending fingerprint를 확보한다.
055가 pending이면 두 소유 DB와 호환 앱을 함께 선택한다. 5개 서비스 outbox, 진행 통화와 PBX 대기 작업을 확인하고
order/consultation 중지 및 종료 중 Pod 소멸을 기다린 뒤 두 DB를 같은 정지 시점에 백업한다.
서버의 0700 디렉터리에 0600 dump를 보관하고 목록·SHA-256을 검사한다. DB 적용 직전에도 정지·설정·백업·이벤트 상태를 재검사한다.
DDL 전 준비 실패는 원래 replica 수로 복구하며, 055 DDL 표식 이후에는 구형 앱 재개를 거부한다.
성공한 DB 적용 이력과 실제 앱 배포 이력은 CI 성공 이력과 구분한다.

새 설치에서 두 Deployment가 모두 없으면 실제 kubectl은 JSON 대신 빈 문자열을 반환했다.
이 응답을 재현한 기존 신규 설치 테스트가 수정 전 실패했고, 조회 공통 처리 수정 후 통과했다.
두 소유자 중 하나만 존재하는 경우의 중지·원래 replica 복구도 검사했다.

## 실행 비용 변경

- 기존 4개 서비스 회귀 검증의 이미지 빌드 호출 31회와 별도 앱 빌드를 공통 준비 단계로 모았다.
  전체 행렬은 checks 5개·production 5개·monolith 2개·Liquibase 1개의 13개 이미지다.
  각 검증과 패키징은 같은 실행의 이미지 ID를 재사용하며, 원본 commit·MSA tree·고정 backend tree·이미지 소유 표식이 다르면 실패한다.
- npm 설치 레이어에 이벤트 테스트 파일이 영향을 주지 않게 COPY 범위를 나눴다.
  다섯 서비스의 빌드·운영 설치는 기존 BuildKit의 npm 다운로드 캐시를 공유한다.
  배포 이미지에는 npm 캐시가 들어가지 않는다. 새 의존성이나 런타임 앱은 추가하지 않았다.
- 검증 대상과 배포 대상을 분리했다. 검증 전용 파일은 필요한 검증만 선택하고 앱 전체 재배포를 유발하지 않는다.
  런타임 공통 이벤트 변경은 기존 호출 의존성에 따라 확대하고, 알 수 없는 비교 기준·검증 도우미는 전체 검증한다.
- Liquibase CLI에 `JAVA_OPTS=-XX:TieredStopAtLevel=1`을 적용했다.
  실제 Jenkins Docker 환경(CPU 1개/메모리 2GiB)에서 각 명령을 CPU 1개/768MiB로 제한해 validate를 교차 실행한 기본값 3회는
  6.285/5.809/5.407초, 변경값은 3.622/3.720/3.536초였다. 모두 exit 0이며 validate가 성공했다.
  이는 CLI 기동 측정이며 전체 CI 시간의 동일 비율 개선을 뜻하지 않는다.

기존 changeset·SQL, 검증 기대값, 실패/복구·재적용·업그레이드 검사와 서비스 검사 명령은 유지했다.
CPU·메모리 제한과 Jenkins 보관 정책은 변경하지 않았다. 타 작업 이미지나 Docker 캐시를 전역 삭제하지 않는다.

## 검증 소스와 기준

전체 CI 수동 실행은 실제 Jenkins agent/dind의 격리 작업공간에서 수행했다.
1차 실행 소스는 `549f6c4c2a428ceb29aaee0af92cf92ad431b636`와 당시 대상 `9f6c72e303866ea6f00953a11c505db1007790c0`을 합친
`0625774524a76e822358b05375d82762ec513306`이다. 이 트리는 작업 브랜치 `1254fb55`와 동일하다.
전체 tree는 `f2de9b2ac42a6d772663bde74e18f577ed3a64eb`, MSA tree는 `0a96abe1c7586e2582ac617d2433c8a141cf85dc`다.

최종 빈 응답 수정 `78fa5730b67fc5af353689b2ac2969aa07a3db6f`의 MSA tree는 `e49d2327cf01f682ab3b0245eca8504e99be476a`다.
이 변경은 배포 전환 스크립트·회귀 테스트 두 파일뿐이며, 아래 Linux 회귀 전체와 실제 DB 복원 검증을 증분 재실행했다.
이후 대상 `f7f492c1`의 별도 backend/infra CI 변경을 정상 병합했고 MSA tree는 그대로다.
전체 실행 이후 services/shared/parity/liquibase/Jenkinsfile에 변경이 없음을 Git diff로 확인했다.

기존 055 CI 회귀의 기준은 baseline.json의 `9624b7789ee7876648b6c56b5e7a4a7a5a9ef378`이며,
backend tree `12c6fa0f17354f53b28244d8b804bd564f1141be`(공개 선언 104개·SQL 54개·워커 6개)다.
현재 소스에서 backend를 변경하지 않고 임시 Git 작업공간의 비교 원본만 고정한다.
이후 056/API 변경은 사용자 요청대로 이번 계약 이식에서 제외했다. 원래 기준 목록의 commit·해시·기대값을 바꾸지 않았다.

## 검증 결과

1차 전체 실행은 3,790.152초 후 order 동시 상세 취소에서 실패했다. 세 요청의 기대 응답은 모두 204였지만
204/500/500이 반환됐다. DB·operations·customer·consultation은 종료 코드 0과 성공 JSON을 확인했고,
실패한 order 결과와 정리 단계의 종료 코드 0을 그대로 보존했다.
같은 소스에 테스트 컨테이너 전용 PG 오류 추적을 넣은 order 전체 재실행은 377.319초/실행 기록 212개로 통과했다.
해당 동시 실패를 설명할 PG 대기 오류는 재현하지 못했다. 최초 요청 로그의 약 8~9초 처리 시간만으로 원인을 확정하지 않는다.

최종 검증 소스 `0b6e9f470915ee953695c16d9922990dac569d93`/MSA tree `e49d2327cf01f682ab3b0245eca8504e99be476a`에서
추적 코드 없이 전체 CI와 동시 취소 3회 추가 반복을 완료했다. 전체 2,241.995초(37분 22초), 모든 단계 exit 0이다.
이는 수동 CI·패키징 시간이며 공식 Job의 산출물 보관·운영 CD 시간은 포함하지 않는다.
캐시 조건과 공유 환경 부하를 통제하지 않았으므로 #40 또는 1차 실행 대비 전체 성능 개선율로 환산하지 않는다.

원본 실패 뒤 진단 실행·최종 추가 반복이 통과했어도 최초 500의 원인은 미확정이다.

이미지 manifest의 ID와 일치했다. DB 패키지의 prepare-cutover.py도 최종 소스와 바이트가 같았다.
보고서·원본 로그·패키지 SHA는 Git 제외 경로의 `current-final.tar.gz`와 `current-validated-summary.json`에 보존했다.
1차 실패·진단·전환 증분 결과는 `first-and-diagnostic.tar.gz`에 별도로 보존했다.

별도 확인:

- 최종 변경의 Linux 배포·범위 선택·이미지 공유·전환 회귀: 로컬 111개/31.073초, Jenkins agent 111개/27.987초, exit 0.
- 최종 변경의 실제 PostgreSQL 검증: 두 dump 복원 후 6개 테이블의 행 비교 일치, 백업 후 신규 이벤트 차단, exit 0/91.282초.
  DB 실행은 실제 Docker PostgreSQL이고, Kubernetes 중지·전개 상태는 fixture다.
- 다섯 서비스 최종 checks/production Docker 빌드 10개 모두 exit 0.
  운영 이미지 5개 각각에서 이벤트 모듈 6개를 로드했고 npm 캐시 파일은 0개였다.
- 이벤트 `verify.py`만 임시 수정한 customer checks 재빌드는 로컬 1.35초이며 npm 설치 레이어가 CACHED였다.
  임시 변경은 원래 바이트로 복구했고 Git diff가 없음을 확인했다. 이 시간은 Jenkins 전체 빌드 시간과 비교하지 않는다.
- 운영 k3s의 설정은 읽기 전용으로 확인했다. 다섯 DB의 host/port/식별자와 PostgreSQL 17.11 dump/restore 도구가 지원 범위였으며,
  없는 Deployment 0개/기존 1개/기존 2개의 실제 kubectl 응답 형태도 대조했다.

로그는 `msa/liquibase/verification-logs/ci-runtime/` 아래 Git 제외 경로에 보관한다.
전체 실행의 단계별 원본 로그·JSON은 Jenkins agent의 해당 격리 작업공간에 생성된다.

## 미검증과 남는 제약

- 공식 Jenkins Job 실행·산출물 보관 플러그인·운영 CD는 이번 수동 검증 범위가 아니다.
  운영 앱을 중지하거나 실제 055 DDL을 실행하지 않았다. 병합 후 실제 Job의 Database/Application Delivery 결과를 확인해야 한다.
- 1차 동시 상세 취소 500의 원인은 현재 미확정이다. 최종 반복 결과와 별개로 재발 가능성을 기록한다.
- 외부 AI outbox·유입 전환·새 계약 준비는 이 코드가 자동 확인할 수 없으며 기존 운영 협업 조건이 남는다.
  055 최초 전환에는 두 서비스의 쓰기 중지가 필요하고, DDL 시작 뒤 실패하면 호환 앱으로 복구해야 한다.
- 052 최초 기준의 전체 업무 동등성은 별도 [MR !364](https://lab.ssafy.com/s15-final/S15P31D109/-/merge_requests/364)의 진단 결과를 유지한다.
  누락 업무 API 23개와 DB/응답 차이가 남아 있으며, 이번 055 기존 회귀 성공은 전체 MSA 업무 동등성 완료를 뜻하지 않는다.
- 최초 빌드·소스 변경에 따른 캐시 미스는 여전히 발생한다. 전체 검증 시간은 고정된 1 CPU 조건과 필요한 DB 시나리오 수에 영향을 받는다.
  이번 실행 도중 `dva-ci-linux-validation #111`과 `dva-ai #104`의 완료 미기록·duration 0인 빌드 레코드도 관측했으며 빌더의 독점 사용은 통제하지 않았다.
  공식 #40의 전체 시간과 CD를 제외한 수동 실행 전체 시간을 동일 조건의 성능 비교로 취급하지 않는다.
