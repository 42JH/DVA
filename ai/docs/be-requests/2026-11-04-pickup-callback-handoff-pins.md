# AI → BE 요청: 수거 요청 시각 · 콜백 요청 · 상담원 연결 · 주소록 갱신

작성: AI 담당 · 2026-11-04 · 기준: `origin/develop-backend` `e5dc008`

AI 전화 접수 서버(리빌드)에 업무 규칙 몇 가지를 반영하려 합니다. 현재 BE 계약으로 안 되는 부분이 있어 변경·신설을 요청드리고, 계약을 확인하고 싶은 부분도 함께 적었습니다. 아래 "제안 형식"은 AI 쪽 초안이라, 실제 경로·필드·오류 코드는 BE에서 정해 주시면 그대로 따르겠습니다.

## 1. [변경 요청] 고객이 정한 수거 요청 시각 보존

**정하려는 업무 규칙**
- 기본 수거 시각은 통화 시각 + 1시간입니다. 수거는 09:00~17:00 안에서만 합니다.
- 통화 시각 + 1시간이 17:00을 넘으면 "금일 수거는 어렵고 익일 수거 가능"으로 안내하고, 기본값을 익일 09:00으로 둡니다.
- 고객이 원하면 영업시간 안에서 시각을 바꿀 수 있습니다. 범위는 오늘부터 3일 이내입니다(임시, 정책 미정).
- AI는 이 시각을 고객에게 되읽어 확인받은 뒤 `pickupRequestedAt`(ISO 8601, +09:00)으로 보냅니다.

**현재 BE 동작(충돌 지점)**
- `ai-integration-current.md:134`: "`pickupRequestedAt`은 호환 선택값, 실제 수거 시각은 BE가 결제 완료 + 1시간으로 확정"
- `order-payment-integration.md:12-13`: 결제 전에는 null, 결제 때 서버가 최종 결정
- `order-payments.repository.ts:103`: notPaid 저장 시 `pickup_requested_at = NULL`
- `order-payments.repository.ts:139`: 결제 시 `pickup_requested_at = paid.at + interval '1 hour'`

결과적으로 AI가 고객과 정한 시각을 보내도 결제 때 버려집니다. 고객에게 안내한 시각과 실제 수거 시각이 달라집니다.

**요청**
1. AI가 보낸 `pickupRequestedAt`이 있으면 결제 이후에도 유지하고, 디버 접수에 그 값을 써 주세요. 없을 때만 지금처럼 결제 완료 + 1시간으로 정하면 됩니다.
2. 결제가 늦어져 요청 시각이 "결제 완료 + 1시간"보다 이르게 되는 경우의 처리를 정해 주세요. 예: 결제 완료 + 1시간으로 미루기, 다음 영업 시각으로 미루기 등.
3. BE에서도 요청 시각을 검증할지 정해 주세요(영업시간, 최소 1시간 이후, 최대 일수). 검증한다면 오류 코드와 AI 쪽 처리 방식도 알려 주세요. AI는 같은 규칙으로 미리 걸러서 보낼 예정입니다.
4. 결제 안내 메시지와 결제 완료 안내의 수거 시각 문구를 정해 주세요. 지금은 "결제 완료 후 1시간 뒤"라는 상대 문구입니다. 요청 시각이 있을 때 이 문구를 어떻게 할지 결정이 필요합니다.
5. 월결제·부서 그룹결제처럼 결제가 바로 처리되는 경우에도 같은 규칙인지 확인 부탁드립니다.

## 2. [신설 요청] 상담원 콜백 요청 API

**업무 규칙:** 상담원 근무 시간이 아니라서 연결할 수 없으면 "성함과 연락처를 남겨 주시면 다음 영업일 오전에 먼저 연락드리겠습니다"로 안내하고 콜백 요청을 남깁니다.

**현재:** 콜백 API가 없습니다. `handoff_requests`는 047에서 삭제됐고, `calls.md:211-214`에 "상담원 연결 제어·콜백은 범위 밖"이라고 되어 있습니다. 지금 AI가 남길 수 있는 것은 분석의 `hasHandoffRequest`와 이벤트 `HANDOFF_REQUESTED`뿐입니다.

**요청:** 관리자 화면에서 확인·처리할 수 있는 콜백 요청 저장 API를 만들어 주세요.

**제안 형식(초안):**
```http
POST /api/ai/calls/{callSessionSeq}/callback-requests
Authorization: Bearer <AI_INSIGHTS_TOKEN>   # 또는 BE가 정한 인증
Idempotency-Key: <uuid>
```
```json
{
  "providerCallId": "live_...",
  "name": "홍길동",
  "phoneNumber": "01012345678",
  "reason": "OUT_OF_HOURS | COMPLAINT | REPEATED_UNANSWERED | CUSTOMER_REQUEST",
  "requestedAt": "2026-11-04T18:20:00+09:00"
}
```
- 응답으로 `callbackRequestSeq`를 받았으면 합니다. 같은 통화·같은 키를 다시 보내면 같은 결과가 오는 멱등 처리를 원합니다.
- 삭제·만료된 통화 처리(404/409)는 다른 AI 쓰기 API와 같은 규칙이면 됩니다.
- 처리 상태(대기·완료)와 관리자 조회는 BE·FE 범위로 정해 주세요.

## 3. [확인 요청] 상담원 연결(통화 전환)에 필요한 정보

**AI 쪽 구현 방식:** 고객 동의를 받은 뒤 OpenAI Live의 `sessions.refer(session_id, target_uri="sip:…")`로 상담원에게 통화를 넘깁니다. PBX 계약 `pbx-sip.md`의 "고객 동의 후에만"을 따릅니다.

**필요한 것**
1. 상담원 전환 대상 SIP URI입니다. BE가 아니라 PBX 담당이라면 담당자를 알려 주세요.
2. 상담원 근무 시간(요일·시각)의 출처입니다. BE 설정 API가 있는지, 없으면 AI 설정값으로 둬도 되는지 알려 주세요.
3. 연결 결과(성공·실패·시각) 기록이 필요한지 알려 주세요. `calls.md`에 "실제 상담원 연결 결과 수집은 후속 범위"로 되어 있어, 필요하면 계약을 정해 주셔야 합니다. 그 전까지 AI는 `hasHandoffRequest`와 `HANDOFF_REQUESTED`만 보냅니다.

## 4. [확인 요청] 접수 후 주소록 갱신

**업무 규칙:** 새 접수에서 출발지나 최근 도착지가 바뀌면, 접수 뒤 고객 정보와 주소록에 반영합니다.

**AI가 쓰려는 기존 API**
- 출발지(고객 기본 주소): `PATCH /api/customers/{id}`의 `address`(`customers.md:8-10`, AI 허용)
- 새 도착지: `POST /api/customers/{id}/pins`. 같은 주소로 409 `DUPLICATE_RESOURCE`가 오면 이미 있는 것으로 봅니다.
- 바뀐 도착지: `PATCH /api/pins/{id}`, `addressData`는 전체 교체

**호출 시점:** 주문 저장 응답(`status`가 저장 상태)을 받은 뒤, 통화와 별개로 백그라운드에서 호출합니다.

**확인 부탁드립니다**
1. 주문 저장 시 BE가 이미 고객 주소나 주소록을 자동으로 갱신하는지요. 그렇다면 AI는 호출하지 않겠습니다.
2. PIN의 "현재 통화 고객" 권한이 통화 중에만 유효한지, 통화가 끝난 뒤(결과 전송 직후)에도 쓸 수 있는지 알려 주세요.
3. 고객 기본 주소를 AI가 바꿔도 되는지, 업무상 확인해 주세요. FE의 보내는 분 수정 흐름(`order-sender-customer-save.md`)은 사용자 동의 뒤에만 고객 정보를 바꿉니다. AI는 통화 중 고객 동의를 받은 경우에만 바꾸는 것으로 하려 합니다.
