# S0c 결과 (2026-11-03): 트리거 대신 독립 Decision API

방법: S0·S0b 통화 로그 6건(고객 발화 57개)을 재생. 고객 발화마다 `POST /v1/decisions`(gpt-6-luna)를 1회, 입력은 "직전 AI 발화 + 고객 발화"만, 질문은 S0 입력 트리거와 같은 선택지(`confirm`, `task`). 스크립트 `replay.py`, 보고서 `logs/report.md`(전사 포함, 커밋 안 함).

## 정확도 (같은 발화, 트리거 마지막 결과 ↔ 독립)
독립이 더 맞은 경우(확인 질문이 아닌데 트리거가 yes):
- "더 보내실 택배가 있으신가요?" 뒤 "마우스 잡고" yes(0.79) → **not_answer(0.96)**, "드래그를…" yes(0.53) → **not_answer(0.97)**
- "연락처도 알려주실 수 있을까요?" 뒤 "네" yes(0.55) → **not_answer(0.97)**
- "맞으실까요?" → "예"(yes) 다음 "됐나요" yes(0.99) → **not_answer(0.85)**

둘 다 맞음: 확인 질문 뒤 "네, 맞습니다"·"예" = yes(0.89~0.99), "아뇨, 아뇨. 현승준이요" = change(트리거 0.69 → 독립 0.97).
독립이 약한 경우: "이름 현승준이요"(직전 AI "성함을 현승준님.")가 change(0.35) — 직전 AI 발화가 확인 질문이 아니라 애매.
용건(`task`): "여보세요"를 트리거는 order·lookup으로도 봤으나 독립은 일관되게 chit_chat, 성함 답을 order(0.79~0.99), "없어요, 끊어요" end(0.93).
→ 문맥을 통화 전체가 아니라 직전 AI 발화로 좁히면 S0의 U3 문제(확인 질문 없이 confirm=yes)가 사라진다.

## 발화 끝 감지
고객 전사 delta 수신 간격(전체 259개, 묶기 전 원자료)이 둘로 갈린다: **0.7초 이하 208개 / 0.8초 초과 51개, 0.7~0.8초 0개**. 1.0~2초 7개는 발화 중 쉼(예: "010" … "2083 5428이요").
→ 규칙: **마지막 delta 뒤 0.8초 동안 새 delta가 없으면 발화 끝** → 판정은 마지막 delta 뒤 약 1.05초에 나온다(Live 첫 응답 p50 0.93초와 비슷). 쉼으로 나뉜 발화는 각각 판정되며, 확인 답 판정에는 해가 없다(앞 조각은 not_answer).

## 판정
- 독립 Decision 호출로 바꾼다: 비용 1/27, 문맥 크기 일정, 확인 답 오판정 감소. 지연은 트리거보다 ~0.9초 늦지만 확인 답·용건 판정은 고객이 듣는 응답을 막지 않는다(Live가 바로 답하고 서버는 뒤에서 확정).
- 출력 트리거는 쓰지 않는다(S0·S0b에서 안전장치로 실패, 비용의 3/4).

## 확인하지 않은 것
- 실통화에서 0.8초 규칙(재생은 서버 수신 시각 기준이라 같지만, 동시 통화 부하에서 delta 간격이 늘 수 있다 → S7).
- 웜 상태 유지: 통화가 뜸할 때 연결이 식으면 첫 호출이 다시 느릴 수 있다(공유 AsyncOpenAI 1개, 필요하면 주기적 호출).
- 57개 발화는 표본이 작다. 정답 라벨은 사람이 보고 판단했다(자동 채점 없음).
