# AI 전달: 유효 상담 통화 등록과 PBX 수신 데이터 30분 보관

## 합의한 동작

AI는 실제 상담 업무 의도를 확인한 뒤 통화를 등록한다. 장난전화·무응답·업무와 무관한 전화는 통화 등록과 업무 결과 전송을 생략한다. 백엔드는 대화 내용을 다시 판정하지 않는다.

첫 고객 확인과 유효 통화 등록은 기존 `POST /api/customers/context`를 두 번 사용하는 방식이다. endpoint·요청 필드를 추가하지 않는다. `call` 없이 조회하는 기존 동작을 사용하며, `call`이 있는 요청은 AI가 업무 의도를 확인했다는 계약으로 처리한다.

## 1. 전화 수신 직후: 조회만

최초 수신 이벤트의 `providerCallId`와 `incomingAt`은 AI가 보관한다. 이때 백엔드에는 전화번호만 보낸다.

```http
POST /api/customers/context
Content-Type: application/json
```

```json
{
  "phoneNumber": "01012345678"
}
```

등록 상태·고객 정보·소속·개인 PIN을 기존대로 조회한다. 응답에는 `callSessionSeq`가 없으며 고객·통화·주문·감사·NO_ORDER 수신 이력을 생성하지 않는다. 기존 고객도 동일하다. 요청 로그의 경로·요청 ID는 기존대로 남으며 전화번호·본문은 기록하지 않는다.

무의미 통화로 끝나면 여기서 종료한다. 다음 단계와 주문·분석·이벤트·미답변 수집 같은 쓰기 API를 호출하지 않는다. 통화를 만들지 않기 위해 빈 주문이나 NO_ORDER 결과를 대신 보내지 않는다.

## 2. 업무 의도 확인 후: 같은 API로 통화 등록

택배 접수·취소·접수 내역 조회·FAQ 문의·상담원 연결 요구 등 실제 상담 업무 의도가 확인되면 `call`을 추가한다. 업무를 끝내거나 주문을 생성할 때까지 등록을 미룰 필요는 없다. FAQ·조회·연결 요구·미답변만 있는 통화도 보존 대상이다.

```json
{
  "phoneNumber": "01012345678",
  "call": {
    "providerCallId": "rtc_original_session_id",
    "incomingAt": "2026-11-02T10:00:00+09:00"
  }
}
```

응답의 `data.callSessionSeq`를 이후 주문 조회·취소·PIN API의 `call_session_seq` 헤더와 통화 분석·이벤트·미답변 API에 사용한다. 최종 주문 결과의 통화 정보도 같은 식별자를 사용한다. 같은 통화 ID·전화번호·수신 시각의 재호출은 통화·CALL_STARTED 감사를 중복 생성하지 않는다.

**`providerCallId`와 `incomingAt`은 최초 전화 수신 이벤트 값으로 고정한다.** 등록 시각이나 현재 시각으로 바꾸면 안 된다. PBX 매칭은 발신번호와 최초 수신 시각을 PBX 시작 시각과 비교하므로, 기본 ±30초 범위를 벗어나면 연결하지 않는다. 이는 아래의 수신 데이터 보관 30분과 다른 기준이다.

기존 인증·고객 상태·전화번호·시각 검증은 유지한다. 다른 번호나 시각으로 같은 통화 ID를 재사용하면 기존대로 409다. 별도의 isMeaningful 필드를 추가하지 않으므로 이 두 단계 호출 순서는 AI 팀에서 반영해야 한다.

## 3. PBX 종료 웹훅: 수신 후 30분 유예

실시간 통화 수 기능(044 migration 이후)은 등록된 통화의 종료를 웹훅 수신 시 바로 반영한다. 웹훅이 먼저 도착했다면 통화 등록 시 대기 수신과 매칭한다. 녹취 다운로드·S3 업로드는 기존 비동기 워커에서 수행하며 종료 저장을 업로드 성공까지 기다리지 않는다. 매칭 장애로 수신만 영속화한 경우 워커가 복구한다. [조회·SSE·전환 계약](active-call-count.md)을 함께 따른다.

PBX 종료 웹훅은 AI의 최종 결과와 별도로 도착한다. 백엔드는 기존 인증·검증·DB 저장 후 200 응답을 유지한다. 수신함은 일시 보관 장소이며, AI 통화가 없다는 이유만으로 즉시 버리지 않는다.

워커는 수신 건별로 통화 연결을 먼저 시도한다. 계속 연결되지 않은 수신은 **백엔드의 `received_at`부터 30분 경과 후 처리 주기에 삭제**하고 재시도를 끝낸다. 전화 시작·종료 시각이나 AI 요청 시각부터 세는 시간이 아니다. 정상 지연과 판단할 수 없는 수신을 구분하기 위한 보관 정책이며, 삭제 자체가 장난전화 판정은 아니다.

| 상태 | 처리 |
| --- | --- |
| 통화 미등록·연결 불가, 수신 후 30분 미만 | 임시 보관하며 기존 매칭 재시도 |
| 연결을 다시 시도해도 미연결, 수신 후 30분 경과 | 수신 행·전화번호·녹취 다운로드 URL을 삭제. 통화·감사·녹취·S3 객체를 만들지 않음 |
| 유효 통화 연결 성공 | 기존대로 S3 저장 후 recordings 연결. 주문·분석 유무는 조건으로 사용하지 않음 |
| 연결된 유효 통화의 S3·DB 저장 실패 | 30분이 지나도 보존하고 재시도 |
| S3 미설정 | 미연결 수신 정리는 계속 실행. 연결된 통화는 업로드를 기다리며 보존 |
| 다른 워커의 유효한 처리권이 있음 | 그 처리권을 빼앗거나 수신을 삭제하지 않음 |

기존 10초 처리 주기·한 번에 최대 5건·5분 처리권을 사용한다. 만료된 미연결 수신을 먼저 처리하며 DB 장애·서버 중지·대량 대기 중에는 정리가 늦어질 수 있다. 연결된 수신과 PROCESSED는 삭제 대상이 아니다. 변경 전의 오래된 미연결 수신도 새 워커가 실행되면 같은 기준으로 정리된다. 30분 정리 정책 자체는 테이블·컬럼·migration을 추가하지 않는다. 실시간 통화 수의 등록 시각 추가는 별도 044 migration을 따른다.

AI는 정상 통화 등록이 PBX 수신 후 30분을 넘기지 않도록 해야 한다. 이미 수신이 삭제된 뒤 등록하면 과거 녹취를 연결할 근거가 없어질 수 있다. 삭제한 recordingId의 웹훅이 다시 도착하면 새로운 임시 수신으로 저장될 수 있으며, 영구적인 제외 목록은 저장하지 않는다. 보관 중인 수신의 동일 재전송·충돌 응답은 기존대로다.

## 4. NO_ORDER와 기존 통화 보존

NO_ORDER의 입력 검증·생성 방지·재전송 처리는 그대로 유지한다. 유효 상담에서 주문 정보가 전혀 없고 기존 조건에 맞는 결과가 오면 주문을 만들지 않고 통화와 결과 식별자를 보존한다. NO_ORDER는 무의미 통화를 버리는 신호가 아니다.

이 변경은 기존 `call_sessions`·통화 분석·감사·녹취를 자동 삭제하지 않는다. AI가 업무 의도 확인 전에 통화를 등록하면 백엔드는 그 통화를 유효 상담으로 취급한다. 등록 후 AI 결과가 없다는 사실만으로 장난전화와 통신 장애를 구분할 수 없으므로 통화를 자동으로 지우지 않는다.

PBX에서 AI로 전달하는 통화 종료 알림은 유지해야 한다. nginx의 종료 웹훅 미러·AI 코드·운영 서버 설정은 이번 backend 폴더 작업에서 수정하지 않는다. 이 문서는 AI 팀 전달용이며 실제 AI 호출 순서 반영과 양 서버 연결 검증은 별도다.
