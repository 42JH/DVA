# AI 담당자용 FAQ 변경 알림·원본 조회 연동 규격

백엔드 구현 범위는 관리자 FAQ 쓰기, 변경 알림 저장·전송, 원본 조회다. 이 문서의 AI 수신 API와 검색 데이터 반영은 AI 담당자가 구현한다. `ai/` 코드는 수정하지 않았다. 관리자 API는 [FAQ 명세](faqs.md)를 따른다.

## 연결 설정

| 항목 | 값 |
| --- | --- |
| 백엔드 → AI | `POST {AI_AGENT_URL}/internal/faqs/refresh` |
| AI → 백엔드 | `GET {BACKEND_URL}/api/ai/faqs` |
| 알림 인증 | `Authorization: Bearer <AI_FAQ_TOKEN>` |
| 알림 토큰 | 백엔드·AI가 공유하는 32자 이상 공백 없는 ASCII 토큰. 실제 값은 비밀 설정으로 전달 |
| 백엔드 알림 타임아웃 | 2초 |

`AI_FAQ_TOKEN`이 비어 있으면 FAQ 변경과 알림 대기는 저장하고 전송만 중단한다. 설정 후 백엔드를 재시작하면 대기를 처리한다. 기존 `AI_PERSONA_TOKEN`과 별개다. AI의 백엔드 FAQ 조회는 기존 MVP 합의에 따라 서비스 인증·통화 헤더를 요구하지 않는다. 관리자 쿠키를 함께 보내면 정상 세션 검사를 받으므로 AI 요청에는 쿠키를 넣지 않는다.

## AI가 구현할 수신 API

```http
POST /internal/faqs/refresh
Authorization: Bearer <AI_FAQ_TOKEN>
Content-Type: application/json
```

```json
{
  "eventId": "f5af1894-3e32-4c75-a2c5-768ea9e48593",
  "operation": "INSERT",
  "faqEntrySeqs": [123, 124]
}
```

| 필드 | 규칙 |
| --- | --- |
| `eventId` | UUID. 같은 변경을 다시 전송할 때 유지되는 중복 제거 키 |
| `operation` | `INSERT`, `UPDATE`, `DELETE` 중 하나 |
| `faqEntrySeqs` | 양의 정수 번호 배열. INSERT·DELETE는 1~100개, UPDATE는 반드시 1개 |

단건 추가·삭제도 같은 배열 형식이다. 알림은 변경 종류와 대상 번호를 식별하며 질문·답변, 관리자 정보, 변경 전후 본문은 보내지 않는다.

AI는 인증과 본문을 검증한 후 이벤트를 **재시작해도 유실되지 않게 보관한 뒤 202**를 반환한다. 동일 `eventId`를 다시 받으면 중복 작업을 만들지 않고 202를 반환한다. 200·204를 포함한 다른 응답은 백엔드가 성공으로 인정하지 않는다. 응답 본문은 사용하지 않는다.

202는 알림 수신 확인이며 임베딩·검색 인덱스 반영 완료가 아니다. 수신 후 색인 작업이 실패하면 AI 내부에서 해당 이벤트를 재시도해야 한다. 이번 계약에 색인 완료 회신 API는 없다.

## 추가·수정 시 원본 조회

알림에 받은 번호를 모두 지정하고 `limit=100`, `offset=0`으로 조회한다. 변경 알림 처리에는 `q` 검색 조건을 넣지 않는다.

```http
GET /api/ai/faqs?faqEntrySeqs=123,124&limit=100&offset=0
```

```json
{
  "data": [
    {
      "faqEntrySeq": 123,
      "question": "깨지기 쉬운 물건은 어떻게 포장하나요?",
      "answer": "각 물품을 완충재로 감싸 주세요.",
      "updatedAt": "2026-10-30T01:00:00.000Z"
    },
    {
      "faqEntrySeq": 124,
      "question": "접수는 어떻게 하나요?",
      "answer": "전화 상담으로 요청해 주세요.",
      "updatedAt": "2026-10-30T01:00:00.000Z"
    }
  ],
  "hasNext": false,
  "total_count": 2
}
```

- 응답 목록은 `faqEntrySeq` 오름차순이다. 날짜는 UTC ISO 8601 문자열이며 관리자 식별자는 없다.
- `faqEntrySeqs`는 중복 없는 번호 1~100개를 쉼표로 구분한다. 빈 값·중복·잘못된 번호는 400이다.
- 한 요청에서 번호를 100개 이하로 지정하고 `limit=100`이면 한 응답으로 받는다. 더 작은 limit을 사용하면 `hasNext=false`까지 offset을 증가시켜 모두 읽는다.
- 응답은 이벤트 발생 당시 복사본이 아니라 **조회 시 커밋된 최신 원본**이다. 이미 후속 수정이 끝났다면 더 최신 답변이 반환될 수 있다.
- INSERT·UPDATE 알림 후 FAQ가 삭제됐으면 해당 번호는 응답에서 빠진다. AI는 조회한 전체 결과를 기준으로 해당 번호들을 갱신하고, 요청했지만 응답에 없는 번호는 검색 데이터에서 제거한다. 빈 목록도 정상 200이다.
- 상세 조회는 기존 `GET /api/ai/faqs/{id}`이며, 없는 번호는 404다.

전체 원본이 필요하면 번호 필터를 생략해 `GET /api/ai/faqs?limit=100&offset=0`부터 `hasNext=false`까지 순회한다. 기존 목록 API는 여러 페이지 전체를 하나의 고정 시점으로 보장하지 않는다. 전체 동기화 도중 동시 변경의 일관된 스냅샷이 필요하면 별도 계약이 필요하다.

## 삭제 반영과 순서

DELETE 알림의 `faqEntrySeqs`에 해당하는 검색 데이터·벡터를 제거한다. 이미 제거된 번호를 다시 제거해도 성공으로 처리한다. 삭제 원본은 조회할 수 없으며 삭제 번호는 백엔드 알림 대기에 보존된다.

AI는 수신 이벤트를 순서대로 처리하고, 같은 FAQ에 대한 조회·색인·삭제 작업을 병렬로 뒤집어 적용하지 않는다. 가장 단순한 구현은 영속 수신 큐를 직렬로 처리하는 방식이다. 수정·삭제의 완료 순서가 뒤집히면 삭제된 FAQ가 검색 데이터에 다시 나타날 수 있다.

## 백엔드 트랜잭션과 재시도

```text
관리자 요청 / 초기 FAQ 등록 명령
 → FAQ 원본 + FAQ별 운영자 감사 + 알림 대기 저장
 → 같은 DB 트랜잭션 커밋
 → 워커가 대기 점유 + SYSTEM 감사 저장 후 커밋
 → DB 트랜잭션 밖에서 AI HTTP 호출
 → 수신 성공 또는 재시도 시각 + SYSTEM 감사 저장
```

실패 시 FAQ 쓰기를 되돌리지 않고 알림을 남긴다. 워커는 시작 시와 5초마다 가장 오래된 미전송 알림 하나를 처리한다. 재시도 간격은 5·10·20·40·80·160·300초이며 실제 실행은 워커 주기에 맞춰진다. 최대 간격 이후에도 재시도한다. 인증 오류·400·5xx·리다이렉트·연결 오류·시간 초과가 모두 재시도 대상이다.

후속 알림은 선행 미전송 알림을 추월하지 않는다. 수신 API 또는 인증 오류가 지속되면 후속 변경 반영도 지연된다. 먼저 설정·수신 장애를 복구해야 한다.

점유는 30초 후 만료된다. 프로세스 종료나 수신 확인 저장 실패로 같은 이벤트가 다시 올 수 있으므로 AI의 영속 중복 제거가 필요하다. 오래된 점유자는 새 점유자의 결과를 덮어쓰지 못한다. 전달은 최소 한 번 방식이며 정확히 한 번 실행을 보장하지 않는다.

현재 32건 초기 등록은 INSERT 알림 하나를 만든다. 이미 FAQ가 있어 초기 등록을 건너뛰면 알림을 추가하지 않는다. 기존 PostgreSQL `faq_changed` 신호는 남지만, 본 HTTP 계약의 이벤트·재시도 보장을 대신하지 않는다. DB 직접 SQL 편집은 HTTP 알림 대기를 만들지 않는다.

## 배포·확인 범위

1. 기존 데이터 백업과 팀 배포 절차에 따라 `020-faq-change-notifications.sql`을 적용한다. 기존 migration 파일은 수정하지 않는다.
2. AI 담당자가 위 수신 API·영속 중복 제거·순차 색인 처리를 구현한다.
3. 백엔드의 `AI_AGENT_URL`, `AI_FAQ_TOKEN`과 AI 수신 토큰을 맞춘 후 백엔드를 재시작한다.
4. 관리자 추가·수정·단건/복수 삭제 후 원본 조회, AI 수신 202, 검색 반영을 함께 확인한다.

백엔드 테스트는 임시 PostgreSQL과 모의 AI HTTP 서버를 사용한다. 실제 AI 서버·검색 인덱스·운영 DB에는 적용하지 않는다. 운영 확인에는 실제 수신 API와 AI 반영 검증이 별도로 필요하다.


모든 목록 응답의 최상위 total_count는 필수인 0 이상 정수이며 같은 검색·필터·권한 범위의 전체 결과 수다. limit·offset 적용 전 COUNT(*)를 목록 데이터와 같은 SQL 스냅샷에서 계산한다. 검색 결과 없음은 0이며 offset이 전체 건수를 넘어 data가 비어도 total_count는 유지한다. 기존 hasNext는 유지한다.
