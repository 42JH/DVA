## 결론

**Live의 빠른 입력 안내와 서버의 동일 규칙 재검증을 함께 적용한다.** 백엔드 코드만 바꾸면 거절 결과를 기다리는 구조는 그대로다. 프롬프트만 바꾸면 모델의 실수로 잘못된 값이 저장될 수 있다. 업무 전환·최종 확인 누락은 별도 코드 수정이 필요하다. 큰 재설계 없이 아래 순서로 고칠 수 있다.

현재 ‘백엔드’는 구분해야 한다. Responses Backend LLM은 음성에서 값을 추출해 도구 인자를 만들고, 실제 주문 BE는 외부 서비스에서 주문을 저장·조회·취소한다. 대화 중 입력 검사는 주로 **AI 서버의 RecordArgs·record_fields·domain/rules.py·domain/pickup.py**에서 한다. 실제 주문 BE 호출 외에 Live → Responses 위임 → 도구 검증 → 위임 재개에서도 대기가 생긴다.

`service.py:132-140`은 Live에 도구 이름·설명만 주고 상세 인자 스키마는 Responses에 준다. `render.py:40-54`는 값을 말하면 위임하고 결과 전에는 판단·다음 질문을 하지 말라고 한다. 스키마 숫자만 바꿔도 Live가 직접 그 제한을 아는 것은 아니다.

비유하면 Live는 창구 직원이고 서버 검사는 계산대 검사다. 직원에게 제한을 알려 주면 2억 원이라는 말을 듣자마자 설명할 수 있다. 그래도 실제 저장 직전 검사는 필요하다.

## 3. 추가로 확인한 문제

### 기본 수거 시각의 올림 결함

`pickup.py:32-35`는 now+1시간 후 초를 0으로 버리고 분이 10의 배수가 아닐 때만 올린다. 현재 **10:00:30 → 기본 11:00:00 → 준비 시간 3,570초**가 된다. 같은 값을 check_pickup에 넣으면 `PICKUP_TOO_SOON`이다. 분·초를 포함해 온전히 올림해야 한다. 상대 시각 프롬프트 노후화와 별개 결함이다.

### 현재 지시문 내부 충돌

- business_rules.md:100은 가액 초과에 처리 불가로 응대하도록 한다. 허용 범위를 설명하고 다시 입력받는 요구에 맞춰야 한다.
- 같은 파일 101은 무관한 요청 지속 시 상담 종료를 지시하지만 87-88과 TOML은 Live가 스스로 끝내지 말고 서버 closing을 기다리라고 한다. 종료 조건과 실행 주체를 구분해야 한다.
- 78·88의 ‘그 말을 맡긴다’는 Responses 위임으로 읽힐 수 있다. 실제 상담원·종료 판정은 Decision 경로이므로 역할을 명확히 해야 한다.
- 92는 서비스·이용 시간 질문을 직접 답하지 말고 RAG에 맡기라고 한다. 새 정책에서는 **현재 주문 입력의 고정 제한은 즉시 설명**, 일반 지식 검색은 근거를 받아 응답하도록 예외 범위를 명시해야 한다.

### 선검증만으로 모든 대기를 없애지는 못한다

기본 발화 끝 대기 800ms, Decision 예산 1초, 확인 뒤 확정 지연 700ms, N2 발화 정지 대기, 위임 완료 누락 시 3초 재개 대체 경로가 있다(config.py:113-125, live.py의 resume·notify·_wait_quiet). 경로가 병렬이므로 항상 단순 합산되지는 않는다. Live 선검증은 **명백한 잘못된 입력의 재질문**을 앞당긴다. 정상 입력·주소 검색·확정 대기까지 전부 없애지는 않는다. 절감 시간은 실측 전 단정하지 않는다.

## 4. 권장 순서

1. **규칙을 한곳에 모으기:** 기존 Policy에 가액·수량 제한을 두고 서버 검사·도구 스키마·Live·Responses 안내에 같은 값을 사용한다. 현재 수거는 TOML, 가액·수량은 RecordArgs에 나뉘어 있다. 구조 전체 교체는 필요 없다.
2. **Live에 명백한 오류 즉시 재질문 허용:** ‘물품 가액은 1원부터 9,999만 9,999원까지 가능합니다. 물품 가격을 다시 알려주시겠어요?’와 같이 응대. 정상 값은 기존 경로로 기록·재검증한다. 입력 형식이 맞다는 것과 저장 성공은 구분한다.
3. **복합 발화·늦은 결과 검토:** 주소와 잘못된 가격을 한꺼번에 말하면 정상 주소까지 버리지 않는다. 애매한 숫자를 추측해 보정하지 않는다. 진행 중인 이전 호출의 늦은 결과가 최신 정정 안내를 덮지 않는지 확인한다.
4. **오류 결과·중복 지시문 정리:** status·code·needs 우선 해석, 범위 초과 문구, 상세주소, 종료·위임 표현. 운영 ACTIVE 페르소나 확인도 필요하다.
5. **흐름 수정:** 모든 단계의 종료·전환과 order 복귀 → PIN·자동 채움 뒤 확인 준비 → 취소 재확인 분리 → more 연결 → 수거 시간 경계·최신 시각 처리.

고객 동의·후보 선택·업무 전환을 전부 Live로 옮기는 일은 프롬프트 보강보다 큰 변경이다. 현재 Decision·확정 관문과 역할이 겹치면 두 판단이 다른 순서로 도착할 수 있다. 우선 **Live는 즉시 이해·설명·재질문, 서버는 저장 상태·동의 반영·실행 확정**을 담당하도록 권장한다. 실측에서 Decision이 주요 병목으로 남으면 판단 소유권 변경을 별도 설계한다.

## 6. 후속 분석: 첫 인사 뒤 개인정보 변경 문의가 검색되지 않는 이유

### ‘규칙을 한곳에’의 뜻

가액 최소 1·최대 99,999,999, 박스 합계 최대 10, 서류 최대 100을 정책 설정에 한 번 정의하고 다음 세 곳이 그 값을 가져다 쓰자는 의미다.

1. Live 프롬프트의 허용 범위 설명.
2. Responses 도구 인자 스키마 및 안내.
3. 서버의 실제 입력 검사.

같은 숫자를 세 파일에 따로 적으면 한 파일만 바꿨을 때 서로 다른 규칙이 된다. 같은 기준표에서 세 장을 출력하는 방식이다. 모든 대화와 FAQ를 한 파일에 합친다는 의미는 아니다. FAQ의 일반 안내와 전화 접수 채널의 실행 가능한 기능도 구별해야 한다.

### 확인한 사실

- 로컬 FAQ 원본 `ai/data/private/dver_web_faq/records.json`에 ‘회원 정보 변경은 어떻게 하나요?’가 있다. 내용은 마이페이지에서 비밀번호·이름·연락처·사업자정보 등을 변경하는 방법이다. 이는 **웹 회원정보 안내**이며 AI 전화로 고객 이름·기본 주소를 즉시 바꿔 준다는 근거는 아니다.
- 로컬 원본에 있는 것과 **운영 관리 FAQ 색인에 들어 있는 것**은 다르다. main.py:55-87은 설정에 따라 관리 FAQ 색인 또는 기존 매뉴얼 색인을 사용한다. 관리 경로에서는 로컬 records.json을 자동으로 모두 읽지 않는다. 운영 색인 포함 여부는 이번에 확인하지 않았다.
- Live 검색 지시 business_rules.md:91-97과 search_manual 도구 설명은 서비스·포장·요금·배송·취소 위주다. 회원정보·기본 이름·기본 주소 변경 문의를 명시적으로 구분하는 문구가 없다. 검색을 금지한 코드는 없지만 다른 흐름으로 해석될 여지가 있다.
- business_rules.md:15는 ‘이름이 틀렸어요’이면 무엇으로 고칠지 **직접 묻도록** 한다. 같은 파일 8·13·17은 등록 고객 접수 제안 및 missing으로 복귀를 강조한다. ‘개인정보 변경이 가능한가요?’를 이번 택배의 정정 요청으로 이해하면 검색 없이 이름을 다시 묻거나 접수 질문으로 돌아갈 수 있다.
- workflow.toml의 intent·origin 질문에는 회원정보 안내 문의와 이번 배송 출발지 정정의 차이에 대한 예가 없다. ‘출발지가 다르지만 택배를 보내려 하면 order’라는 지시는 있다. 사용자가 보내려는 의도를 밝히지 않았는데도 이를 적용하면 오분류가 된다. 실제 모델이 그렇게 판단했는지는 통화 로그가 필요하다.
- **inquiry로 분류되어도 검색이 자동 실행되지는 않는다.** live.py의 _on_intent는 상태·알림을 처리할 뿐 search_manual을 호출하지 않는다. Live가 별도로 위임하고 Responses가 도구를 골라야 검색한다. 따라서 Decision 분류가 맞아도 검색이 생략될 수 있다.
- 모델에 제공하는 도구에는 회원정보 수정 도구가 없다. record_fields의 sender_name은 이번 택배 값이다. 현재 AI client에는 고객 이름 수정 함수가 없고 update_customer_address만 있다(api.py:280-286). 기본 주소 갱신도 택배를 담은 뒤 주소 저장 제안·동의 경로에서 실행한다(address_book.py:15-29, live.py:_maybe_save_addresses, results.py:133-154). **배송 없이 고객 이름·기본 주소만 바꾸는 독립 흐름은 구현되어 있지 않다.** BE 계약 customers.md의 이름·주소 PATCH 가능 여부와 AI가 그 기능을 연결했는지는 별개다.

### 원인 판단

고객 설명대로 search_manual 호출 자체가 없었다면, 우선 의심할 곳은 검색 품질보다 **질문 이해·검색 위임 단계**다. ‘변경 방법/가능 여부 문의’, ‘이번 택배의 정보 정정’, ‘저장된 회원정보 실제 변경’을 구분하지 않아 접수·정정 흐름으로 빠질 가능성이 높다. 동시에 실제 변경 기능의 부재도 대화가 자연스럽게 이어지지 않는 구조적 원인이다. 개인정보라는 단어를 차단하는 특별한 분기는 현재 살펴본 경로에 없다.

최종 원인을 특정하려면 해당 통화의 고객 전사 → Decision task/origin/switch → delegation 생성 여부 → 도구 이름·인자·결과를 순서대로 확인해야 한다. search_manual이 있었다면 다음으로 운영 색인 포함 여부, 검색 질문 보존 여부, 결과 근거를 확인한다. 이번 분석은 실제 통화 로그·운영 색인·모델 재현 없이 코드와 로컬 FAQ 원본을 대조한 결과다.

### 작은 개선 방향

1. ‘개인정보 변경 가능한가요?’, ‘등록된 이름을 바꾸는 방법이 있나요?’는 **방법/가능 여부 질문**으로 검색하도록 Live·Responses·Decision 설명을 맞춘다. 접수 의도가 없으면 접수 누락 항목을 묻지 않는다.
2. ‘이번 택배는 다른 주소에서 보내요’는 이번 배송 정보 정정, ‘앞으로 기본 주소도 바꿔 주세요’는 저장 정보 변경으로 구분한다. 애매할 때는 이번 배송용인지 저장된 기본정보인지 한 번 묻는다.
3. 검색된 웹 FAQ로 안내할 때 웹의 마이페이지 방법을 전화 변경 기능으로 확대 해석하지 않는다. FAQ에 있는 안내와 실제 전화 기능의 범위를 같이 전달한다.
4. 배송 없이 고객 정보만 수정하는 기능은 안내 수정과 별도 구현 과제다. 기존 record_fields에 새 값을 넣는 것만으로 고객 원장이 수정되었다고 말하면 안 된다.

서비스 코드·운영 프롬프트 변경이나 모델 API 실험은 하지 않았다. 후속 확인 질문 예시는 익명 가상 발화이며 실제 고객 로그를 문서에 복사하지 않았다.
