# Decision 입력·지침 개편 계획

상태: 2~4단계 구현·재생 검증 완료, 배포 전(2026-11-11, 결과는 §8) · 계획 기준 코드: develop-ai `87996ab4`, 구현 기준: `45e8ed4f` · 관련: `delegation.md` §3(Decision), `server-turn-pipeline-plan.md`(v4 구조 전환, 이 계획은 그 1단계를 구체화한 것)

## 0. 요약
- Decision 오판과 "네"를 못 알아듣는 문제의 주원인은 하한 값이 아니라 **입력에 담긴 정보**다. 지금 입력은 직전 AI 발화 한 조각과 고객 발화 한 조각뿐이고, 서버가 어떤 질문의 답을 기다리는지는 들어가지 않는다.
- 운영 발화 재생에서 "열린 질문" 한 줄을 넣자 출발지 "네"가 0.53에서 0.98로, 잘린 되읽기 "네"의 끝내기 판정이 0.64에서 0.40으로 바뀌었다(§2).
- 이 계획은 구조(Live·Backend·Decision의 역할)를 바꾸지 않는다. 지금 통화 흐름 안에서 바꾼다.
  1. 입력에 서버가 기다리는 질문(열린 질문)을 넣는다.
  2. 직전 AI 발화의 범위를 "마지막 고객 발화 이후 AI가 한 말 전체"로 넓힌다. 끊어진 고객 발화도 이어 붙인다.
  3. 지침을 열린 질문 기준으로 다시 쓴다. Live의 특정 문장에 기댄 규칙을 없앤다.
  4. 하한을 확률 기준으로 바꾸고 판정 종류별로 나눈다. 판정이 갈리면 같은 질문을 반복하지 않고 선택지를 풀어 한 번 다시 묻는다.
- 바꾸기 전에 운영 발화 재생으로 질문 종류별 정확도를 재고, 바꾼 뒤 같은 재생으로 비교해 배포한다.

## 1. 지금 동작

### 1.1 입력
`app/calls/live.py` `judge`가 만드는 입력은 두 줄이다.
```
직전 AI 발화: {prev.text}
고객 발화: {utt.text}
```
- `prev`(`_customer_done`): 고객 발화 시작 전에 시작한 마지막 AI 발화 묶음 하나. AI 출력 전사가 0.8초(`utterance_gap_ms`) 넘게 끊기면 새 묶음이 된다(`on_output`).
- `utt`: 입력 전사가 0.8초 끊길 때까지의 고객 발화 한 조각.
- 질문 목록은 단계 기본값(`workflow.toml` `[[stage]] decision`)과 상태 조건(`judge` 안의 pick·pending·callback·origin·sender_change·name_scope·box)으로 정한다(`render.py` `decision_questions`).
- 판정 적용은 `_answer`가 돌려준 confidence를 하한 0.6(`decision_min_confidence`)과 비교한다. 확인 yes만 `policy.confirm.yes_min`을 따로 쓴다.

### 1.2 이 입력 때문에 생기는 문제

| 문제 | 실제 사례 | 원인 |
|---|---|---|
| 직전 AI 발화가 잘림 | 되읽기 중 Live가 13초 멈춘 뒤 "이대로 접수할까요?"만 이어 말함. 입력이 `. 이대로 접수할까요?`가 되어 "네"가 끝내기 0.80으로 판정, 접수 없이 종료(2b1762d6) | 0.8초 넘는 쉼마다 AI 발화가 끊김 |
| 질문 뒤 맞장구가 직전 발화가 됨 | "음...", "잠시만요" 뒤에 고객이 답하면 그 맞장구가 직전 AI 발화 | 마지막 묶음 하나만 봄 |
| 고객 발화가 쪼개짐 | "어... 여기가 그" / "부산광역시 서구 구덕로…"가 따로 판정됨 | 고객 쉼 0.8초 |
| 서버가 기다리는 질문을 모름 | "등록된 발송 주소로 보내실까요?"에 "네"가 출발지 yes 0.53으로 하한 미달, 세 번 반복(bc1a4f4e) | 지침이 특정 문장("발송 주소도 바꾸시겠어요?")을 기준으로 극성을 정함. Backend·Live가 다른 문장으로 물으면 확신하지 못함 |
| 한 발화에 질문이 여럿 붙어 "네"가 나뉨 | 같은 "네"에 출발지·보내는 분 변경·이름 범위·업무 전환이 함께 붙음. 이름 범위 동의 0.27, 끝내기 0.33이 섞임 | 질문마다 "이 질문의 답일 때만"이라는 조건이 약함 |
| 열린 질문 감지 오판 | 주소 변경 요청을 택배 수정으로 판정(18ecdae3, 9f254f87). 받는 분 성함을 보내는 분 변경으로 판정(bc1a4f4e, 배포본 148) | 질문 목록에 맞는 질문이 없거나 지침이 넓음 |

### 1.3 이미 반영된 것 (오늘 다른 담당자 수정)
- `cba402e4`: 짧은 동의 정규식에 "아·어·음" 앞말 허용(`SHORT_YES`). 첫 인사 "아 네"와 발송 주소 질문의 짧은 동의는 Decision 없이 처리. sender_change 지침에 "직전 질문이 받는 분 성함이면 그 이름만 답한 것은 none" 추가.
- `da380470`: 종료 질문(`END_QUESTION`)에 대한 짧은 예/아니요는 Decision 없이 처리. 같은 발화에서 접수 확인 yes와 끝내기가 함께 나오면 바로 끝내지 않고 확인(`end_check_turn`). switch에 `edit_other_parcel` 추가, `edit_parcel` 지침 좁힘.

이 계획은 위 수정과 겹치지 않게, 정규식 지름길에 걸리지 않는 발화(길거나 섞인 답, 다른 문장으로 물은 질문)를 다룬다.

## 2. 근거: 운영 발화 재생 (2026-11-11, 배포본 149 정책, 각 3회, 3회 모두 같은 값)

| 발화 | 입력 조건 | 결과 |
|---|---|---|
| "등록된 발송 주소로 보내실까요?" → "네" | 지금(질문 4개) | 출발지 yes p 0.53, confidence 0.30 |
| 같은 발화 | 출발지 질문만 | yes 0.53 (질문을 줄여도 그대로) |

| `. 이대로 접수할까요?` → "네" | 지금(confirm+switch) | confirm yes 0.85, **switch end 0.64** |
| 같은 발화 | + `열린 질문: 되읽은 접수 내용 확인(yes=이대로 접수)` | confirm yes 1.00, end 0.40 |
| 전체 되읽기 문장 → "네" | 지금 | confirm yes 0.99, switch none 0.85 |
| "받는 분 성함부터 알려주시겠어요?" → "나가줘" | 지금 | **switch end 0.66** |
| "받는 분 성함을 알려 주세요" → "현승준입니다" | 지금(149) | sender_change none 1.00 (148에서는 name 0.87, cba402e4로 고쳐짐) |

읽는 법:
- 같은 입력은 같은 결과를 낸다. 같은 질문을 같은 문장으로 다시 물어도 결과가 바뀌지 않는다.
- 하한을 0.5로 내리면 출발지 "네"는 통과하지만 끝내기 0.64·0.66도 통과한다. 하한 조정으로는 둘을 함께 해결할 수 없다.
- confidence와 선택지 확률이 크게 다를 수 있다(0.30 대 0.53). 비교 기준을 하나로 정해야 한다.
- 재생 방법은 부록 B.

## 3. 변경 내용

### 3.1 입력 형식
```
열린 질문: {서버가 기다리는 질문의 종류와 선택지 뜻}        ← 신규
지금 받는 항목: {missing 첫 항목 이름}                       ← 신규(열린 질문이 없을 때)
최근 AI 발화: {마지막 고객 발화 이후 AI가 한 말 전체}          ← 범위 확대
고객 발화: {이번 고객 발화, 끊어진 앞 조각 포함}               ← 범위 확대
```

**최근 AI 발화 범위**
- 직전 고객 발화가 끝난 뒤부터 이번 고객 발화가 시작되기 전까지의 AI 발화 묶음을 시간순으로 모두 이어 붙인다. 되읽기 중간 쉼, 질문 뒤 맞장구가 모두 들어간다.
- 길이 상한은 400자다. 넘으면 앞쪽을 자르고 마지막 문장을 남긴다. 되읽기 전문이 대개 150~250자다.
- 고객이 AI 발화 중간에 끼어든 경우에는 끼어든 시점까지만 넣는다. 지금의 `customer_cut_in` 판단을 재사용한다.

**고객 발화 이어 붙이기**
- 이번 발화 앞에 AI 발화 없이 3초 안에 끝난 고객 조각이 있으면 이어 붙인다. 예: "어... 여기가 그" + "부산광역시 서구…".
- 앞 조각에 이미 판정이 적용됐으면 이어 붙이지 않는다(`latest_applied`). 같은 답이 두 번 적용되지 않게 한다.

**열린 질문 줄**
서버 상태에서 만든다. Live 문장에서 추측하지 않는다. 우선순위는 표의 위쪽부터 하나만 쓴다.

| 서버 상태 | 열린 질문 문구 |
|---|---|
| `end_check_turn` | 통화 종료 여부(yes=통화 종료) |
| `pending`(parcel), 또는 단계 readback | 되읽은 접수 내용 확인(yes=이대로 접수, change=내용 고침) |
| `pending`(cancel) | 취소 대상 확인(yes=취소 진행) |
| `candidates`(destination) | 받는 곳 후보 선택: {이름표 목록} |
| `candidates`(order) | 조회한 택배 선택: {이름표 목록} |
| `candidates`(parcel) | 고칠 택배 선택: {이름표 목록} |
| `box_proposal` | 박스 후보 확인: {이름표}(yes=이 크기·개수로 기록) |
| `ask_customer_name_save` | 등록 이름도 바꿀지(yes=등록 이름 변경, no=이번 택배만) |
| `sender_change_next == ask_address_change` | 발송 주소도 바꿀지(yes=새 주소로 바꿈) |
| `origin_offered`이고 답 없음 | 등록된 발송 주소 사용 여부(yes=등록 주소 사용) |
| 첫 인사 직후(`_greeting_offer`) | 첫 인사: 택배 접수 시작과 안내한 발송 주소 사용 여부 |
| `callback_offered` | 담당자 연락 동의(yes=연락 받음) |
| 단계 more_parcels | 추가로 보낼 택배 여부(yes=더 있음) |
| 없음 | 열린 질문 없음 |

- 열린 질문과 최근 AI 발화가 어긋날 수 있다. Live가 서버 질문을 아직 묻지 않았거나 다른 것을 물은 경우다. 지침 공통 규칙에 "최근 AI 발화가 열린 질문을 실제로 물었을 때만 그 답으로 본다"를 둔다(§3.2).
- "yes=…" 표기는 질문마다 선택지 극성을 고정한다. 지금 origin 지침처럼 문장에 따라 yes와 no의 뜻이 뒤바뀌는 규칙을 없앤다. 서버는 열린 질문 종류에 따라 답을 상태로 옮긴다(예: "발송 주소도 바꿀지"의 yes → origin no).

### 3.2 지침
**공통 규칙**(입력 맨 앞 또는 질문마다 앞에 붙임)
- 열린 질문이 있으면, 최근 AI 발화가 그 질문을 실제로 물었고 고객이 그에 답했을 때만 그 질문의 답을 고른다. 그 밖에는 not_answer.
- 짧은 동의·거절("네", "아니요", "맞아요")은 열린 질문의 답이다. 다른 질문의 동의로 보지 않는다.
- 고객이 답과 함께 새 값(이름·번호·주소·물품)이나 고침을 말하면 그 사실이 드러나는 선택지(change 등)를 고르고, 단순 동의(yes)로 보지 않는다.

**질문별 정리 방향**

| 질문 | 바꿀 점 |
|---|---|
| origin | "'발송 주소도 바꾸시겠어요?'에 '네'는 no" 같은 문장 기준 극성 규칙 삭제. 열린 질문이 "등록 발송 주소 사용 여부"일 때만 yes·no. 주소 변경 질문의 답은 별도 열린 질문으로 처리 |
| sender_name_scope | 선택지 7개 중 confirm_once·confirm_save는 열린 질문이 "등록 이름도 바꿀지"일 때만. 그 밖의 짧은 동의는 not_answer |
| sender_change | 열린 질문이 첫 인사·발송 주소 관련일 때만 묻는다. "지금 받는 항목"이 받는 분 정보면 질문 목록에서 뺀다 |
| switch | end·agent는 고객이 직접 요청했을 때만. 짧은 동의·거절은 열린 질문이 통화 종료 여부일 때만 end. 음성 인식이 불분명한 짧은 말(예: "나가줘")은 none |
| confirm | "질문을 끝까지 말했고" 조건을 "최근 AI 발화에 확인 질문이 있고"로 바꾼다. 범위를 넓혀 잘린 되읽기 문제를 없앤다 |
| task | 첫 인사 열린 질문일 때 "네"는 order. 출발지 사용 여부는 origin이 맡는다 |
| box, more, callback, pick | 열린 질문 조건 문구만 맞춘다 |

**질문 목록 구성**
- 열린 질문이 있으면 그 질문 + switch만 보낸다. 지금처럼 출발지·보내는 분 변경·이름 범위를 한 번에 묶지 않는다.
- 열린 질문이 없으면 switch만 보낸다. 첫 인사 직후에만 task·origin·sender_change를 함께 보낸다.

### 3.3 하한과 판정 실패 처리
- 비교 기준을 선택지 확률로 바꾼다(`_answer`가 돌려주는 확률 분포). confidence는 기록만 한다.

| 판정 종류 | 적용 조건(제안, 재생으로 확정) |
|---|---|
| 열린 질문의 답 | 최상위 확률 0.7 이상, 둘째와 차이 0.3 이상 |
| switch의 lookup·inquiry·edit_parcel·edit_other_parcel | 0.75 이상 |
| switch의 end·agent·cancel·cancel_current | 0.9 이상이고, 같은 발화에 열린 질문의 yes가 없을 때. 그 밖에는 확인 질문(`end_check_turn` 재사용) |

- 열린 질문의 답이 조건에 못 미치면 같은 질문을 반복하지 않는다. 서버가 선택지를 풀어 한 번 다시 묻는다. 예: "등록된 주소에서 보내시면 '예', 다른 주소면 '다른 주소'라고 말씀해 주세요." 두 번째도 실패하면 상담원 연결 또는 콜백 안내로 넘긴다.
- 다시 묻는 안내는 N2(commentary)로 보낸다. 같은 턴의 Backend 안내와 겹치지 않게, 이 경우에는 기존 N2 대기 규칙을 그대로 따른다.

## 5. 검증 방법
- **정답 표**: 11-08 이후 통화에서 Decision이 불린 고객 발화를 뽑아 질문 종류별로 정답을 표시한다. 열린 질문의 답 100개 이상, switch에서 none이 아닌 발화 전부, 정규식 지름길에 걸리지 않은 첫 인사 답 전부를 포함한다. 이번 분석에 나온 오판 사례는 빠짐없이 넣는다.
- **비교**: 기존 입력·지침과 새 입력·지침으로 같은 발화를 한 번씩 돌린다. 같은 입력은 같은 결과를 내므로 반복할 필요가 없다.
- **지표**: 질문 종류별 정확도, 적용된 오판 수(특히 end·agent), 열린 질문 답 미적용 비율, 입력 길이와 판정 지연(p50·p95).
- **합격선**
  - end·agent 오적용 0.
  - 열린 질문의 짧은 동의·거절 적용률 95% 이상.
  - 다른 질문 종류의 정확도가 기존보다 낮아지지 않음.
  - 판정 지연 p95 증가 50ms 이내. 지금 웜 상태 p95는 284ms이고, 입력은 평균 370토큰이다.

## 6. 배포 뒤 볼 것
- 통화 기록의 Decision 이벤트에 `open_question`과 입력 길이를 남긴다.
- 같은 질문 반복 횟수, 선택지 풀어 다시 묻기 횟수와 그 뒤 성공률, 확인 질문(`end_check_turn`) 발생 수, 접수 없이 끝난 통화 중 종료 판정이 원인인 것.

## 부록 B. 재생 방법
- 운영 AI 컨테이너(`dva-ai-ai-1`) 안에서 `/app/.venv/bin/python`으로 실행한다. API 키는 컨테이너 환경에 있다. `load_policy()`로 배포된 정책을 읽고 `AsyncOpenAI().decisions.create(model="gpt-6-luna", input=…, questions=…)`를 부른다.
- 질문 항목은 `policy.decision[name].questions`에서 `{type, name, instructions, choices}`로 만든다.
- 통화 기록의 Decision 이벤트 `data.input`이 그때 보낸 입력이다. 새 입력을 만들려면 `transcript`(speaker·text·t)와 `events`로 상태를 재구성해야 하므로, 1단계 스크립트는 통화 기록에서 열린 질문을 추정하는 규칙을 함께 둔다(되읽기 문구, 후보 이름표 이벤트, 출발지 알림 등).
- 결과는 판정마다 선택지·confidence·확률 분포를 남긴다. 스크립트 파일은 컨테이너에 남기지 않는다.

## 8. 적용 결과 (2026-11-11, develop-ai `45e8ed4f` 기준)

### 8.1 계획과 달라진 점
- 계획을 쓴 뒤 운영 경로가 서버 주도 통화(`turn_mode = "server"`, `app/calls/turn.py` `TurnPipeline`)로 바뀌었다. 입력·질문 목록·하한·다시 묻기는 이 경로에 넣었다. 기존 경로(`live.py` `judge`·`apply`)는 지침을 함께 쓰므로 입력만 새 형식으로 바꾸고 하한(0.6)과 질문 목록은 그대로 두었다.
- 열린 질문의 순서는 표(§3.1) 대신 서버가 실제로 먼저 묻는 순서(`observe_turn`)를 따른다: 종료 확인 → 콜백 → 취소 확인 → 조회·수정 후보 → 첫 인사 → 등록 이름 → 발송 주소 변경 → 등록 주소 사용 → 받는 곳 후보 → 박스 → 되읽기 → 추가 택배.
- 받는 곳·택배 후보 선택(pick)은 열린 질문의 답이어도 하한을 낮추지 않았다(확률 0.85). 재생에서 이름이 같은 후보 셋 중 하나를 0.75로 고른 사례가 나왔다.
- 종료는 0.9 이상이면 바로, 0.75~0.9이면 "통화를 마칠까요?"로 한 번 확인한다. 상담원·취소는 0.9 미만이면 적용하지 않는다(확인 질문이 없다).
- 두 번째 다시 묻기 실패는 강제 연결 대신 상담원 연결을 권한다(`agent: suggest`).
- 서버 주도 경로의 "발송 주소도 바꾸시겠어요?"에 대한 짧은 "네"가 등록 주소 사용으로 반대로 적용되던 것을 함께 고쳤다.
- 최근 AI 발화에 질문·요청이 하나도 없으면(맞장구만) 20초 안의 가장 최근 질문을 앞에 붙인다.
- 끊어진 고객 조각을 이어 붙인 문장은 Backend 입력에도 쓴다(앞 조각의 처리가 새 발화로 취소되면 그 내용이 사라지던 문제).
- 2~4단계는 `turn.py` 한 곳에서 맞물려 커밋 하나로 묶었다.

### 8.2 재생 결과 (`scripts/replay_decisions.py`, 정답 표 `evaluation/datasets/decision_v1.json`)
11-08 이후 통화 107건의 Decision 발화 1,232개 가운데 208개(정답 332개: 열린 질문의 답 181개, switch 151개)를 골라 기존 입력·지침과 새 입력·지침으로 한 번씩 돌렸다. 새 쪽을 두 번 돌려 답 411개가 모두 같았다.

| 질문 | 정답 수 | 정확도 기존 → 새 | 놓친 답 기존 → 새 | 잘못 적용 기존 → 새 |
|---|---|---|---|---|
| origin | 50 | 38 → 48 | 21 → 0 | 0 → 0 |
| confirm | 31 | 31 → 31 | 2 → 2 | 0 → 0 |
| pick | 30 | 28 → 29 | 1 → 0 | 0 → 0 |
| task | 29 | 25 → 28 | 11 → 1 | 0 → 0 |
| more | 21 | 21 → 21 | 3 → 2 | 0 → 0 |
| box | 13 | 13 → 13 | 2 → 0 | 0 → 0 |
| sender_name_scope | 6 | 5 → 5 | 3 → 1 | 0 → 0 |
| switch | 151 | 143 → 148 | 15 → 3 | 0 → 0 |

- 기존 = 서버 주도 경로의 지금 기준(confidence 0.85, 접수 확인의 동의는 확인 관문 0.7), 새 = §3.3 기준. "놓친 답"은 정답이 실제 답인데 적용되지 않은 것이다. 새 쪽 switch의 3건 중 1건은 종료 확인 질문으로 넘어간다.
- 짧은 동의·거절의 적용: 38건 중 기존 23건 → 새 38건.
- 정답이 none인데 종료 확률이 0.3을 넘은 발화: 기존 4건(최고 0.54) → 새 0건.
- 입력 길이 평균 67자 → 462자. Decision 지연은 로컬 PC에서 4회 재어 p50 차이 −4~+12ms, p95 차이 −117~+54ms였다. 회차마다 흔들리는 폭이 차이보다 크고, 한 번은 합격선(50ms)을 4ms 넘었다. 배포 뒤 서버에서 다시 본다.

### 8.3 남은 한계
- 정답 표는 사람이 아니라 구현자가 통화 기록을 읽고 표시했다. 뜻이 갈리는 발화 37개는 뺐다. 배포 전에 사람이 표를 검수해야 한다.
- 재생의 열린 질문은 통화 기록에서 추정한 것이다(부록 B). 실제 통화에서는 서버 상태로 정한다. 추정이 틀린 발화(이미 답한 출발지 질문 등)도 그대로 돌렸다.
- 표본이 적은 종류: sender_name_scope 6, sender_change 1, 상담원 요청 0, 콜백 0, 종료 확인 0. 이 종류의 하한은 제안값 그대로다.
- 나빠진 발화 2건: 되읽기 도중 "아니요, 그렇게 접수해 주세요"(동의 0.80 → 0.59, 한 번 더 묻게 됨), 등록 이름 질문에 "이렇게 해주십시오"(동의 0.95 → 해당 없음 0.58).
- 다시 묻기(clarify)와 종료 확인은 재생으로 볼 수 없다. 단위 테스트만 있고 실제 통화 확인이 필요하다(§6).
- 서버 주도 경로가 배포된 뒤의 통화는 1건뿐이라 재생 자료는 거의 기존 경로의 것이다.
