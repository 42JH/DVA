# 구조 변경 계획 v3 — 업무 규약은 프롬프트가 이끌고, 코드는 계약·안전만 지킨다

상태: 계획(승인 전). 2026-11-04. v1(코드 고정)·v2(문장만 파일화)를 대체한다.

## 0. 결정과 원칙
사용자 결정:
- 업무 규약이 바뀔 때마다 코드를 고치지 않는다. **업무 규약은 프롬프트(`policy/business_rules.md`)를 따르고, 코드는 강제하지 않는다.**
- 페르소나만 BE에서 받는다(`promptText`). 업무 규약 .md는 운영 중 수정하지 않는다(배포로만).
- a~i: a 수거 일시(통화 시각+1시간부터, 09~17시, 요청 시 조정) · b·c 서버 방식 유지 · d~i 제시 프롬프트 방식.

경계 원칙 — 코드에 **남기는 것은 세 가지뿐**:
1. **BE 계약**: 요청 본문 스키마, 필수값·형식(COMPLETE 조건은 BE 규약), 멱등키·아웃박스, 에러 분류.
2. **부작용 안전**: 주문 전송·취소처럼 되돌리기 어려운 일은 고객 확인(관문 G1~G6)과 서버 결과 뒤에만. 서버 결과 없는 "완료" 안내 검사.
3. **데이터 정합성**: 들은 값 검증·정규화(전화번호 자릿수, 주소 보정, 이름 말끝, 시각 형식), 이미 보낸 접수와 다른 값을 확정한 것처럼 만들지 않기.

그 밖의 **대화 절차·순서·안내 방침·허용 범위(영업시간 등)·이관 조건**은 프롬프트로 옮긴다.

AGENTS.md와의 관계: "업무 상태는 LLM 컨텍스트에만 의존하지 않는다"는 지킨다(값·확인·전송 상태는 계속 서버가 가짐). "Backend LLM: 업무 절차에 따른 후속 판단"(§5)에 더 가까워진다. 단, **"영업시간 밖 수거 시각" 같은 업무 규칙을 코드가 막지 않으므로, 모델이 규약을 어기면 그대로 BE로 갈 수 있다** — 이 위험을 받아들이는 결정이다(§6).

## 1. 현재 코드가 강제하는 업무 규칙과 처리

| # | 지금 코드가 하는 일(위치) | 분류 | 변경 |
|---|---|---|---|
| 1 | 받는 순서·단계 판정, 다음에 물을 항목(`assess.stage`/`missing`, `workflow.toml [[stage]]`) | 업무 절차 | **제거**. 도구 결과는 "기록된 값 + BE 필수값 중 비어 있는 것"만 돌려준다(순서 없음). 순서는 프롬프트 |
| 2 | 되읽기 개방 조건(필수값이 다 찼을 때 `issue_parcel_confirmation`) | 계약+안전 | **유지**. 필수값 목록은 BE 계약 기준 데이터(`config`)로 |
| 3 | 확인 관문 G1~G6, 확정 지연, 취소 확인 | 부작용 안전(b) | **유지** |
| 4 | 단계별 Decision 질문 묶음(intent·collect·confirm·more·pay·pick, `decision_questions`) | 혼합 | confirm(확인 대기 중)·pick(후보 있을 때)은 **유지**(b·안전). 단계에 묶인 more·pay·switch·task는 **단계 대신 서버 상태 사실로 묶음**(예: 결제 방식 2개 이상이고 미정이면 pay 질문) — 단계 엔진 없이 동작 |
| 5 | "더 없음 + 결제 확정 → 결과 전송"(`_maybe_submit`) | 업무 절차 | **변경**. 프롬프트가 정한 시점에 Backend가 도구 `finish_order`를 부르면 전송. 통화 종료 시 미전송이면 지금처럼 전송(INCOMPLETE 포함, 정합성) |
| 6 | 결제 방식: 하나면 자동, 선택지는 가능 방식만(`payment_auto`) | 계약+업무 | 값 ∈ 고객 가능 방식 **검증은 유지**(계약). "하나면 자동" 같은 안내 방침은 프롬프트(서버는 가능 방식 목록만 사실로 줌) |
| 7 | 수거 일시 없음(결정 1-b) | — | **재도입(a)**: `record_fields.pickup_at`. 코드는 **형식·미래 시각·BE 계약 범위만** 검사, 기본값(+1시간)·09~17시·조정 허용은 프롬프트. 전송 본문 `pickupRequestedAt`(§5 계약 확인 후) |
| 8 | 전화번호 자릿수·정규화, 주소 보정, 이름 말끝 | 정합성 | **유지** |
| 9 | 번호 정정 방식(전체 다시 받기, 프롬프트) | 업무 | **프롬프트(d)**: 틀린 부분만. Backend 규칙(`backend_rules.md`)에 "이전 번호와 합쳐 전체 번호로 기록". 코드는 자릿수만 검사 |
| 10 | 다시 묻기 3회(`[reask]`) | 업무 | **프롬프트(h)**. 코드 카운터 제거 |
| 11 | 문구 검사(`[forbid].claims`: 접수·취소·결제 완료, 확인 대기 중 "진행하겠") | 안전 | 결과 완료 문구 검사는 **유지**(서버 결과 없는 성공 안내 금지). "진행하겠" 같은 표현 규칙은 프롬프트로 이동 |
| 12 | 접수 후 수정·추가 잠금(`ORDER_SUBMITTED`) | 정합성 | **유지**(보낸 접수에 반영 안 되는 값을 확정한 것처럼 만들지 않음). 안내 문구는 프롬프트(제시안: 상담원 이관 권유) |
| 13 | 상담원: 미설정 사실만(P11) | 업무+연동 | **프롬프트(e)** + 도구 `transfer_call`·`create_callback_request` 신설 — **BE·PBX 계약이 있어야 구현**(§5) |
| 14 | 첫 인사·마무리·다시 확인 신호(N2 `call_started`·`closing`·`ask_again`) | 연동 | 신호(사실)는 **유지**. 문구는 프롬프트(인사·고정 마무리 멘트) |
| 15 | 신규 고객 등록 시점·순서 | 계약 | **유지**(원본 register 절차) |
| 16 | 주소록 수정(출발지·도착지 변경 시) | 업무+연동 | **신설(g)**: 접수 뒤 서버가 BE PIN 저장/갱신 — **BE API 확인 후**(§5) |
| 17 | 인사의 등록 출발지 | 데이터 | **신설(f)**: 통화 정보에 기본 출발지(도로명까지) |

## 2. 프롬프트·설정 파일 구성

```
Live instructions = [페르소나] + [업무 규약] + [통화 정보]
  policy/persona_default.md   BE promptText가 없을 때의 페르소나
  policy/business_rules.md    업무 규약 전부(제시 프롬프트의 업무 절 + 서버 결과 키의 뜻 + 위임 기준 + 도구 목록)
  통화 정보                    서버가 넣는 값: 시각, 등록 여부, 성함, 기본 출발지

Backend instructions = policy/backend_rules.md   값 추출·도구 선택·번호 합치기(d)
Decision 질문          = policy/decisions.toml     confirm·pick·pay·more·task·switch 질문 문장(서버 상태로 고름)
서버 데이터            = config/server.toml 등     BE 필수값 목록, 시각 형식, 관문 수치, 완료 문구 검사 phrases
```

- 코드(`app/policy/render.py`)는 **파일을 이어 붙이고 통화 정보 값을 넣기만** 한다. 문장 생성(`render_policy`)·우선순위 문장 삭제.
- `workflow.toml`의 `[[stage]]`·`goal`·`rule`·`[speech]`·`[results]`·`[reask]`·`[forbid].items` 삭제(문장은 `business_rules.md`로). 필드 정의는 BE 계약 데이터로 축소.
- **업무 규약 변경 = `business_rules.md`만 수정·배포**. 코드는 안 바뀐다. 단 새 정보가 필요하면(새 필드, 새 도구, 새 BE API) 그때만 코드 작업.

## 3. 도구 정리(Backend가 고르는 일)

| 도구 | 하는 일 | 코드 검사(계약·정합성만) |
|---|---|---|
| `record_fields` | 값 기록(+`pickup_at`) | 형식·자릿수·주소 보정·시각 형식/미래·접수 후 잠금 |
| `find_destination`, `lookup_orders`, `search_manual`, `get_state` | 지금과 같음 | — |
| `finish_order`(신규) | 더 없음·결제 방식을 받고 결과 전송 시작 | 확인 끝난 택배 ≥1, 결제 방식 ∈ 가능 방식, 멱등(아웃박스) |
| `transfer_call`, `create_callback_request`(신규, 계약 후) | 상담원 연결·콜백 요청 | BE·PBX 계약대로 |

`finish_order`와 확정 관계: 택배 담기 확정은 지금처럼 고객 확인(Decision confirm + 관문)으로만. `finish_order`는 이미 확정된 택배만 보낸다.

## 4. 제시 프롬프트 반영 메모
- "진행 상태" → "서버 결과(도구 결과·`[서버 결과]` 알림)"로 용어 통일. "통화 정보의 첫 질문" → 삭제(첫 질문도 규약 문장으로).
- "확인 질문의 답도 백엔드에 맡긴다" → b(서버 Decision)에 맞게 "맡기지 않는다"로 고쳐 쓴다.
- "번호 받은 직후 되읽지 않는다" → c(서버 방식: 새 번호는 바로 끊어 읽어 확인)로 고쳐 쓴다.
- "검색 결과가 여러 조각으로 도착" → 리빌드는 결과 한 번(근거 최대 3개)으로 고쳐 쓴다.
- 수거 절은 a대로(기본 통화 시각+1시간부터, 09~17시, 요청 시 영업시간 안에서 조정).

## 5. 구현 전 확인할 계약(추측 구현 금지)
| 항목 | 확인할 것 | 없으면 |
|---|---|---|
| a 수거 일시 | `pickupRequestedAt`을 BE가 실제로 쓰는지, 형식·범위·검증(최신 규약 §3, `order-submit.md`) | 프롬프트는 시각을 약속하지 않게(BE가 결제+1시간으로 정함) 유지 |
| e 상담원 연결·콜백 | 통화 전환 방식(PBX/SIP), 콜백 요청 BE API, 상담원 근무 시간 출처 | 도구 없이 "담당자가 확인 후 연락" + 미답변/분석 `hasHandoffRequest` |
| g 주소록 수정 | PIN 추가·수정 API와 시점(`pins.md`, `order-sender-customer-save.md`) | 문장 제외 |

## 6. 위험
- **규약 위반이 BE로 갈 수 있다**: 영업시간 밖 수거 시각, 순서 건너뛰기 등은 코드가 막지 않는다. BE가 검증하면 400/422로 돌아오고(INCOMPLETE), 아니면 그대로 저장된다. 완화: 도구 결과에 사실(예: 기록된 수거 시각, 현재 시각)을 돌려주어 모델이 규약과 대조하게 하고, 실통화 로그로 위반률을 잰다.
- **응답 일관성**: 단계 엔진이 없어지면 "다음 질문"을 모델이 정한다. 실통화에서 순서 이탈·누락을 측정한다(받는 순서 준수율).
- **지연**: 규약 .md가 길어진다. `finish_order` 위임이 하나 늘 수 있다. 첫 발화·위임 P50·P95를 잰다.
- **프롬프트-서버 어긋남**: 결과 키·도구 이름·BE 필수값을 규약이 잘못 적을 수 있다 → 테스트로만 검사(문장 강제 아님): 결과 키 전부 설명됨, 도구 이름 일치, 필수값 이름 일치.
- **AGENTS.md 정합**: §2 "기존 서비스와 합의된 업무 규칙"(수거 1-b)을 a로 바꾸는 것은 사용자 승인으로 처리. BE와의 합의(수거 시각 주체)는 §5 확인 결과로 보고.

## 7. 단계
1. **계약 확인**(§5): a·e·g. 결과 보고 → 범위 확정.
2. **프롬프트 분리**: `persona_default.md`, `business_rules.md`(제시 프롬프트 + 서버 결과 키 + 위임 기준 + a~i), `backend_rules.md`, `decisions.toml`. `render.py`는 이어 붙이기만.
3. **단계 엔진 제거**: `assess.stage`·`[[stage]]`·`[reask]` 제거, 도구 결과를 "기록된 값 + 빈 BE 필수값"으로. Decision 질문 선택을 단계 → 서버 상태 사실로.
4. **도구**: `finish_order` 신설·`_maybe_submit` 대체, `record_fields.pickup_at`(a, 계약 확인 후), 통화 정보 기본 출발지(f).
5. **계약 있는 경우만**: `transfer_call`·`create_callback_request`(e), 주소록 갱신(g).
6. 테스트: 계약(본문·필수값), 안전(관문·잠금·완료 문구), 정합성(번호·주소·시각), 프롬프트-서버 일치. 기존 단계 테스트 정리.
7. worklog·커밋 → 로컬 실통화(가짜 BE): 순서 준수·수거 시각·마무리 멘트·지연 측정 → MR.
