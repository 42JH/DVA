# Live 지시문 배치 계획 — 페르소나만 교체, 업무 규칙은 고정

상태: 계획(승인 전). 작성 2026-11-04. 입력: 사용자가 제시한 전체 시스템 프롬프트(페르소나 + 업무 규칙 + 검색 자료).

## 1. 현 구조 점검

현재 Live `instructions` = `render_live()`(`app/policy/render.py:55`)

```
[① BE promptText 또는 policy/default_prompt.md]   ← 통째로 교체됨
"페르소나 지시와 아래 절차가 충돌하면 페르소나 지시를 따르되, '하지 않는 것'은 항상 지킵니다."
[② 정책 렌더링: policy/workflow.toml → 순서·단계·위임 기준·금지·읽기 규칙·서버 결과 읽는 법]
[③ 통화 정보: 전화 받은 시각·등록 여부·성함]
```

| # | 문제 | 영향 |
|---|---|---|
| P-1 | **우선순위가 반대**: 충돌하면 페르소나를 따른다 | 관리자 프롬프트가 업무 규칙(확인·위임·안내 범위)을 덮을 수 있다. 목표(업무 고정)와 반대 |
| P-2 | **교체 범위가 너무 크다**: promptText가 있으면 `default_prompt.md` 전체가 빠진다 | 기본 프롬프트 안의 업무 규칙(인사·주소 듣기·전화번호·끼어들기·처리 불가·마무리)이 운영에서 사라진다 |
| P-3 | **업무 규칙이 여러 벌**: `default_prompt.md`(손으로 쓴 규칙) + `workflow.toml` 렌더 + 제시 프롬프트(순서를 또 손으로 씀) | 순서·문구가 어긋나면 모델이 어느 쪽을 따를지 모른다 |
| P-4 | **제시 프롬프트의 업무 규칙 일부가 현재 서버 동작과 다르다**(§4) | 그대로 넣으면 지시와 서버가 서로 다른 일을 한다 |

결론: ①을 **페르소나 칸**으로 좁히고, 업무 규칙은 항상 들어가는 고정 칸으로 옮기며, 우선순위를 "업무 규칙 > 페르소나"로 뒤집는다.

## 2. 목표 구조

```
# 페르소나 (말투·성격만 — 바꿀 수 있음)            ← BE promptText, 없으면 policy/default_persona.md
[C]

# 업무 규칙 (바꿀 수 없음. 위 페르소나와 충돌하면 이 규칙을 따른다)
[A] policy/business_rules.md                       ← 고정: 인사·마무리 문구, 주소·숫자·전화번호, 안내 범위, 검색 자료로 답하기
[B] policy/workflow.toml 렌더(render_policy)        ← 고정: 받는 순서, 단계, 위임 기준, 금지, 서버 결과 읽는 법(단일 원천)

# 통화 정보
[D] 전화 받은 시각, 등록 여부, 성함, (신규) 기본 출발지(도로명까지)
```

- 페르소나를 맨 앞(정체성), 고정 규칙을 그 뒤에 두고 우선순위 문장을 명시한다. 기존 문장("충돌 시 페르소나 우선")은 삭제.
- 받는 순서·단계·위임 기준은 **`workflow.toml`에서만** 렌더한다. `business_rules.md`에는 순서를 다시 쓰지 않는다(P-3 해소).
- BE 계약: `ai-persona-next-call.md` "전체 promptText의 실행 프롬프트 주입 대상 … 은 AI에서 구현" — 주입 위치·범위는 AI 재량. API 경로·스키마·검증(INVALID_CONFIG 등)은 그대로.

## 3. 제시 프롬프트 배치표

| 제시 프롬프트 절 | 배치 | 비고 |
|---|---|---|
| Identity / 역할, Personality, Speaking Style(톤·속도·"네" 금지·고령자 속도), Backchannel, Interruption("네 고객님"), Response Boundaries(대기 문구 3종) | **C 페르소나**(교체 가능) | 관리자가 BE에서 수정. `default_persona.md`는 같은 내용을 기본값으로 |
| 인사 문구(처음/등록 고객, "아니오" → "무엇을 도와드릴까요?") | **A 고정** | `{고객명}`·`{등록된 출발 주소지}`는 D 통화 정보로 채운다(§5 구현) |
| 통화 시작(먼저 인사, 먼저 용건 말하면 짧게 받고 첫 질문) | **A 고정** | "통화 정보의 '첫 질문'"은 원본 서버 개념 — "서버 결과의 missing 첫 항목"으로 바꿔 씀. 첫 인사 신호는 서버 N2 `call_started`(구현됨) |
| 택배 정보 받는 순서 | **B만**(`workflow.toml` 렌더) | 문장 중복 삭제. "진행 상태" → "서버 결과(missing)"로 용어 통일 |
| 받는 말(응대), 과한 사과 금지 | **A 고정** | "수거 일시" 예문은 §4-a 결정에 따름 |
| 수거 일시 말하기, 수거(9~17시·조정) | **보류 → §4-a** | 현재 서버는 수거 일시를 받지 않음 |
| 주소 듣기("인동 구길" → 9길, 하이픈 "다시", 어느 주소인지 넣어 다시 묻기) | **A 고정** | "주소는 한 번만 묻는다"는 B의 다시 묻기 규칙과 맞춘다 |
| 숫자 발화 | **A 고정** | |
| 전화번호 | **A 고정** | 되읽기 시점·정정 방식은 §4-c·d 결정에 따름 |
| 등록 고객과 주소록 | **A 고정** | "주소록 수정"은 §4-g |
| 결제 안내 | **A 고정** | "진행 상태" → "서버 결과". `[results].order`와 같은 뜻 |
| 접수 안내 | **A 고정** | 서버 `[forbid].claims`가 문구 검사 |
| 백엔드에 맡기는 일 | **B로 통합** | 위임 기준은 `render_policy`가 단일 원천. "확인 질문의 답도 맡긴다"는 §4-b |
| 조회·취소, 접수 후 수정은 이관 권유 | **A 고정** | 서버의 접수 후 수정 잠금(`ORDER_SUBMITTED`)과 일치 |
| 상담원 연결(조건·멘트·근무 시간 외) | **A 고정, 단 §4-e** | 도구 `transferCall`·`create_callback_request` 없음 |
| 마무리("이용해 주셔서 감사합니다. 좋은 하루 보내세요" 고정) | **A 고정** + `[results].closing` 문구 일치 | |
| 검색 자료로 답하기 | **A 고정** | "여러 조각으로 도착·전달 완료 신호"는 원본 방식 — 리빌드는 search_manual 결과 JSON 한 번(근거 최대 3개)으로 고쳐 씀 |

## 4. 현재 서버와 다른 규칙 — 결정 필요

| # | 제시 프롬프트 | 현재 서버 | 권장 |
|---|---|---|---|
| a | 수거 일시: 최소 1시간 뒤부터, 고객 요청 시 조정, 9~17시 밖은 접수 불가 | 결정 1-b: 묻지 않음, `pickupRequestedAt` 안 보냄(BE가 결제 완료 + 1시간) | 서버 유지 시 수거 절은 "결제 완료 후 1시간 안 방문, 시각 약속 안 함"으로. 조정을 받으려면 필드·BE 전송·검증 재도입(별도 작업) |
| b | 확인 질문의 답(예/아니요·결제 방식·취소·상담원)도 백엔드에 맡긴다 | 고르는 답은 위임하지 않고 서버 Decision이 판단(S0c). 위임은 값 추출만 | 서버 방식 유지(위임·지연·비용 증가 방지). 제시 문장 제외 |
| c | 번호를 받은 직후 되읽지 않고, 진행 상태가 확인하라고 할 때 한 번 | `phones_to_read`: 새로 받은 번호는 바로 한 번 끊어 읽어 확인 | 결정 필요. 제시안이면 `phones_to_read` 제거(되읽기 단계에서만 확인) |
| d | 번호 정정은 틀린 부분만 고침(예시 포함) | 기본 프롬프트: 번호 전체를 다시 받음 | 결정 필요. 부분 정정은 Backend가 이전 번호와 합쳐야 해 오기록 위험 — 전체 다시 받기 권장 |
| e | 상담원 이관 `transferCall`, 근무 시간 외 `create_callback_request`, 근무 시간 안내 | 상담원 미설정(P11): "담당자가 확인 후 연락" 사실만, 도구 없음 | 도구가 생길 때까지 연결·콜백 멘트는 "담당자가 확인 후 연락"으로. 근무 시간 정보 출처 필요 |
| f | 등록 고객 인사에 `{등록된 출발 주소지}` | 통화 정보에 성함만 | 서버가 기본 출발지(도로명·건물번호, 상세주소 제외)를 통화 정보에 추가 |
| g | 출발지·최근 도착지가 바뀌면 접수 후 주소록 수정 | AI는 신규 고객 등록 때 PIN만 저장. 그 외 수정 없음 | BE 계약(`order-sender-customer-save.md`) 확인 전까지 문장 제외 |
| h | 동일 질문 3회 못 답 → 이관, 해결되면 카운트 0 | `[reask].max_attempts = 3`(같은 항목 3회 실패 → 다른 방법 → 상담원 제안), 초기화 개념 없음 | 서버 규칙으로 통일, 문장은 B 렌더에 맡김 |
| i | 주소 말할 때 받아 쓰듯 되풀이(맞장구) | 기본 프롬프트: 주소를 다시 말하지 않고 "주소 확인했습니다"만 | 결정 필요(페르소나 vs 업무 규칙 충돌). 업무 규칙 우선이면 맞장구 절에서 삭제 |

## 5. 구현 단계(승인 후)

1. `policy/business_rules.md` 신설: 제시 프롬프트의 업무 절(§3 'A 고정') + 현 `default_prompt.md`의 업무 규칙을 합치고 §4 결정을 반영. 용어 "진행 상태" → "서버 결과".
2. `policy/default_persona.md` 신설: 제시 프롬프트의 페르소나 절. `default_prompt.md`는 삭제(또는 둘로 분리).
3. `render_live()` 변경: `# 페르소나` → C, 우선순위 문장, `# 업무 규칙` → A + B, `# 통화 정보` → D. 기존 "충돌 시 페르소나 우선" 문장 삭제.
4. 통화 정보에 기본 출발지 추가(§4-f): 1단계 고객 확인의 기본 출발지 도로명. 저장된 상세주소는 넣지 않는다(읽기 규칙).
5. `workflow.toml` 정리: `[results].closing`에 고정 마무리 멘트, §4 결정에 따른 `[speech].pickup`·`phones_to_read`.
6. 테스트: 렌더 순서·우선순위 문장, promptText에 업무 문구가 있어도 A·B가 항상 포함, promptText 없음 → 기본 페르소나, 통화 정보 출발지, 기존 정책 테스트.
7. worklog·커밋 → 로컬 실통화(가짜 BE)로 인사·마무리·이중 인사 확인 → 새 MR.

## 6. 운영·협의

- **BE 관리자 페르소나 정리 필요**: 지금 운영 ACTIVE `promptText`에 제시 프롬프트 전체가 들어 있다면, 새 구조에서는 업무 규칙이 두 번(페르소나 칸 + 고정 칸) 들어간다. 관리자 화면에서 페르소나 절만 남기도록 안내한다(검증으로 자르지 않는다 — 내용 필터는 오탐 위험).
- 지시문 길이: 고정 칸이 늘어나므로 Live 세션 시작·첫 발화 지연을 실통화로 잰다(P50·P95).
- 기존 계약·외부 인터페이스 변경 없음(BE API, PBX, 페르소나 API 그대로).
