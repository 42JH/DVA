# 구조 계획 v4 — 서버가 업무 규약을 강제, 프롬프트는 파일로 분리(페르소나만 BE)

상태: 계획(승인 전). 2026-11-04. v3(프롬프트 주도)를 철회하고 서버 강제 방식으로 되돌린다.

## 0. 결정
- 업무 규약은 **서버 코드가 강제**한다(단계·확인 관문·검증·전송 조건). 프롬프트에 의존하지 않는다.
- 프롬프트는 파일로 분리한다: 페르소나만 BE `promptText`, 업무 규약 문장은 저장소 파일(운영 중 수정 없음).
- a~i(사용자 결정):

| # | 결정 | 서버가 강제하는 것 |
|---|---|---|
| a | 수거 일시: 기본 = 통화 현재 시각 + 1시간부터, 09~17시 안. 그 시각이 17시를 넘으면 "금일 수거는 어렵고 익일 수거 가능" 안내, 기본 익일 09:00. 고객 요청 시 영업시간 안·3일 이내(임시)에서 조정 | 기본값 계산, 허용 범위 검증(거절 코드), 되읽기·전송 |
| b | 확인 답은 서버 Decision(위임 안 함) | 지금과 같음 |
| c | 새 번호는 받은 직후 끊어 읽어 확인(`phones_to_read`) | 지금과 같음 |
| d | 번호 정정은 틀린 부분만 고침 | Backend 규칙으로 합친 전체 번호 기록 + 서버 자릿수 검증 + 되읽기 재확인 |
| e | 상담원 이관 권유·연결(`transferCall`), 근무 시간 외 콜백(`create_callback_request`). 불만·격앙은 **Live가 판단**해 이관을 권유(지연 추가 없음) | 고객의 연결 요청은 기존 Decision 용건 `agent`로 판정, 도구 실행(**계약 확인 후**) |
| f | 등록 고객 인사에 성함·등록 출발지 | 통화 정보에 기본 출발지 |
| g | 출발지·최근 도착지가 바뀌면 접수 후 주소록 수정 | 접수 결과 뒤 서버가 BE 주소록 갱신(**계약 확인 후**) |
| h | 같은 질문에 3번 연속 답 못 하면 이관 권유, 해결되면 횟수 0 | 서버가 답 못 한 횟수를 세고 3회면 이관 사실 전달 |
| i | 고객이 주소를 말할 때 받아 쓰듯 작게 되풀이 | 프롬프트(페르소나 맞장구). 기존 "주소를 다시 말하지 않음" 규칙 삭제 |

## 1. 프롬프트 파일 구성

```
Live instructions = [페르소나] + [업무 규약] + [통화 정보]
  페르소나     BE ACTIVE promptText, 없으면 policy/persona_default.md
  업무 규약     policy/business_rules.md   제시 프롬프트의 업무 절(아래 §1.1 수정 반영)
              + policy/workflow.toml 렌더  받는 순서·단계·위임 기준·금지·서버 결과 읽는 법(서버 강제 규칙과 같은 원천)
  통화 정보     시각, 등록 여부, 성함, 기본 출발지(f)
Backend instructions = policy/backend_rules.md (render_backend 문장 이동 + d 번호 합치기)
```

- 우선순위: "업무 규약이 페르소나보다 우선"을 `business_rules.md` 첫머리에 둔다. 지금의 "충돌 시 페르소나 우선" 문장(`render.py:59`)은 삭제.
- 받는 순서·단계·위임 기준·서버 결과 키는 **`workflow.toml`에서만** 렌더한다(서버 판정과 같은 데이터). `business_rules.md`에 순서를 다시 쓰지 않는다.
- `policy/default_prompt.md` → `persona_default.md`(말투)와 `business_rules.md`(업무)로 나누고 삭제.
- BE: 지금 ACTIVE `promptText`에 업무 규약까지 있으면 관리자 화면에서 페르소나 절만 남긴다.

### 1.1 제시 프롬프트 → `business_rules.md` 반영 시 고칠 문장
- "진행 상태" → "서버 결과(도구 결과·`[서버 결과]` 알림)". "통화 정보의 첫 질문" → "서버 결과의 missing 첫 항목".
- 백엔드에 맡기는 일: "확인 질문의 답도 맡긴다" 삭제(b). 받는 순서·위임 기준 문장은 렌더로 대체.
- 전화번호: "받은 직후 되읽지 않는다" → c(받은 직후 한 번 끊어 읽어 확인). 정정은 d(틀린 부분만).
- 수거: a대로. "내일 오후 여덟 시" 같은 예문은 영업시간 안의 예로 바꾼다.
- 검색 자료: "여러 조각으로 도착·전달 완료 신호" → 결과 한 번(근거 최대 3개).
- 상담원: e·h 문장 유지, 실제 연결·콜백은 서버 결과(도구 결과)에 따른다고 명시.
- 마무리: "이용해 주셔서 감사합니다. 좋은 하루 보내세요" 고정(서버 `closing` 신호 뒤).

## 2. 기능별 서버 변경

### a. 수거 일시(결정 1-b 철회)
- 필드 `pickup_at` 재도입(`workflow.toml` 필드·단계, `record_fields` 인자, 되읽기·확인 스냅샷 포함).
- **기본값**: 통화 시작 시각(`incomingAt`, KST) + 1시간. 09:00 전이면 당일 09:00, 17:00을 넘으면 **익일 09:00**(사실 `pickup_today_unavailable`로 "금일 수거는 어렵고 익일 수거 가능" 안내). 고객에게는 기본값을 안내하고 묻지 않는다. 주말·공휴일은 구분하지 않는다(정책 없음).
- **조정**: 고객이 시각을 말하면 `parse_pickup`(기존 `app/domain/rules.py`)으로 해석 → `현재 + 1시간 ≤ 시각`, `09:00 ≤ 시각 ≤ 17:00`, `시각 ≤ 오늘 + 3일`이 아니면 `rejected`(`PICKUP_TOO_SOON`·`PICKUP_OUT_OF_HOURS`·`PICKUP_TOO_FAR`) + 허용 범위 사실.
- 설정: `config/server.toml [pickup]` `lead_hours=1`, `open="09:00"`, `close="17:00"`, `max_days_ahead=3`(임시 — 정책 미정), 기본 익일 시각 `next_day_default="09:00"`(규약 바뀌면 설정만).
- 전송: 결과 본문 `pickupRequestedAt`(ISO 8601) — **BE가 이 값을 수거 시각으로 쓰는지 계약 확인 후**. BE가 "결제 완료 + 1시간"으로 덮어쓰면 고객 안내와 실제가 달라진다(§3).

### d. 번호 부분 정정
- `backend_rules.md`: "고객이 번호 일부만 고치면 기록된 번호에서 그 부분만 바꾼 전체 번호를 넣는다".
- 서버: 지금처럼 자릿수·정규화 검증, 바뀐 번호는 `phones_to_read`로 다시 끊어 읽어 확인(c와 함께 오기록 방지).

### e·h. 상담원 이관
- **이관 조건**: ① 고객의 연결 요청 → Decision 용건 `agent`(서버, 기존 질문) ② 불만·격앙 → **Live가 판단해 이관을 권유**(프롬프트, Decision 질문 추가 없음 — 지연 방지). 고객이 동의하면 ①로 판정 ③ 같은 질문 3회 연속 답 못 함(h, 서버): `search_manual`의 `KB_NO_EVIDENCE`·`KB_LOW_SCORE`·`unavailable`를 질문별로 세고, 답이 나오면 0으로. 3회면 N2 `{"agent":"suggest"}`.
- **연결**: 고객이 동의(Decision confirm)하면 `transfer_call`(통화 전환), 상담원 근무 시간 밖이면 콜백 안내 → `create_callback_request`(성함·연락처).
- 설정: 상담원 근무 시간(`config [agent]`).
- **전제: BE·PBX 계약**(통화 전환 방식, 콜백 요청 API, 근무 시간 출처). 없으면 지금처럼 "담당자가 확인 후 연락" + 분석 `hasHandoffRequest`·미답변 등록.

### f. 등록 고객 인사
- 1단계 고객 확인의 기본 출발지(personalPins 기본/최근 출발지)를 통화 정보 "등록된 출발지"(도로명·건물번호, 상세주소 제외)로 넣는다. 인사 문구는 `business_rules.md`.
- 등록 고객이 "아니오" → "무엇을 도와드릴까요?"(문장). 서버는 Decision 용건으로 그대로 처리.

### g. 주소록 갱신
- 결과 전송이 저장(`SAVED`)된 뒤, 이번 접수의 출발지·도착지가 기존 PIN과 다르면 BE PIN 저장/갱신(백그라운드, 대화 무관).
- **전제: BE 계약**(`pins.md`·`order-sender-customer-save.md`: BE가 접수 때 이미 저장하는지, 수정 API가 있는지). BE가 이미 하면 AI는 하지 않는다.

### i. 주소 맞장구
- 프롬프트만. `default_prompt.md`의 "주소는 다시 말하지 않는다" 삭제. 서버 동작 변화 없음.

## 4. 세부 결정(2026-11-04)
1. a 기본값이 17시를 넘으면: "금일 수거는 어렵고 익일 수거 가능" 안내, 기본 익일 09:00. 주말·공휴일 구분 없음.
2. a 조정 범위: 3일 이내(임시 — 정책 미정, 설정값).
3. e 불만·격앙 판단: Live 모델(프롬프트). Decision 질문을 늘리지 않는다.

## 5. 단계
1. 계약 확인(§3) → 보고·범위 확정.
2. 프롬프트 분리(§1): `persona_default.md`·`business_rules.md`·`backend_rules.md`, `render_live`·`render_backend` 정리, 우선순위 문장 교체.
3. f 통화 정보, i 문장, d Backend 규칙(코드 소량).
4. a 수거 일시(필드·검증·설정·되읽기·전송).
5. h 답 못 한 횟수·이관 사실, e·g(계약 있는 부분만).
6. 테스트: 렌더(페르소나 맨 앞·규약 항상 포함·우선순위), 수거 기본값·범위·거절, 부분 정정 되읽기, 이관 횟수 초기화, 계약 본문(`pickupRequestedAt`). 기존 테스트 갱신.
7. worklog·커밋 → 로컬 실통화(가짜 BE) → MR.

## 6. 위험
- a: BE가 `pickupRequestedAt`을 쓰지 않으면 고객 안내 시각과 실제 수거가 다르다(§3에서 확정).
- d: 부분 정정은 Backend가 잘못 합칠 수 있다 → 되읽기 재확인으로만 막는다.
- e: 계약이 없으면 프롬프트의 연결 멘트("바로 연결해 드리겠습니다")가 실제와 달라진다 → 계약 전에는 해당 문장을 "담당자가 확인 후 연락"으로 둔다.
- 지연: 규약 파일 길이 → 실통화 P50·P95. 불만 판단은 Live가 하므로 Decision 호출은 늘지 않는다.
- e(불만): Live 판단이라 서버가 검증하지 않는다. 이관 실행은 고객 동의(Decision `agent`)가 있어야만 한다.
