# S15P31D109-159 통화 종료 후 미답변 수집

2026-11-05 후속 확장: 같은 종료 검토에서 답변 근거 FAQ들을 판정하여 배열 이벤트로 연결하는 v2 구현은 [faq-answer-evidence.md](faq-answer-evidence.md)를 따른다. 기존 확정 판정·전송 데이터는 변경하지 않으며 새 배열 전송은 별도 스위치로 제어한다.

## 범위와 결정

- RAG 검색·리랭킹·Live 응답 경로는 유지한다. 보고용 Live 도구는 추가하지 않는다.
- 종료 훅에서 전사·검색 결과·기존 인사이트 초안을 SQLite에 먼저 저장한다. 서비스 소유 백그라운드 작업이 전체 대화를 검토한다.
- 검색 성공 여부와 실제 답변 여부는 다르다. 최종 미답변만 수집하며, 확인 중·명확화 질문·후속 해결·같은 문의의 반복 검색은 중복 수집하지 않는다.
- 고객 원문과 AI 발화의 인덱스·직접 인용을 검증한다. 사유는 연결된 마지막 검색 결과로 코드에서 결정한다: 정상 검색이면 KB_NO_ANSWER, unavailable이면 KB_UNAVAILABLE. 판정 실패를 KB_UNAVAILABLE로 바꾸지 않는다.
- 입력과 검증된 판정을 영속한다. 확정된 판정은 재시작 때 재판정하지 않고 같은 eventId·본문으로 보낸다. faqAnswerCount는 검토된 문의 중 ANSWERED 수다. 이는 사실 정확성 평가와는 별개다.

## 처리 순서

1. 기존 주문 결과 처리는 유지한다.
2. 종료 전사·검색 기록·인사이트 초안을 review_jobs에 저장한다.
3. 종료 훅은 반환하고, 별도 작업이 구조화된 LLM 판정을 수행한다. 저장되지 않은 원본 질문을 만들어 내지 않는다.
4. 결과 검증 후 판정 및 전송 예정 인사이트를 하나의 SQLite 업데이트로 확정한다.
5. 백엔드 reason 계약 활성화 후 기존 미답변 → QUESTION_UNANSWERED 이벤트 → 분석 순서로 전송한다.
6. API 실패·프로세스 종료 시 영속 상태에서 재개한다. 백엔드 전송 전에 판정이 확정되어 분석 본문이 바뀌지 않는다.

## 외부 계약 확인 / 운영 적용 대기

2026-11-04 `origin/develop-backend` fbbaca1의 계약·DTO를 확인했다. 기존 6필드는 필수이고 reason은 선택으로 KB_NO_ANSWER / KB_UNAVAILABLE / null을 허용한다. 생략/null은 미분류, 명시한 reason은 멱등성 본문 비교에 포함된다. 현재 전송 형식과 일치한다. 최신 원문은 docs/be-contract/backend에 보관한다. 이후 사용자가 백엔드 배포 완료를 확인했다. 운영 DB 상태나 실제 수집 API에 직접 요청하여 검증한 것은 아니다.

설정 클래스의 기본값은 두 플래그 모두 false다. 현재 작업 브랜치의 server.toml은 사용자 배포 확인과 아래 실제 모델 검증을 반영해 enabled=true, reason_contract_enabled=true로 준비했다. 이 설정은 AI 코드와 함께 배포돼야 적용된다. 운영 AI 배포·실제 관리자 수집 확인은 아직 하지 않았다. 구버전 백엔드를 쓰는 환경에는 이 설정을 적용하지 않는다. reason_contract_enabled=false이면 판정은 저장하지만 해당 통화 인사이트 전송은 보류한다.

## 검증과 한계

단위·통합 테스트에는 가짜 모델과 가짜 백엔드를 쓴다. 실제 API·전화 호출은 하지 않는다. 시간 초과·거절·잘못된 참조·입력 한도 초과는 검토 오류로 보존하고 미답변으로 전송하지 않는다. 자동 재시도 횟수는 제한한다. 모델의 의미 판정 정확성은 별도 검토 데이터로 확인해야 한다.

### 실제 모델 가상 통화 검증 (2026-11-04)

scripts/check_unanswered_review.py로 gpt-6-luna에 개인정보 없는 가상 통화 8건을 전달했다. 정상 검색 후 미답변·검색 장애·부정형 정상 답변·장애 후 해결·확인 중 이후 해결·명확화·확인 중만 남음·두 문의가 섞인 통화가 모두 기대한 사유/미답변 수/답변 수와 일치했다(8/8). 판정 및 인용은 output/unanswered-review/backend-deployed-20261104.json에 저장했다. 실제 백엔드·전화·RAG에는 요청하지 않았다. 이 작은 사전 점검 결과를 전체 실통화 정확도라고 해석하지 않는다.

판정 1건은 2.181~4.468초였다. 통화 종료 후 처리 시간이며 고객 응답 지연에 합산하지 않는다. 환경에 BACKEND_MODEL이 없어 현재 compose 기본 모델 gpt-6-luna를 CLI로 명시했다. 운영이 다른 모델이면 같은 스크립트에 --model로 그 모델을 명시해 다시 확인한다.

현재 검토 오류가 재시도 상한에 도달하면 FAILED로 남기고 해당 통화의 이벤트·분석도 보류한다. 기존 주문/통화 결과 전송은 유지한다. 검토 실패 때 검색 횟수를 답변 횟수로 대신 보내지 않는다. 운영 활성화 전 FAILED 감시·보류 해소 절차와 실제 모델 판정 검증이 필요하다.

설정의 모델은 기존 BACKEND_MODEL을 사용한다. 호출은 통화 종료 후 1회(실패 시 제한된 재시도)이며, 요청 저장 옵션은 store=false다. 프로세스 내에서 검토를 직렬 수행한다. 다중 워커로 동일 SQLite를 공유하는 배포의 작업 선점은 현재 지원하지 않는다.

백엔드 전달안은 [unanswered-reason-proposal.md](../contracts/unanswered-reason-proposal.md)에 별도로 정리했다.

전사는 현재 통화 기록의 보존 범위(최대 300행)를 따른다. 잘린 긴 통화나 확인할 수 없는 대화는 UNKNOWN으로 남겨야 한다. 수집 범위는 search_manual과 연결된 문의다. RAG 호출 없이 끝난 대화는 이 기능으로 추정 수집하지 않는다.

review_jobs에는 개인정보가 포함될 수 있다. 기존 Outbox와 같은 접근·보존 정책을 적용하고 일반 로그에 입력·인용을 출력하지 않는다.
