# Live 주도 업무 판단·기록 분리 설계

2026-11-05 · Jira S15P31D109-161 · 최초 기준 develop-ai `f229c41` · 최신 재검토 기준 `c101c5e`

상태: 사용자 진행 승인 후 로컬 구현·검증 완료. 아래 설계 검토 기록의 미구현 표시는 당시 상태이며 최신 구현 결과는 §14를 우선한다. 운영 서버/페르소나 원본은 변경하지 않았다.
사용자 방향: 제약 충족 여부와 대화 진행은 Live-1이 판단하고, 적절한 값이 들어왔을 때 도구로 기록한다. 금액뿐 아니라 전체 흐름을 같은 기준으로 재검토한다.

## 1. 목표와 역할

택배 접수 창구 직원이 매 질문마다 뒤쪽 사무실에 허락을 구하지 않고, 책상 위 규칙표를 보고 바로 상담하는 구조다. 사무실에는 조회·기록·실제 접수처럼 처리할 일이 있을 때 요청한다.

- **Live**: 고객 말의 뜻, 허용 범위, 부족하거나 애매한 정보, 재질문, 다음 질문, 정정·중단·업무 전환, 확인 답의 의미를 판단한다.
- **기록 어댑터**: Live가 기록 대상으로 선택한 정보를 도구 인자로 전달한다. 별도 LLM이 필요한 동안에도 절차 판단과 정책 재심사는 맡기지 않는다.
- **애플리케이션**: 값 저장, 작업 순서와 버전, 실제 조회·접수·취소·전환, 성공·실패 통지를 담당한다.
- **외부 BE**: 기존 계약과 실제 업무 상태를 유지한다. AI 서버 안의 백엔드 LLM·검증 코드와 구분한다.

대화에서 정상적으로 거절할지 판단하려고 매번 서버를 기다리는 경로를 없앤다. 저장 직전 자료형·계약 범위 확인은 짧은 로컬 처리로 남기되, 정상 대화의 다음 질문을 승인하는 역할은 하지 않는다. 모델 판단과 실제 저장이 다르면 이를 숨기지 않고 해당 항목을 복구한다.

## 2. 현재 대기와 순서 문제의 근거

| 위치 | 현재 동작 | 개편 방향 |
| --- | --- | --- |
| `app/policy/render.py:render_policy` | 자유형 값마다 위임. 결과 대기 중 판단·다음 질문 금지 | 규칙 위반·모호한 값은 Live가 재질문. 정상 값의 기록과 독립 질문을 분리 |
| `policy/business_rules.md` | 다음 질문·상세주소·가격·전화번호 안내가 서버 결과에 의존 | 수집 순서와 입력 규칙을 Live에 완결된 형태로 제공 |
| `app/calls/service.py:session_config` | 함수 도구가 `delegation.responses.tools`에 있으며 백엔드 모델이 호출 | 프롬프트 판단 이동과 도구 전달 경로 변경을 별도 단계로 검증 |
| `app/tools/record.py:record_fields` | 이름·번호·물품·금액·주소·수거 처리와 확인 준비가 한 호출에 결합 | 빠른 값 기록, 느린 주소 처리, 최종 확인 준비를 분리 |
| 같은 함수의 주소 `gather` | 같은 호출에 주소가 있으면 다른 값 반영도 주소 결과 뒤에 진행 | 이름·금액 등 독립 값은 먼저 반영하고 주소는 별도 작업 |
| `app/tools/outcome.py:state_summary` | 서버의 `stage/missing/can_proceed` 반환 | 누락 목록은 복구·최종 확인용. 매 질문의 지휘자는 Live |
| `app/calls/live.py:judge/apply` | 발화 끝 뒤 별도 Decision이 의도·동의·후보·종료 등을 판단 | 의미 판단을 Live로 일원화하는 목표. 신뢰할 수 있는 이벤트 전달 방식 확인 후 전환 |
| `app/domain/confirm.py` | 되읽기 시점·스냅샷·별도 판단·지연 후 확정 | Live가 동의를 해석하고 서버는 확인 대상·버전·실행 가능 상태를 검사 |
| `app/calls/live.py:notify/_wait_quiet/resume` | 위임 완료·발화 종료를 기다려 결과 안내, 재개 이벤트 전송 | 기록 성공은 조용히 반영. 현재 대화에 필요한 결과만 안내 |

설정 기본값은 발화 끝 감지 800ms, Decision 예산 1초, 확정 지연 700ms, 응답 완료 이벤트 누락 시 재개 대기 3초다. N2 안내와 고객 발화 대기는 각각 최대 8초다. 서로 다른 경로의 값이므로 합산해서 통화 지연이라고 단정하지 않는다. 이번에는 실통화 시간을 측정하지 않았다.

| 조회·취소 | 용건·대상·동의 해석, 조건 설명 | 본인 범위 조회·실제 취소·현재 상태 확인·중복 방지 |

| 요금 | 제공된 요금표로 일반 정책 설명 가능하도록 검토 | 실제 주문의 합계는 결정적 계산 결과 사용. 물품 가액과 구분 |
| FAQ | 이미 프롬프트에 고정 제공된 접수 규칙은 즉답. 그 밖은 검색 판단 | RAG 원본 유지. 최신 정책·근거 검색과 답변 근거 기록 |
| 재질문·이관 | 단순 실패·불만·무관 요청을 보고 대화 방식 결정 | 실제 장애/실패 정보·상담원 가용 정보 제공, 연결 실행 |
| 마무리 | 더 필요한 일이 있는지 판단, 안내·인사 | 실제 접수 결과·재시도·통화 종료·종료 후 분석 |

주소의 존재, 주문 상태, 취소 성공, 고객 자격은 외부 사실이다. 규칙을 프롬프트에 넣더라도 이 사실까지 모델의 기억으로 결정할 수는 없다.

### 금액 등 현재 확인된 불일치

- 기록 인수 `item_price`: 0~100,000,000원 **양 끝 포함**.
- 업무 프롬프트: **1억 원 이상**을 처리하기 어렵다고 응대. 정확히 1억 원에서 코드와 다르다.
- BE 문서 `docs/be-contract/backend/orders.md`: 0~9,007,199,254,740,991 정수. 이는 전송 가능한 기술 범위이며 서비스 접수 상한과는 구분한다.
- 0원은 현행 BE에서 수집 가능한 값이지만, 사용자 결정(2026-11-05)으로 새 AI 접수 정책에서는 허용하지 않는다. 외부 BE 계약 자체를 변경하는 것은 아니다.
- 현재 물품 수량은 규격별 0~99로 구현돼 있으나, 사용자 확정 정책은 **받는 곳별 택배 묶음마다 박스 소형·중형·대형 합계 최대 10개, 서류는 별도로 최대 100개**다. 규격별 10개나 통화 전체 합계가 아니다. 합산은 해당 묶음의 정정 후 전체 물품 구성을 기준으로 판단한다. 한도를 맞추려고 같은 묶음을 자동 분할하지 않는다.
- 수거 3일 이내는 `workflow.toml`에서 임시로 표시돼 있었으나 사용자가 최대 3일로 확정했다. 최소 현재 시각부터 1시간 이후 조건도 유지한다. 날짜 상한은 기존처럼 한국 시간 오늘+3일의 날짜까지로 해석한다. 최신 정책에서는 수거 시각을 받으므로, 오래된 문서의 ‘수거 시각을 묻지 않고 값도 보내지 않음’을 근거로 기능을 제거하지 않는다.

사용자 확정(2026-11-05): 원 단위 정수 가액은 `0 < 가액 < 1억 원`, 즉 1~99,999,999원만 허용한다. 0원 이하와 1억 원 이상이면 Live가 재질문한다. 수량·수거 정책도 위와 같이 확정했으며 실행 코드 반영은 후속 구현 단계다.

## 4. 목표 대화 흐름

```text
고객 발화
  → Live가 규칙·대화 맥락으로 판단
      ├─ 범위 밖/불명확 → 즉시 설명·재질문 (판단을 위한 도구 호출 없음)
      ├─ 정상 값 → 기록 요청 + 독립적인 다음 질문
      └─ 외부 사실 필요 → 조회 요청. 주소 조회는 완료될 때까지 다음 작업을 시작하지 않음

기록/조회 작업 결과
  → 요청·택배·필드 버전 대조
      ├─ 정상 기록 → 조용히 수신 확인
      ├─ 현재 대화에 필요한 결과 → 해당 질문/안내에 반영
      ├─ 실패 → 미기록 항목을 알려 복구
      └─ 오래된 결과 → 이전 값으로 덮지 않음

최종 확인
  → 필요한 기록·주소 조회 완료 → 서버 기록본으로 되읽기
  → 읽는 중 고객이 내용을 이해·수락하거나 진행을 요청하면 남은 되읽기는 중단 가능
  → Live가 고객 동의/정정 구분 → 대상·버전 검사 → 실제 접수/취소
  → 실제 결과로 완료 안내
```

### 무엇을 기다리고 무엇은 계속하는가

- 이름 기록 중: 받는 분 연락처처럼 독립적인 질문을 계속할 수 있다.
- 주소 조회 중: 사용자 결정(2026-11-05)으로 다음 작업·다음 항목 질문을 시작하지 않는다. 조회가 성공하고 주소가 정리된 뒤 다음 순서로 진행한다. 못 찾거나 실패하면 해당 주소를 재질문하거나 복구하고, 실패 결과가 도착했다는 이유만으로 다음 작업을 진행하지 않는다. 고객이 먼저 말을 보태거나 정정하면 수용하고 해당 조회의 버전을 갱신하되, 다른 업무를 먼저 시작하지 않는다.
- 주소 조회 결과가 없는데 해당 주소가 맞다고 확정하거나, 주소록 후보를 추측해 적용하지 않는다.
- 모든 값이 들렸지만 기록 중이면 같은 항목을 다시 묻지 않는다. 최종 되읽기 직전에 필요한 작업만 한 번 기다린다.
- 취소·접수·연결 완료처럼 실제 실행 결과에 의존하는 말은 그 결과를 기다린다.

예: 고객이 ‘물건 값은 이억 원이에요’ → Live가 즉시 허용 범위를 설명하고 재질문한다. 기록 도구를 불러서 거절을 받아오는 과정은 없다.

예: 고객이 ‘삼만 원이에요. 소형 두 개고요’ → Live가 두 값을 판단해 기록 요청한다. 아직 받지 않은 독립 정보가 있으면 질문한다. 모든 정보가 끝났다면 기록 수신 확인 후 저장된 내용으로 되읽는다.

예: ‘네, 그런데 받는 분은 김민수예요’ → 동의로 확정하지 않고 정정을 기록한다. 이전 이름을 읽어 준 확인은 폐기하고 수정된 내용으로 다시 확인한다.

## 5. 규칙 원본과 프롬프트 구성

제안 파일 `policy/input_rules.toml`에 금액·수량·전화 형식·문자열 길이·허용 품목을 선언한다. 기존 `workflow.toml`의 수거·수집 순서와 역할을 분명히 나눈다. 같은 규칙을 Markdown과 Python에 따로 적지 않는다.

1. **규칙 원본**: 허용 경계의 포함/제외, 단위, 미수집/0/없음의 의미까지 명시.
2. **Live 지시문**: 원본에서 사람이 이해하는 규칙과 정상/거절/애매함 예시를 생성.
3. **기록 스키마**: 같은 원본에서 자료형·전송 한도를 생성. 서비스 정책과 API 기술 한도는 이름을 구분.
4. **운영 페르소나**: 말투·인사만 덮어쓰며 업무 규칙을 바꾸지 못함.
5. **백엔드 어댑터 지시문**: 값과 행동의 전달에 한정. 다음 절차나 재질문을 다시 판단하지 않음.

프롬프트는 ‘server missing의 첫 항목을 묻는다’ 대신 ‘고객이 이미 제공했거나 등록 정보에서 확인된 항목을 제외하고 기본 순서대로 묻는다. 기록 중은 미수집으로 보지 않는다’를 포함한다.

시간 조건은 통화 시작 시각만으로 판단하지 않는다. 한국 시간의 현재 시각과 계산된 허용 구간을 통화에 공급하고, 자정·마감시간을 넘기면 갱신한다. 동적 정보 전달·프롬프트 길이·충돌은 별도 확인한다.

## 6. 기록과 대화의 어긋남 방지

Live가 ‘들은 값’과 서버가 ‘기록한 값’을 분리하되, 서로 맞추는 절차를 둔다. 새 접수 항목을 모델 대화 기억에만 보관하지 않는다.

- 제안 요청 정보: `request_id`, `parcel_id`, `utterance_id`, 대상 필드, 필드별 수정 순서, 근거 발화 참조.
- 요청 식별자는 가능한 한 서버가 발급·연결한다. 모델에게 순번 계산을 맡기지 않는다.
- 빠른 필드는 먼저 기록한다. 주소 조회 실패가 같은 호출의 정상 금액·이름을 막지 않게 한다.
- 필드별 `아직 안 들음 / 기록 중 / 기록됨 / 조회 중 / 재입력 필요`를 구분한다.
- 수신 확인은 적용한 필드와 수정 순서를 돌려준다. 오래된 `missing`으로 앞 질문에 되돌아가지 않는다.
- ‘주소 변경’은 기본·상세·조회 결과를 같은 주소 버전으로 묶는다. 이전 주소의 상세나 우편번호를 새 주소에 붙이지 않는다.
- 물품 정정은 현재 전체 구성을 기준으로 처리하고, 서로 다른 시점의 전체 구성을 완료 순서대로 덮지 않는다.
- 여러 택배 사이에서 늦은 결과가 현재 택배에 들어가지 않게 한다.
- 동시 기록 허용 시 순서 기준은 완료 시각이 아닌 고객의 정정 순서다. 판별할 수 없으면 성공으로 덮지 않고 복구한다.
- 실패를 조용히 버리지 않는다. 현재 항목의 기록 실패를 통지하고 재기록/재질문한다. 이미 성공한 값은 다시 묻지 않는다.
- 되읽기는 최신 기록 버전이 모두 반영된 시점의 확인본을 사용한다. 동의 이후 수정이 오면 그 확인본은 무효다.
- 사용자 결정: 최종 되읽기는 하되, 고객이 중간에 ‘알겠어요’, ‘그렇게 해주세요’처럼 내용 수락·진행 의사를 밝히면 남은 내용을 끝까지 읽거나 끝에 다시 같은 확인을 요구하지 않는다. Live가 발화 전체와 맥락으로 판단한다. ‘네, 그런데 이름은…’은 정정이며, ‘알겠는데 주소를 다시 말해주세요’는 추가 확인 요청이다. 중간 수락은 해당 확인본에 대한 동의로 연결하며, 아직 읽지 않은 항목을 모두 발화했다고 기록하지 않는다.
- 위 문구는 예시일 뿐 허용 문구 목록이 아니다. 특정 단어의 포함 여부나 고정 문장 일치로 판단하지 않는다. 표현이 달라도 고객이 내용을 받아들이거나 더 듣지 않고 진행하기를 원한다는 뉘앙스라면 Live가 문맥으로 판단해 되읽기를 마치고 진행한다. 정정·질문·조건이 이어지면 그 의도를 먼저 처리한다.
- 접수·취소·주소 저장은 기존 중복 실행 방지와 재시도 규칙을 유지한다.

위 요청 정보는 AI 서버 내부 설계 제안이다. 외부 BE 요청 필드를 추가한다는 뜻이 아니다.

## 7. 도구 호출 경로와 Decision의 전환

현재 설치 SDK와 코드에서 확인한 것은 Live의 Responses 위임과 그 안의 함수 도구다. 현재 설정은 Live가 구조화된 기록 도구를 직접 호출하는 형태가 아니다. SDK에 client 위임 타입은 있으나, 그것만으로 Live의 판단·검증된 값이 서버에 구조화되어 도착한다고 결론 내릴 수 없다.

**1단계 권장**: Live가 정상/거절·재질문·다음 질문을 맡고, 기존 Responses 위임은 정상 값 기록에만 사용한다. API 연동을 크게 바꾸지 않고 판단 이동 효과를 먼저 측정한다. 정상 값에서도 위임 자체의 지연은 남는다. Live의 기록 의도가 어댑터에 정확히 전달되는지 반드시 실제 세션으로 확인한다.

**최종 목표**: Live의 판단을 명시적인 기록·행동 요청으로 전달하고, 별도 모델이 같은 의미를 다시 판단하는 경로를 제거한다. 직접 전달 경로가 확인되지 않으면 ‘백엔드 LLM 제거 완료’라고 하지 않는다. 고객 원문을 어댑터가 다시 정책 판정하는 방식도 최종 목표와 다르다.

별도 Decision은 의도·후보·동의·추가 택배·저장·콜백 판단을 Live로 옮기는 동안 대조 측정만 할 수 있다. 최종 실행의 판단자는 하나여야 하므로 두 모델의 답을 모두 요구하지 않는다. Live의 행동 요청을 안정적으로 수신할 경로가 준비된 뒤 항목별로 교체한다.

확인·취소·주소 저장에서는 Live가 ‘고객이 동의했다’는 의미를 판단하되, 서버는 요청의 확인 ID·대상·버전·이미 실행 여부를 검사한다. 최종 주문 되읽기는 고객이 중간에 수락하면 끝낼 수 있으므로 기존 G3의 ‘되읽기 종료·확인 질문 완료 후 답만 허용’ 조건은 그 경로에서 변경해야 한다. 단순 맞장구와 수락·진행 요청의 구분은 Live가 발화 전체로 판단한다. 이 조기 종료 규칙을 취소·주소 저장 동의까지 자동 확대하지 않는다. AI가 소리 내 말한 자연어를 정규식으로 읽어 실행 신호로 쓰지 않는다.

작은 실험에서 확인할 것:

1. Live가 규칙 위반 값에 위임 없이 즉답하는가?
2. 정상 값 기록 위임 중 독립 질문을 실제로 계속할 수 있는가? 프롬프트 변경만으로 보장하지 않는다.
3. Live가 승인한 값·정정·행동을 어떤 구조화 경로로 정확히 전달할 수 있는가?
4. 조용한 기록 수신 확인과 필수 결과 안내가 가능한가? 기존 `response.create`를 임의로 없애지 않는다.
5. 고객 끼어들기·연속 정정·동시 주소 처리에서 요청과 발화를 연결할 수 있는가?

- 수거: 현재+60분 전후, 09:00·17:00 경계, 3일 경계, 자정 통과, 장시간 통화.
- 흐름: 한 번에 여러 값, 순서 밖 정보, 같은 항목 연속 정정, 주소 조회 중 다른 값, 여러 택배, 문의 후 복귀.

- 장애: 기록 실패·재시도·중복 호출·결과 역전·통화 종료 직전 기록·이미 접수한 주문 수정.

동일 대본의 기존/개편 세션에서 고객 발화 끝→유효한 다음 응답, 위임→기록, 최종 값→되읽기, 불필요 재질문, 누락·오저장·오확정, 위임/Decision 횟수, 비용을 비교한다. 지연은 P50/P95와 표본 수를 함께 보고한다. 무관한 맞장구로 응답 시간만 짧게 보이게 하지 않는다.

규칙 위반만 있는 발화에서는 기록 도구 호출 0회가 목표다. 정상 수집에서 서버 기록을 기다리는 불필요한 대화 중단이 줄고, 누락·오저장·잘못된 확정이 평가 대본에 없어야 한다. 성능 개선 수치와 처리량은 측정 전 미확정이다.

단계별 전환 설정으로 기존 경로로 돌아갈 수 있게 하되, 한 통화에서는 하나의 판단 방식만 사용한다. 진행 중 통화의 정책 버전과 판단 방식을 중간에 바꾸지 않는다.

## 10. 사용자 확정 사항

1. **확정**: 물품 가액은 0원을 허용하지 않고 1억 원부터 거절한다. 원 단위 정수 1~99,999,999원.
2. **확정**: 받는 곳별 택배 묶음마다 박스 소형·중형·대형 합계 최대 10개, 서류는 별도로 최대 100개. 통화 전체 합계 제한이 아니다. 수거는 최대 3일 이내·현재부터 최소 1시간 이후.
3. **확정**: 주소 조회가 마무리되어야 다음 작업으로 진행한다. 조회 중 다른 항목으로 건너뛰는 예외는 두지 않는다.
4. **확정**: 최종 되읽기는 진행한다. 특정 문구와 무관하게 고객이 내용 수락·진행을 원하는 뉘앙스이면 Live가 문맥으로 판단해 남은 되읽기를 끝내고 진행한다. 서버 기록본을 기준으로 하되 끝까지 읽어야만 동의를 인정하는 기존 조건은 개편한다.

도구의 직접 전달 가능성은 사용자에게 추측을 요구할 결정이 아니라 구현 전 작은 실험으로 확인할 기술 항목이다.

## 11. 전체 연결 재점검과 추가 보완 (2026-11-05)

검토 범위: 서버 조립·설정·프롬프트 생성, 통화 시작/위임/전사/판단/종료, 도구 실행·기록·조회·취소, 도메인 상태·확인·택배 보관·수거·요금, 주소 어댑터, BE 매핑·등록·결과 전송·아웃박스·종료 후 분석, 관제/대시보드·관련 테스트, 배포 진입점. RAG 내부 검색 알고리즘은 변경 대상으로 재설계하지 않았다.

결론: 방향은 유지하되 아래 연결부를 보완해야 한다. 프롬프트 변경만으로 전체 설계가 검증됐다고 볼 수 없고, Live 행동 전달 경로·대기 중 진행 가능성은 0단계 실험이 선행돼야 한다.

### A. 주소 조회 ‘완료’는 함수 반환과 다르다

현재 `AddressService`는 시간 초과/장애를 `error`, DB 미설정을 `off`로 반환하며 `record_fields`는 들은 주소를 기록하고 진행할 수 있다. `confirmed`여도 지번·동명·우편번호 조회가 실패해 geo가 없을 수 있다. 이는 새 ‘주소를 마무리하고 진행’ 규칙과 맞지 않는다.

목표: 조회 중/주소 확인됨/못 찾음/시스템 장애/미설정/추가 주소 정보 부족을 구분한다. 정상 진행 조건은 기존 후보 정책에 따른 주소 확정(ambiguous는 현행 1순위 정책 유지)과 BE에 필요한 주소 정보 확보다. `off/error/geo 없음`을 정상 완료로 숨기지 않는다. 실패는 시간 제한과 복구 경로를 가지며 무한 대기하지 않는다. 고객에게 같은 주소를 반복시키기 전에 고객 입력 문제와 시스템 문제를 구분한다. 기존 상담원/미완료 경로로 종료할 때에도 주소 확인 성공으로 표시하지 않는다.

한 발화에 보내는 곳·받는 곳 주소가 함께 오면 둘 다 보존하고 조회할 수 있으나, 해당 주소 작업이 정리되기 전에 다음 질문을 시작하지 않는다. 같은 발화의 다른 값은 기록할 수 있으며, 이는 다음 업무를 먼저 시작한다는 뜻이 아니다.

### B. 되읽기 중 수락과 후속 발화의 충돌

G3만 제거하면 `claims.py`의 `no_pending` 검사나 기존 확정 타이머가 Live의 정상 진행 발화를 다시 막을 수 있다. Live 수락 이벤트는 확인본 ID·버전에 연결하고, 그 이벤트를 서버가 받아 확인 대기 상태를 정리한 뒤 진행한다. 의미는 재심사하지 않되, 대상·수정 버전·중복 실행 여부는 검사한다.

‘알겠어요… 그런데 이름은’처럼 발화가 이어질 수 있으므로 첫 단어만으로 확정하지 않는다. 현재 발화가 끝난 단위로 판단하고, 새 정정이 들어오면 진행 예약을 취소한다. 이때 사용하는 발화 끝 감지·짧은 실행 유예는 기존 설정을 출발점으로 측정하며 임의로 0으로 만들지 않는다. 단순 추가 택배 질문으로 넘어가는 것과 실제 주문 접수 완료 안내는 구분한다.

### C. 수거 시각도 확인본과 연결

현재 `pickup_at`은 통화 공용 상태이고 `draft_snapshot`의 택배 항목에 없으며, 기본 시각은 확인 대기를 만든 뒤 기록한다. 따라서 수거 시각을 바꿨는데 과거 확인본의 동의가 유효한 것으로 남을 위험을 따로 다뤄야 한다.

되읽기에 수거 시각을 포함하면 해당 시각의 버전을 확인본에 연결한다. 고객이 바꾸면 기존 수락을 그대로 쓰지 않는다. 자정·마감시간·최소 1시간 경계가 지나 유효 범위가 달라진 경우에도 실행 직전 계산 결과와 안내 내용을 맞춘다. 수거 시각이 통화 공용인 현행 외부 계약은 유지하며 받는 곳마다 임의의 다른 시각을 만들지 않는다.

### D. 수량의 합계·정정·범위

사용자 확인: 제한은 받는 곳별 묶음마다 적용한다. 소형 6+중형 4는 허용, 소형 6+중형 5는 거절한다. 서로 다른 묶음 A 10개/B 10개는 각각 한도 내다. 서류 100개는 별도 한도이며 박스 합계에 넣지 않는다.

묶음의 서버 ID를 기준으로 현재 전체 구성에 적용한다. 정정은 기존 수량에 무조건 더하지 않고 교체·증감 의도를 Live가 해석해 최종 구성으로 기록한다. 받는 곳 변경만으로 같은 물품을 새 묶음에 복제하거나 한도를 회피하도록 자동 분할하지 않는다. `other_item`은 별도 수량 근거가 없으므로 박스 수에 임의 합산하지 않으며 현행 기타 물품·요금 미확정 경로를 유지한다.

### E. 기록 중 종료·수정 중 접수

현재 `finalize`는 통화 작업을 취소한 후 결과 전송 훅을 호출하며, `_maybe_submit`은 기록/수정 대기 전체를 확인하지 않는다. 비동기 기록을 늘리면 정상 발화의 값이 반영되기 전에 전송 본문을 고정할 수 있다.

정상 마무리 시에는 새 업무 수신을 닫고 이미 수신한 기록 작업을 제한 시간 안에서 정리한 뒤 확인본과 전송 본문을 고정한다. 실제 연결 끊김·시간 초과 시 미완료 작업은 성공으로 간주하지 않고 미완료 사유를 남긴다. 아웃박스에 들어간 본문은 기존 키·본문 그대로 재전송한다. 늦은 작업으로 이미 전송한 본문을 몰래 바꾸지 않는다.

`store.snapshot_for_submit`의 ‘수정 중 종료 시 마지막 확인본 전송’은 기존 사용자 결정이다. 이번 작업에서 임의로 폐기하지 않는다. 정상 통화에서는 수정 중인 항목이 있는데 접수를 먼저 보내지 않도록 하고, 예기치 않은 종료 시 기존 정책 적용 사실을 내부 기록에 남긴다.

### F. Live가 거절한 입력도 대화 상태에 반영

위반 입력에 도구를 호출하지 않으면 기존 `record_invalid` 기반 재질문 횟수는 증가하지 않는다. 그래서 ‘도구 호출 0회’와 재질문 한도 추적은 별도다. Live가 재질문·항목 전환을 판단하고, 경량 대화 이벤트로 거절 항목·사유·발화 참조를 관측한다. 이는 값 기록 도구 호출이나 또 다른 의미 판정이 아니다. 이 이벤트 경로도 0단계에서 검증한다. 다른 항목/다른 문의의 실패를 같은 실패로 누적하지 않는다.

관제의 단계·미수집·기록 중·확인 상태, 이탈 단계와 종료 후 분석을 새 이벤트에 맞춘다. 현재 대기 지표는 첫 AI 발화부터 반응으로 세므로, 개선 평가는 맞장구와 실제 다음 질문/재질문/결과 안내를 구분해 별도 측정한다. 외부 대시보드 API 필드·열거형은 그대로 유지한다.

### G. 두 정책을 동시에 실행하지 않기

프롬프트, 기록 스키마, 확인 관문, 기존 Decision, 결과 문구 검사, 테스트 기대값을 같은 정책 버전으로 전환한다. 전환하지 않은 판단까지 Decision 전체를 먼저 제거하지 않는다. 전환된 판단은 Live가 유일한 판단자이며 기존 Decision은 실행 권한 없이 비교 관측만 가능하다.

기존 ‘서버 승인 전 번호 확정 금지’·‘확인 질문 끝까지 듣기’ 문구와 새 규칙이 같이 남지 않도록 `workflow.toml`, `business_rules.md`, `render.py`, 관련 AGENTS/설계 문서를 함께 점검한다. 실제 조회·취소·접수 성공을 서버 결과로만 안내하는 규칙은 유지한다.

### H. 구현 시작 조건과 남는 검증

업무 정책 결정은 문서에 반영됐다. 추가 정책 결정을 가정해서 구현하지 않는다. 구현 브랜치에서 가장 먼저 작은 세션 실험으로 구조화된 판단 전달·기록 위임 중 발화·되읽기 중 수락을 검증한다. 검증 실패 시 실패한 기능을 완료로 표시하지 않고 전환 범위를 조정한다. 이 실험 전에는 백엔드 LLM 제거 가능·지연 개선·전체 설계 무결성을 단정할 수 없다.

이 재점검은 코드 읽기와 설계 검토이며 실행 코드 변경·전체 테스트·실제 모델 평가·운영 검증을 대신하지 않는다.

### 12.1 최종 확인 준비를 공통 처리로 통합

`record_fields`뿐 아니라 PIN 선택·등록 고객 정보 채움·주소 조회 완료·수정 완료·수거 변경 뒤에도 같은 준비 검사를 수행한다. 준비 처리는 값·주소 조회·필요한 등록 작업·미결 기록을 확인하고, 기본 수거 시각 확정→확인본 생성→되읽을 값 구성 순서로 실행한다. 주소 저장 제안의 조건은 준비하되 질문은 최신 팀 구현대로 택배를 담은 뒤 별도로 한다(§13). 확인본 ID·버전이 같으면 중복 안내하지 않는다. 단순히 can_proceed=true만 보내고 Live가 읽을 값과 동의 대상은 없는 상태를 만들지 않는다.

개별 택배를 담는 확인과 접수 직전 마지막 최종 확인을 구분한다. 최종 접수 본문을 고정하기 전에 고객이 확인/수락한 최신 묶음과 실제 제출 묶음이 같은지 확인한다. 최종 확인 데이터에는 직접 말한 상세주소를 포함한다. 고객이 의미상 수락하면 읽기를 끝낼 수 있다는 결정도 유지한다. 중간 확인을 했다는 이유만으로 미반영 수정이나 미확인 추가 묶음을 최종 확인에 포함하지 않는다.

### 12.2 업무 전환·종료는 모든 단계에 공통

공통 행동: 접수 시작/복귀, 조회, 취소, 문의 삽입/복귀, 같은 주문에 택배 내용 추가, 상담원 요청, 종료 요청. 주업무와 잠시 삽입한 문의를 구분하고, 접수 작성 상태·후보·확인 상태를 각각 보관한다. 업무 전환 시 맞지 않는 후보/확인 요청은 무효화하고 늦은 응답은 이전 업무의 것으로 처리한다. 대기 중이어도 종료 의사를 받을 수 있어야 한다. 실제 종료는 기록 정리·하나의 주문 전송·마무리 절차를 따른다.

추가 택배도 같은 통화·주문 안에 보관한다. 받는 곳별 내역을 구별하는 내부 parcel ID는 별도 주문 ID가 아니며 기존 `parcels[]` 구조를 유지한다. 이름/연락처/주소/물품/가액의 이전 수신인 값을 다른 수신인에게 자동 복사하지 않는다. 동일 발송인 재사용은 현재 확인된 발송인 정보의 출처·버전을 보존한다. 이미 order_submitted인 상태의 추가/수정은 성공으로 처리하지 않는다. 전송 시점의 최종 결정은 §13을 따른다.

### 12.3 확인의 종류와 오류 판독

확인 요청은 `kind`, 확인 ID, 대상 ID, 확인본 버전, 목적별 읽기 데이터를 갖는다. 접수·취소·주소 저장·콜백 동의를 구분한다. 취소 재확인은 현재 작성 주문의 유무와 무관하게 선택한 취소 대상의 반환된 사실로 구성하고 ‘취소할까요’라는 목적을 유지한다. 취소 동의로 접수하거나 접수 동의로 취소하지 않는다.

오류 결과를 Live에 전달할 때 `status`, `code`, `needs`를 숨기지 않는다. 부분 성공이면 실제 반영 필드와 실패 필드를 분리한다. 기존 유효 번호를 유지한 채 새 번호만 거절된 경우는 ‘수정 안 됨’이며, 기존 번호가 VALID라는 사실만으로 성공을 추론하지 않는다. 새 규칙에서 Live가 사전 거절하더라도 도구의 실제 실패 판독 경로는 필요하다.

### 12.4 상대 시각과 상세주소

‘한 시간 뒤’는 세션 시작이 아닌 해당 고객 발화의 한국 시간 기준으로 계산한다. 발화 시각과 실행 시각의 작은 차이로 반복 거절되지 않도록 기준 시각을 요청에 연결하고 기존 10분 단위 올림을 활용한 후보를 제시한다. 한 시간 조건 자체를 느슨하게 바꾸지 않으며 실행 시점에 너무 가까워졌으면 갱신된 가능한 시각을 안내한다.

사용자 확정: **접수 직전 마지막 단계의 최종 확인에서는 직접 말한 상세주소를 읽는다.** 모든 대화 단계에서 상세주소를 반복한다는 뜻은 아니다. `speech`, business_rules, readback 데이터 필터와 테스트를 이 구분으로 통일한다. 저장된 주소록 상세주소는 먼저 읽지 않는다. 고객 정정으로 직접 입력한 상세주소가 되면 새 출처를 기록한다.

### 12.5 팀원 변경의 보존과 새 비동기 경로

이번 최신화에는 다음이 포함돼 있다.

- 통화 등록 번호를 먼저 보관하고 이전 접수의 출발지/도착지를 별도 병렬 조회한다. 새 설계에서도 번호 확보를 이력 조회 뒤로 되돌리지 않는다. 늦은 이력 조회 결과가 고객이 이미 정정한 값·선택한 후보·확인본을 덮거나 지난 출발지 질문을 다시 만들지 않도록 버전·출처 검사를 추가한다.
- 기본주소의 상세만 바뀌어도 저장을 제안한다. 기본주소 비교 시 도로명만이 아닌 상세주소까지 비교하는 변경을 유지한다.
- SENT_UNCERTAIN 주문을 실행 중에도 같은 키·본문으로 재확인한다. 기존 worker/lock/중복 방지와 재시도 제외 조건을 유지한다. 나중에 재전송 성공 시 과거 종료 분석의 주문 개수는 자동 갱신하지 않는 기존 한계도 유지·기록하며, 대화 구조 개편에서 이를 해결했다고 주장하지 않는다.

### 12.6 구현 순서와 회귀 기준 변경

0단계 실험 후, 운영 프롬프트 정합성·전역 업무 행동·확인 종류 분리·실패 결과 판독·공통 확인 준비를 우선 구현한다. 이후 Live 판단 전환과 기록 비동기화를 진행한다. QA 2~7은 프롬프트만 바꿔 해결했다고 표시하지 않는다. 운영 페르소나는 원문 확인과 검토 가능한 수정본 준비 후 승인된 적용 절차를 따르며 이번 검토에서 운영 설정을 직접 바꾸지 않는다.

## 13. 최신 변경 확인·주문 단위·프롬프트 배치 확정안

2026-11-05 사용자 요청으로 develop-ai `c101c5e`까지 최신화했다. 실행 코드는 변경하지 않았으며 구현 진행 오더를 기다린다. 이 절의 결정이 앞선 ‘추가 묶음’ 및 전송 시점 표현보다 우선한다.

### 13.1 취소 재확인: 최신 develop-ai에는 아직 남아 있음

`app/calls/live.py`의 `_follow(ask_confirm)`는 여전히 `pending and st.current is not None`일 때 접수용 `readback_facts`를 구성한다. `workflow.toml`의 `results.confirmation`도 여전히 ask_again을 ‘이대로 접수할까요?’로 설명한다. 따라서 취소용 재확인 분리 수정은 이 커밋에서 확인되지 않았다. 다른 브랜치에 작업됐을 가능성은 추측하며, develop-ai 반영 완료로 표시하지 않는다.

이번에 병합된 `5265473`은 **주소 저장 동의를 접수 확인에서 분리**한 작업이다. 택배를 담은 뒤 주소 저장을 별도로 묻고, 보내는 곳·받는 곳 저장을 한 번의 동의로 정한다. 취소 확인 수정과 다른 변경이며 이 최신 동작을 유지한다. `c101c5e`에는 FAQ 검색 후보와 최종 답변 근거 구분도 포함돼 있어 종료 후 근거 판정 경로를 과거 방식으로 되돌리지 않는다.

### 13.2 추가 택배는 통화 종료 시 하나의 주문으로 전송

사용자 명확화: 추가 택배 요청마다 별도 주문을 만드는 개편은 하지 않는다. 한 통화에서 추가·정정한 내역을 모으고, 종료 시 한 주문 본문의 `parcels[]`에 넣어 한 번 전송한다. 받는 곳별 박스 10개·서류 100개 제한과 내역 구분은 유지한다.

‘추가 수집을 시작한다’는 뜻은 같은 주문 안에서 다음 택배 정보를 받는다는 뜻이다. `more` 처리 보완은 다음에 무엇을 받을지 이어주는 것이며 주문 생성/제출 도구를 호출한다는 뜻이 아니다. 더 없다고 답한 뒤 문의나 정정이 이어질 수 있으므로 그 답만으로 주문을 먼저 전송하거나 수정 불가로 만들지 않는다.

현재 `_follow(no_more)`가 `_maybe_submit`을 호출하는 조기 전송 경로도 있으므로, ‘현재 코드가 항상 통화 종료에만 전송한다’고 설명하지 않는다. 개편 시 이번 사용자 지시에 맞춰 종료 시점의 하나의 전송 경로로 정리하고 중복 호출은 기존 아웃박스로 막는다. 정상 종료에서는 최종 확인·기록 정리를 완료하고 통화 마무리 과정에서 전송하며, 갑작스러운 끊김에는 기존 미완료/마지막 확인본 정책을 적용한다. 실제 결과 전까지 접수 완료를 약속하지 않는다.

### 13.3 Live 규칙이 들어갈 파일

Live에 전달되는 최종 프롬프트는 `app/policy/render.py:render_live`에서 조립하고 `app/calls/service.py:session_config`의 `instructions`에 넣는다. 사람이 관리하는 원문과 모델이 실제 받는 최종 문자열을 구분한다.

| 원문/설정 | 넣을 내용 | Live에 전달하는 방법 |
| --- | --- | --- |
| `policy/business_rules.md` | 고객 발화의 의미 판단, 허용/거절/재질문 원칙, 주소 조회 뒤 진행, 정정, 최종 확인과 의미상 수락, 주문 하나로 종료 시 전달, 실패 안내·개인정보 읽기 규칙 | 업무 규칙 본문으로 직접 포함 |
| `policy/input_rules.toml` **신규 예정** | 가액 1~99,999,999원, 박스 규격 합계 10·서류 100·받는 곳별 적용, 형식·단위 등 수치 규칙 | `render.py`가 한국어 규칙으로 변환해 Live 본문에 삽입. 파일 자체를 모델이 읽는 것은 아님 |
| `policy/workflow.toml` | 기본 수집 순서·필수 항목·기존 수거 1시간/3일/운영시간 설정·각 처리 결과의 의미 | `render_policy`가 상담 절차와 수거 규칙을 생성. 현재 서버 판단 전용 문구는 개편 |
| BE 운영 페르소나 `promptText` / 미설정 시 `policy/persona_default.md` | 역할·말투·인사·발화 스타일 | 페르소나 영역. 업무 규칙/도구 호출의 과거 제어 지시는 제거한 검토본 준비 |
| 통화별 동적 정보 | 현재 한국 시각/허용 수거 범위, 고객·기록/조회 상태, 도구 처리 결과 | 시작 정보와 통화 중 갱신 경로. 고정 파일에 당시 시각을 적어 두지 않음 |

`policy/backend_rules.md`는 Live 프롬프트가 아니라 Responses 위임 백엔드용이다. 별도 모델이 필요한 기간에는 기록/조회 인자 전달과 실제 결과의 오류 판독만 맡기고 Live와 같은 정책 판단을 중복 수행시키지 않는다. `prompts/unanswered_review.md`는 통화 종료 후 FAQ/미답변 검토용이므로 통화 중 접수 규칙의 원본으로 쓰지 않는다.

규칙 숫자와 예시를 여러 파일에 따로 하드코딩하지 않는다. 수치 원본으로 생성한 규칙과 사람이 작성하는 대화 원칙을 최종 Live 프롬프트에서 함께 볼 수 있도록 하고, 실제 조립 결과를 검토/회귀 기준으로 삼는다.

## 14. 구현 결과와 검증

### 실제 실행 경로

`config/server.toml`의 `[call].live_led=true`로 새 모드를 준비했다. `CallConfig` 자체 기본값은 false여서 설정이 없는 기존 환경은 기존 경로를 유지한다. 모드는 통화 생성 때 고정하고 진행 중 바꾸지 않는다.

- Live 원문: `policy/business_rules.md` + `input_rules.toml`에서 생성한 제약 + `workflow.toml`의 순서/수거/결과 의미. 기존 규칙은 `business_rules_legacy.md`로 보존했다.
- Responses 어댑터: `backend_rules_live.md`. Live는 계속 Responses에 위임하며, 네이티브 구조화 도구 인자가 Live에서 직접 나온다고 가정하지 않는다. 프롬프트에 맞는 발화를 실제 함수 인자/행동으로 바꾸는 어댑터는 남는다.
- 새 경로에서는 고객 발화 끝에 별도 Decision을 호출하지 않는다. 대신 `manage_conversation`이 용건·수락·후보·저장·콜백·추가·종료 행동을 기존 실행 계층으로 연결한다. 인자 전달 시 발화 ID·확인 ID·후보 버전과 현재 상태를 검사한다.
- 검토한 운영 페르소나 버전을 지정하기 전에는 새 경로에서 PersonaManager의 조회/적용 회신을 끄고 서버 기본 말투를 사용한다. 버전을 지정하면 그 버전만 사용하고 다른 PENDING을 APPLIED로 회신하지 않는다. 원문을 추측해 정규식으로 일부만 제거하지 않는다.

### 반영한 동작

- 가액 1~99,999,999원, 받는 곳별 박스 합계 10개·서류 100개. Live는 부적합한 값에 바로 재질문하고 기록 경계도 같은 수치 원본을 사용한다. 자료형/계약 방어 검사는 남는다.
- 단순 기록은 질문 진행 허용, 주소는 조회/필요 정보 확보 뒤 진행. 장애/off/지번 등 누락을 성공으로 넘기지 않는다.
- 기록 요청을 직렬화하고 발화 참조가 오래되면 반영하지 않는다. 기록/주소 대기·실패를 미수집과 구분하며, 거절된 정정 때문에 이전 값이 남아 있어도 확인을 열지 않는다.
- 기록/PIN 선택/출발지 적용이 공통 확인 준비를 호출한다. 기본 수거 시각을 정한 후 확인본을 만들고 수거 버전도 확인에 포함한다.
- 접수 되읽기 도중 의미상 수락은 허용하며 최신 확인본에만 연결한다. 새 발화가 오면 예약된 확정을 취소한다. 취소 확인은 별도 대상·문구·끝난 질문 조건을 유지한다.
- 문의/조회/취소에서도 종료·접수 복귀를 처리한다. 미확인 내용을 두고 ‘추가’로 건너뛰지 않으며, 추가 내역에는 발송인만 재사용하고 이전 수신인은 복사하지 않는다.
- ‘더 없음’만으로는 전송하지 않는다. 종료 과정에서 이미 받은 기록을 제한 시간 안에서 정리하고 여러 내역을 한 주문으로 전송한다. 기존 마지막 확인본/미완료/아웃박스 키·본문 보존 규칙은 유지한다.
- 상대 시각은 `pickup_after_minutes`로 서버가 현재 실행 시각에서 계산한다. 최신 시각/발화 시각도 통화와 get_state에 공급한다. 기본 수거 시각의 초 단위 버림으로 최소 1시간을 어기던 경계도 올림으로 수정했다.
- 늦은 주소 이력은 후보만 보충하며 이미 바꾼 기본주소·작성값을 되돌리지 않는다. 팀원의 주소 저장 분리·주기 재확인·FAQ 최종 근거 판정은 보존한다.

### 검증 근거와 한계

로컬 회귀는 별도 Decision 없는 경로, 금액/수량 경계, PIN 확인, 중간 수락, 취소 재확인, 상태/후보 참조, 늦은 주소/타임아웃, 상대 수거 시간, 기록 중 종료, 한 주문 합산, 페르소나 적용 회신을 검사한다. 전체 **633 passed, 14 warnings / 23.31초**. 마지막 프롬프트 수치 중복 제거·거절 기록의 등록 방지 수정 후 관련 **63 passed / 5.39초**를 확인했다. 경고는 기존 의존성의 사용 중단 예정 안내다.

실제 API 검사 도구 `scripts/check_live_led.py`는 공개 가상 정보·합성 음성만 사용하며 실제 PBX/BE/RAG를 호출하지 않는다.

- 가액 2억 원: 도구 호출 없이 허용 범위 안내·재질문 성공.
- 가액 3만 원: 발화 ID를 포함한 record_fields로 실제 로컬 기록 성공.
- 되읽기 중 ‘충분히 알겠으니 그대로 진행’ 의미의 합성 발화: 실제 LiveFlow에서 get_state→manage_conversation(confirm)→해당 확인본 담기 성공.

처음 금액 실험의 고정 get_state가 재질문을 유발해 실제 기록 상태를 반환하도록 실험 도구를 고쳤다. 중간 수락 실험의 초기 두 실행은 입력 오디오 공급 전 context_injection_incomplete/종료가 발생했으며, 지속 무음 입력으로 음성 시계를 진행한 세 번째 실행에서 성공했다. 실패 기록도 output에 보존한다. 각 성공은 소수 사례의 관측이며 모든 표현의 정확성이나 운영 품질을 보장하지 않는다.

실제 PBX 전화·운영 백엔드 연동·다수 통화 부하·대기시간 P50/P95 개선·운영 페르소나 수정은 미검증/미실행이다. RAG 내부와 외부 API 필드/인증/경로는 바꾸지 않았다. 저장된 모델 응답을 실행 신호로 파싱하지 않고 구조화 도구 요청만 사용한다.

공식 API 근거: [GPT-Live 위임과 도구](https://developers.openai.com/api/docs/guides/live-delegation), [GPT-Live 프롬프트](https://developers.openai.com/api/docs/guides/live-prompting).
