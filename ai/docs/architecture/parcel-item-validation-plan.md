# 전화 택배 접수 물품 검증 설계서

2026-11-06 · 구현 설계 및 검증 기준 · `feat/parcel-item-validation` · 기준 `develop-ai` `4878a08`

## 1. 접수 기준

전화 접수는 **서류, 소형 박스, 중형 박스, 대형 박스** 네 가지 규격으로 받는다. 고객이 “소형 박스 하나요”라고 하면 기존대로 진행한다. 모든 고객에게 박스 안의 물건, 무게, 치수를 추가로 묻는 절차는 두지 않는다.

고객이 포장 방식이나 내용물을 먼저 말하면 두 가지를 각각 확인한다.

- **포장 규격** — “옷을 보내려고요”처럼 내용물만 말하면 박스 규격을 묻는다. “쇼핑백 그대로 보낼게요”처럼 지원하지 않는 포장이라면 지원 규격을 안내하고 박스로 다시 포장할 수 있는지 묻는다.
- **내용물 제한** — “소형 박스에 현금을 넣었어요”처럼 금지 물품이 실제로 포함되어 있으면 규격과 관계없이 그 택배를 차단한다. 유리컵처럼 포장 조건이 적용되는 물건은 해당 조건만 확인한다.

변경 전 [`record_fields`](../../app/tools/record.py)는 박스 수량과 물품 가액의 범위를 검사하고 `other_item` 설명도 물품으로 기록했다. 기타 설명이 있으면 [배송비 계산](../../app/domain/fare.py)이 실패해 미완료가 되지만, `소형 박스 1개`만 기록하면 내용물 검사 없이 완료될 수 있었다. [FAQ 검색](../../app/tools/lookup.py)은 고객 문의에 답하는 데 사용한다.

## 2. 판정과 고객 안내

| 고객 발화 | 서버 판정 | 고객 안내 및 다음 동작 |
| --- | --- | --- |
| “서류 두 개요.” / “소형 박스 하나요.” | `ALLOW` | 규격과 수량을 기록하고 기존 절차 진행 |
| “옷을 보내려고요.” / “박스 하나요.” | `NEEDS_FORMAT` | “소형·중형·대형 중 어떤 크기의 박스로 보내시나요?”처럼 빠진 정보만 질문 |
| “쇼핑백 그대로요.” | `UNSUPPORTED_FORMAT` | “서류나 소형·중형·대형 박스로 접수할 수 있어요. 박스에 담아 보내실 수 있을까요?” |
| “소형 박스 안에 현금도 있어요.” | `PROHIBITED_ITEM` | “현금은 박스에 넣어도 보낼 수 없어요.” 해당 택배의 확인과 제출을 차단 |
| “유리컵을 박스에 넣었어요.” | `NEEDS_CONDITION` | “유리컵은 완충 포장이 필요해요. 완충재로 감싸 포장하셨나요?” |
| “완충 포장 안 했어요.” | `CONDITION_UNMET` | 포장 조건을 안내하고, 충족했다는 답변을 받기 전까지 보류 |
| “현금은 빼고 옷만 보내요. 소형 한 개요.” | `ALLOW` | 같은 택배에서 금지 물품을 뺐다는 정정을 반영한 뒤 다시 확인 |
| “배터리가 들어 있어요.” | `NEEDS_CONDITION` | 적용 정책에 따라 배터리만 따로 보내는 건지 확인. 단독 발송 여부를 추정해서 차단하지 않음 |
| “현금도 보낼 수 있나요?” | 문의 | 배송 정책을 답변. 그 질문만으로 현재 택배에 현금이 들어 있다고 처리하지 않음 |

금지 물품이 명확하면 규격을 다시 묻기 전에 금지 사유부터 알린다. 제한 품목이나 포장 조건이 언급됐는데 포함 여부가 애매하면 그 한 가지만 확인한다. 익숙하지 않은 물건 이름만으로 금지 판정을 내리지 않는다. `ALLOW`는 현재 들은 정보로 이 검사를 통과했다는 뜻이다. 고객에게 접수 완료를 알리는 기준은 기존 백엔드 결과를 따른다.

## 3. 정책의 출처

- 접수 판정에 사용하는 규칙은 [`policy/workflow.toml`](../../policy/workflow.toml)에 둔다. [정책 로더](../../app/policy/model.py)가 품목 분류와 수치 제한을 읽고, [정책 렌더러](../../app/policy/render.py)가 같은 분류를 위임 모델 지침에 전달한다. 수량과 가액의 기존 제한은 그대로 적용한다.
- [배송 FAQ](../../manuals/delivery_faq.md)의 `[디버]` 취급금지 목록과 `[일반]` 제한 안내를 전화 접수 판정에 적용한다. 현금성 물품, 독극물·폭발물·총포·도검, 살아 있는 동물·동물 사체, 귀중품, 인화성 물질·가스, 냉장·냉동·부패성 물품, 운송 제한품은 확인 시 차단한다. 배터리 단독 발송, 액체의 누수 방지, 유리·도자기의 완충 포장은 각 조건을 확인한다. 고객이 밝힌 한 변이 160cm를 넘거나 무게가 30kg을 넘으면 해당 치수나 무게를 사유로 안내한다.
- 전화 접수에서 ‘기타’로 받는다는 FAQ 문구와 예시를 네 가지 지원 규격에 맞춘다. 운영 FAQ가 관리자 등록본에서 제공되는 경우 해당 항목도 같은 내용으로 갱신할 수 있도록 변경 대상을 식별한다. 접수 중 판정에는 정책 파일을 사용하므로 매번 FAQ를 검색할 필요가 없다.

## 4. 발화에서 서버 판정까지

1. **고객 발화를 연결한다.** [`LiveFlow`](../../app/calls/live.py)의 고객 전사와 기존 위임 연결 방식을 사용한다. 모델은 `record_fields`에 규격별 수량과 함께, 고객이 실제 발송 대상으로 언급한 품목·포장·조건 및 근거 구절을 선택적으로 넘긴다. 질문이나 부정, 정정이 있으면 그 문맥도 전달한다. 규격이 없어도 물품 발화만으로 판정을 요청할 수 있게 한다.
2. **서버가 판정한다.** 서버는 위임과 연결된 고객 발화에 `item_evidence`의 근거 구절이 있는지 확인하고, 접수 정책을 적용해 결과 코드를 정한다. 모델이 내용물을 빼먹은 경우를 줄이기 위해 접수 중 고객 전사에서 등록된 제한 품목 후보와 명시된 수치도 직접 확인한다. 품목 후보만 잡히면 실제로 포함됐는지 짧게 확인한 뒤 진행한다.
3. **같은 택배에 적용한다.** 상태 변경은 기존 통화 잠금 안에서 발화 순서와 대상 택배를 확인한 뒤 적용한다. 늦게 도착한 도구 응답이 최신 정정을 덮어쓰거나 다음 택배에 적용되지 않게 한다. 대상이 애매한 경우 어느 택배인지 먼저 묻는다. 모델 응답이 늦거나 실패해도 서버가 발견한 미해결 후보는 접수 가능으로 바뀌지 않는다.
4. **상담 AI는 결과에 맞춰 말한다.** 도구 결과에 사유 코드와 다음 질문에 필요한 사실을 넣는다. 포장 재질문과 내용물 차단을 서로 다른 결과로 전달한다. 이미 들은 다른 정상 정보는 보존한다. 고객이 새 규격만 말해도 금지 물품이 제거됐다는 뜻으로 처리하지 않는다.

`other_item`은 새 전화 접수 도구의 허용 규격에서 제거한다. 기존 데이터와 백엔드 주문 계약이 사용하는 `otherItemDescription`은 호환을 위해 유지한다. 새 접수 판정의 품목 근거나 원문 발화는 주문 요청에 추가하지 않는다. 운영 확인에는 기존 도구 추적과 사유 코드를 활용한다.

## 5. 확인과 제출에서 지킬 조건

판정은 통화 전체가 아니라 **택배 묶음별**로 보관한다. 아직 언급된 제한이 없는 택배와, 금지 또는 포장 조건 미확인으로 보류된 택배를 구분한다. `items`가 이미 유효한 상태에서 일반 `record_invalid`를 호출하면 이전 값이 유지되므로, 배송 제한은 별도의 차단 상태로 다룬다. [현재 필드 상태 처리](../../app/domain/state.py)

| 시점 | 처리 |
| --- | --- |
| 물품 기록 및 되읽기 전 | 규격이 유효하고 미해결 제한이 없는 경우에만 되읽기를 시작한다. |
| 되읽기 직후, 고객 확인 전후 | 금지나 미확인 조건이 드러나면 기존 확인 대기를 무효로 한다. 뒤늦게 도착한 “네”로도 확정할 수 없다. 기존 확인 지연과 재검사 경로를 이용한다. |
| 이미 담은 택배를 정정 | 배송 제한을 알게 된 해당 묶음을 보류한다. 현재 수정본뿐 아니라 마지막 확인 기록도 제출에서 제외한다. 물품 제외나 조건 충족이 확인되면 새 내용으로 다시 고객 확인을 받는다. |
| 마무리 또는 통화 종료 | 해당 발화의 물품 판정이 반영되기 전에 완료 본문을 고정하지 않는다. 미해결 묶음이 남아 고객 확인을 받지 못한 경우 `INCOMPLETE`로 처리하고, 차단된 묶음은 전송 대상에서 뺀다. |
| 고객이 차단 묶음을 빼 달라고 명시 | 남은 묶음을 고객이 확인하면 정상 접수를 이어갈 수 있다. 다른 묶음을 조용히 대신 접수하지 않는다. |

확인 발급과 담기에는 [`confirm.py`](../../app/domain/confirm.py), 마지막 확인 기록 선택에는 [`store.py`](../../app/domain/store.py), 통화 결과 생성에는 [`outcome.py`](../../app/domain/outcome.py)를 사용한다. 자동 마무리와 강제 종료 경로 모두 [결과 본문 저장](../../app/calls/results.py) 전에 같은 판정을 적용한다. 이미 전송된 주문의 변경은 기존 상담원 안내 절차로 다룬다.

## 6. 구현 순서와 검증

1. 접수 정책과 서버 판정을 추가한다. 명확한 금지, 포장 재질문, 조건 확인, 정상 진행을 구분한다.
2. `record_fields`와 통화 흐름에 연결한다. 발화 근거, 대상 택배, 정정 순서, 상담 응답을 검증한다.
3. 확인과 제출에 제한 상태를 반영한다. 마지막 확인 기록으로 되돌아가는 경로와 통화 종료 시점을 함께 점검한다.
4. 상담 지침과 FAQ를 맞추고 기존 배송비·입력 제한·백엔드 계약 테스트를 실행한다. 아래 사례는 기존 테스트에서 다루지 않는 회귀 검증으로 추가한다.

| 검증 구간 | 통과 기준 |
| --- | --- |
| 정상 접수 | 내용물을 말하지 않은 서류·박스는 추가 질문 없이 진행한다. 혼합 규격의 수량과 요금 계산이 유지된다. |
| 포장 변경 | 쇼핑백을 거절한 뒤 고객이 소형 박스로 바꾸면 같은 택배의 접수가 가능하다. |
| 금지와 조건부 | 현금은 박스 수량을 함께 줘도 차단된다. 유리컵의 포장 미확인·미충족·충족을 구분한다. |
| 문맥과 누락 | “현금은 빼고”, 단순 FAQ 질문, 모델이 박스 수량만 전달한 금지 물품 발화를 각각 올바르게 처리한다. |
| 정정과 순서 | 확인 대기나 담기 이후 금지 물품이 드러나도 이전 내용으로 확정·제출되지 않는다. 늦은 응답은 최신 정정을 덮어쓰지 않는다. |
| 여러 택배와 종료 | 차단 상태가 다른 택배에 섞이지 않는다. 미해결 상태로 끊으면 차단된 택배가 전송되지 않고, 명시적으로 제외한 뒤 확인한 나머지 택배는 정상 접수할 수 있다. |
| 가상 음성 통화 | 규격이 정상일 때 질문이 늘지 않고, 문제를 발견하면 가격이나 접수 확인을 묻기 전에 해당 사유를 안내한다. |
