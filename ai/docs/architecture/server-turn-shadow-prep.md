# 서버 주도 발화의 그림자 모드

그림자 모드는 같은 고객 발화를 두 흐름에서 비교한다. 기존 흐름은 고객에게 응답하고 업무를 처리한다. 새 흐름은 같은 시점의 접수 내용을 복사해 “어떤 값을 기록하고 다음에 무엇을 물을지”를 계산한다. 예를 들어 고객이 “네, 맞습니다”라고 답하면, 두 흐름이 같은 받는 곳을 선택하는지 비교한다. 새 흐름의 선택은 비교 결과에만 남는다.

## 구현 상태와 실행 방법

- 구현 기준은 MR !527이 포함된 `develop-ai`의 `56a8396b`다. 운영 통화 `afc5ae01`에서 첫 인사 뒤 맞장구가 질문을 가린 경우를 회귀 대본으로 재생한다.
- 설정은 기본적으로 꺼져 있다. 측정 환경의 `config/server.toml`에 다음 값을 넣으면 활성화된다. 발화 수 상한은 프로세스마다 새로 센다.

```toml
[call]
turn_shadow_enabled = true
turn_shadow_max_concurrent = 2
turn_shadow_timeout_sec = 7.0
turn_shadow_max_turns = 300
```

- 완료한 비교는 기존 통화 로그의 `Turn shadow` 이벤트에 남긴다. `python -m call_analysis.turn_shadow_report logs/calls`로 건수, 일치율에 쓸 분모, 필드 차이, P50·P95를 집계한다. 기존 흐름은 질문이 전사에 시작된 시각을, 그림자 흐름은 결과를 계산한 시각을 잰다. 실제 재생 지연을 평가하려면 SIP 음성을 따로 확인한다.
- 현재 새 흐름의 도구는 복사본의 `record_fields`와 `get_state`다. 신규 주소는 외부 보정 없이 기록하고 `address_unverified`로 표시한다. 업체 검색·주문 조회·매뉴얼과 같이 외부 자료가 필요한 업무는 비교 가능 범위를 표시한다.

## 구현 순서

1. [LiveFlow의 고객 발화 끝 처리](../../app/calls/live.py)에서 기존 판단이 상태를 바꾸기 직전의 상태를 잠금 안에서 복사한다. 같은 발화 번호에 직전 질문과 당시 후보를 묶는다. 잠금을 풀고 기존 흐름과 별도로 새 작업을 실행한다. 통화가 끝나거나 새 발화로 결과가 낡으면 작업을 정리하고 비교에서 제외한다.
2. 새 경로의 판단은 현재 열린 질문부터 확인한다. MR !527의 주소 동의와 후보 선택을 같은 상태 변경 함수로 반영한다. 주소 변경, 전화번호 정정 등 다른 값이 섞였거나 판단이 불명확하면 새 Backend에 넘긴다. 마지막 접수 동의와 통화 종료 요청이 겹친 사례는 둘 다 보류하고 종료 확인을 비교 결과로 남긴다.
3. 새 Backend 연결은 [backend_turn.py](../../app/calls/backend_turn.py)에 두고, 발화 순서와 다음 질문을 정하는 코드는 [turn.py](../../app/calls/turn.py)에 둔다. [기존 도구 실행기](../../app/tools/executor.py)의 입력 검증을 사용한다. 이전 고객 발화에 대한 비교가 끝나기 전에 새 고객 발화가 오면 이전 비교를 취소한다. 발화 병합과 새 흐름의 음성 출력은 이후 검증 단계에서 다룬다.
4. 비교에는 기록한 필드 이름, 선택 결과의 일치 여부, 다음 질문 종류, 처리 시간만 남긴다. 서로 다른 값을 기록했는지는 메모리에서 비교하고 주소·전화번호·전사 원문은 새 로그에 넣지 않는다. 기존 흐름에서 실제 다음 안내를 관측하지 못한 발화는 별도로 센다.

## 운영 경로와 분리하는 지점

| 분리 대상 | 구현 기준 |
| --- | --- |
| 접수 상태 | [ConversationState](../../app/domain/state.py)의 내부 필드와 후보까지 복사한다. `ToolContext`는 새로 만들고 잠금, 도구 결과 캐시, 쓰기 작업 상태를 새로 가진다. |
| 외부 업무 | 복사 상태는 운영 Backend 객체나 운영 통화 콜백 없이 만든다. [도구 실행기](../../app/tools/executor.py)의 허용 목록은 복사본의 기록과 조회만 받는다. |
| 음성·통화 | 기존 Live 연결은 비교 작업에 넘기지 않는다. 종료나 이관을 판단해도 비교 결과에만 적는다. 기존 통화의 결과 전송과 재시도에도 그림자 결과를 넣지 않는다. |
| 비용·지연 | 기본 설정은 꺼 둔다. 켠 경우에도 동시 실행 수와 발화별 시간을 제한하고, 가득 차면 건너뛴 이유만 기록한다. 기존 응답은 비교 결과를 기다리지 않는다. |

## 첫 검증 목록

- 등록 주소를 인사에서 읽은 경우와 읽지 않은 경우에 모두 “네”를 한 번 반영하는지 본다.
- 후보 중 한 주소를 지목한 “네, 맞습니다”와 같은 건물의 여러 호수 중 어느 곳인지 알 수 없는 “네”를 구분한다.
- “네, 그런데 연락처는 바꿀게요”처럼 답과 새 정보가 섞이면 새 값이 빠지지 않는지 본다.
- 택배 확인과 종료가 동시에 판단됐을 때 접수 확정과 통화 종료를 둘 다 보류하는지 본다.
- 모델 시간 초과, 다음 발화 도착, 중복 도구 호출, 통화 종료를 재현한다. 복사 상태를 변경한 뒤에도 실제 상태·주문·음성 출력에 변화가 없는지 검사한다.

분리 검증을 통과한 뒤 대표 실통화 20건 이상에서 기존 경로와 새 경로의 다음 질문, 필수 정보 누락, 종료·이관 오판, 다음 안내 지연을 비교한다. 운영 회선에서 얻은 그림자 결과로 두 판단의 차이를 확인할 수 있다. 새 경로의 실제 재생 횟수와 고객이 끼어들 때의 음성 중단은 별도 SIP 검증 항목이다.
