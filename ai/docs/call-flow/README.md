# 통화 흐름(준수 사항)

재구성할 서버가 지켜야 할 고객 응대 흐름이다. `S15P31D109/ai`(2026-11-03 `exp/no-speech-injection` 기준)에서 복사했다. 문서 사이의 링크는 이 폴더와 `../be-contract/`를 가리키게 고쳤다.

**지킬 것은 "무엇을"(업무 규칙·관문·문구)이다.** "어떻게"(서버 판별기, `thinking.append` 진행 상태, 위임 안전망, LangGraph 단계 정의, sideband 타이밍)는 옛 구현의 설명이라 참고만 한다. 다만 그 장치가 생긴 이유인 실제 통화 사례는 새 구조에서도 다시 생길 수 있는 문제라 읽어 둘 만하다.

## 반드시 지킬 것(요약, 근거는 위 문서)

1. **받는 순서**: 보내는 분 성함 → 발송 주소 → 발송 상세주소 → 받는 분 성함 → 받는 분 연락처 → 받는 곳 주소 → 받는 곳 상세주소 → 물품 → 가액. 두 주소가 갖춰지면 동 이름으로 한 번 확인한다(`confirm_route`). 추가 택배는 직전 택배와 같은 발송 주소인지 먼저 확인한다.
   - 등록 고객이 발송 주소를 들은 뒤 받는 분 정보를 주기 전에 변경을 요청하면 서버 결과의 `sender_change_next`를 먼저 따른다. 성함 변경은 빠진 새 성함을 받고 `sender_change_question`으로 발송 주소도 바꿀지만 확인한다. 고객이 주소 변경을 선택했거나 처음부터 주소만 변경하겠다고 했으면 새 발송 주소를 먼저 받는다.
   - 기존 발송 주소를 쓸지 아직 답하지 않았으면 `origin_confirm`을 먼저 처리한다. 발송 주소를 변경하면 새 기본주소와 상세주소를 서버에 기록한 뒤 받는 분을 묻는다. 상세주소를 함께 말했으면 다시 묻지 않고, 없다는 답도 기록한다.
   - 새 성함을 이번 택배에만 쓴다고 하면 주문에만 기록한다. 범위를 말하지 않으면 등록 이름도 바꿀지 한 번 묻고, 동의한 경우 택배를 담을 때 등록 이름을 갱신한다.
   - 보내는 분 연락처는 발신번호로 채우고 묻지 않는다.
   - 이미 기록된 항목은 다시 묻지 않는다.
   - 순서 밖에서 말한 값과 정정도 버리지 않고 기록한다.
2. **되돌릴 수 없는 동작은 확인 단계를 거친다**: 택배 담기(되읽기 `A_CONFIRM`), 결제 방식(`A_PAYMENT`), 취소(`C_CANCEL_CONFIRM`), 상담원 전환(`D_AGENT_OFFER`).
   - 동의는 두 열쇠다. Live-1의 보고와 서버의 판단이 둘 다 "예"여야 한다.
   - 담기·결제·취소는 확정 지연(`commit_delay_ms`) 뒤에 실행한다.
   - 취소는 서버만 부른다.
3. **임시 주문이 유일한 근거다**: 되읽기와 접수는 모델이 기억하는 값이 아니라 기록된 값으로 한다. 접수는 통화가 끝날 때 담은 택배 그대로, 통화당 한 번(`POST /api/orders`, Idempotency-Key)이다.
4. **값 검증은 서버가 한다**: 주소는 주소DB로 확정하고, 못 찾으면 기록하지 않고 다시 묻는다. 전화번호는 자릿수가 틀리면 저장하지 않는다. 지난 수거 시각은 받지 않는다.
5. **읽어 주는 값**:
   - 고객이 불러 준 번호만 끊어 읽는다. 발신번호와 저장된 번호·상세주소는 읽지 않는다.
   - 주소를 다시 물을 때는 시·구와 도로명·건물번호로 읽는다. 되읽기는 "OO님이 OO동에서 OO동의 OO님께 보내시는 것으로 확인했습니다. 이대로 접수할까요?"만(2026-11-09): 주소·연락처·상세주소·물품·가액은 다시 읽지 않는다.
   - 접수번호와 요금은 서버가 준 값만 말한다. 결제 완료나 메시지 발송은 안내하지 않는다.
6. **통화는 서버가 끝낸다**: 마무리 인사가 끝난 뒤 끊는다. Live-1이 스스로 끝내지 않게 한다.

## BE 계약과 부딪히는 곳(BE는 바꾸지 않는다, `../be-contract/`)

- **수거 시각**: 흐름은 고객에게 수거 일시를 받는다(10번째 항목). 그런데 BE 원문과 소스(develop-backend a629c60)는 결제수단과 상관없이 고객이 말한 시각을 쓰지 않는다.
  - 원문(`ai-order-billing-integration.md`·`orders.md`): `pickupRequestedAt`은 생략할 수 있고, 서버가 결제 완료 시각 + 1시간으로 정한다.
  - 소스:
    - 개인 카드(`billing`): 결제 대기로 바꿀 때 받은 시각을 지우고, 결제 완료 시각 + 1시간을 넣는다.
    - 후불(`credit`·`groupBilling`): 접수 즉시 결제 완료로 처리하면서 접수 시각 + 1시간을 넣는다.
    - 위치: `order-payments.repository.ts` `waitForPayment`·`billed`, `order-submission.service.ts` `prepareSubmission`.
  - 그래서 "내일 오후 8시에 방문하도록 할게요" 같은 안내(`voice.md`·`flow.toml`)는 실제 수거 시각과 다르다.
  - BE를 바꾸지 않는다면 새 서버가 정해야 한다.
    - 수거 일시를 계속 받되 확정 시각처럼 약속하지 않는다.
    - 아니면 묻지 않고 "결제(접수) 후 1시간 안에 방문"으로 안내한다.
    - 어느 쪽이든 정하기 전에 BE 담당자에게 의도를 확인한다.
  - `LANGGRAPH_REVIEW.md` "수거 시각" 행이 가리키는 "고쳐 둔 사본"은 AI 저장소에서 원문 문장을 AI 팀 결정으로 바꿔 둔 사본이다. `../be-contract/backend/`에 있는 것은 BE 원문이다.
- **고객 확인 2단계**: 진입(`CALLER_ID` → `IS_REGISTERED`)은 전화번호 조회만으로 한다. 업무 의도(접수·조회·취소·문의·상담원)가 확인된 뒤에 통화를 등록한다(`meaningful-call-registration-handoff.md`).
  - 이전 접수 주소(`{기존 출발지}`, 최근 도착지)와 조회·취소·주소록은 통화 번호(`callSessionSeq`)가 필요하다. 그래서 등록 전에는 쓸 수 없다.
  - 옛 구현은 수신 직후 바로 등록했다.
- **좌표 없음**: 문서의 "주소 확정(주소DB·좌표)"에서 좌표는 BE 계약에서 빠졌다. 지번·동명·우편번호만 쓴다.
- **주문 정보가 없는 통화**: 무의미 통화는 통화 등록과 결과 전송을 하지 않는다. 문의만 있었던 통화는 등록한 뒤 주문 정보 없이 끝낸다(`empty-ai-order-results.md`).
