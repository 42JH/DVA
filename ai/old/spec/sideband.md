# sideband에서의 GPT-Live 동작

## client 위임(보류)

2026-10-28 실제 통화에서 client 위임이 한 번도 생기지 않아(도구 미실행) 운영 설정을 `responses`로 되돌렸다. 원인 확인 전까지 client는 보류(`docs/WORKLOG.md`). 받은 이벤트 종류는 통화마다 처음 한 번 INFO 로그(`sideband 이벤트`), target이 client가 아닌 위임은 `위임 무시` 경고로 남긴다.

- `session.delegation.created`의 `target="client"`와 ID를 받아 서버 SDK로 도구를 선택한다. 위임 이벤트에 고객 질문 본문이 들어오는 것으로 가정하지 않고 최근 받아쓰기를 사용한다.
- 결과를 `thinking.append`로 나누어 전달하고 `session.thinking.appended.client_event_id`가 송신 event_id와 일치하는지 확인한다. 이후 `commentary.append`로 Live가 결과를 판단해 안내하도록 한다. 결과는 백엔드 LLM으로 재전송하지 않는다. 작업 실패·오래된 위임·중복 이벤트도 처리한다.
- 통화별 요청과 ACK는 분리하며, 전사·GPU·검색·백엔드·전달 timeout을 기록한다. ACK만으로 올바르게 말했거나 고객이 들었다고 판단하지 않는다.
- 아래 `response.event` 함수 반환 규칙은 **복귀용 responses 위임에서만** 적용한다. client 위임에서는 이 중첩 함수 이벤트를 실행하지 않는다. `spec/rag.md`를 함께 참조한다.

- 함수 호출: sideband의 `response.event` 안에 중첩된 백엔드 이벤트를 본다. **`response.output_item.done`(type `function_call`)에서만 실행**한다(인수 완료 이벤트엔 name·call_id가 없음). 결과는 `conn.response.item.create(function_call_output)` 후 **반드시 `conn.response.create()`**를 보낸다. 안 보내면 백엔드가 멈춘다. 오류나 없는 도구여도 결과는 꼭 돌려준다.
- 관제 표시용: `response.output_item.added`(호출 시작), `response.function_call_arguments.delta`(인수 작성 중), `session.delegation.created`, `error`, `session.usage.updated`.
- 음성 모델에 조용히 맥락 주기: `conn.session.thinking.append(content, delegation_id=None)`(Responses 위임에서는 `delegation_id`가 null이어야 함). **500토큰 한도**라 길이 상한을 테스트로 지킨다. 백엔드 도구 결과(`function_call_output`)에 `state`를 붙여 보냈으면 그 `state.next`가 백엔드 모델을 거쳐 음성 모델에 가므로 같은 진행 상태를 `thinking.append`로 또 보내지 않는다(같은 질문을 두 번 말함). 고객이나 상담원이 말하는 중(마지막 고객 받아쓰기 조각이 `listener.pause_ms` 안, 또는 상담원 출력 받아쓰기의 끝 시각이 아직 지나지 않음)이면 진행 상태를 미뤘다가 말이 멈추면 `watch_flow`가 보낸다(말 겹침 방지, 2026-10-31). 되돌릴 수 없는 확정(접수 완료)을 기다리는 동안은 새 질문 없이 기다리게 하고(`COMMIT_WAIT`), 확정 전이의 말(운임·결제 안내)은 확정 뒤 다음 질문(추가 접수)과 한 진행 상태로 차례대로 보낸다. `thinking.append`는 말없이 주는 맥락이라(SDK 설명: 말할 결과는 `commentary.append`) 고객 말 없이 서버가 단계를 옮기면(확정·검색 시간 초과·서버 도구 결과, `_fire`·`run_server_tool`) 다음 할 말을 `commentary.append`(문구 `speak`)로도 보낸다(2026-10-31: 확정 뒤 추가 접수 질문을 하지 않고 멈춤). 백엔드 모델은 위임을 받을 때 단계를 몰라 `get_state`부터 부르거나 엉뚱한 도구(받는 분 성함에 `lookup_orders`)를 고르고 정정을 기록하지 않아(2026-10-31 실측), 상태가 바뀔 때마다 백엔드 지시문 끝의 "지금 상태"(`engine.summary`, 문구 `backend_state`)를 `session.update`(`delegation.responses.instructions`만, 이후 위임부터 적용, `session.updated`로 확인)로 갱신한다(`progress.update_backend`, 말하는 중이어도 미루지 않음). 이 상태는 한 박자 늦을 수 있어 `get_state`는 남긴다(최신 상태 확인·값 없는 위임에서 다음 할 말을 실제로 말하게 하는 경로). 도구 목록은 바꾸지 않는다(캐시·늦은 상태로 필요한 도구가 빠지는 것 방지). 판별 시간 초과면 같은 말을 한 번 더 판별하고, 정정(`correction`)이나 기록할 값이 든 말(판별 `value`)은 음성 모델이 넘기지 않았으면 `record_heard` 설정과 상관없이 서버가 백엔드에 넘긴다(아래 "서버가 대신 넘김"). `commentary.append`(말할 내용), `instructions.append`(압축 뒤에도 유지)도 같은 한도.
- **고객 답 판별**(`app/listener.py`): 고객 받아쓰기를 이번 단계에서 아직 판별하지 않은 말에 이어 붙이고, `listener.pause_ms` 동안 새 조각이 없으면 "이 단계의 답(`answer`) + 전역 의도(`intent`: question·restricted·correction·lookup·wait·end) + 정정 항목(`slot`)"을 판별한다. 판별 API는 설정 `[listener] engine`: `decisions`(기본, Decision API `client.decisions.create`, `gpt-6-luna`만, 고르기 질문 셋, 고를 답이 없는 단계는 답 질문을 뺌, 거절은 none) 또는 `responses`(Responses API strict JSON, `store=false`). 2026-11-01 실측(실제 통화 문장 13개 × 3번): 중앙값 Decision 약 0.25초 / Responses 약 1.3초, 정답은 선택지 설명을 다듬은 뒤 같은 수준. 상담원의 실제 말(출력 받아쓰기)이 아니라 **고객이 말을 시작할 때 서버가 물은 질문**(`Call.heard_asked`)을 같이 넘긴다: 음성 모델이 판별보다 먼저 다음 질문을 말해, 그 말을 주면 "네"가 엉뚱한 질문의 답으로 읽혔다(2026-11-01 21:47 통화). **상태를 바꾸는 것은 확인 단계(`Stage.confirm`)의 답뿐이다**(동의는 Live-1의 `answer` 보고와 둘 다 같아야 처리하는 두 열쇠, 짝이 `[listener] consent_wait_sec` 안에 오지 않으면 `watch_flow`가 `consent_retry`로 확인 질문을 다시 하게 한다. `spec/flow.md` "두 열쇠")(다른 용건이 섞이지 않은 답만, `spec/flow.md` "서버의 고객 말 판별"). 그 밖의 단계에서는 위임 안전망(아래 "서버가 대신 넘김")에만 쓴다. 판별 결과로 상태가 바뀌면 바로 `thinking.append`. 판별 실패·시간 초과는 상태를 바꾸지 않고 관제에 오류로 남긴다. 판별 기록은 관제 도구 패널에 `listener`로 보인다.
- **끼어들기·정정**(LANGGRAPH_REBUILD §2.5). 시각은 받아쓰기의 `start_ms`·`end_ms`(세션 타임라인 ms, SDK 타입으로 확인)로 본다. 서버의 "지금" 세션 시각은 (받은 시각 − `end_ms`)의 가장 작은 값으로 추정한다(`Call.now_ms`). 단계에 들어올 때 이 시각을 `FlowState.entered_ms`에 남긴다.
  - (1) 질문을 다 듣기 전 답: 확인 단계 질문 문구마다 핵심 구간(`prompts/flow.toml` `[core]`)을 두고, 고객 말이 시작될 때까지 나간 상담원 받아쓰기에 그 낱말이 차례대로 없고(숫자는 한글로 읽혔을 수 있어 뺀 부분도 본다) 상담원이 말하는 중에 고객이 말을 시작했으면(겹침, `[flow] heard_grace_ms`) 예/선택 답을 받지 않고 같은 질문을 다시 하게 한다(`reask`). 질문마다 한 번만(받아쓰기 비교가 늘 어긋나 되풀이하지 않게). 거절("아니오")은 되돌릴 수 있어 받는다(`Stage.unheard_ok`). 시각을 모르면 따지지 않는다.
  - (2) 질문이 바뀌기 전에 한 말: `start_ms`가 단계 진입보다 이른 조각과, 판별 중 단계가 바뀐 말은 단계 답으로 쓰지 않는다. 끼어드는 용건이면 미뤄 둔 확정만 버리고, 정정·값이면 위임 안전망으로 넘긴다.
  - (3) 판별 리비전: 고객 말 조각이 올 때마다 `Call.heard_rev`가 1 늘고, 판별은 시작할 때의 리비전과 같을 때만 반영한다(늦게 온 옛 판별·그사이 말이 더 이어진 판별은 버림, 말은 다음 판별이 이어서 본다). 되돌릴 수 없는 확정(취소 "예", 결제 단계 진입)은 `[flow] commit_delay_ms` 동안 새 말이 없을 때만 실행한다(`watch_flow`가 `COMMIT` 사건). 새 말이 오면 멈추고, 그 말이 번복·끼어드는 용건(wait·question·restricted·correction·end)이면 버리고, 아니면 다시 잰다. 결제 단계 진입처럼 다 찬 상태에 걸리는 확정은 번복 뒤 다음 말이 번복이 아니면 다시 건다. 판별이 실패하면 "예"에 걸린 확정은 버린다.
  - (4) 정정: 음성 모델이 응대하고(값이 없으면 직접 묻는다) 백엔드가 `record_order`로 고친 값을 기록하면 한 번 확인한 뒤(`CORRECTED`) 현재 단계 질문을 다시 한다. 확인 단계에서 답과 정정이 섞이면 답은 받지 않는다. 저장된 곳에서 가져온 받는 곳을 다른 곳으로 말하면(`match_pins`) 그 받는 분 묶음을 비우고 새로 찾는다. 정정으로 값이 비면 정보 받기로 되돌아간다.
  - (5)(6) 듣지 않는 단계(취소 실행 중인 `C_CANCEL`)의 고객 말은 버리지 않고 쌓았다가, 단계가 끝나고 상담원이 바뀐 단계의 안내를 마친 뒤(또는 `[flow] flush_wait_sec`) 판별한다(확정을 버릴 용건인지, 위임 안전망으로 넘길지). 실행 중인 취소는 고객이 끼어들어도 멈추지 않고 실제 결과를 안내한다.
  - (7) 음성 모델이 그래프와 다르게 스스로 마무리 인사를 하면(출력 받아쓰기에 `drift_markers`) 아직 판별하지 않은 고객 말과 백엔드 응답(끝내자는 말의 보고)을 기다린 뒤에도 같은 단계면 `session.instructions.append`(`drift_fix`)로 바로잡는다(단계마다 한 번). 서비스 질문에 직접 답하기·값 바꾸기는 받아쓰기로 확실히 알 수 없어 지시문(`voice.md`)으로만 막는다.
  - (8) 통화가 끝날 때 실행 중인 쓰기 도구(취소)는 끊지 않고 결과를 기록한 뒤 끝내고(`write_tasks`, 최대 `tool_timeout_sec`), 확정 지연 중인 전이는 버린다. 감시의 `call.ending`도 통화별 잠금을 기다려 쓰기 결과를 반영한 뒤 들어간다.
- **서버가 대신 넘김**(위임 안전망, `listener.forward_later`, 늘 켜짐): 판별이 정정이거나 `value`(고객 말에 이름·연락처·주소·물품·가격·수거 일시 값이 있음)거나, 확인 단계가 아닌데 질문의 답·끼어드는 용건(기다림 제외)이 있으면, 말이 끝나고 `[listener] delegate_wait_sec` 뒤에도 그 말을 시작한 뒤의 `session.delegation.created`가 없을 때 아래와 같은 방식(`response.item.create` + `response.create`, 문구 `record_heard`)으로 백엔드에 넘긴다(끝내는 단계 밖). 백엔드가 지금 상태에 맞게 `answer`·`switch_task`·`record_order` 등으로 보고한다. 백엔드 응답 중(`response.event`의 `response.created`~`response.done`, `call.backend_busy`)이면 끝날 때까지(최대 `timeout_sec`) 기다린다. 음성 모델이 "저장할게요"라고 말로만 받고 위임하지 않아 정정이 빠지던 것(2026-10-31·11-01 22:41 통화). 고객이 번호 중간에 쉬어 말이 나뉘면(22:41: "…번호를 010" / "1234-5678") 직전 판별한 말(`joined_sec` 안)을 판별 상황에 "바로 앞에 한 말"로 같이 주고, 넘길 때도 이어서 넘긴다(앞말로 걸어 둔 요청은 취소).
- **서버가 기록을 맡김**(`listener.record_heard`, 설정 `[listener] record_heard`, **기본 꺼짐**: 2026-10-29 통화에서 위임된 FAQ 응답 중에 이 요청이 끼어들어 답이 돌아오지 않고 상담원이 50초 멈췄다): 음성 모델이 주문 정보를 듣고도 위임하지 않는 통화가 있어(2026-10-28 13:26·17:44, 주소 보정·기록 0건) `record_order`를 쓰는 단계(접수 단계)에서 판별이 answer·intent 모두 none이고 고객 말이 끝난 뒤 `session.delegation.created`가 없었으면, 그 말을 `response.item.create`(user 메시지, 문구 `record_heard`) + `response.create`로 백엔드에 넘긴다(공식 문서 live-delegation "Accept typed input"). 백엔드가 부른 도구는 위 함수 호출 경로로 실행된다. 미확인: 서버가 시작한 백엔드 응답의 글이 음성으로 나가는지, 백엔드 응답 중에 보낸 `response.create`가 어떻게 되는지. 위임과 거의 동시에 겹치면 같은 값이 두 번 기록될 수 있다(덮어쓰기라 무해). QnA·상담원 흐름(D_AFTER_ANSWER·D_AGENT_OFFER·D_AFTER_NO_AGENT) 중에도 백엔드가 주문 값을 기록할 수 있고, 접수 업무 중이었으면 하던 접수 단계로 돌아간다(`order.updated` → RESUME_TASK). 판별 기준에 "상담원 질문에 되묻는 말은 question이 아님"을 두었다(되물음이 매뉴얼 검색으로 빠지던 것).
- GPT-Live 세션의 `triggers`(type `decisions`)·Decision API는 SDK 타입에는 있으나 공개 문서에 없어 **미확인**이라 쓰지 않는다. 확인되면 판별 수단으로 바꿀 수 있다.
- 받아쓰기: `session.input_transcript.delta` / `session.output_transcript.delta`. **문장 경계·item ID가 없다**(대신 `start_ms`·`end_ms`가 있다). 말하는 쪽의 마지막 말풍선이 맨 끝이거나, 그 말풍선의 끝과 새 조각의 간격이 서버 설정 `monitor.bubble_gap_ms` 안이면 이어 붙인다(겹쳐 말해도 쪼개지지 않게). 아니면 새 말풍선.
- 먼저 인사: 세션 `input`에 developer 메시지("전화가 방금 연결됐습니다. 지금 바로 인사하세요.")를 넣는다.
- 통화 종료: 종료 요청·"더 없음"을 판별해 `END_CALL`에 들어간 직후 끊으면 마무리 인사가 잘린다. **요청 뒤 마무리 안내(진행 상태)를 음성 모델에 전한 다음 상담원 출력 받아쓰기(`output_transcript.delta`)가 나오고**, 그 받아쓰기의 끝 시각(세션 타임라인)이 지난 뒤 서버 설정의 시간(`hangup_silence_sec`)만큼 멈추면 hangup한다. 안내 전의 맞장구는 인사로 치지 않는다. 받아쓰기는 음성보다 먼저 오므로 받은 시각으로 재면 인사가 잘리고, `output_audio.delta`는 말하지 않을 때도 와서 기준으로 쓰지 않는다(턴 끝·말 끝 이벤트는 SDK에 없다). 최대 대기(`hangup_max_wait_sec`)는 안내를 전한 때부터 재고, 그때도 말이 다 나가고 멈춘 뒤에만 끊는다. 상담원 연결(`AGENT_HANDOFF`)에서도 같은 기준으로 기다린 뒤 refer한다. refer가 실패하면 실패 안내(진행 상태)와 마무리 인사를 기다린 뒤 hangup한다.
- 고객 끊김: 보통 고객이 끊으면 OpenAI가 세션을 닫고(`session.closed` `remote_hangup`) PBX 종료 웹훅도 온다. 둘 다 오지 않는 경우의 안전장치로, 고객 받아쓰기가 `call.idle_hangup_sec` 동안 없거나 통화가 `call.max_call_sec`를 넘으면 `END_CALL`로 옮겨 마무리 인사 후 끊는다(`watch_idle`). 통화가 끝나면 이유를 INFO 로그로 남긴다.
- 시간으로 정해지는 흐름(`watch_flow`, 0.1초마다): 확정 지연이 끝나면 `COMMIT`, 듣지 않던 단계에서 쌓인 말의 판별.
- 서버가 실행하는 도구(취소): 단계 진입 때 `Call.server_tool`에 두면 상태를 바꾼 뒤(`progress.after_change`) 따로 작업을 띄워 통화별 잠금 안에서 디스패처로 실행한다. 결과 사건 없이 실패하면(시간 초과·예외) 실패 분기 사건을 낸다.
- 함수 호출은 통화별 작업으로 돌려 이벤트 받기를 막지 않고, 통화별 잠금(FIFO)으로 순서를 지킨다. 구현: `app/sideband.py`.
