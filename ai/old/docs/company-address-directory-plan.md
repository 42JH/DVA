작성일: 2026-11-02. 상태: 구현 및 가짜 회귀 검증 완료. 실제 백엔드·통화 검증은 후속 단계.

- 사용자 지정 Jira: S15P31D109-65, S15P31D109-62. 사용자는 두 이슈 모두 API 연결 관련이라고 설명했다. 이 계획의 구현 분담으로 65번에 고객 기본주소 API 반영, 62번에 기업 배송지 검색 API 연결을 배정한다(실제 Jira 제목을 조회한 것은 아님).

- 브랜치 전략: [팀 규칙](BRANCH_STRATEGY.md). 이슈별 작업 브랜치 → MR → develop-ai, 리뷰 1명 이상, Squash Merge 권장.

## 작업 A: 현재 고객 기본 출발지

1. 가짜 HTTP와 FakeBackend에 customer.name/phoneNumber/address를 포함한 사례를 준비한다. 과거 PIN과 현재 이름이 다른 실패 사례부터 고정한다.
2. CallerContext에 기본 출발지를 별도로 전달한다. 실제 customers/context 계약에서 customer.address의 필드 형태와 nullable 조건을 먼저 확인한다.
3. 등록 고객의 첫 출발지는 현재 고객 이름·발신번호·기본주소로 제안한다. 개인 PIN이 없어도 사용할 수 있어야 한다. 기본주소가 없다면 과거 주소를 자동 채택하지 않고 사용자에게 묻거나 선택할 추가 주소를 확인한다.
4. use_place/set_place에서 출발지 적용과 수신인 전체 복사를 구분한다. 이름 보호를 모든 배송지에 일괄 적용해 수신인 선택을 망가뜨리지 않는다. 사용자가 이번 통화에서 명시적으로 고친 이름도 보존한다.
5. 두 번째 택배에서 직전 출발지를 재사용하는 규칙, 상세주소 선택 규칙, 기존 주소 보정 경로를 유지한다. 좌표 1을 완성된 정상 좌표로 단정하지 않으며 기존 정책의 처리 결과를 테스트한다.
6. 신규 고객 등록/개인 PIN 저장 정책은 이번 인계만으로 재설계하지 않는다. 등록 고객의 기본주소 사용과 충돌하는 부분만 확인한다.

## 작업 B: 기업·사원 배송지 검색

1. BackendAPI에 GET /api/companies/search 호출을 추가한다. httpx2의 params로 q·limit·offset을 인코딩하고 data/hasNext/total_count와 새 항목 구조를 검증한다. 빈 결과·시간 초과·5xx·잘못된 응답을 구분한다.
2. organizationSeq/membershipSeq/customerSeq는 검색 후보 식별값으로만 관리한다. 개인 PIN ID로 변환하지 않는다. 후보에는 organizationName/departmentName/addressData를 함께 보관해 동명이인을 구분한다.
3. 기존 match_pins 경로를 확장해 개인 주소록 검색과 기업 검색을 연결한다. 도구 인수에 기업·부서·새 검색 여부를 명시할 수 있게 설계하고 엄격한 스키마, 도구 설명, backend 프롬프트를 함께 맞춘다. 대화 의미를 서버의 문자열 추측으로 판별하지 않는 기존 원칙을 따른다.
4. 회사/사원을 지정했으면 개인 PIN 0건만으로 종료하지 않는다. 기업명과 사원명 등을 새 검색어로 구성한다. 전체 단어 AND 조건이므로 정정 때 이전 이름/회사/부서/상세·후보·거절 상태를 제거한다. 같은 후보를 좁히는 추가 발언은 필요한 조건을 유지한다.
5. 후보 1개는 기존 확인 관문에 연결하고, 복수는 기업·사원·부서·주소 차이로 고르게 한다. hasNext가 참이면 첫 페이지만 보고 유일 후보라고 판단하지 않는다. 페이지 이동/검색어 추가 확인 방식과 상한은 새 계약 확인 후 정하고 제한에 걸리면 검색 완료로 표시하지 않는다.
6. 확인한 addressData의 이름·전화번호·주소·상세·좌표를 이번 임시 주문에 함께 복사한다. 저장된 전화번호를 다시 묻지 않고 기존 개인정보 가림 규칙을 적용한다. 새 기업 배송지에 originPin을 지정하지 않는다.
7. 검색 중 정정이나 새 택배가 시작되면 오래된 응답을 적용하지 않도록 통화별 검색 세대/조건을 확인한다. 통화 간 후보를 공유하거나 전체 사원 명단을 시작 응답에 적재하지 않는다.
8. 검색 q에 개인정보가 포함될 수 있으므로 현재 '개인정보를 URL에 넣지 않는다' 규칙과의 예외를 명세에 분명히 기록한다. 새 계약이 요구하는 검색어만 보내고 로그·오류에 q/응답 주소를 노출하지 않는다. 기존 주문 조회의 이름 필터 정책은 유지한다.

## 구현 순서와 문서

- 먼저 새 백엔드 검색 계약과 customer.address 형태를 확정한다. 통합 전 백엔드/AI 계약 버전을 맞춘다.
- 기본 출발지 작업 → 기업 검색 클라이언트/후보 모델 → 도구·정정 상태·확인 흐름 → 모의 회귀 검증 순으로 진행한다.
- 두 브랜치를 모두 develop-ai에서 시작한다면 기본 출발지 MR 반영 후 기업 검색 브랜치에 최신 develop-ai를 반영하고 충돌/회귀를 확인한다. 사용자 커밋/푸시 요청으로 기본주소 변경을 65번 커밋 1258627에 분리했다. 62번은 해당 커밋을 기반으로 기업 검색 변경을 추가한다. develop-ai에는 병합하지 않는다. MR 검토는 65번을 먼저 반영한 뒤 62번을 진행하는 순서다.
- 각 변경과 함께 spec/backend-api.md, spec/scenario.md, spec/flow.md, spec/tools.md, 필요한 prompts/backend.md·flow.toml을 갱신한다. 고객 기본주소와 개인 PIN, 기업 검색을 구분하고 동일 계약을 여러 문서에 중복하지 않는다.
- app/mock_backend.py와 tests/conftest.py의 FakeBackend도 새 계약에 맞춘다. 백엔드 DB의 활성 필터를 AI에 중복 구현하지 않는다.

## 구현 반영 사항 (2026-11-02)

- 현재 고객 기본주소를 별도 출발지로 파싱하고 개인 PIN·과거 주문의 자동 기본주소 사용을 제거했다. 현재 이름/전화 및 통화 중 정정을 보존한다.
- 기업 검색 클라이언트, 기업/부서/소속 후보 모델, match_pins의 기업 검색 및 restart 조건을 추가했다. 후보 확인 후 주소만 주문에 복사한다.
- 다음 페이지/상한 초과는 조건을 더 묻고, 장애·0건·잘못된 응답을 구분한다. 새 검색/직접 수신인 수정/새 택배 뒤 이전 응답을 버린다. httpx2 검색 로그를 가린다.
- 기본좌표 1이나 없는 좌표는 저장된 주소 선택 후 기존 보정 경로를 적용한다. 신규 고객의 개인 PIN 저장과 기본주소 갱신은 별개라는 새 정책으로 회귀 기대값을 맞췄다.
- 새 백엔드 브랜치 fetch는 원격 ref가 없다는 응답을 받았다. customer.address의 객체/null 형태는 기존 customers 문서에서 확인했고, 새 기업 검색 구조는 인계 문서를 기준으로 구현했다. 실제 백엔드 통합과 통화는 아직 미검증이다.


최종 검증: 전체 가짜 테스트 676개 통과(48.21초), 기존 경고 1건. 새 회귀 25개 포함. diff 공백 검사 통과. 기본주소/기업 검색 테스트를 파일별로 나눠 각 이슈 커밋에 포함한다.


## 커밋·푸시 진행 (2026-11-02)

사용자가 커밋과 푸시를 요청했다. 65번은 1258627로 기본주소 변경을 커밋하고 독립 전체 테스트 655개를 통과했다. 62번은 65번 변경을 포함하는 후속 브랜치이며 기업 검색만 추가 커밋한다. 기능 브랜치 두 개만 푸시하고 MR 생성/develop-ai 병합/배포는 수행하지 않는다.

분리 후 검증 완료: Jira65 단독 전체655개 통과(53.75초), Jira62 통합 전체676개 통과(80.78초). 새 회귀는 기본주소4개+기업검색21개=25개다. 기능브랜치 푸시 후에도 실제 백엔드/통화 검증은 남는다.
