## 1. 목표와 전체 흐름

백엔드는 FAQ 원본과 변경 알림을 관리하고, AI는 받은 번호의 검색 자료를 갱신한다. 하나의 MD 파일에 계속 덧붙이지 않는다.

```text
관리자 추가/수정/삭제
 → BE: 원본+감사+알림 대기 함께 커밋
 → BE 워커: 변경 종류와 FAQ 번호를 AI로 알림
 → AI: 인증·검증·영속 접수 후202
 → INSERT/UPDATE: 해당 번호의 최신 원문 조회
 → DELETE: 번호로 모든 청크 제거
 → Qdrant와 BM25 반영·검증
```

원본 저장 완료, AI 알림 접수, AI 검색 반영 완료는 서로 다른 상태다. 이번 BE 계약에는 최종 색인 완료 회신 API가 없다. AI에서 처리 상태와 실패 재시도를 관리한다.

## 2. 변경하지 않는 검색 설정

- OpenAI text-embedding-3-large/3072차원, 기존 원문+유효한 선택 검색 설명 입력.
- Kiwi 사전/전처리와 BM25 설정. Kiwi 단어 목록을 따로 임베딩하지 않는다.
- RRF: BM25 0.4/dense0.6, c60, 후보Top5.
- 고정 Qwen3-Reranker-0.6B 원문A/FP16/1024토큰, 원문Top3, 현재 responses 위임.
- 짧은FAQ는 기존 방식, 긴FAQ만 질문과 표/목록 맥락을 보존한 자식청크로 확장하고 회귀 평가한다.
- 고객 질문 처리 중 원본 동기화나 문서 임베딩을 하지 않는다. 질문 자체의 검색용 임베딩은 기존대로 한다.

## 3. 기존 관리자 API와 AI 알림의 차이

| 작업 | 관리자→BE API | 건수 |
|---|---|---|
| 등록 | POST /api/faqs | 단건 또는1~100건 |
| 수정 | PATCH /api/faqs/{id} | 단건 |
| 삭제 | DELETE /api/faqs | 단건 또는1~100개 번호 |

등록 복수 본문은 items:[{question,answer},...]이며 기존 단건 {question,answer}도 지원한다. 수정은 question/answer 중 전달한 필드만 변경한다. 삭제는 아래 형식이다.

```json
{ "faqEntrySeqs": [123, 124] }
```

한 건은 [123]으로 보낸다. DELETE /api/faqs/{id}는 없다. 관리자 삭제 대상 하나라도 없으면404로 전체 롤백하며 반복 삭제는404다. 반면 **AI 알림 재처리에서 이미 없는 벡터 삭제는 정상 무변경**으로 처리한다. 두 동작을 혼동하지 않는다.

질문1,000자·답변20,000자, JSON100KiB 제한, 관리자 세션/Origin/감사 규칙은 BE 계약을 따른다. 원본 ID는 faqEntrySeq이며 수정해도 유지한다.

## 4. AI가 구현할 실제 수신 계약

POST /internal/faqs/refresh
Authorization: Bearer <AI_FAQ_TOKEN>

```json
{
  "eventId": "f5af1894-3e32-4c75-a2c5-768ea9e48593",
  "operation": "INSERT",
  "faqEntrySeqs": [123, 124]
}
```

- eventId: UUID. 같은 알림 재전송에도 유지한다.
- operation: INSERT/UPDATE/DELETE.
- faqEntrySeqs: 중복 없는 양의 정수 배열. INSERT/DELETE는1~100개, UPDATE는정확히1개. 구현 시 BE의 정수 범위도 맞춘다.
- 질문·답변·관리자 정보·revision은 알림에 없다. 임의의 추가 필드를 요구하지 않는다.
- AI_FAQ_TOKEN은 BE/AI 공유32자 이상 공백 없는 ASCII 비밀값이며 AI_PERSONA_TOKEN과 별개다. 실제 값은 로그/문서에 남기지 않는다.
- 인증·본문 검증 후 이벤트를 영속 저장하고2초 이내202로 응답한다. 응답 본문은 BE가 사용하지 않는다. 같은eventId는 중복작업을 만들지 않고202를 반환한다. 같은ID에 다른본문이 오면 충돌로 기록·거부한다.
-200/204는 BE에서 수신 성공이 아니다. 임베딩이나 색인 완료까지 HTTP를 붙잡지 않는다.

## 5. INSERT/UPDATE: 알림 번호만 최신 원문 조회

```http
GET /api/ai/faqs?faqEntrySeqs=123,124&limit=100&offset=0
```

```json
{
  "data": [
    {
      "faqEntrySeq": 123,
      "question": "착불도 되나요?",
      "answer": "선결제만 가능하며 착불은 불가합니다.",
      "updatedAt": "2026-10-30T01:00:00.000Z"
    }
  ],
  "hasNext": false
}
```

알림 처리에는 검색어q를 넣지 않는다. 관리자 쿠키·통화 헤더를 보내지 않으며 기존 MVP 조회 인증 규칙을 따른다. 한 이벤트의 번호100개 이하를 limit100으로 받으므로 한 번에 전체 대상 확인이 가능하다.

응답은 이벤트 시점 복사본이 아니라 **조회 시점 최신 원본**이다. UPDATE 이전/이후 본문을 이벤트에서 재구성하지 않는다.

- 요청 번호 중 응답에 있는 FAQ: 최신 질문·답변으로 upsert.
- 요청 번호 중 응답에 없는 FAQ: 이미 삭제된 것이므로 해당 번호의 검색 자료를 제거.
- 정상200·빈목록·hasNext=false: 대상 번호 모두 삭제/미존재로 처리 가능.
- HTTP오류·시간초과·형식오류·hasNext=true·요청하지 않은ID: 완전한 최신 결과가 아니므로 삭제로 해석하지 않고 재시도.

전체FAQ 목록을 매번 조회하지 않는다. 기존 v2의 '전체100건 이하' 제한과 다르며 현재 제한은 이벤트당 최대100개다.

## 6. 영속 큐·중복·처리 순서

BE는 FAQ 원본+감사+알림 대기를 같은 트랜잭션에 남긴다. 워커는 가장 오래된 미전송 이벤트 하나를5초 주기로 보내고202만 성공으로 인정한다. 실패 시5/10/20/40/80/160/300초 간격으로 계속 재시도하며 후속 이벤트가 선행 미전송을 추월하지 않는다. 점유30초 만료/응답유실로 같은eventId가 다시 올 수 있다.

AI는 별도 rag_state 영속볼륨의 SQLite에 이벤트 본문·접수순번·처리 상태를 저장하는 단일 소비자 큐를 제안한다. 메모리 BackgroundTasks만 사용하지 않는다.

1. 수신 순서와 중복제거를 영속화한다.202 후 장애는 AI 내부 책임으로 재시도한다.
2. 최신 원문 조회부터 임베딩·색인·삭제 완료까지 큐를 순차 처리한다. FAQ별 작업을 병렬로 뒤집어 적용하지 않는다. 임베딩은 이벤트 루프 밖에서 수행해 통화 처리를 막지 않는다.
3. 이전 upsert 원격 쓰기가 끝나기 전에 뒤의 삭제를 완료했다고 보고하지 않는다. 타임아웃으로 결과가 불명확한 쓰기는 재확인한다.
4. 순차 처리 중 실패는 처리완료로 건너뛰지 않고 상태와 재시도 시각을 남긴다. 지속 실패가 뒤의 변경도 지연할 수 있음을 운영 상태에 표시한다.
5. 수신된 DELETE 번호는 처리 대기 중에도 검색/반환 차단 목록에 기록하는 보완을 제안한다. 실제DB삭제는 직렬 큐에서 수행하고, 검색차단을 삭제완료라고 표시하지 않는다. 최종삭제 확인 전 옛작업이 해당ID를 공개하지 않도록 한다.

현재 계약에 없는 FAQ revision은 요구하지 않는다. BE의 순서있는 최소한번 전달+AI의 영속FIFO/중복제거+최신원문 조회가 기준이다. 삭제된 ID를 새 FAQ에 재사용하지 않는 전제를 확인한다. 다중AI인스턴스에는 별도 공통 큐/분산잠금이 필요하다.

## 7. 문서·청킹·증분 임베딩

- faq_id=backend-faq:123은 불변 관리번호다. FAQ→자식청크/버전 포인트 매핑을 저장한다.
- 짧은FAQ는 질문+답변 전체를 유지한다. 긴FAQ는 제목·문단 경계와 기존Recursive splitter800자/겹침50자를 우선 사용한다.
- 자식청크에는 원래 질문과 필요한 절 제목을 반복한다. 표는 헤더·구분행·단위·조건과 데이터 행을 함께 보존한다. splitter 기본 동작만으로 표가 안전하다고 가정하지 않는다.
- 내용 해시와 실제 임베딩 입력 해시를 분리한다. 질문+본문청크+유효검색설명+모델/차원/형식버전이 같을 때만 벡터를 재사용한다.
- 새/변경 청크만 임베딩한다. 질문 수정은 여러 자식청크를 바꾸며 분할경계 이동도 인접청크를 바꿀 수 있다. '수정1문장은항상벡터1개'라고 약속하지 않는다.
- 기존 검색 설명의 사용 방식은 유지하고 본문 해시가 맞지 않는 설명은 몰래 재사용하지 않는다. 새로운 FAQ에 설명이 없어도 원문만으로 처리한다.
-800/50은 문자 단위다. Qwen1024토큰은 고객질문·지시문·특수토큰·문서 합계다. 고정tokenizer로 검증하는 위치/질문 예산은 구현 때 확정한다. 초과를 조용히 자르거나 전화중 재청킹하지 않는다. 전화서버에GPU모델/torch를 넣지 않는다.

## 8. Qdrant·BM25 적용

추가·수정은 새버전 포인트를 준비하고 동일한 문서 집합의 Kiwi/BM25를 만든다. BM25는 전체 최신 자료로 재구성하지만 임베딩API는 변경청크만 호출한다. 변경없는 벡터는복사/재임베딩하지않는다.

준비중 포인트는 활성 ID 필터에 포함하지 않는다. 검증 후 불변 IndexSnapshot(문서·BM25·물리컬렉션·포인트ID집합)을 짧은 잠금으로 바꾼다. 질문 하나는 같은 판본의 두 검색을 사용한다. 검색 요청에서 소스조회/임베딩 작업을 실행하지 않는다.

같은FAQ의 여러청크가 후보에 올 수 있으므로 기존 Top5/Top3가 필요한 문맥을 충분히 담는지 평가한다. FAQ별 가중치나 top-k를 임의 변경하지 않는다. source원본은API응답 그대로 보존하고 기대답변을모델입력에넣지않는다.

## 9. DELETE: 벡터 실제 삭제와 검증

DELETE 알림의 faqEntrySeqs 각각에 대해 다음을 수행한다.

1. 검색/반환 차단과 삭제이력을 영속화한다. 기존 판본으로 진행 중인 검색도 반환 전 현재 삭제 차단 목록을 확인한다.
2. 원문·BM25·활성포인트 목록에서 해당FAQ의 모든자식청크를 제외한다. 삭제에는 임베딩이 필요 없다.
3. 활성·준비중·예전 수정버전의 해당FAQ 포인트를 Qdrant에서 **실제 삭제**하고 완료 후 해당FAQ 포인트0건을 확인한다. 기존upsert와직렬화해뒤늦은쓰기로부활하지않도록한다.
4. 로컬 원문·검색설명·본문을 포함한 임베딩캐시도 정리한다. 삭제된FAQ를 포함하는 이전판본으로 자동복귀하지 않는다.
5. 검색차단/BM25반영/DB삭제/캐시정리의 상태를 구분한다. 실제삭제 실패는 대기/실패로 남기고 재시도하며 완료로 위장하지 않는다. 이미 없는 벡터를 다시 삭제하는 것은 정상무변경이다.

원문 없는 eventId/삭제ID/처리상태 보관은 본문을 검색DB에남기는것과다르다. 이미Live에전달하거나발화한말은소급회수할수없다. 백업/스냅샷영구소거는별도보존정책이다.

## 10. 최초 이전·복구·운영 상태

현재MD32개와BEseed32개는출처·분류제거로입력이달라질수있다. 기존포인트에는BE ID가없으므로ID매핑/내용diff 후별도관리용컬렉션에서최초이전한다. 동일입력을증명하지못한항목은최초1회임베딩이필요할수있다.

초기등록은INSERT알림하나를생성한다. 이미BE데이터가있어초기등록을건너뛰면새알림은없으므로별도bootstrap이필요하다. 전체목록조회는이최초가져오기/누락복구/대조용으로남긴다. 다중페이지전체는고정시점을보장하지않으므로동시변경의복구계약을확인한다.

BE토큰이비어있으면전송이꺼지고대기는남는다. 새앱전020 migration, 양쪽AI_FAQ_TOKEN,AI_AGENT_URL과수신API준비가필요하다. 이번작업에서는migration/비밀값/운영DB를수정하지않는다.

상태는AI내부관제/로그로제공한다. BE에는색인완료callback계약이없으므로새회신API를필수로가정하지않는다. 관리자화면까지반영상태를보여줄지는별도후속협의다.

## 11. 구현 순서와 검증

1. 실제 수신 스키마·AI_FAQ_TOKEN 인증·2초 이내 영속접수202·중복 검증.
