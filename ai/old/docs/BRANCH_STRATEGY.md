# 팀 브랜치 및 커밋 규칙

사용자가 2026-10-23에 제공한 `Branch Strategy` PDF를 기준으로 정리했다. 이 문서는 팀 규칙을 다음 작업에서도 확인하기 위한 저장소 내 참조다.

## 커밋 메시지

PDF 5~6페이지의 Squash 예시 형식을 따른다. 커밋 제목과 브랜치 타입의 이름은 구분한다. 기능 브랜치 타입은 `feature`, 기능 커밋 타입은 `feat`다.

```text
feat: Markdown 자료 등록 파이프라인 구현

- Markdown 로드와 제목 기반 청킹 연결
- OpenAI 임베딩과 Qdrant 최초 등록 추가
- 기존 컬렉션의 중복 등록 방지

S15P31D109-118
```

- 제목은 `타입: 한국어 설명`으로 작성한다.
- 본문은 필요한 경우 실제 변경 내용과 검증 결과를 적는다. 미완료 사항을 완료했다고 쓰지 않는다.
- Jira 이슈 키는 예시처럼 마지막 줄에 단독으로 적는다. 위 예시는 현재 프로젝트의 이슈 키로 바꾼 적용 예다.
- 이 문서를 받기 전 제안했던 `feat: [S15P31D109-118] 설명` 대신 위 형식을 우선 사용한다.
- PDF에 커밋 타입 전체 목록은 없으며 제목 예시는 `feat`, `fix`, `refactor`다. 문서·의존성 등은 저장소의 기존 `docs`, `build`, `chore`, `test`, `ci` 관례에 맞는 타입을 사용한다.
- 사용자가 요청했을 때만 커밋·푸시한다. 커밋 요청을 푸시나 MR 생성 요청으로 확대하지 않는다.

## 브랜치 이름과 생성 기준

- AI 작업 브랜치는 `develop-ai`에서 생성하고, 완료 후 MR을 통해 `develop-ai`로 병합한다.
- 작업 브랜치는 `타입/작업내용` 형식이고 Jira 이슈 번호를 반드시 포함한다.
- 작업 내용은 영문 소문자와 하이픈으로 작성한다.
- 하나의 Jira 이슈를 하나의 작업 브랜치 기준으로 관리한다.
- PDF는 Jira 번호의 정확한 위치를 지정하지 않는다. 다음은 적용 가능한 예이며 문서의 원문 예시는 아니다.

```text
feature/S15P31D109-118-rag-indexing
feature/S15P31D109-119-rag-search
build/S15P31D109-116-rag-dependencies
```

| 브랜치 타입 | 용도 |
| --- | --- |
| `feature` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 리팩토링 |
| `design` | UI·디자인 |
| `docs` | 문서 |
| `test` | 테스트 |
| `build` | 빌드·의존성 |
| `ci` | CI/CD |
| `chore` | 기타 작업 |

기존 브랜치의 개명·분리는 자동으로 하지 않는다. 특히 사용자가 앞서 명시적으로 지정한 `feat/rag-load`는 팀 문서와 이름이 다르므로, 기존 작업과 사용자 지시를 보존한 뒤 새 규칙 적용 방식을 정한다.

## 병합과 푸시

- 배포 브랜치, `develop`, `develop-*`에는 직접 푸시하지 않고 MR을 통해 병합한다.
- 최소 1명 이상의 리뷰 후 병합한다.
- 병합 전 충돌을 해결하고 빌드·기본 동작을 확인한다.
- 작업 브랜치 → 파트별 develop 병합은 Squash Merge를 권장한다. 여러 커밋을 하나의 Jira 작업 단위로 정리한다.
- 파트별 develop → 공통 develop → 배포 브랜치 병합은 기존 작업 단위의 커밋 이력을 유지한다.
- 작업 브랜치는 짧게 유지하고 병합 완료 후 삭제한다. 에이전트가 요청 없이 병합하거나 삭제하지 않는다.

## 문서 내 표기 차이

- PDF 앞부분은 배포 브랜치를 `main`, 뒤쪽 흐름·병합 규칙은 `master`라고 쓴다. 실제 저장소의 대상 브랜치를 확인하며 둘을 임의로 생성하거나 개명하지 않는다.
- `develop-frontend`, `develop-android`와 Android 설명도 혼용돼 있다. AI 작업 대상은 일관되게 `develop-ai`다. 다른 파트의 이름은 실제 저장소 기준으로 확인한다.
