# FAQ 변경 알림 — 영속 접수·원문 조회·자동 소비자

현재 구현은 접수·FIFO 상태 관리, 대상 원문 조회, JSON 문서 준비, 추가·수정·삭제 색인, 자동 소비자와 관리 FAQ 검색 경로까지다.
운영 생성기는 관리 전용 Qdrant 컬렉션과 영속 색인을 만들고, 배포된 GPU의 실제 Qwen 토크나이저로 등록 길이를 확인한다.
`search_manual`은 관리 색인의 Top5를 기존 리랭커로 정렬해 Top3를 Live에 전달하며, 삭제된 FAQ는 리랭킹 후와 진단 결과에서도 다시 제외한다.
GPU `/validate-documents` API는2026-10-31 배포·인증/길이 거절 실검증을 완료했다. 해당 API가 없거나 계약이 다르면 관리 모드 기동을 실패 처리한다.
`faq_sync.receive_enabled=false`, `process_enabled=false`가 기본이며 운영 준비 전 활성화하지 않는다.
202는 검색 반영 완료가 아니라 **재전송 가능한 알림을 디스크에 안전하게 보관했음**을 뜻한다.

## 최초 이전 명령

기존 BE 데이터에 알림이 없을 때 `scripts.bootstrap_faq`로 번호를 영속 큐에 넣는다.
동일한 FAQ 번호 집합은 고정 UUID를 사용하므로 재실행해도 같은 초기 작업이다. 일반 재동기화 명령은 아니다.
먼저 알림 수신을 준비해 조회 이후의 추가/수정/삭제도 접수되도록 한다. 최초 전환 중 관리자 변경은 멈추고 대조하는 것을 권장한다.

```sh
# ai/에서 실행. 실행 환경에 BACKEND_API_URL을 준비한다. 미리보기도 BE 읽기 요청은 발생한다.
uv run python -m scripts.bootstrap_faq
# 실제 서버와 같은 상태 DB/볼륨을 사용하는 환경에서만 접수한다.
uv run python -m scripts.bootstrap_faq --enqueue
```

명령은 `.env`를 자동으로 열지 않는다. 실행 프로세스에 주입한 환경변수를 사용한다.
목록의 번호/원문/UTC/정렬/중복/hasNext를 모두 검사한 뒤 하나의 INSERT 알림을 만든다.
소비자는 저장한 본문이 아닌 해당 번호의 최신 원문을 다시 조회한다. APPLIED를 확인하기 전에는 검색 반영 완료가 아니다.
100건 이하의 단일 완전 응답만 지원한다. hasNext=true면 큐 등록 없이 실패한다.
다중 페이지는 고정 시점 API가 없어 별도 이전 절차가 필요하다. 빈 목록은 기존 색인을 지우지 않는다.
이 명령은 Qdrant를 직접 수정하거나 유료 임베딩을 직접 호출하지 않지만, 실행 중인 소비자가 큐를 처리하면 임베딩 비용이 발생한다.

## 변경 알림 입력

`POST /internal/faqs/refresh`, `Authorization: Bearer <AI_FAQ_TOKEN>`.
토큰은 다른 연동과 구분하는 32자 이상 공백 없는 ASCII 문자열이다.

```json
{"eventId":"5bacfcef-2cce-487a-a993-b09a95c32553","operation":"INSERT","faqEntrySeqs":[123,124]}
```

- INSERT/DELETE: 번호 1~100개. UPDATE: 하나만 허용한다.
- 번호는 중복 없는 양의 정수이며 최댓값 2147483647. 문자열·실수·bool은 거절한다.
- eventId는 UUID. 질문/답변/revision 등 추가 필드는 받지 않는다.
- 잘못된 토큰401, 잘못된 본문400, 큰 본문413, 같은 eventId의 다른 변경409.
- 비활성/토큰 설정 오류/용량 초과/디스크 오류/잠금/시간 초과503.
- 같은 eventId·operation·번호 집합의 재전송은 다시202이며 작업을 추가하지 않는다.
- 새 알림은 SQLite COMMIT 성공 후에만202를 반환한다. 백엔드는202 외 응답 시 재전송한다.
- DELETE는 알림과 반환 차단 번호를 같은 트랜잭션에 저장한다. 차단 저장이 실패하면 알림도 롤백하고503이다.

## 저장·순서·복구

`rag_state/faq-events.sqlite3`에 WAL + synchronous=FULL로 저장한다.
Docker에서는 `/app/data` 읽기 전용 주소DB와 분리된 `rag_state` named volume을 사용한다.
배포 시 `docker compose down -v`로 이 볼륨을 지우면 미처리 알림과 중복 기록도 사라지므로 보존한다.
SQLite 파일·WAL·SHM을 실행 도중 개별 복사하는 대신 SQLite 백업 API나 서비스 정지 후 백업한다.

상태는 `QUEUED → PROCESSING → APPLIED`, 실패 시 `PROCESSING → RETRY → PROCESSING`이다.
가장 오래된 미완료 작업만 꺼내며 선행 작업이 실행 중이거나 재시도 시각 전이면 후행 작업도 대기한다.
활성화한 앱을 재시작하면 처리 중 상태를 RETRY로 복구한다. 작업 소비자는 서버 전체에서 하나만 둔다.
여러 프로세스/복제 인스턴스가 같은 파일을 쓰는 운영 방식은 현재 지원하지 않는다.
오류 저장은 정해진 코드만 사용하며 토큰·본문·상세 예외를 기록하지 않는다.
완료 기록은 재전송 중복 방지를 위해 유지한다. 보관/정리 정책은 아직 별도로 정하지 않았다.

## 자동 소비자와 재시도

관리 검색의 `config/faq-bm25-descriptions.json`은 BM25 전용 설명이다.
실제 FAQ 관리번호와 원문 source_sha256가 같을 때만 BM25 입력에 붙이며 답변 근거/벡터 입력은 바꾸지 않는다.
현재 이용시간 FAQ3번에 이전 검증 설명을 연결했다. 다른 환경의 번호가 다르면 해당 환경의 실제 번호/원문을 확인해 설정해야 한다.
원문이 수정돼 해시가 달라지면 설명은 적용하지 않는다. 설명 파일 변경은 관리 색인을 재생성/재시작해야 반영된다.
기존 청크의 embedding_text에 보관하는 설명과 이 BM25 전용 설정은 적용 범위가 다르다.

`faq_processor.py`가 한 번에 알림 하나를 `대상 최신 원문 조회 → 문서/청크 준비 → 색인 검증·적용 → APPLIED` 순서로 처리한다.
원문 조회는 알림 시점의 복사본이 아니라 처리 시점의 백엔드 최신 원문이다. DELETE에는 조회가 없다.
같은 원문 해시의 검증된 검색용 설명만 유지하며 원문이 바뀌면 오래된 설명을 제거한다.
HTTP202는 저장 성공만 뜻하고, 위 네 단계가 모두 끝난 뒤에만 APPLIED다. 최종 완료를 BE에 되돌리는 API는 없다.

실패는 FETCH_FAILED/PREPARE_FAILED/INDEX_FAILED/ACK_FAILED 등 고정 코드로 RETRY에 저장한다.
재시도는 최초5초에서 두 배씩 늘려 최대300초이며 무제한 반복한다. 실패한 맨 앞 알림을 뒷 알림이 추월하지 않는다.
재시도 상태 기록 자체가 실패하면 메모리에서 그 알림을 붙잡아 다시 기록하고, 재시작 시 PROCESSING을 RETRY로 복구한다.
작업 취소/서버 종료는 이미 실행한 동기 임베딩·색인 스레드가 끝날 때까지 기다린 뒤 INTERRUPTED로 표시한다.
앱의 수신 알림은 소비자를 깨우지만, 깨우기 유실 뒤에도 `poll_sec` 폴링으로 처리한다.

삭제 이력은 `reconcile_sec`마다 재확인한다. PENDING은 전체 삭제 반영을 재시도하고,
CLEANED는 늦게 다시 생긴 포인트만 지운다. 후자는 불필요한 새 색인 세대를 만들지 않는다.
재점검은 큐의 APPLIED 표시와 별개다. 삭제 차단은 CLEANED 뒤에도 유지한다.

앱 기동에서 접수 큐와 관리 색인이 같은 상태 DB, 컬렉션, 모델, 차원인지 확인한다.
`process_enabled=true`에는 `receive_enabled=true`가 필수다. 앱은 관리 색인을 생성하며 GPU 길이 검증 API·전용 컬렉션·모델/차원 불일치 시 기동을 거절한다.
현재 운영 기본 설정은 비활성이다. GPU 새 API 배포, 최초 백엔드 FAQ 전체 이전, 기존95문항/긴 FAQ 회귀평가와 실통화 확인 뒤 활성화를 판단한다.

등록 길이 검증은 고정 Qwen 모델/리비전·최대1024토큰과 같은 토크나이저를 사용한다.
빈 질문 기준 입력 길이에 질문 예비256토큰과 경계 여유32토큰을 더해 검사하며 자동으로 원문을 자르지 않는다.
실제 고객 질문은 예비 공간을 넘을 수 있으므로 `/rerank`가 최종 전체 길이를 다시 검사하고 넘으면 실패로 돌려준다.
문자800자만으로 이 모델의1024토큰을 보장한다고 보지 않는다.

기본 설정은 `config/server.toml`의 `faq_sync`에 둔다. 본문16KiB, 미완료1000건,
접수 제한1.5초, SQLite 잠금 대기0.1초다. 백엔드 HTTP 제한2초보다 여유를 둔다.
HTTP 제한 뒤 저장 스레드가 커밋한 경우에도202를 미리 응답하지 않으며,
백엔드의 같은eventId 재전송을 중복 검사로 처리한다.

## 대상 원문 조회와 입력 준비

`BackendAPI.faq_entries(ids)`가 `GET /api/ai/faqs?faqEntrySeqs=123,124&limit=100&offset=0`을 호출한다.
번호는 중복 없는 양의 정수1~100개이며 전송 전에 검증한다. 전체 FAQ 개수를100개로 제한하는 뜻이 아니다.
기존 `BACKEND_API_URL`과 `[backend] timeout_sec`를 사용한다. 검색어q·관리자 쿠키·서비스 인증 토큰·통화 헤더를 보내지 않고 리다이렉트도 따라가지 않는다.

원문 모델 `FaqEntry`는 `faqEntrySeq`, `question`, `answer`, `updatedAt`만 받는다.
번호/문자열 타입, 질문1000자·답변20000자, 공백만 있는 본문/NUL 금지, UTC ISO 시각을 검증한다.
문자열을 strip하거나 Markdown/표/줄바꿈을 수정하지 않는다.
목록은 명시적인 `data` 배열·`hasNext=false`, 요청 범위 내의 중복 없는 오름차순 번호여야 한다.
누락 필드·예상 밖 필드·잘못된 항목·부분 조회는 전부 오류다. 일부 항목만 성공 처리하지 않는다.

- 완전한 정상200의 반환 항목: 갱신할 최신 원문.
- 완전한 정상200에서 빠진 요청 번호: 삭제 대상. 정상 빈 목록도 가능하다.
- 비200(404 포함)·연결/시간 초과·JSON/스키마 오류·부분 목록: `BackendError`. 빈 목록으로 바꾸지 않는다.
- 상세 예외나 응답 원문 대신 고정 오류 코드 `FAQ_FETCH_FAILED`, `FAQ_HTTP_ERROR:<상태>`, `FAQ_INVALID_RESPONSE`를 전달한다.

`prepare_faq_refresh(event, source)`는 INSERT/UPDATE의 원문을 조회하고 `upserts`, `delete_ids`, `event_id`를 준비한다.
DELETE는 원문이 이미 없으므로 조회 없이 받은 번호를 삭제 대상으로 준비한다.
이 함수는 큐 완료·벡터 쓰기/삭제·임베딩·원문 캐시 저장을 하지 않는다. 원문 조회 성공만으로 APPLIED를 표시하지 않는다.

## JSON FAQ → 검색 문서와 청크

구현은 `app/rag/faq_documents.py`다. `prepare_faq_documents`는 한 FAQ를,
`prepare_faq_document_refresh`는 이벤트의 갱신/삭제 묶음을 준비한다. 한 항목이라도 실패하면 전체 준비 결과를 반환하지 않는다.
원문 FaqEntry는 그대로 보관하며 짧은 FAQ의 본문은 `### Q. {question}\n{answer}`다.
기존 MD 로더·청킹과 검색 서비스는 변경하지 않았다. 신규 문서가 현재 운영 검색에 자동으로 섞이지 않는다.

- `faq_id=backend-faq:123`: 원문 번호에 연결된 불변 관리번호. 같은 질문이 등록돼도 번호가 다르면 별개다.
- `source_sha256`: 질문/답변 원문 해시. 수정시각과 관리번호를 제외한다.
- `faq_version`: 실제 청크·검색 입력·형식 버전·모델/차원을 묶은 AI 내부 판본 해시. BE에 revision을 요구하는 필드가 아니다.
- `point_id/chunk_id`: FAQ 관리번호+내부 판본+자식 순번으로 만든 UUID5. 같은 입력은 같은 ID이며 수정 준비 포인트는 기존 판본과 분리한다.
- `embedding_sha256`: 실제 검색 입력+모델+차원+형식 버전 해시. 수정시각만 바뀌거나 별개 FAQ의 입력이 같으면 재사용 가능하다.
- 같은 FAQ의 일부가 수정돼 판본 포인트 ID가 바뀌어도, 입력이 같은 자식의 임베딩 해시는 유지한다. 벡터 캐시와 판본 포인트 쓰기는 아래 증분 색인 모듈에서 처리한다.

검색 설명은 선택 사항이며 FAQ 관리번호/원문 해시가 일치하는 설명만 받는다. 기존 `search_documents`와 같은 형식으로 검색 입력에만 붙인다.
설명이 오래됐으면 호출자가 새 원문에 전달하지 않아야 하며, 잘못 전달하면 오류다. 원문/리랭킹/Live 근거에는 검색 설명을 넣지 않는다.

`[faq_sync] chunk_size=800`, `chunk_overlap=50`은 문자 기준이다. 질문과 반복 문맥을 포함해800자 이내로 만든다.
짧은 FAQ는 공백·표·개행을 그대로 유지하고, 긴 FAQ는 다음 범위에서 구조를 보존한다.

- 일반 문단: 질문·ATX 절 제목·상위 절 본문을 반복하고 남은 공간에 RecursiveCharacterTextSplitter를 적용한다. 겹침은 본문 부분에 적용한다.
- 일반 pipe 표: 질문·절 문맥·표 머리글/구분행을 각 조각에 반복한다. 같은 절의 표 밖 조건(VAT 등)도 보존한다. 행은 통째로 유지한다. 이스케이프/인라인 코드의 pipe는 열 구분으로 세지 않는다.
- 글머리/번호 목록: 같은 절의 금지/예외 설명을 반복하고 최상위 항목 단위로 묶는다. 부모와 하위 항목은 분리하지 않는다.
- fenced 코드: 내부 제목/표를 별도 구조로 해석하지 않고 한 블록으로 유지한다.
- 표 한 행·목록 한 항목·코드 블록·필수 반복 문맥이 너무 크거나 구조가 맞지 않으면 FaqChunkingError다. 자동 잘라내기나 항목 누락으로 성공 처리하지 않는다.
- 표/목록의 독립 행·항목은 중복하지 않는다. HTML 표, 병합 셀, 임의 Markdown 확장까지 지원한다고 간주하지 않는다.

문자 수만으로 Qwen의 전체1024토큰을 보장하지 않는다. 실제 GPU 토크나이저로 등록 길이를, 리랭킹 요청에서 전체 길이를 각각 검증한다.
새 청킹의 검색 정확성도 기존95문항과 긴 FAQ 평가로 별도 확인해야 한다.

### 오프라인 확인

```sh
uv run python -m scripts.inspect_faq_json data/private/faq-api-response.json --show-chunks
```

파일은 실제 번호/질문/답변/updatedAt을 담은 JSON 배열 또는 `{data:[...],hasNext:false}`이며1~100건을 받는다.
`--chunk-size`, `--chunk-overlap`으로 값을 바꿔 볼 수 있다. API·임베딩·Qdrant를 호출하지 않고 원본 파일도 수정하지 않는다.

2026-10-30 Git의 BE 초기32건과 기존 MD를 오프라인 비교했다. 질문32개가 연결됐고 새 청크32개, 본문 최대523자,
기존 실제 검색 입력과 완전 동일한 항목0개다. 출처/분류/문서 형식·검색 설명 차이가 있어 최초 이전 시32건 신규 임베딩을 준비해야 한다.
이는 검색 성능 평가가 아니다. 비교용 임시 번호는 실제 BE 번호가 아니며 보고서로 색인하지 않는다.

## 추가·수정 증분 색인과 같은 판본 검색

- `faq_index_state.py`: 기존 영속 SQLite에 원문/청크 판본, 세대 번호, 입력별 임베딩 캐시, FAQ별 캐시 참조를 저장한다.
- `faq_vectors.py`: 관리 전용 Qdrant 컬렉션의 준비 포인트 저장/검증과 정확한 ID 목록에 제한한 검색을 수행한다.
- `faq_index.py`: 변경 입력 임베딩, BM25 재구성, 포인트 검증, 영속 판본 커밋과 검색 스냅샷 교체를 직렬화한다.

관리 대상은 `[faq_sync] collection=manuals_backend_faq_large`, 임베딩 묶음은 `embedding_batch_size=32`다.
기존 `[rag] collection`과 같으면 서버 설정 검증에서 거부한다. 색인 모듈은 기존 컬렉션을 자동 생성/초기화/삭제하지 않는다.
Qdrant 어댑터는 생성자가 전달받은 컬렉션의 unnamed/Cosine/차원을 확인한다. 현재 운영 서비스는 여전히 기존 MD 경로를 사용한다.

추가·수정 처리 순서는 다음과 같다.

1. 단일 쓰기 잠금 아래 현재 세대/원문을 읽고 대상 원문을 합친다. 변경이 없으면 기존 판본을 반환한다.
2. GPU의 실제 Qwen 토크나이저 등록 길이 검증기를 실행하고 모델/차원/실제 입력 해시를 대조한다.
3. 후보 원문 전체의 Kiwi/BM25를 만든다. BM25에는 청크별 실제 검색 입력을 사용하고 결과 근거에는 원문만 사용한다. 기존 MD 경로의 제목별 설명 처리는 그대로다.
4. 캐시에 없는 입력 해시만 중복 제거해 묶음 임베딩한다. 반환 개수·숫자/차원·유한 float32 비영벡터를 검증하고 성공한 묶음을 즉시 디스크에 커밋한다.
5. 기존 활성 ID에 없는 새 판본 포인트만 `wait=true`/strong ordering으로 준비하고 원문/메타데이터/벡터 방향을 재조회해 검증한다.
6. 새 판본 전체의 포인트도 확인한다. 이상이 없으면 세대 비교 조건을 걸어 원문 전체와 세대를 한 SQLite 트랜잭션으로 커밋한다.
7. 준비된 BM25/원문/포인트 ID 목록 객체를 짧은 잠금으로 교체한다. 진행 중인 추가·수정 전 검색은 캡처한 이전 판본을 끝까지 사용한다.

벡터 검색은 해당 검색 판본의 HasId 목록으로 제한한다. 실패한 준비 포인트나 이전 수정 버전이 있어도 새 검색에 섞지 않는다.
입력이 같은 자식은 새 FAQ 판본의 포인트를 준비하더라도 캐시 벡터를 재사용한다. 변경하지 않은 다른 FAQ의 벡터를 전체 복사/재임베딩하지 않는다.
상세 근거는 [Qdrant 포인트 관리](https://qdrant.tech/documentation/manage-data/points/)와 [필터](https://qdrant.tech/documentation/search/filtering/)이며 설치된 SDK 인수도 확인했다.
메모리 Qdrant 테스트는 운영1.13.4 서버에서의 실연동 검증을 대신하지 않는다.

원문/캐시는 체크섬을 확인하며 모델/차원/컬렉션/형식이 다른 상태 파일을 그대로 열어 혼용하지 않는다.
재시작은 디스크 판본과 기존 포인트를 검증하고 BM25를 재구성하며 문서 임베딩을 호출하지 않는다.
임베딩/준비 쓰기/검증/커밋 실패 시 기존 검색 객체는 유지한다. 응답이 유실된 Qdrant 쓰기는 같은 포인트 ID로 재시도한다.
영속 커밋 직후 메모리 교체 전에 프로세스가 종료돼도 재시작하면 커밋된 판본을 읽는다.
SQLite와 Qdrant는 분산 트랜잭션이 아니며, 이미 비용이 발생한 임베딩 응답 자체를 받기 전에 연결이 끊긴 경우까지 중복 비용을 막을 수는 없다.

같은 프로세스에 여러 색인 소비자를 만들거나 여러 프로세스가 함께 쓰는 구성은 지원하지 않는다.
이 모듈은 동기 함수이므로 자동 소비자 연결 시 이벤트 루프 밖에서 실행해야 한다. 검색 요청이 변경분 문서 임베딩을 수행하지 않는다.

## 삭제·반환 차단·복구

삭제 번호는 본문 없는 `faq_delete_blocks`에 `PENDING`으로 영속 저장한다. 정리가 끝난 `CLEANED` 이후에도 차단은 유지한다.
FAQ 번호를 삭제 후 재사용하지 않는 전제다. 새 FAQ는 새 번호로 등록하며 번호 재사용/DB 초기화는 별도 이전 작업이다.
INSERT/UPDATE의 완전한 원문 조회에서 빠진 번호도 `FaqIndex.apply`에 들어오면 같은 삭제 경로를 사용한다.

1. DELETE 알림은 영속 접수와 동시에 차단한다. 원문 누락으로 확인한 삭제는 색인 적용 진입 시 차단한다.
2. 긴 수정 작업의 쓰기 잠금을 기다리기 전부터 차단을 보관한다. 준비 중 새 차단이 오면 후보에서 제외하고 다시 준비한다.
3. 원격 쓰기/삭제는 같은 색인 소비자 잠금으로 직렬화한다. `metadata.faq_id` 필터로 현재·예전·실패한 준비 버전의 모든 포인트를 실제 삭제한다.
4. `wait=true`/strong ordering의 COMPLETED를 확인하고 exact count=0인지 확인한다. 실패/응답 유실/잔여 포인트는 성공으로 바꾸지 않는다.
5. 남은 FAQ 판본을 검증하고 SQLite 원문/판본 전환·해당 FAQ의 캐시 참조 제거·무참조 캐시 제거·CLEANED 상태를 같은 트랜잭션으로 커밋한다.
6. 공유 캐시를 다른 FAQ도 사용하면 그 참조와 벡터는 유지한다. 마지막 참조가 사라져야 해당 캐시 본문/벡터를 제거한다. 삭제에는 임베딩을 호출하지 않는다.

차단은 SQL 세대/원문과 별도로 유지하므로 물리 삭제나 마지막 커밋이 실패해도 검색을 되살리지 않는다.
재시작은 차단된 원문을 파싱/벡터 검증 대상에서 먼저 제외하고 모든 삭제 이력을 다시 정리한다.
삭제된 원문이 손상됐거나 포인트가 이미 없어도 정리할 수 있다. `reconcile_deletions`는 수동/기동 점검에도 사용한다.
삭제 완료 뒤 오래 지연된 원격 쓰기나 외부 쓰기로 포인트가 다시 나타나면 차단이 노출을 막고 재점검이 다시 제거한다.
0건 확인은 확인한 시점의 결과이며 미래의 임의 외부 쓰기까지 영구 금지하는 Qdrant 제약은 아니다. 자동 주기 점검은 소비자에서 수행한다.

`faq_search.py`의 검색 래퍼는 캡처한 옛 판본에도 현재 차단을 적용한다.
검색 시작 전 차단된 FAQ는 BM25/벡터 조회 대상에서 제외하고, 결과 반환 전 다시 검사한다.
삭제와 DB 조회가 겹쳐 포인트가 사라지면 남은 목록으로 재검색한다. 목록이 줄지 않는 오류는 숨기지 않는다.
재검색에서도 질문 임베딩은 요청 내에서 한 번만 호출하며 재시도 시간은 별도로 기록한다.
리랭킹 전에 구한 결과가 오래 남을 수 있으므로 **실제 전달 경로는 리랭킹 후 `FaqIndex.filter_rows`를 다시 호출해야 한다.**
관리 검색 서비스는 이 필터를 리랭킹 후 Live 도구 응답 구성에 적용한다. 이미 외부 모델에 전달했거나 발화한 내용은 회수하지 못한다.
새 판본/차단 조회는 단일 프로세스 전제이며, 최종 차단 검사 후 새 삭제가 도착하는 시간 경계도 존재한다.

원문/캐시 삭제는 관리 저장소의 논리 행과 Qdrant 포인트 제거다. 과거 MD 평가 자료, 파일 시스템 여유 페이지/WAL,
백업의 포렌식 영구 소거까지 뜻하지 않는다. 본문 없는 삭제 ID/상태/이벤트 기록은 중복·부활 방지용으로 유지한다.
큐를 APPLIED로 만드는 자동 소비자는 관리 색인 주입 시 연결된다. 운영 기본 설정은 비활성이다.

## 운영 전환의 경계

원문은 알림 번호로 `GET /api/ai/faqs`에서 조회한다. 유효한 전체200에서 빠진 번호만 삭제로 판단한다.
조회 오류를 삭제로 바꾸지 않는다. 색인 성공·교체 후에만 APPLIED로 표시하고 실패는 RETRY로 남긴다.
실제 적용은 재시도해도 안전해야 한다. SQLite 접수만으로 Qdrant와의 원자적 트랜잭션이 보장되지는 않는다.
기존 임베딩·Kiwi/BM25·RRF·리랭킹·Top3 검색 동작은 이번 단계에서 변경하지 않는다.
