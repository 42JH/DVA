# 통화 시나리오와 분기

통화 흐름의 구조(서버는 가드레일, 단계 = 업무와 확정 관문)는 `spec/flow.md`가 기준이다. 조회·취소·QnA 노드와 다이어그램 문구는 `spec/LANGGRAPH_REBUILD.md`(dva_mvp_flow.drawio)에서 왔고, 정보 받기 노드(A·B)는 `ORDER` 하나로 합쳤다(2026-11-01). 문구는 `prompts/flow.toml` `[say]`에 다이어그램 ID로 있다. 이 문서에는 **구현이 정한 것**(다이어그램에 없거나 백엔드 계약 때문에 달라진 것)만 적는다. 코드에는 `TODO(flow):`로 표시했고, 결정한 것·결정이 필요한 것은 `spec/LANGGRAPH_REVIEW.md`에 있다.

## 진입

| 고객 | 경로 |
|---|---|
| 신규(발신번호 없음·미등록·고객 확인 실패) | `CALLER_ID` → `IS_REGISTERED` → `HUB`(GREET_NEW) |
| 등록(기존 출발지 있음) | `CALLER_ID` → `IS_REGISTERED` → `ORDER`(GREET_REGISTERED = 기존 출발지 제안) |
| 등록(기존 출발지 정보 없음) | `IS_REGISTERED` → `HUB`(GREET_REGISTERED_PLAIN). 백엔드가 최근 접수를 아직 주지 않아서(TODO(flow), 보완사항 29) |
| 탈퇴 | `IS_REGISTERED` → `AGENT_HANDOFF`(D9 안내 후 refer). 신규로 다루지 않는다(TODO(flow)) |

- 고객 유형·주소록·최근 접수 1건(출발지·도착지)은 통화 시작 때 백엔드 고객 확인으로 받는다(`spec/backend-api.md` 1번). 발신번호 주인 것만 받는다.
- 인사(기존 출발지 제안): 예 → 그 출발지를 쓰고 받는 곳으로, 아니요(다른 곳에서) → 보내는 곳 주소를 묻는다, 접수가 아닌 용건("아니요"만·다른 용건) → "무엇을 도와드릴까요?" → `HUB`(접수 업무를 끝냄). 조회·취소 같은 이미 보낸 택배에 대한 용건은 판별 의도 `lookup`으로 어느 단계에서나 `C_REQUIRED_INFO`. 기존 출발지가 나오기 전의 "예"는 다시 묻는다(아니요·다른 용건은 받는다).
- HUB: 접수 → `ORDER`, 조회(신규 고객은 이 번호로 접수한 택배가 없어 NEW_LOOKUP 안내 뒤 `ORDER`) → `C_REQUIRED_INFO`, 더 없음 → `END_CALL`. 용건을 고르지 않고 주문 정보부터 말해 기록되면 바로 `ORDER`.
- `{기존 출발지}`: 이전 접수(ACCEPTED) 주문의 출발지, 없으면 본인 주소록의 주소(발신번호와 같은 번호의 핀, §9 "고객 등록 주소"). 둘 다 없으면 출발지 없이 인사(GREET_REGISTERED_PLAIN).

## 통화 하나 = 백엔드 주문 하나

- `A_DONE`(접수 완료)은 받은 택배를 **접수 목록에 담는 것**이다. 백엔드 접수(`POST /api/orders`, 택배들은 `parcels`)는 `END_CALL`에서 한 번 한다(백엔드는 통화 한 건에 주문 한 건만 받는다).
- 수거 일시는 주문(통화)에 하나다. 두 번째 택배부터는 이미 차 있어 묻지 않는다.
- 결제(`A_PAYMENT`): 다이어그램은 MVP 현장 결제(분기 보류)인데 백엔드에 현장 결제가 없다. 후불 자격(월결제·부서 그룹결제)이 하나면 그것, 둘 다면 고객에게 묻고(PAY_ASK, 고른 답은 확정 지연 뒤에 정함), 없으면 개인 카드(TODO(flow), 2026-10-31 결정). 결제 방식은 통화(주문)에 하나라 두 번째 택배부터는 묻지도 안내하지도 않는다.
- 운임(A6 "운임은 {운임}원이에요."): 서버 요금표(`[fare]`)로 계산한 받는 중인 택배의 배송비. 모르면 말하지 않는다. A6 뒷문장은 결제 방식별 사실(PAY_CREDIT·PAY_GROUP·PAY_BILLING)로 바꿨다. 결제 완료·결제 안내 발송은 말하지 않는다.
- 신규 고객의 성함(`customer`)은 보내는 분 성함이다(MVP: 고객 = 보내는 분).
- 신규 고객은 보내는 분 정보(성함·주소·상세주소)가 다 기록되는 순간 백엔드에 고객 등록 + 보내는 곳을 개인 주소록에 저장하고(`spec/backend-api.md` 1-1, 통화에 한 번), 이때부터 등록 고객으로 다룬다(2026-10-31 결정).

## 정보 받기(`ORDER`)

- 빠진 항목을 권장 순서(보내는 분 성함 → 보내는 곳 주소 → 상세 → 받는 분 성함 → 연락처 → 주소 → 상세 → 물품 → 가액 → 수거 일시)로 진행 상태의 "다음"에 준다. 고객이 순서 밖 항목을 먼저 말해도 기록하고 빠진 것만 묻는다. 다 차면 `A_CONFIRM`.
- 보내는 분 전화번호는 묻지 않고 발신번호로 채운다(발신번호가 없는 통화만 A1_3으로 묻는다). 등록 고객은 성함도 고객 정보로 채운다.
- 상세주소는 어느 주소의 것인지 넣어 묻는다(A_ADDR_DETAIL_SENDER·RECEIVER, 순서가 자유라서).
- 주소는 기록하면서 주소DB로 확정하고, 못 찾으면 지우고 예외 문구(A_ADDR_RETRY_SENDER/RECEIVER)로 찾을 때까지 다시 묻는다(다른 빈 항목보다 먼저, 들은 그대로 기록하지 않음, `spec/address.md`). 주소가 바뀌어 상세주소가 비면 다시 묻는다.
- 지난 수거 일시는 `record_order`가 거절하고 A5_PAST를 한 번 알린 뒤 수거 일시를 다시 묻는다. 물품 크기·개수, 가액이 애매한 답은 음성 모델이 되묻는다(서버 예외 문구 없음).
- 제안(저장된 값을 쓸지)은 그 항목의 질문 자리에 들어가고 답은 서버 판별로 받는다. 답마다 바로 이어서 할 말을 진행 상태에 미리 준다(`order_preview`).
  - 두 번째 택배부터 출발지는 앞 택배의 출발지를 묻지 않고 쓴다(번호·상세주소는 저장된 값처럼 읽지 않는다).
  - 최근 접수 1건 = 이번 통화에서 담은 마지막 택배, 없으면 백엔드가 준 가장 최근 접수(`Call.recent_place`). 최근 도착지가 있으면 "이번에도 {도착지 주소}로 보내시나요?"(B4, 다이어그램은 "지난번처럼…", 이번 통화의 택배도 최근 접수라 바꿈). 예면 그 도착지(받는 분 포함)를 그대로 쓰고, 아니요면 주소록이 있는 고객은 B6("어디로 보내실 건가요?"), 없으면 받는 분 성함.
- 주소록 찾기(`match_pins`): 핀 = 백엔드 주소록(개인·기업 PIN)과 이번 통화에서 접수한 받는 곳(맨 앞). 주소록에는 방향·날짜가 없어 발신번호와 다른 번호의 핀을 앞에 두고, 앞쪽 `[flow] pin_recent_count`개에서 먼저 찾는다(거기 없으면 전체). 앞서 말한 이름·장소와 합쳐 찾고, 못 찾았는데 한쪽만 말했으면 빠진 쪽을 묻는다(이름만 → A2_3 주소, 장소만 → A2_1 성함).
  - 여러 개면 후보끼리 다른 값(상세주소 → 주소 → 이름)을 `{후보}`로 이어 묻는다(B8, 앞쪽 핀부터 `[flow] max_pin_options`개). 고른 답은 판별(`pin_1`…), "이 중에 없다"면 고객이 말한 값을 받는 분 정보로.
  - 하나면 받는 분 확인(B9). 아니오면 그 핀은 버리고, 후보를 좁히던 중이면 남은 후보로 다시 묻고, 없으면 "{수신인}님으로 저장된 다른 배송지가 없으니 새로 접수하겠습니다."(B11_NEW) 뒤 새 받는 분으로.
  - 없으면 고객이 말한 받는 분 이름·장소를 받는 분 정보로 가져간다(핀의 값은 가져가지 않음). 장소는 번지·건물번호(숫자)가 있을 때만 주소로 보고 주소DB로 확정한다(보완사항 30).
- 정정: 언제든 기록된다. 값 없이 고친다고만 하면 음성 모델이 직접 묻는다. 저장된 곳에서 가져온 받는 곳을 다른 곳으로 말하면(`match_pins`) 받는 분까지 비우고 새로 찾는다(이전 주소록 찾기 결과는 버림). 고친 값은 한 번 확인(CORRECTED)한다.

## 되읽기 확인(`A_CONFIRM`)

- 택배를 담기 전 접수 내용(보내는 곳·받는 분·받는 곳·물품·가액·수거 시각)을 임시 주문 그대로 되읽고 "이대로 접수할까요?"를 묻는다(2026-11-01 사용자 결정, 택배 하나가 완성됐을 때마다, LANGGRAPH_REVIEW 1번). 주소록·최근 접수에서 온 상세주소는 읽지 않고, 번호는 기록할 때 이미 읽었으므로 뺀다.
  - "예" → `A_PAYMENT`는 되돌릴 수 없는 확정이라 `commit_delay_ms` 동안 새 말이 없을 때만 간다. 확정되면 운임·결제 안내(A6)를 다음 질문과 함께 한다. 결제 방식을 물어야 하면 `A_PAYMENT`로 바로 가고, 고른 답(→ `A_DONE`)이 확정 지연 대상이다. "잠깐만요"로 확정을 버리면 고객이 다시 "예"라고 해야 한다.
  - "예"에 정정이 섞이면 확정하지 않는다(정정을 기록하고 다시 되읽기). 질문이 섞이면 질문만 받고 답한 뒤 다시 확인한다.
  - "아니요" → "어느 부분을 고쳐 드릴까요?"(`A_CONFIRM_FIX`). 고친 값이 기록되면 바뀐 내용으로 다시 되읽는다. 고치다 값이 비면(주소를 못 찾음 등) `ORDER`로 돌아가 다시 받는다.
- 추가 접수 질문(`A_CHOICE`)에 다음 택배 정보를 바로 말하면 기록하고 `ORDER`로 간다.

## C — 조회·취소

- `lookup_orders`(받는 분 성함, 기억 안 나면 서버가 성함 없이 최근 것부터)로 찾고, 결과 사건으로 분기한다. 그분께 보낸 택배가 없으면 같은 단계(C2_NONE), 조회 실패면 같은 단계에서 다시 확인할지 묻는다(C3_FAIL, 업무 처리 불가 +1, 다시 조회 상한 `[flow] retry_limit`).
- 이 번호로 접수된 택배가 하나도 없으면(C_NO_ORDERS) HUB, 더 이전 택배가 없으면(C2_END) 받는 분 성함부터 다시(TODO(flow)).
- 조회는 통화 고객의 최근 주문 `[backend] lookup_limit`건을 택배(주문 상세) 단위로 읽는다(`spec/backend-api.md` 2번). 상태를 확인하지 못하면 "조회가 안 됨"으로 본다. `{배송 상태}`는 주문 상태(취소한 상세는 CANCELLED)를 `[status_names]` 표로 말한다. 수거·배송 상태는 백엔드에 없다.
- 취소 가능은 미완료(`COLLECTING`)·개인 카드 결제 대기(`notPaid`)만. 이미 취소됨(C7_CANCELLED) → HUB, 그 밖(결제가 끝나 접수 진행) → C7_LOCKED(+1) → HUB. 다이어그램의 "이미 기사님이 수거해 가셔서…"는 수거 상태가 없어 바꿨다(TODO(flow)).
- 취소 "예" → 확정 지연 → `C_CANCEL`에서 서버가 `cancel_order`를 실행한다(작업 번호, 실행 중 고객 말은 쌓았다가 결과를 안내한 뒤 판별). 실패면 다시 시도할지 묻고(C9_FAIL, +1), 다시 시도 전에 조회로 이미 취소됐는지 확인한다.
- 수정은 보류(§5.4): `C_CHOICE`의 "수정"은 제한된 요청(D6)으로 보낸다.

## D — QnA·상담원 Hub

- 질문은 백엔드의 매뉴얼 검색 결과(`rag.*`)로 `GLOBAL_INTENT`에 들어와 바로 답변 단계(RAG Yes) 또는 상담원 제안(RAG No)으로 간다. 제한된 요청은 백엔드의 `switch_task`(`agent`)로 들어온다.
- RAG Yes = 근거가 있음(임계값 `[rag] min_score`를 두면 1등 리랭커 점수도). 답변은 음성 모델이 검색 근거로 하고 서버는 D2만 붙인다.
- 상담원 연결 가능 여부는 `[flow] agent_open_hour`~`agent_close_hour`(한국 시간)로만 본다(TODO(flow)).
- 고객이 직접 상담원을 원하면 제한된 요청으로 처리한다(§9).
- 통화를 끝내겠다고 하면(`end`) 어느 단계에서나 `END_CALL`(TODO(flow)). 같이 한 답은 버린다.

## 통화 결과(통화가 끝날 때 한 번)

| 상황 | outcome | 담는 택배 |
|---|---|---|
| HUB "더 없음"(`END_CALL`)으로 이미 보냄 | (다시 보내지 않음. 처리 중이었으면 같은 키·같은 본문으로 확인만) | |
| 상담원에게 넘김(탈퇴 고객 포함) | `INCOMPLETE` | 접수한 택배 + 받는 중이던 택배. 접수한 택배가 있어도 접수하지 않는다 |
| 끊김·무응답·종료 요청, 접수한 택배 있음, 필수값(지번·좌표·배송비·결제 방식) 다 있음 | `COMPLETE` | 접수한 택배만 |
| 그 밖(접수한 택배 없음 등) | `INCOMPLETE` | 받는 중이던 택배(있으면) |

- 확정 지연 중에 끊기면 그 확정(결제 단계 진입)은 실행하지 않는다(받는 중이던 택배로 미완료).
- `END_CALL`은 결과가 `ACCEPTED`일 때만 접수 완료·접수번호를 말하고(END_ACCEPTED), 개인 카드 결제 대기(`notPaid`)면 결제가 확인되면 접수가 진행된다고(END_NOT_PAID), 그 밖에는 확인 후 연락(END_PENDING) 뒤 마무리 인사(TODO(flow)).
