# 통화 시나리오와 분기

통화 흐름의 노드·분기·문구는 `spec/LANGGRAPH_REBUILD.md`(dva_mvp_flow.drawio)가 기준이다. 노드 이름은 다이어그램 ID 그대로이고(`app/flow/stages/`), 문구는 `prompts/flow.toml` `[say]`에 표의 ID로 글자 그대로 있다. 이 문서에는 **구현이 정한 것**(다이어그램에 없거나 백엔드 계약 때문에 달라진 것)만 적는다. 코드에는 `TODO(flow):`로 표시했고, 결정한 것·결정이 필요한 것은 `spec/LANGGRAPH_REVIEW.md`에 있다.

## 진입

| 고객 | 경로 |
|---|---|
| 신규(발신번호 없음·미등록·고객 확인 실패) | `CALLER_ID` → `IS_REGISTERED` → `A_NEW_ORDER`(GREET_NEW) |
| 등록(최근 접수 있음) | `CALLER_ID` → `IS_REGISTERED` → `B_GREET_CHOICE`(GREET_REGISTERED: 기존 출발지 확인) |
| 등록(최근 접수 정보 없음) | `IS_REGISTERED` → `HUB`(GREET_REGISTERED_PLAIN). 백엔드가 최근 접수를 아직 주지 않아서(TODO(flow), 보완사항 29) |
| 탈퇴 | `IS_REGISTERED` → `AGENT_HANDOFF`(D9 안내 후 refer). 신규로 다루지 않는다(TODO(flow)) |

- 고객 유형·주소록·최근 접수 1건(출발지·도착지)은 통화 시작 때 백엔드 고객 확인으로 받는다(`spec/backend-api.md` 1번). 발신번호 주인 것만 받는다.
- 인사 질문(`B_GREET_CHOICE`): 예 → 바로 접수(`B_ORIGIN_ROUTE`), 아니오 → "무엇을 도와드릴까요?" → `HUB`, "아니요, 새로 보낼게요"처럼 아니라면서 접수하겠다고 분명히 하면(`new_origin`) 다시 묻지 않고 바로 새 출발지(`B_ORIGIN_CHANGE`, 2026-10-31 통화), 조회·취소 같은 이미 보낸 택배에 대한 용건 → `C_REQUIRED_INFO`. 아니오면 이번 통화의 다음 접수는 새 출발지부터(`new_origin_requested`). 이 질문도 기존 출발지가 나오기 전의 "예"는 다시 묻는다(아니오·조회는 받는다).
- HUB의 "조회"는 조회·배송 확인·취소·수정처럼 이미 보낸 택배에 대한 용건 전부다.
- 신규 고객은 보내는 분 정보(성함·주소)를 다 말한 순간 백엔드에 고객 등록 + 보내는 곳을 개인 주소록에 저장하고(`spec/backend-api.md` 1-1), 이때부터 등록 고객으로 다룬다(지시서 §5.2의 "`A_DONE` 이후"보다 앞당김, 2026-10-31 결정). HUB에서 접수하면 B 흐름으로, 방금 접수한 택배가 최근 접수다(출발지 그대로, "이번에도 {도착지 주소}로").
- `{기존 출발지}`: 이전 접수(ACCEPTED) 주문의 출발지, 없으면 본인 주소록의 주소(발신번호와 같은 번호의 핀, §9 "고객 등록 주소"). 둘 다 없으면 출발지 없이 인사(GREET_REGISTERED_PLAIN).

## 통화 하나 = 백엔드 주문 하나

- `A_DONE`(접수 완료)은 받은 택배를 **접수 목록에 담는 것**이다. 백엔드 접수(`POST /api/orders`, 택배들은 `parcels`)는 `END_CALL`에서 한 번 한다(백엔드는 통화 한 건에 주문 한 건만 받는다).
- 수거 일시는 주문(통화)에 하나다. 두 번째 택배부터 `A_PICKUP_TIME`은 이미 차 있어 건너뛴다.
- 결제(`A_PAYMENT`): 다이어그램은 MVP 현장 결제(분기 보류)인데 백엔드에 현장 결제가 없다. 후불 자격(월결제·부서 그룹결제)이 하나면 그것, 둘 다면 고객에게 묻고(PAY_ASK, 고른 답은 확정 지연 뒤에 정함), 없으면 개인 카드(TODO(flow), 2026-10-31 결정). 결제 방식은 통화(주문)에 하나라 두 번째 택배부터는 묻지도 안내하지도 않는다.
- 운임(A6 "운임은 {운임}원이에요."): 서버 요금표(`[fare]`)로 계산한 받는 중인 택배의 배송비. 모르면 말하지 않는다. A6 뒷문장은 결제 방식별 사실(PAY_CREDIT·PAY_GROUP·PAY_BILLING)로 바꿨다. 결제 완료·결제 안내 발송은 말하지 않는다.
- 신규 고객의 성함(`customer`)은 보내는 분 성함이다(MVP: 고객 = 보내는 분).

## B — 최근 접수와 도착지 핀

- 최근 접수 1건 = 이번 통화에서 담은 마지막 택배, 없으면 백엔드가 준 가장 최근 접수(`Call.recent_place`).
- 출발지(`B_ORIGIN_ROUTE`): 새 출발지를 원했거나(인사 질문 아니오) 최근 접수가 없으면 `B_ORIGIN_CHANGE`(보내는 분 = 고객·발신번호 그대로, 주소만 A1_2와 주소 예외 문구로 받음, 이번 주문에만), 아니면 최근 접수의 출발지를 그대로 쓴다.
- 도착지(`B_LOAD_RECENT`): 최근 접수가 있으면 "이번에도 {도착지 주소}로 보내시나요?"(B4, 다이어그램은 "지난번처럼…", 이번 통화의 택배도 최근 접수라 바꿈). 예면 그 도착지(받는 분 포함)를 그대로 쓰고, 아니오·최근 접수 없음이면 B6.
- 핀 = 백엔드 주소록(개인·기업 PIN)과 이번 통화에서 접수한 받는 곳(맨 앞). 주소록에는 방향·날짜가 없어 발신번호와 다른 번호의 핀을 앞에 두고, 백엔드가 준 순서를 최근 순으로 보아 앞쪽 `[flow] pin_recent_count`개에서 먼저 찾는다(거기 없으면 전체).
- 핀 매칭은 백엔드 모델의 `match_pins`(고객이 말한 이름·장소·층/호수) 결과로 분기한다. 앞서 말한 이름·장소와 합쳐 찾고, 못 찾았는데 한쪽만 말했으면 빠진 쪽을 묻는다(이름만 → A2_3 주소, 장소만 → A2_1 성함). 둘 다 말했는데 없으면 `A_RECEIVER_HUB`. 확인 질문(B4)에 바로 다른 곳을 말해도 같이 찾는다.
- 여러 개면 후보끼리 다른 값(상세주소 → 주소 → 이름)을 `{후보}`로 이어 묻는다(B8). 앞쪽 핀부터 `[flow] max_pin_options`개만. 그 답("301호요")은 선택지라 서버 판별(`pin_1`…)로도 받는다. "이 중에 없다"면 `A_RECEIVER_HUB`.
- 하나면 받는 분 확인(B9). 아니오면 그 핀은 버리고 "{수신인}님으로 저장된 다른 배송지가 없으니 새로 접수하겠습니다."(B11_NEW) → `A_RECEIVER_HUB`.
- `A_RECEIVER_HUB`로 갈 때 고객이 말한 받는 분 이름·장소는 가져간다(핀의 값은 가져가지 않음). 장소는 번지·건물번호(숫자)가 있을 때만 주소로 보고 주소DB로 확정한다(보완사항 30). 매칭 단계에서 새 받는 분 정보를 말해 기록되면 같은 곳으로 간다.
- 정정: 최근 접수에서 가져온 출발지를 고치면 주소만 비우고 `B_ORIGIN_CHANGE`, 최근 접수·핀에서 가져온 도착지를 고치면 받는 분까지 비우고 `B_DEST_MATCH`부터(이전 매칭 결과는 버림). 고친 뒤 받던 단계로 돌아온다.

## A — 항목 받기와 예외

- 단계의 항목이 다 차면(백엔드 `record_order` 기록 → `order.updated`) 다음 단계로 간다. 이미 찬 단계는 건너뛴다.
- 보내는 분 전화번호는 묻지 않고 발신번호로 채운다(`A_REGISTER_SENDER`는 성함 → 주소). 발신번호가 없는 통화는 고려하지 않는다.
- 수신인 정보 Hub(`A_RECEIVER_HUB`)는 받는 분 성함 → 연락처 → 주소(→ 상세주소) 중 빈 것만 묻는다. 다 차면 `A_REGISTER_RECEIVER`(등록) → `A_ITEM_SIZE`.
- 주소는 기록하면서 주소DB로 확정하고, 못 찾으면 지우고 그 단계에서 구간 예외 문구(A_ADDR_RETRY_SENDER/RECEIVER)로 찾을 때까지 다시 묻는다(다른 빈 항목보다 먼저, 들은 그대로 기록하지 않음, `spec/address.md`). 상세주소가 비면 A_ADDR_DETAIL로 묻는다.
- 정정으로 앞 단계 값이 비면(못 찾은 주소를 지움, 주소가 바뀌어 상세주소가 빔) 그 단계로 되돌아간다.
- 지난 수거 일시(A5_PAST)는 `record_order`가 지난 시각을 거절할 때, 크기·개수(A3_VAGUE·A3_PARTIAL)와 가액 불명확(A4_UNCLEAR)은 서버 판별 선택지로 같은 단계를 다시 묻는다.
- `A_PICKUP_TIME` → `A_PAYMENT`는 되돌릴 수 없는 확정이라 `commit_delay_ms` 동안 새 말이 없을 때만 간다. 기다리는 동안 운임·결제 안내(A6)를 먼저 한다. 결제 방식을 물어야 하면 `A_PAYMENT`로 바로 가고, 고른 답(→ `A_DONE`)이 확정 지연 대상이다.

## C — 조회·취소

- `lookup_orders`(받는 분 성함, 기억 안 나면 서버가 성함 없이 최근 것부터)로 찾고, 결과 사건으로 분기한다. 그분께 보낸 택배가 없으면 같은 단계(C2_NONE), 조회 실패면 같은 단계에서 다시 확인할지 묻는다(C3_FAIL, 업무 처리 불가 +1, 다시 조회 상한 `[flow] retry_limit`).
- 이 번호로 접수된 택배가 하나도 없으면(C_NO_ORDERS) HUB, 더 이전 택배가 없으면(C2_END) 받는 분 성함부터 다시(TODO(flow)).
- 조회는 통화 고객의 최근 주문 `[backend] lookup_limit`건을 택배(주문 상세) 단위로 읽는다(`spec/backend-api.md` 2번). 상태를 확인하지 못하면 "조회가 안 됨"으로 본다. `{배송 상태}`는 주문 상태(취소한 상세는 CANCELLED)를 `[status_names]` 표로 말한다. 수거·배송 상태는 백엔드에 없다.
- 취소 가능은 미완료(`COLLECTING`)·개인 카드 결제 대기(`notPaid`)만. 이미 취소됨(C7_CANCELLED) → HUB, 그 밖(결제가 끝나 접수 진행) → C7_LOCKED(+1) → HUB. 다이어그램의 "이미 기사님이 수거해 가셔서…"는 수거 상태가 없어 바꿨다(TODO(flow)).
- 취소 "예" → 확정 지연 → `C_CANCEL`에서 서버가 `cancel_order`를 실행한다(작업 번호, 실행 중 고객 말은 쌓았다가 결과를 안내한 뒤 판별). 실패면 다시 시도할지 묻고(C9_FAIL, +1), 다시 시도 전에 조회로 이미 취소됐는지 확인한다.
- 수정은 보류(§5.4): `C_CHOICE`의 "수정"은 제한된 요청(D6)으로 보낸다.

## D — QnA·상담원 Hub

- 질문(판별 `question`) 또는 백엔드의 매뉴얼 검색 결과(`rag.*`)가 `GLOBAL_INTENT`로 들어온다. 검색 결과가 판별보다 먼저 오면 그 결과로 바로 답변 단계까지 가고, 같은 말의 질문 판별은 버린다. 판별이 먼저면 `RAG`에서 검색 결과를 기다린다(`[flow] rag_wait_sec`, 넘으면 RAG No).
- RAG Yes = 근거가 있음(임계값 `[rag] min_score`를 두면 1등 리랭커 점수도). 답변은 음성 모델이 검색 근거로 하고 서버는 D2만 붙인다.
- 상담원 연결 가능 여부는 `[flow] agent_open_hour`~`agent_close_hour`(한국 시간)로만 본다(TODO(flow)).
- 고객이 직접 상담원을 원하면 제한된 요청으로 처리한다(§9).
- 통화를 끝내겠다고 하면(`end`) 어느 단계에서나 `END_CALL`(TODO(flow)).
