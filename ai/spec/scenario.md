# 통화 시나리오와 분기

## 시작

| 조건 | 첫 단계 |
|---|---|
| 신규(발신번호 없음, 미등록 번호, 고객 확인 실패) | `collecting`(신규 순서) |
| 등록 | `find_destination`(주소록이 없으면 바로 `collecting`) |
| 탈퇴 | `ending`(상담원 연결 안내 후 refer). 신규로 다루지 않는다 |

- 고객 유형과 주소록은 통화 시작 때 백엔드 고객 확인으로 받는다(`spec/backend-api.md` 1번). 주소록(개인·기업 PIN)은 출발지·도착지 구분이 없어 두 쪽 모두의 후보로 쓴다. 발신번호 주인 것만 받는다.
- 백엔드는 지난 주문을 주지 않는다. "최근 배송"은 이번 통화에서 앞서 확인한 택배다(`recent_offer`).

## 통화 하나 = 백엔드 주문 하나

- 택배 하나(보내는 곳·받는 곳·물품·가액)를 받을 때마다 고객 확인을 받아 **접수 목록에 담고**, 접수는 통화 끝에 한 번 한다(백엔드 `POST /api/orders`, 택배들은 `parcels`). 백엔드는 통화 한 건에 주문 한 건만 받는다.
- 수거 희망 시각·결제 방식·전화 주신 분 성함은 주문(통화)에 하나다. **첫 택배를 확인하기 전에** 받는다. 그래야 중간에 끊겨도 확인한 택배를 접수할 수 있다.

## 단계와 분기

각 단계의 질문에 대한 고객 답(예/아니오, 어느 곳, 맞음/정정, 결제 방식 등)은 서버가 고객 말을 직접 판별해 분기한다(`spec/flow.md`). 이름·연락처·주소·물품·가액·수거 시각 같은 값만 백엔드 도구(`record_order`)로 기록한다.

### `collecting` — 주문 정보 받기

- 신규 순서: 보내는 분 이름 → 보내는 분 연락처 → 출발지 → 도착지 → 받는 분 이름 → 받는 분 연락처 → 물품 → 물품 가액 → (통화 항목)
- 등록 순서: 도착지 → 받는 분 이름 → 받는 분 연락처 → 출발지 → 보내는 분 이름 → 보내는 분 연락처 → 물품 → 물품 가액 → (통화 항목)
- 물품 = 규격별 수량(서류·소형·중형·대형 박스) 또는 기타 물품 설명. 가액은 원 단위.
- 통화 항목(아직 없을 때만): 전화 주신 분 성함(미등록 고객이고 보내는 분 번호가 발신번호와 다를 때만. 같으면 보내는 분 성함) → 수거 희망 시각(미래, 한국 시간) → 결제 방식(고객 답 판별. 정산은 공통, 그룹카드는 기업 소속, 개인카드는 개인 고객)

| 조건 | 다음 |
|---|---|
| 새 주소가 기록됨 | `address`(주소 확정) → 돌아와서 아래 조건 |
| 택배 항목·통화 항목이 다 참 | `confirming` |
| 등록 고객, 다음 항목이 출발지, 주소록 있음(택배마다 한 번) | `find_origin` |
| 그 밖 | 다음 항목 |

### `recent_offer` — 앞 택배와 같은 곳으로 보내는지

이번 통화에서 택배를 하나 담은 등록 고객이 택배를 더 보낼 때.

| 답 | 다음 |
|---|---|
| 예 → 앞 택배의 출발지·도착지·보내는 분·받는 분 채움 | `collecting`(물품) |
| 아니오 | `find_destination` |

### `find_destination` — 주소록에서 받는 곳 찾기

| 결과 | 다음 |
|---|---|
| 1곳 → 도착지·받는 분 채움 | `collecting` |
| 이름만 말함 | 지역 묻고 다시 찾기 |
| 여러 곳 | 지역·건물명 묻고 다시 찾기 |
| 0곳(처음) | 주소 더 묻고 다시 찾기 |
| 0곳(다시 찾아도) 또는 새 받는 분 | `collecting`(도착지부터) |

### `find_origin` — 보내는 곳이 주소록의 곳인지

| 답 | 다음 |
|---|---|
| 같음, 주소록 1곳 → 출발지·보내는 분 채움 | `collecting` |
| 같음, 여러 곳 | 어느 곳인지 묻고 다시 찾기 |
| 다름 | `collecting`(출발지부터) |

### `confirming` — 택배 하나 확인

| 답 | 다음 |
|---|---|
| 맞음 → 임시 주문 그대로 접수 목록에 담고 비움 | `after_order` |
| 정정, 필수 항목 다 있음 | `confirming` |
| 정정, 빠진 항목 생김(예: 주소만 바꿔 상세 주소를 다시 물어야 함) | `collecting` |
| 정정으로 새 주소가 기록됨 | `address`(주소 확정) → 돌아와서 위 조건 |

### `address` — 주소 확정(머무르지 않음)

고객에게 묻지 않는다. 들어오자마자 새로 기록된 주소를 주소DB로 실제 도로명주소로 정하고(확정 → 그 주소, 애매함 → 1등, 못 찾음 → 들은 그대로), 그 주소로 카카오에서 지번·동명·우편번호·좌표를 찾는다(`spec/address.md`). 그다음 들어온 단계(`collecting`·`confirming`)로 돌아간다. 돌아간 단계는 들어온 직후 조건(ENTERED)으로 다음을 정한다.

### `after_order` — 택배 추가 여부

| 답 | 다음 |
|---|---|
| 더 있음 | 통화 시작과 같은 규칙(신규 → `collecting`, 등록 → `recent_offer`). 통화 항목은 다시 묻지 않는다 |
| 없음 → 담은 택배 전부를 한 번에 접수(COMPLETE). 지번·좌표 등 필수값을 못 찾았으면 미완료(INCOMPLETE)로 | `ending`(결과 안내) |
| 상담원 연결 등 | 하위 흐름 |

### `ending` — 마무리 인사 후 종료

| 변형 | 안내 |
|---|---|
| `accepted` | 백엔드 결과가 `ACCEPTED`일 때만: 택배 n건 접수 완료, 접수번호(`parcelNo`) |
| `pending` | 그 밖(처리 중·확인 필요·실패·미완료): 접수됐다고 말하지 않고 "확인 후 담당자가 연락" |
| `cancelled` | 고객이 접수를 그만둠 |
| `handoff` · `refer_failed` | 상담원 연결 안내 · 전환 실패 사과 |

## 통화 결과(통화가 끝날 때 한 번)

통화가 끝나면(`app/sideband.py` → `Call.finish`) 아직 결과를 보내지 않았으면 하나를 보낸다. 같은 키(통화마다 UUID 하나)로 보내므로 다시 보내도 중복되지 않는다.

| 상황 | outcome | 담는 택배 |
|---|---|---|
| "더 없어요"로 이미 보냄 | (다시 보내지 않음. 처리 중이었으면 같은 키·같은 본문으로 확인만) | |
| 상담원에게 넘김(탈퇴 고객 포함) | `INCOMPLETE` | 확인한 택배 + 받는 중이던 택배(상담원이 이어 받게). 확인한 택배가 있어도 접수하지 않는다 |
| 고객이 접수를 그만둠(`quit`) | `CANCELLED` | |
| 끊김·무응답, 확인한 택배 있음, 필수값 다 있음 | `COMPLETE` | 확인한 택배만 |
| 그 밖(확인한 택배 없음 등) | `INCOMPLETE` | 받는 중이던 택배(있으면) |

## 하위 흐름

어느 단계에서나(`ending` 제외) 들어가고, 끝나면 들어온 단계로 돌아간다. 돌아간 단계는 같은 사건을 다시 본다.

| 흐름 | 분기 |
|---|---|
| `handoff` 상담원 연결 | 고객이 요청하면 한 번 확인 / 처리할 수 없는 요청(`help`: 민원·배송 사고·분실 등)·지난 주문의 조회·수정·취소 요청·답 처리가 두 번 연달아 실패하면 서버가 먼저 제안(`offer`) / 예 → "잠시만 기다려 주세요" 안내 후 refer, refer 실패 → 사과·마무리 인사 후 종료 / 아니오 → 복귀 |
| 접수 그만둠(`quit`) | `ending`(cancelled) |
| 종료 요청 | `ending` |

- 조회(`lookup`)·수정(`modify`)·취소(`cancel`)는 **보류**: 백엔드에 AI가 통화 중 쓸 API가 없다(`spec/backend-api.md`). 단계 정의(`app/flow/stages/subflows.py`의 `HELD`)와 도구는 두고 흐름에는 넣지 않는다. 그 용건은 상담원 연결 제안으로 간다.

## 시나리오

아래 표는 `tests/test_flow.py`의 `SCENARIOS`에 그대로 있다. 시나리오를 추가하면 둘 다 고친다.

| 시나리오 | 경로 |
|---|---|
| 신규 접수 한 건 | `collecting` → `confirming` → `after_order`(없음) → `ending` |
| 신규, 한 번에 말하고 끝냄 | `collecting` → `confirming` → `after_order` → 종료 요청 → `ending`(확인한 택배는 끊긴 뒤 COMPLETE) |
| 등록, 주소록으로 | `find_destination`(1곳) → `collecting` → `find_origin`(이곳) → `collecting` → `confirming` → `after_order` → `ending` |
| 등록, 받는 곳 못 찾음 | `find_destination`(0곳) → `find_destination`(0곳) → `collecting` → … → `find_origin` → … → `confirming` |
| 등록, 출발지만 바뀜 | … → `find_origin`(다름) → `collecting` → … → `confirming` |
| 마지막 확인에서 정정 | … → `confirming`(정정) → `confirming`(맞음) → `after_order` |
| 정정하다 빠진 항목이 생김 | … → `confirming` → `address` → `confirming` → `collecting` → `confirming` |
| 택배 추가(신규) | … → `after_order`(더 있음) → `collecting`(통화 항목은 안 물음) → … → `after_order`(없음) → `ending` |
| 택배 추가(등록) | … → `after_order`(더 있음) → `recent_offer`(예) → `collecting` → `confirming` → `after_order` |
| 조회·수정·취소 요청 | `collecting` → `handoff`(제안) → `collecting` |
| 상담원 연결 | 아무 단계 → `handoff`(예) → `ending` |
| 접수 그만둠 | `collecting` → `ending`(cancelled) |
| 고객 무응답 | 고객 말이 `idle_hangup_sec` 동안 없음(또는 통화가 `max_call_sec`를 넘음) → `ending` → 끊기 |
