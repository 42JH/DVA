# LangGraph 전면 재구성 지시서 (dva_mvp_flow.drawio 기준)

현재 LangGraph 그래프를 `dva_mvp_flow.drawio`(페이지-1)의 대화 플로우로 **완전히 교체**한다. 이 문서는 그 다이어그램을 노드·분기·발화 단위로 옮긴 것이다. 다이어그램에 있는 것만 구현하고, 다이어그램에 없는 동작은 §9 "다이어그램 밖 구현 결정"에 적힌 기본값을 쓰되 코드에 `TODO(flow):` 주석을 남긴다.

---

## 0. 작업 규칙

1. **봇 발화 문구는 글자 그대로 상수로 정의**한다. `{...}`는 런타임 치환 변수다. 문구는 한 파일(`prompts.py` 또는 기존 프로젝트의 문구 모듈)에 모으고, 상수 이름은 아래 표의 `ID`를 쓴다.
   - 실제 음성은 GPT-Live가 내보내므로 표현이 바뀔 수 있다(§9 "발화 문구 재현 수준" 참고).
   - 단, **치환 변수 값**(이름, 주소, 금액, 날짜, 배송 상태)은 바꿔 말하지 않도록 Live 지시문에 명시한다.
2. **노드 이름 = 아래 표의 노드 ID.** 코드와 다이어그램을 1:1로 추적할 수 있게 한다.
3. "선택" 노드는 모두 **고객 응답을 받아 분기하는 라우터**다. 분기 조건은 표에 적힌 것만 둔다.
4. "구간 예외" 표의 문구는 다이어그램에서 해당 구간 옆 대괄호로 묶여 있던 것이다. 그 구간의 입력을 처리하다 해당 상황이 생기면 출력하고, 표에 별도 이동이 적혀 있지 않으면 **같은 단계를 다시 묻는다**.
5. **보류 영역(접수 수정)은 구현하지 않는다.** §5.4 참고.
6. 기존 코드를 지우기 전에 §1 Phase 0의 매핑표를 먼저 출력하고, 재사용할 것과 버릴 것을 정한 뒤 진행한다.

## 1. 작업 순서

**Phase 0 — 현재 구조 파악 (코드 수정 전)**
- 그래프 빌더(`StateGraph` 생성부), State 정의, 노드 함수, 라우터, 툴 구현, 체크포인터 설정, 그래프 호출부(턴마다 어떻게 invoke/resume 하는지)를 찾는다.
- 다음 매핑표를 출력한다: `기존 노드/툴 → 새 노드 ID(재사용 / 수정 / 삭제)`.
- §2.1의 두 진입 경로가 코드에 실제로 그렇게 있는지 확인한다. 아래 위치는 코드 읽기로만 파악한 것이므로 실행 로그로 한 번 검증한다.
  - 받아쓰기 → 판별 → `engine.apply()`: `app/sideband.py:100`, `app/listener.py:77`, `app/listener.py:188`
  - 도구 실행 → `dispatcher`: `app/dispatcher.py:50`, `app/sideband.py:91`
  - 감시 → `call.ending`: `app/sideband.py:204`
- **이 진입 경로들과 그 인터페이스는 유지**하고, 그 뒤의 그래프(상태·노드·전이)만 갈아엎는다.

**Phase 1** — §3의 State 스키마 작성.
**Phase 2** — §2 공통 메커니즘(전역 의도 감지, 복귀, 실패 카운터) 구현.
**Phase 3** — §4~§6의 노드와 라우터 구현. 순서는 HUB → B(기존 고객 접수) → A(신규 접수, B와 공유) → C(조회·취소) → D(QnA·상담원).
**Phase 4** — 그래프 조립, 기존 노드·엣지 삭제. 툴 구현(`lookup_orders`, `cancel_order` 등)은 이름과 역할이 맞으면 재사용한다.
**Phase 5** — §8 시나리오 테스트 작성 및 통과.

## 2. 공통 메커니즘

### 2.1 진입 경로와 책임 분담 (현재 코드 구조 기준)

그래프는 "턴마다 멈췄다 재개"하는 구조가 아니다. 아래 세 경로가 그래프를 움직인다.

| 경로 | 흐름 | 맡는 일 |
|---|---|---|
| ① 받아쓰기 | `session.input_transcript.delta` → `listener.heard()`가 단계별 버퍼에 누적 → `pause_ms` 침묵 시 판별 모델 → `engine.apply()` | **단계 전환**: 예/아니오, 선택지, 끼어드는 용건(§2.2), 정정(§2.5) |
| ② 도구 | Live 백엔드의 `function_call` → `run_tool` → `dispatcher` → 그래프 | **값 기록**: 슬롯 채우기, 조회 결과, `cancel_order` 실행 결과 |
| ③ 감시 | 무응답·최대 통화 시간 → `call.ending` | 통화 종료 |

책임 분담 원칙은 다음과 같다.

- **단계 전환은 ①만 한다.** ②의 도구 결과는 슬롯과 결과값만 바꾸고 `step`을 직접 옮기지 않는다. 단, 도구 결과로 정해지는 분기(핀 매칭 결과, 조회 실패, 취소 성공·실패)는 예외로, 결과를 받은 `dispatcher`가 그 분기를 적용한다.
- **②에서 들어온 도구가 현재 단계에 맞지 않으면 실행하지 않는다.** 각 단계에 허용 도구 목록을 두고 `dispatcher`가 확인한다. 예: `cancel_order`는 `C_CANCEL` 단계에서만, 그것도 ①이 `C_CANCEL_CONFIRM`에서 "예"를 확정한 뒤에만 실행한다.
- ①의 판별 결과는 항상 아래 순서로 처리한다.

```
[판별 결과] → GLOBAL_INTENT ─ 질문 의도 ──────→ QNA
                            ├ 제한된 요청 의도 ─→ RESTRICTED_REQUEST
                            ├ 정정 ────────────→ §2.5
                            └ 그 외 ───────────→ state.step 의 처리기(현재 단계 계속)
```

### 2.2 전역 의도 감지 (`GLOBAL_INTENT`)

다이어그램 노드: "전역 의도 감지 (모든 단계) / 진행 중 업무·단계·슬롯을 {업무}로 저장"

- **모든 단계**의 고객 발화에 대해 실행한다.
- 질문 의도 → `QNA`, 제한된 요청 의도 → `RESTRICTED_REQUEST`.
- QnA·상담원 쪽으로 빠지기 직전에 `state.resume`에 현재 업무명, 단계(`step`), 수집된 슬롯을 저장한다. 이것이 `{업무}`다.
- 이미 QnA·상담원 흐름 안에 있을 때는 `resume`을 덮어쓰지 않는다.

### 2.3 기존 업무 복귀 (`RESUME_TASK`)

다이어그램 노드: "기존 업무 복귀 (진입 직전 단계로)"

- **특정 노드로 가는 고정 엣지를 만들지 않는다.** 어느 단계에서 QnA로 들어왔는지 미리 알 수 없기 때문이다.
- `state.resume`에 저장된 단계로 동적으로 돌아간다. 예: `Command(goto=state.resume.step)` 또는 라우터에서 `state.resume.step` 반환.
- 슬롯은 저장해 둔 값을 그대로 복원한다.
- `D_AGENT_OFFER` → `RESUME_TASK`로 올 때는 "네, 그럼 이어서 진행하던 {업무}를 도와드릴게요."를 출력한다(§6.2 D7).

### 2.4 도와드리지 못한 횟수 (`state.fail_count`)

다이어그램 메모: "도와드리지 못한 횟수가 연속 3번이면 상담원 연결 유도 (RAG 실패·제한된 요청·업무 처리 불가 모두 셈, 해결되면 0으로 초기화)"

| 구분 | 내용 |
|---|---|
| +1 | `RAG` No / `RESTRICTED_REQUEST` 진입 / §5의 업무 처리 불가 예외 |
| 0으로 초기화 | `RAG` Yes, 업무 성공 완료(`A_DONE`, `C_CANCEL` 성공, `C_CHECK_RECORD` 도달) |
| 3번째일 때 | `RAG` No와 `RESTRICTED_REQUEST`에서만 "(3번째)" 문구로 상담원 연결을 제안한다 |

업무 플로우 안의 예외 문구는 횟수와 상관없이 표에 적힌 그대로 출력한다. 상담원 제안은 QnA·상담원 Hub에서만 나간다. **상담원 연결은 최대한 미룬다.**

### 2.5 끼어들기·정정 처리

GPT-Live는 고객이 끼어들면 말을 멈춘다. 하지만 그 사이 고객이 **무엇을 들었는지**, 그리고 **어느 단계에 대한 말인지**는 우리 코드가 판단해야 한다. 아래 규칙을 ① 받아쓰기 경로와 그래프에 넣는다.

#### (1) 질문을 듣기 전에 끼어든 경우 — `prompt_heard`

- 단계에 들어갈 때마다 `step_entered_ms`를 기록한다. 그 단계 질문의 출력 transcript(`session.output_transcript.delta`의 `start_ms`/`end_ms`)를 쌓아서 `prompt_spoken_text`를 만든다.
- **질문의 핵심 구간**(선택지나 확인 대상이 나오는 부분. 예: "{받는 분}님께 {주소}로")을 문구 상수마다 표시해 둔다. 출력 transcript에 핵심 구간이 다 나오기 전에 고객 발화가 시작되면 `prompt_heard = False`다.
- `prompt_heard = False`일 때 판별 결과가 예/아니오나 선택지 응답이면 **적용하지 않고 같은 질문을 다시 한다.** 끼어드는 용건(질문, 제한된 요청, 정정)은 그대로 적용한다.
- 출력 transcript는 "생성된 음성"이지 "고객이 실제로 들은 음성"이 아니다. 근사치로만 쓰고, 애매하면 다시 묻는 쪽으로 처리한다.

#### (2) 단계가 바뀌는 순간에 걸친 발화 — 버퍼 귀속

- `listener.heard()`의 단계별 버퍼는 단계 전환 시 비운다. 다만 **전환 시각(`step_entered_ms`)보다 `start_ms`가 이른 조각**은 받아쓰기 지연으로 늦게 도착한 이전 단계의 말이다. 새 단계 버퍼에 넣지 않고 이전 단계 기준으로 판별한다. 예: "네, 맞아요 그리고…" 중 "그리고…" 부분.
- 이전 단계로 판별한 결과가 정정이면 (4)를 적용하고, 아니면 버린다.

#### (3) 말이 여러 번 끊기는 경우 — 판별 리비전과 확정 지연

- 판별 호출마다 그 시점의 버퍼 리비전 번호를 붙인다. `engine.apply()`는 **현재 리비전과 같은 결과만 적용**하고, 늦게 도착한 이전 리비전 결과는 버린다.
- **되돌릴 수 없는 동작으로 이어지는 확정**(지금 범위에서는 `C_CANCEL_CONFIRM`의 "예"와 `A_PAYMENT` 진입)은 판별 직후 바로 실행하지 않는다. `commit_delay_ms` 동안 새 입력이 없을 때만 실행한다. 그 사이 "아, 잠깐만요", "아니요" 같은 조각이 들어오면 보류를 취소하고 다시 판별한다.
- 되돌릴 수 있는 단계 전환(예: 출발지 "예")은 바로 적용하고, 뒤이은 말이 번복이면 (4)로 처리한다.

#### (4) 이미 지나간 값을 고치는 경우 — 정정

- 판별 결과에 `correction: {slot, value}`를 둔다. 예: 가액을 묻는 중에 "아 받는 분 번호가 틀렸어요".
- 정정은 **해당 슬롯만 고치고 현재 단계로 돌아온다.** 고친 값을 한 번 확인하고("받으시는 분 연락처를 {새 값}으로 바꿀게요") 현재 단계 질문을 다시 한다.
- 고친 슬롯 때문에 이후 단계 결과가 무효가 되면 그 단계로 되돌아간다. 예: 도착지가 바뀌어 핀 매칭을 다시 해야 하는 경우. 슬롯마다 revision을 두고, 낡은 revision 기준으로 나온 도구 결과는 버린다.
- `C_CANCEL` 실행 뒤의 정정은 받지 않는다. 이미 실행된 결과를 그대로 안내한다.

#### (5) 도구 실행 중 끼어들기

- 고객이 끼어들어도 **이미 시작된 `cancel_order`는 멈추지 않는다.** 결과가 나오면 실제 결과를 안내한다. 결과가 나오기 전에 "취소되었어요"라고 말하지 않는다.
- 모든 쓰기 도구 호출에 `operation_id`를 붙인다. "한 번 더 시도해 볼까요?"에서 재시도하기 전에 **먼저 조회로 원래 요청이 이미 처리됐는지 확인**한다. 중복 취소를 막기 위해서다.
- 도구 실행 중 들어온 고객 발화는 버리지 않는다. 버퍼에 두었다가 도구 결과를 적용한 뒤에 판별한다. 질문 의도라면 결과를 안내한 다음 QnA로 간다.

#### (6) listen이 꺼진 단계

- 지금 코드는 listen이 꺼진 단계에서 판별을 하지 않는다. 그러면 다이어그램의 "전역 의도 감지 (모든 단계)"가 그 단계에서 빠지고, 그 사이 끼어든 말도 사라진다.
- **listen이 꺼진 단계에서도 받아쓰기는 버퍼에 계속 쌓는다.** 단계가 끝나면 그 버퍼를 전역 의도 기준으로만 판별한다(질문 / 제한된 요청 / 정정 / 멈춤 요청). 단계 응답으로는 쓰지 않는다.

#### (7) Live 음성 모델이 그래프를 건너뛰는 경우

- GPT-Live는 위임 없이 직접 대답할 수 있다. 예를 들어 서비스 관련 질문에 RAG 없이 스스로 답하거나, 작별 인사를 하고 끝내는 경우다.
- Live 지시문(`session.instructions`)에 다음을 넣는다.
  - 서비스·정책 질문에 직접 답하지 않는다.
  - 통화를 스스로 끝내지 않는다.
  - 단계 문구와 변수 값을 바꾸지 않는다.
- 그래프 상태는 ① 경로의 판별을 기준으로 삼는다. 음성 모델이 그래프와 다른 말을 했다면(출력 transcript로 감지) `session.instructions.append`로 바로잡는다.

#### (8) 통화 종료와 진행 중 작업

- ③ `call.ending`이 들어왔을 때 보류 중인 확정이나 실행 중인 쓰기 도구가 있으면, **도구 결과를 기록한 뒤** 종료한다. 확정 보류 상태(3)는 실행하지 않고 버린다.

## 3. State 스키마 (최소 필드)

```python
class CallState(TypedDict):
    caller_number: str
    customer: dict | None          # 발신번호 조회 결과, None이면 신규
    step: str                      # 현재 응답을 기다리는 노드 ID
    task: str | None               # "new_order" | "order" | "lookup" | "cancel"
    slots: dict                    # 수집 값 (보내는 분/받는 분/주소/규격/개수/가액/수거일시/선택된 주문 등)
    resume: dict | None            # {"task", "step", "slots"} — 전역 의도 감지 때 저장
    fail_count: int                # §2.4
    agent_offered: bool            # 직전 안내에 상담원 제안이 포함됐는지 (D8 조건)
    pin_candidates: list           # 도착지 핀 후보
    recent_order: dict | None      # 최근 주문 1건 (B_LOAD_RECENT)
    new_origin_requested: bool     # 인사 질문에서 기존 출발지가 아니라고 함 → B_ORIGIN_CHANGE
    target_order: dict | None      # 조회·취소 대상 주문
    messages: list                 # 기존 프로젝트의 메시지 필드가 있으면 그것 사용
    # --- 끼어들기·정정 (§2.5) ---
    step_entered_ms: int           # 현재 단계 진입 시각 (세션 타임라인 기준)
    prompt_spoken_text: str        # 현재 단계 질문의 출력 transcript 누적
    prompt_heard: bool             # 질문 핵심 구간이 다 나간 뒤에 고객이 말을 시작했는지
    buffer_revision: int           # 판별 리비전, 최신 결과만 적용
    pending_commit: dict | None    # 확정 지연 중인 동작 {action, revision, due_ms}
    slot_revisions: dict           # 슬롯별 revision, 낡은 도구 결과 폐기용
    running_ops: dict              # operation_id → {tool, args, status}
```

필드 이름은 기존 프로젝트 관례가 있으면 그것을 따른다.

## 4. 진입과 HUB

### 4.1 진입

| ID | 노드 | 처리 | 다음 |
|---|---|---|---|
| `CALLER_ID` | 착신 → 발신번호로 고객 조회 | 발신번호로 고객 조회 | `IS_REGISTERED` |
| `IS_REGISTERED` | 등록 고객? | 아니오 → 신규 / 예 → 기존 | `A_NEW_ORDER` 진입부 / `B_GREET_CHOICE` |
| `B_GREET_CHOICE` | 선택 | 예 → 기존 출발지에서 접수 / 아니오 → HUB | `B_ORIGIN_ROUTE`(HUB 안의 `택배 접수 order.py`) / `HUB` |

- **신규 고객:** "택배 접수를 원하시거나 궁금하신 점이 있으시면 편하게 말씀해 주세요"를 출력하고 `A_NEW_ORDER`로 간다.
- **기존 고객:** "{고객명}님, 안녕하세요. {기존 출발지}에서 보내시는 택배 맞으실까요?"를 출력하고 `B_GREET_CHOICE`로 간다.
  - **예:** HUB에서 의도를 다시 묻지 않고 바로 `택배 접수 order.py`(§5.1의 `B_ORIGIN_ROUTE`)로 간다.
  - **아니오:** "무엇을 도와드릴까요?"를 출력하고 `HUB`로 간다. 이때 고객이 "다른 곳에서 보낼 거예요"처럼 기존 출발지가 아님을 밝혔다면 `slots.new_origin_requested = True`로 기록한다(§5.1 B1에서 사용).

**신규 고객이 조회를 요청하면** 다음 문구를 출력한 뒤 신규 택배 접수로 진행한다:
"이 번호로 접수된 택배를 찾지 못했어요. 다른 번호로 접수하셨다면 그 번호로 전화해 주세요. 택배 접수는 지금 바로 도와드릴 수 있어요."

### 4.2 HUB

| 고객 의도 | 다음 |
|---|---|
| 택배 접수 | `B_ORIGIN_ROUTE` (`order.py`) |
| 택배 조회 | `C_REQUIRED_INFO` (`lookup_orders.py`) |
| 더 없음 | `END_CALL`: "이용해 주셔서 감사합니다. 좋은 하루 보내세요." 출력 후 통화 종료 |

- HUB로 돌아오는 경로: `A_CHOICE`, `C_CHOICE`(아니오), `C_CANCEL`(성공 / 아니오), 업무 예외의 "(→ HUB)" 및 "아니오: HUB".
- HUB는 자체 인사말이 없다. 들어올 때 지나온 선의 문구("무엇을 도와드릴까요?", "더 도와드릴 일이 있으실까요?" 등)가 질문 역할을 한다.

## 5. 업무 플로우

### 5.1 B — 기존 고객 택배 접수 (`order.py`)

출발지 핀 매칭 흐름은 **없앴다.** 출발지는 인사 단계에서 확인한 기존 출발지를 쓰고, 고객이 새 출발지를 원할 때만 `B_ORIGIN_CHANGE`로 바꾼다. 이후에는 최근 주문 1건의 도착지를 먼저 확인한다.

#### 출발지

| # | From | 조건 | 봇 발화 | To |
|---|---|---|---|---|
| B0 | `B_GREET_CHOICE` 예, 또는 HUB 택배 접수 | — | — | `B_ORIGIN_ROUTE` (선택) |
| B1 | `B_ORIGIN_ROUTE` | 새 출발지에서 보내길 원함 (`new_origin_requested`) | — | `B_ORIGIN_CHANGE` (출발지 변경 — 다이어그램 라벨: "발신자 유지하는 새 주문 플로우") |
| B2 | `B_ORIGIN_ROUTE` | 그 외 (기존 출발지 사용) | — | `B_LOAD_RECENT` |
| B3 | `B_ORIGIN_CHANGE` | — | (§9 참고) | `B_LOAD_RECENT` |

`B_ORIGIN_CHANGE`는 **발신자(이름·번호)는 그대로 두고 출발지 주소만 새로 받는** 단계다. 묻는 문구와 주소 저장 범위는 다이어그램에 없으므로 §9 기본값을 따른다.

#### 도착지

| # | From | 조건 | 봇 발화 | To |
|---|---|---|---|---|
| B4 | `B_LOAD_RECENT` (최근 주문 1건 불러오기) | — | 지난번처럼 {도착지 주소}로 보내시는 게 맞나요? | `B_DEST_CONFIRM_Q` (선택) |
| B5 | `B_DEST_CONFIRM_Q` | 예 | — | `B_DEST_FIXED` (도착지 확정) |
| B6 | `B_DEST_CONFIRM_Q` | 아니오 | 어디로 보내실 건가요? 받으실 분이나 장소를 말씀해 주세요 | `B_DEST_MATCH` (도착지 핀 매칭) |
| B7 | `B_DEST_MATCH` | 여러 개 | — | `B_DEST_DIFF` (차이 나는 필드 확인 — 층수·상세주소, 최근 N개 핀 우선) |
| B8 | `B_DEST_DIFF` | — | {층수}·{상세주소} 중 어디로 보내시나요? | `B_DEST_MATCH` |
| B9 | `B_DEST_MATCH` | 하나 | 받으시는 분은 {수신인} 님 맞으신가요? | `B_DEST_VERIFY` (선택) |
| B10 | `B_DEST_VERIFY` | 예 | — | `B_DEST_FIXED` |
| B11 | `B_DEST_VERIFY` | 아니오 | (다이어그램에 선 없음 — §9) | §9 |
| B12 | `B_DEST_MATCH` | 없음 | (새로 받는 분 정보 받기) | **`A_RECEIVER_HUB`(수신인 정보 Hub)로 합류** |
| B13 | `B_DEST_FIXED` | — | (물건 규격으로 이어서) | **`A_ITEM_SIZE`로 합류** |

**B6 이후 입력 규칙 (다이어그램 메모):** "제공 정보가 주소면 -> 이름 묻기 / 반대로 이름이면 -> 주소 묻기"
- 고객이 주소만 말했으면 받으실 분 이름을 묻고, 이름만 말했으면 주소를 묻는다. 둘 다 받은 뒤 `B_DEST_MATCH`를 실행한다.
- 이 단계에서 받은 이름·주소는 B12로 `A_RECEIVER_HUB`에 들어갈 때 **그대로 가져가서**, 이미 받은 항목은 다시 묻지 않는다.

물건 규격부터 접수 완료까지는 §5.2와 **같은 노드를 공유**한다. 별도 복제 노드를 만들지 않는다.

### 5.2 A — 신규 고객 택배 접수 (`new_order.py`)

**전제 (다이어그램 메모):** "MVP에서는 신규 고객이 바로 자기 이름 + 전화번호로 보낸다고 가정함. 실제로는 보내는 사람이 다를수도"
→ MVP에서는 고객 = 보내는 사람으로 처리한다.

**필요 정보:** 발/수신자 이름, 주소, 번호 / 접수 물건 규격(서류/소/중/대) / 접수 물건 가액

| # | From | 봇 발화 (순서대로) | To |
|---|---|---|---|
| A1 | `A_NEW_ORDER` | ① 네 택배 접수를 도와드릴게요. 먼저 성함을 말씀해주세요 ② 보내시는 곳 주소를 알려주시겠어요? | `A_REGISTER_SENDER` (고객 등록 + 보내는 사람 정보 등록) |
| A2 | `A_REGISTER_SENDER` → `A_RECEIVER_HUB` (수신인 정보 Hub) | 받으시는 분 성함을 말씀해주세요 / 받으시는 분 연락처를 알려주시겠어요? / 받으시는 분 주소를 말씀해주세요 | `A_REGISTER_RECEIVER` (받는 사람 정보 등록, Hub 안) |
| A3 | `A_REGISTER_RECEIVER` | 보내시는 물건의 크기와 개수는 어떻게 되시나요? | `A_ITEM_SIZE` (물건 규격 확인) |
| A4 | `A_ITEM_SIZE` | 보내시는 물건의 가격은 대략 얼마인가요? | `A_ITEM_VALUE` (물건 가액 기록) |
| A5 | `A_ITEM_VALUE` | 택배를 수거하실 기사님은 언제 방문하면 될까요? 가장 빠른 수거는 1시간 뒤 입니다. | `A_PICKUP_TIME` (수거 희망 일시) |
| A6 | `A_PICKUP_TIME` | 운임은 {운임}원이에요. 결제는 기사님 방문 시 해 주시면 됩니다. | `A_PAYMENT` (결제 — MVP: 기사님 방문 시 현장 결제) |
| A7 | `A_PAYMENT` | — | `A_DONE` (접수 완료) |
| A8 | `A_DONE` | 추가로 택배를 접수하시거나, 다른 도움이 필요하신가요? 궁금하신 점도 편하게 말씀해 주세요. | `A_CHOICE` |
| A9 | `A_CHOICE` | 추가 접수·조회·다른 업무 → `HUB` / 질문 → `GLOBAL_INTENT`가 `QNA`로 보냄 / 더 없음 → `HUB` → `END_CALL` | — |

- A1의 ①②는 각각 별도 턴이다.
- **보내는 분 전화번호는 묻지 않는다.** 이전 다이어그램의 "전화번호는 이 번호로 등록해드릴까요?"가 삭제됐다. 발신번호를 그대로 등록한다.
- **수신인 정보 Hub(`A_RECEIVER_HUB`):** 받으시는 분 성함·연락처·주소를 모으는 묶음이다. 비어 있는 항목만 위 문구로 묻고(기본 순서: 성함 → 연락처 → 주소), 고객이 한 번에 여러 항목을 말하면 채워진 항목은 건너뛴다. 세 항목이 다 차면 `A_REGISTER_RECEIVER`로 등록한다. B12(기존 고객, 도착지 없음)도 여기로 들어온다.
- **`A_PICKUP_TIME` → `A_PAYMENT` 구간은 MVP에서 분기 보류**(다이어그램 메모 "MVP에선 분기는 보류"). 결제 방식 분기 없이 직선으로 진행한다.
- **신규 고객은 `A_DONE` 이후 등록 고객이다.** HUB 재진입 시 기존 고객으로 취급한다.

| 구간 | 상황 | 봇 발화 |
|---|---|---|
| A1 ②, `A_RECEIVER_HUB` 주소 | 주소를 찾지 못함 | 죄송하지만 보내시는 곳/받으시는 곳 주소를 찾지 못했습니다. 시·구와 도로명, 건물번호를 한 번만 다시 말씀해 주시겠어요? — **"보내시는 곳/받으시는 곳"은 현재 단계에 맞는 쪽만 말한다** |
| A1 ②, `A_RECEIVER_HUB` 주소 | (위에 이어서) | (동이나 호수같은 상세주소가 있으시면 말씀해주세요) |
| A3 | 크기·개수를 말하지 않음 | 보내실 물건을 "소형 박스 두개", "서류 한 통" 처럼 크기와 개수로 말씀해주세요 |
| A3 | 크기 또는 개수 누락 | 크기와 개수도 말씀해주세요. |
| A4 | 가액 불명확 | 물품이 대략 얼마 정도인지, 천원, 만원 단위로 말씀해주세요 |
| A5 | 지난 날짜 | 말씀하신 날짜는 이미 지나서 수거 요청이 어려워요. 오늘은 {월}월 {일}일입니다. 수거를 원하시는 날짜를 다시 말씀해 주시겠어요? |

### 5.4 수정 — **보류 (구현하지 않음)**

다이어그램에서 이 영역 전체가 "보류 (접수 수정은 일단 안함)"으로 묶여 있다. `record_order`, `modify_order` 노드는 만들지 않는다.

다만 `C_CHOICE`의 "수정" 분기는 그래프에 남아 있으므로, 고객이 수정을 고르면 §9의 기본 처리를 따른다. 나중에 구현할 때 참고하도록 다이어그램 문구를 `prompts.py`에 주석으로만 보관한다.

- **노드:** 필요 정보 → "어떤 내용을 바꿔 드릴까요?" → 고칠 항목·새 값 기록(`record_order`) → "{항목}을 {새 값}으로 바꿔 드릴까요?" → 예: 접수 수정(`modify_order`) → "수정되었어요. 더 도와드릴 일이 있으실까요?" → HUB / 아니오: "그대로 둘게요." → HUB
- **예외 문구:**
  - 주소 못 찾음
  - 전화번호 자릿수 틀림
  - 바꿀 수 없는 항목(예: 다시 묻기 / 아니오: HUB)
  - 이미 수거(→ HUB)
  - 수정 처리 실패(예: 다시 수정 / 아니오: HUB)

## 8. 테스트 시나리오 (전부 통과해야 완료)

1. 기존 고객 → "{기존 출발지}에서 보내시는 택배 맞으실까요?" 예 → (HUB 의도 질문 없이) "지난번처럼 {도착지 주소}로…" 예 → 규격 → 가액 → 수거 일시 → 운임 안내 → 접수 완료 → "더 없음" → 통화 종료.
2. 기존 고객 → 인사 질문 아니오 → "무엇을 도와드릴까요?" → 조회 → `C_REQUIRED_INFO`.
3. 기존 고객 → 인사 질문 아니오("다른 곳에서 보낼 거예요") → HUB → 접수 → `B_ORIGIN_CHANGE`(이름·번호 재질문 없음) → 최근 주문 1건 도착지 확인.
3-1. 도착지 확인 아니오 → "어디로…" → 주소만 말함 → 이름 질문 → 핀 매칭 여러 개 → 층수·상세주소 확인 → 하나 → 예 → 도착지 확정.
3-2. 도착지 핀 없음 → `A_RECEIVER_HUB` 합류, 앞서 받은 이름·주소는 다시 묻지 않고 연락처만 질문.
4. 신규 고객 → 성함 → 보내는 곳 주소(전화번호 질문 없음, 발신번호 등록) → 수신인 정보 Hub(한 번에 성함+주소를 말하면 연락처만 질문) → 주소 못 찾음 재질문(보내는 곳 / 받는 곳 문구 각각) → 완료 → HUB에서 기존 고객으로 동작.
5. 신규 고객 → 조회 요청 → 안내 문구 → 신규 택배 접수 진행.
6. 조회 → 기억 안 남 → 최근 택배부터 → "아니라고 함" → 그 전 택배 → 확인 → 배송 상태 → 아니오 → HUB.
7. 조회 → 취소 → 예 → 성공 → HUB (fail_count 0 초기화 확인).
8. 조회 → 취소 → 이미 수거 → HUB (fail_count +1).
9. 접수 중 수거 일시 단계에서 질문 → QnA → 답변 → 다른 업무 → **수거 일시 단계로 복귀, 슬롯 유지.**
10. RAG 실패 1·2번째: 상담원 제안 없음. 3번째: 상담원 제안 → 예 → 연결 가능 Yes → 이관.
11. 상담원 제안 전에 "예"류 응답이 와도 `D_AGENT_AVAILABLE`로 가지 않음.
12. 상담원 연결 불가 → 추가 질문 → QnA / 다른 업무 → 복귀.
13. 제한된 요청 1·2·3번째 문구 차이 확인. 업무 예외 1회 + RAG 실패 2회 = 3번째에 상담원 제안(연속 합산).
14. 조회 결과에서 "수정" 선택 → §9 처리.
15. 도착지 확인 질문("지난번처럼 {도착지 주소}로 보내시는 게 맞나요?")의 주소가 나오기 전에 "네"라고 끼어듦 → 적용하지 않고 다시 묻기.
16. 확인 질문 도중 "아니 그거 말고 다른 거요" → 아니오 분기로 처리.
17. 취소 확인에서 "네… 아 잠깐만요" (commit_delay_ms 안에 번복) → `cancel_order` 미실행, 다시 판별.
18. `cancel_order` 실행 중 고객이 "잠깐만요" → 취소는 계속 진행, 실제 결과 안내.
19. 취소 실패 → "한 번 더" → 재시도 전 조회로 이미 처리됐는지 확인, 중복 호출 없음 (`operation_id` 기록 확인).
20. 단계 전환 직후 이전 단계 답의 꼬리 조각이 늦게 도착 → 새 단계 응답으로 쓰이지 않음.
21. 가액 단계에서 "받는 분 번호가 틀렸어요" → 연락처만 고치고 가액 질문으로 복귀.
22. 도착지 정정 → 핀 매칭 단계로 되돌아가고, 이전 매칭 결과는 폐기.
23. listen이 꺼진 단계에서 고객이 질문 → 단계가 끝난 뒤 QnA로 진입.
24. 판별 리비전: 판별 2회가 겹쳐 이전 결과가 늦게 도착 → 무시됨.
25. 쓰기 도구가 실행 중일 때 `call.ending` → 결과 기록 후 종료.
