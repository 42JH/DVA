# 통화 흐름: 서버는 가드레일

음성 모델(gpt-live-1)이 대화를 이끌고, 서버는 **지켜야 할 것만 코드로 강제**한다(2026-11-01 사용자 결정).
이전 구조(다이어그램 노드 42개를 그대로 옮긴 상태 기계, `spec/LANGGRAPH_REBUILD.md`)는 고객이 순서 밖에서 말한 값·정정을 버리고, 한 마디에 섞인 답과 정정 중 하나를 지워 대화가 멈췄다(2026-11-01 20:05 통화: 인사 질문에 "네, 근데 이름이…" → 답·정정이 다 버려져 인사 단계에 머묾). 문제는 LangGraph가 아니라 "순서·분기를 서버가 전부 쥐는" 설계였다. LangGraph(실행부)는 그대로 쓰고, 노드는 **업무와 확정 관문**만 남긴다.

구현에서 정한 시나리오·문구는 `spec/scenario.md`, 다이어그램 문구·조회·취소·QnA 노드의 원래 정의는 `spec/LANGGRAPH_REBUILD.md`, 보완사항·결정은 `spec/LANGGRAPH_REVIEW.md`.

## 누가 무엇을 정하나

| 영역 | 정하는 쪽 | 방식 |
|---|---|---|
| 정보 받기(성함·주소·연락처·물품·가액·수거 일시) | 음성 모델 | 묻는 순서·되묻기·받는 말·정정은 모델이 한다. 서버는 진행 상태로 **기록된 값·빠진 항목·권장 다음 질문·제안**만 준다. |
| 값 기록 | 서버(도구) | 접수 업무 중이면 **단계와 상관없이 언제든** `record_order`로 기록한다. 기록을 단계가 막지 않는다. |
| 값 검증 | 서버(코드) | 주소 확정(주소DB·좌표), 전화번호 자릿수, 지난 수거 일시. 통과하지 못한 값은 기록하지 않고 다시 묻게 한다. |
| 되돌릴 수 없는 동작 | 서버(상태 그래프) | 택배 담기·접수·취소·상담원 전환. 확인 질문의 "예"를 서버가 판별하고 확정 지연(`commit_delay_ms`) 뒤 실행한다. |
| 업무 전환 | 고객 말 판별 → 서버 | 접수 ↔ 조회·취소 ↔ 질문(QnA) ↔ 상담원·종료. 판별기의 단계 답·전역 의도로 옮긴다. 확정을 기다리는 중이면 확정을 버리고 옮긴다. |

## 상태 그래프(업무와 관문)

| 흐름 | 단계 | 하는 일 |
|---|---|---|
| 진입(`entry`) | `CALLER_ID` → `IS_REGISTERED` | 발신번호로 고객 확인 결과에 따라 시작 단계를 고른다. 탈퇴 → `AGENT_HANDOFF`, 등록·기존 출발지 있음 → `ORDER`(인사가 출발지 제안), 그 밖 → `HUB`. |
| | `HUB` | "무엇을 도와드릴까요?"(접수·조회·더 없음). 고객이 바로 주문 정보를 말해 기록되면 `ORDER`. |
| 접수(`order`) | `ORDER` | **택배 하나의 정보를 받는 단계 하나.** 빠진 항목·제안(기존 출발지, 최근 도착지, 주소록 후보)을 상태로 계산해 진행 상태에 준다. 항목이 다 차면 `A_CONFIRM`. |
| | `A_CONFIRM` | 관문: 접수 내용을 임시 주문 그대로 되읽고 "이대로 접수할까요?". 예 → 확정 지연 → `A_PAYMENT`, 아니요 → 고칠 곳을 묻고 고친 뒤 다시 되읽기. 값이 비면 `ORDER`로. |
| | `A_PAYMENT` → `A_DONE` → `A_CHOICE` | 결제 방식(후불 자격 둘이면 묻고 그 답이 확정 관문), 택배를 접수 목록에 담기, 추가 접수·다른 업무·더 없음. |
| 조회·취소(`lookup_orders`) | `C_*` | 받는 분 성함으로 찾기(`lookup_orders` 결과로 분기), 상태 안내, 취소 확인(관문) → 서버가 `cancel_order`. |
| QnA·상담원(`qna`) | `GLOBAL_INTENT` … `RESUME_TASK` | 어느 단계에서나 질문·제한된 요청으로 들어와 끝나면 하던 단계로 돌아간다. 상담원 전환 확인도 관문. |
| 마무리 | `END_CALL` | 담은 택배를 한 번에 접수(`POST /api/orders`)하고 마무리 인사 뒤 끊는다. |

- 단계 수: 42 → 27. 사라진 것: 다이어그램의 정보 받기 노드(`A_NEW_ORDER`·`A_REGISTER_SENDER`·`A_RECEIVER_HUB`·`A_REGISTER_RECEIVER`·`A_ITEM_SIZE`·`A_ITEM_VALUE`·`A_PICKUP_TIME`)와 기존 고객 출발지·도착지 노드(`B_GREET_CHOICE`·`B_ORIGIN_ROUTE`·`B_ORIGIN_CHANGE`·`B_LOAD_RECENT`·`B_DEST_CONFIRM_Q`·`B_DEST_MATCH`·`B_DEST_DIFF`·`B_DEST_VERIFY`·`B_DEST_FIXED`). 이들이 하던 일은 `ORDER`의 상태(빠진 항목·제안)로 옮겼다.
- 업무(`FlowState.task`)는 `order`·`lookup`·`cancel` 셋이다(신규·기존 고객 접수를 나누지 않는다).

## ORDER: 정보 받기

- **빠진 항목**(권장 순서): 보내는 분 성함 → 보내는 곳 주소 → 상세주소 → 받는 분 성함 → 연락처 → 주소 → 상세주소 → 물품 → 가액 → 수거 일시. 보내는 분 연락처는 발신번호로 채우고 묻지 않는다. 등록 고객은 보내는 분 성함도 고객 정보로 채운다. 수거 일시는 통화에 하나라 두 번째 택배부터는 이미 차 있다.
- 진행 상태의 "다음"은 빠진 첫 항목의 질문이고, 둘 이상 남았으면 그다음 항목도 같이 준다. 음성 모델은 이를 권장 순서로 따르되, **고객이 다른 항목을 먼저 말하면 그대로 받아 기록을 맡기고 빠진 것만 묻는다.** 이미 기록된 항목은 다시 묻지 않는다.
- **제안**(저장된 값을 쓸지 묻기). 받을 항목의 질문 자리에 제안 질문이 대신 들어가고, 그 답은 서버 판별로 받는다(예/아니오, 후보 고르기).
  - 기존 출발지: 등록 고객의 첫 택배. 인사(GREET_REGISTERED)가 곧 이 질문이다. 예 → 그 출발지(보내는 곳 주소·상세·연락처)를 쓴다, 아니요(다른 곳) → 보내는 곳 주소를 묻는다, 아니요(용건이 접수가 아님) → `HUB`. 두 번째 택배부터는 앞 택배의 출발지를 묻지 않고 쓴다(새 출발지를 원했으면 묻는다).
  - 최근 도착지: "이번에도 {도착지 주소}로 보내시나요?"(B4). 예 → 받는 분까지 그대로, 아니요 → 받는 곳을 묻는다.
  - 주소록 후보: 고객이 받는 분·장소를 말하면 백엔드가 `match_pins`로 찾는다. 하나면 "받으시는 분은 {수신인} 님 맞으신가요?"(B9), 여럿이면 차이 나는 값으로(B8, 고른 답은 판별 `pin_1`…), 없으면 고객이 말한 이름·장소를 받는 분 정보로 가져가 빠진 것만 묻는다. 확인에서 아니라고 한 핀은 버린다(B11_NEW).
  - 고객이 제안에 답하지 않고 새 값을 말하면(예: "아니, 부산으로 보내요" + 주소) 기록된 값이 이기고 제안은 사라진다.
- **정정**은 언제든: 음성 모델이 고친 값을 맡기면 기록되고, 바뀐 값을 한 번 확인한다(CORRECTED). 판별기가 정정만 알아듣고 값이 없으면 그 항목을 다시 묻는다(CORRECT_ASK). 저장된 곳에서 가져온 출발지·도착지를 고치면 그 묶음(주소·상세, 도착지는 받는 분까지)을 비우고 다시 받는다.
- 주소를 주소DB에서 못 찾으면 기록하지 않고 지운 뒤 그 항목을 다른 빈 항목보다 먼저 예외 문구로 묻는다. 지난 수거 일시는 한 번만 붙이는 말(A5_PAST)로 알린다.
- 신규 고객은 보내는 분 정보(성함·주소·상세)가 다 기록되는 순간 백엔드에 고객 등록 + 보내는 곳을 주소록에 저장한다(`record_order`, 2026-10-31 결정).

## 고객 말 판별: 한 마디에 여러 행동

판별 결과는 `(단계 답 answer, 전역 의도 intent, 정정 항목 slot)`이다(`app/listener.py`). **둘 다 적용한다.**

1. 의도가 `wait`(기다림·번복)·`end`(종료)면 단계 답은 버린다.
2. 확정 관문 단계(확정 지연 전이가 있는 단계: `A_CONFIRM`·`A_PAYMENT`·`C_CANCEL_CONFIRM` 등)에서는 의도가 있으면 단계 답을 보류한다. "네, 근데 받는 분이 틀렸어요"의 "네"로 접수가 확정되면 안 된다. 의도를 처리한 뒤(정정 기록·질문 답변) 확인을 다시 받는다.
3. 그 밖에는 단계 답을 먼저 적용하고(예: 인사 질문의 "네" → 기존 출발지 사용), 옮겨 간 단계에서 의도를 적용한다(정정 → 그 항목 고치기, 질문 → QnA 뒤 그 단계로 복귀, 조회 → 조회 업무).
4. 확정을 기다리는 중의 끼어드는 용건(`wait`·`question`·`restricted`·`correction`·`lookup`·`end`)은 확정을 버린다.

- 전역 의도: `question` 질문, `restricted` 제한된 요청·상담원 요청, `correction` 정정, `lookup` 이미 보낸 택배 조회·취소, `wait`, `end`. `lookup`은 조회·취소 업무 중이면 무시한다.
- 판별은 Decision API로 한다(설정 `[listener] engine`, 약 0.25초). 판별 기준은 음성 모델이 실제로 한 말이 아니라 고객이 말을 시작할 때 서버가 물은 질문이다(음성 모델이 먼저 다음 질문을 말해도 흔들리지 않게).
- 판별마다 말 리비전·단계를 확인해 낡은 결과는 버리고, 단계가 바뀌기 전에 한 말은 전역 의도로만 본다(끼어들기 세부 규칙은 `spec/sideband.md`).

## 진행 상태와 멈춤 막기

- 상태가 바뀌면 서버가 `thinking.append`로 "기록된 값 + 다음(권장 질문) + 그다음"을 준다. 고객 말 없이 서버가 옮기면(확정·검색 시간 초과·서버 도구 결과) `commentary.append`로 말하게도 한다.
- 백엔드 모델은 지시문 끝 "지금 상태"(`session.update`)와 모든 도구 결과의 `state`로 같은 상태를 본다.
- 단계가 허용하지 않는 도구를 부르면 거절 결과에 지금 상태와 다음 할 말을 붙이고, 음성 모델에도 진행 상태를 다시 보낸다(그대로면 음성 모델이 지시 없이 혼자 말한다).

## 엔진(LangGraph)

- 기동 시 단계 정의로 그래프를 한 번 만든다(단계 하나 = 노드 하나). **사건 하나 = 그래프 실행 한 번**(`ainvoke`): 현재 단계 노드에서 전이(가드)를 보고 `Command(goto=…)`로 옮기고, 전이가 없으면 끝난다.
- 상태 엔진(`app/flow/engine.py`)은 업무를 모른다. 단계 정의를 읽어 "현재 단계 + 사건 → 다음 단계"를 계산하고, 허용 도구 확인과 진행 상태 문구 생성만 한다.
- 진행 상태(`FlowState`: 단계·업무·복귀 정보·할 말·확정 지연·진입 시각·전이 기록)는 통화 객체가 든다. 그래프 상태(`Step`)는 단계·사건·도구 이름뿐(개인정보 없음)이고 통화 객체는 `context`로 넘긴다. 체크포인터·`interrupt()`는 쓰지 않는다(도구가 어느 단계에서나 기록하고, 다시 실행하면 접수가 두 번 날 수 있음).
- 노드·라우터는 async로만(동기 함수는 다른 스레드에서 돌아 통화 객체가 스레드 안전하지 않음). 가드는 노드 안에서 부른다. 사건 하나로 `MAX_HOPS`번 옮기면 정의 오류(`FlowError`).
- LangGraph는 분기 구조에만 쓴다. 에이전트·도구 루프는 쓰지 않는다(도구 선택은 OpenAI 안의 백엔드 모델). LLM 호출은 openai SDK로.

### 단계 정의(`app/flow/stages/`, 흐름마다 파일 하나, 자동 등록)

단계 하나가 선언하는 것: 이름·설명, 허용 도구, 답 선택지와 답 처리(`choices`·`on_answer`, 듣지 않는 단계는 `listen=False`), 받을 항목과 항목별 질문(`fields`·`field_texts`, 함수면 상태로 질문이 바뀜)과 머무를 때의 질문(`ask`), 전이(`사건 + 조건 → 다음 단계`, 화살표 문구 `say`, 할 일 `action`), 진입 시 할 일(`on_enter`).

- 엔진 확장점: `enter_on`(그 사건이면 어디서나 들어옴), `forward`(들어간 단계가 같은 사건을 먼저 봄), `subflow`+`RETURN`(QnA·상담원에서 복귀), `STAY`(옮기지 않고 할 말을 새로 계산, 문구가 있으면 그 항목의 예외 문구), `commit`(확정 지연 뒤 `COMMIT` 사건으로 옮김), `final`(끝내는 단계), 들어온 직후 `stage.entered` 사건(머무르지 않는 단계·건너뛰기), `preview`(답마다 바로 이어서 할 말을 단계가 계산, 예: ORDER의 제안), `then`("그다음" 항목 알림을 줄지, 답에 따라 다음이 갈리는 질문이면 끔).
- 할 말: 전이 경로의 말(`say`) + 머무는 단계의 질문(빠진 첫 항목의 질문 또는 `ask`) + 한 번만 붙이는 말(`notice`: 정정 확인·번호 확인·지난 수거 일시·핀 거절).
- 숫자·문구는 정의에 박지 않고 `config/server.toml`·`prompts/flow.toml`에서 가져온다. 기동 시 단계·도구·문구·자리표시자를 검증하고 실패하면 기동을 멈춘다. 흐름도는 그래프에서 만든다(`engine.GRAPH.get_graph().draw_mermaid()`).
- 백엔드 상태 전달: 모든 도구 결과에 `state`(단계·빠진 항목·쓸 수 있는 도구·기록된 값·다음 할 말). 상태만 읽는 `get_state`도 둔다.
- 기록된 값 중 저장된 곳에서 온 번호·상세주소는 "저장됨(읽지 않음)", 발신번호는 "지금 전화하신 번호"로 보인다(고객이 불러 주지 않은 값을 읽지 않게).
- 시나리오 테스트: "보고(판별 결과·도구 호출·확정 지연 끝) 순서 → 단계 경로"를 데이터로 적는다(`tests/test_flow.py` `SCENARIOS`, 시각이 필요한 끼어들기는 `tests/test_sideband.py`). 분기 로직 전체를 LLM 없이 검증한다.

## LangGraph Studio로 보기 (개발용)

전화 없이 흐름을 눈으로 따라가 보는 도구다. 운영 이미지에는 들어가지 않는다(`studio/graph.py`, `langgraph.json`, dev 의존성 `langgraph-cli[inmem]`).

- **띄우기**(`ai/`에서): PowerShell `$env:PYTHONUTF8=1; uv run langgraph dev` / bash `PYTHONUTF8=1 uv run langgraph dev`. `PYTHONUTF8=1`이 없으면 한국어 Windows 기본 인코딩(cp949) 때문에 기동에 실패한다. 브라우저에서 `https://smith.langchain.com/studio/?baseUrl=http://127.0.0.1:2024`(LangSmith 무료 계정 로그인). 연결이 안 되면 셸 환경변수 `LANGSMITH_API_KEY`를 넣고 다시 띄운다.
- **쓰는 법**: 그래프 `call_flow`, 스레드 하나 = 가짜 통화 하나.
  1. 첫 실행은 `customer`만: `new` 신규, `saved` 주소록이 있는 등록 고객, `floors` 같은 건물 여러 층 핀, `orders` 접수한 택배가 있는 등록 고객, `picked` 그 택배가 이미 수거됨, `withdrawn` 탈퇴.
  2. 그다음부터 실행마다 하나: `answer`(결과의 `choices` 중 하나, 같이 들은 전역 의도가 있으면 `intent`·`slot`도), `intent`만, `tool` + `args`(결과의 `tools` 중 하나, `record_order`는 `example_args`를 붙여 넣으면 됨), `commit`(결과의 `pending`이 true일 때).
  3. 사건이 지나간 단계 노드가 차례로 켜지고, 결과에 단계·다음 할 말·답 선택지·허용 도구·기록된 값·경로가 나온다. 매뉴얼 검색은 가짜(질문에 "모르는"이 있으면 RAG No).
- **동작**: 보고 처리는 실제 코드(`call.prepare`, `listener.apply_answer`, `dispatcher.dispatch`)를 그대로 부르되 단계 이동만 막고 사건을 모아, 실제 엔진 노드(`engine._step`)로 단계 노드를 하나씩 지나가게 한다. 판별 모델은 부르지 않는다.
- **한계**: 가짜 통화는 스레드별로 서버 메모리에 있어 되감기·포크·상태 편집이 반영되지 않는다(처음부터 보려면 새 스레드). 실행은 한 번에 하나만.
- **추적**: `langgraph.json`에서 `LANGSMITH_TRACING=false`로 고정한다.
- **테스트**(`tests/test_studio.py`): `tests/test_flow.py`의 시나리오를 Studio 그래프로 돌려 같은 경로인지 확인한다.
