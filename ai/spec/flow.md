# 통화 상태(state)와 분기

주문이 지금 어느 단계인지를 **코드가 들고 있는 별도의 상태(state)**로 관리한다. 모델의 대화 기억으로 단계를 추측하게 하지 않는다.
통화 흐름(노드·분기·문구)은 `spec/LANGGRAPH_REBUILD.md`(dva_mvp_flow.drawio)를 따른다. 구현에서 정한 것은 `spec/scenario.md`, 보완사항·결정은 `spec/LANGGRAPH_REVIEW.md`.

- **임시 주문(데이터)과 통화 상태(단계)는 따로 둔다.** 임시 주문은 받아 적은 값, 통화 상태는 "지금 무엇을 하는 중인가"(단계 + 플래그). 둘 다 통화 객체 안의 pydantic 모델이다.
- 전이는 사건으로만 코드가 일으킨다. 사건은 세 곳에서 온다: **서버의 고객 답 판별**(①, `app/listener.py`), 백엔드의 **값 기록·핀 매칭·조회 도구와 서버가 실행하는 취소**(②, `app/dispatcher.py`), **감시**(③ 무응답·최대 통화 시간·확정 지연·검색 대기, `app/sideband.py`). 모델이 단계를 직접 지정하는 수단은 만들지 않는다.
  - 단계를 바꾸는 판단은 ①이 한다. ②의 도구는 값만 바꾸고 사건(`order.updated` 등)을 내며, 단계의 항목이 다 찼는지·핀 매칭·조회·취소 결과로 갈 곳은 그래프가 그 사건으로 정한다.

## 분기는 코드가 조건문으로 판단한다

LLM은 **고객 말을 정해진 형태의 값으로 옮기는 일(추출·분류)만** 하고, 그 값을 보고 어느 분기로 갈지·다음에 무엇을 할지는 **코드의 조건문**이 정한다.

- **고객 답에 따른 상태 전환은 도구 호출로 하지 않는다.** 답마다 백엔드 도구 왕복을 거치면 그만큼 상태가 늦게 바뀌고 음성 모델이 낡은 상태로 말한다. 그래서 서버가 고객 받아쓰기를 직접 듣고(말이 멈추면) 작은 모델로 판별한다(`app/listener.py`, 설정 `[listener]`).
  - 판별은 **정해진 선택지 중 하나만** 고른다: 단계가 선언한 답 선택지(`choices`, 예: `yes`/`no`, HUB의 `order`/`lookup`/`no_more`, 늘어놓은 핀 `pin_1`…) + 전역 의도(`question` 질문·`restricted` 제한된 요청·`correction` 정정·`wait` 기다림/번복·`end` 종료) + 정정 항목(`slot`). 애매하면 `none`. 선택지 밖 출력은 버린다.
  - **전역 의도가 먼저다**(LANGGRAPH_REBUILD §2.1): 질문 → `GLOBAL_INTENT` → `QNA`, 제한된 요청 → `RESTRICTED_REQUEST`, 정정 → 그 항목만 고치기. 그 밖일 때만 현재 단계의 답을 처리한다.
  - 판별마다 그때의 **말 리비전**(고객 말 조각이 올 때마다 1 증가)을 붙여, 그사이 새 말이 왔거나 단계가 바뀌었으면 결과를 버린다(단계가 바뀐 경우 그 말은 지난 단계의 말로 전역 의도만 다시 본다). 판별은 통화별 잠금 안에서 반영해 도구 실행과 순서가 섞이지 않는다.
  - 끼어들기·정정의 세부 규칙(질문을 다 듣기 전 답, 늦게 온 꼬리 조각, 확정 지연, 듣지 않는 단계)은 `spec/sideband.md`.
- **백엔드 도구는 값 기록과 주문 작업만.** 이름·연락처·주소·물품처럼 자유 값은 판별로 꺼낼 수 없으므로 백엔드가 `record_order`로 기록한다. 주소록 핀 매칭(`match_pins`)·택배 조회(`lookup_orders`)도 도구 결과로 분기한다. 취소(`cancel_order`)는 고객의 "예"를 확정 지연 뒤 서버가 실행한다.
- **코드가 하는 일 = 분기.** 판별 결과는 단계의 `on_answer`가 처리해 사건을 내고, 상태 엔진이 조건(guard)으로 다음 단계를 정한다(`none`이면 그대로, 다시 묻기 등도 코드가 정함). 조건은 if/else로 읽히는 순수 함수이고, LLM 호출을 넣지 않는다.
- **다음에 할 말도 코드가 정한다.** 상태가 바뀌면 서버가 `thinking.append`로 음성 모델에 바로 알린다. 도구 결과의 `state.next`도 같은 곳에서 만든다.
- **단계가 받는 것만 허용.** 단계의 허용 도구 밖 호출은 디스패처가, 단계 선택지 밖 판별은 listener가 거절한다.
- **확인이 필요한 행동도 같은 구조.** 취소·상담원 연결은 그 단계의 확인 질문에 대한 고객 답(`yes`)을 판별했을 때 코드가 조건을 보고 실행한다. 되돌릴 수 없는 확정(취소 "예", 결제 단계 진입)은 바로 하지 않고 `[flow] commit_delay_ms` 동안 새 말이 없을 때만 한다. 접수는 통화당 한 번이다(`spec/backend-api.md`). 택배 담기(A_DONE)는 다이어그램대로 확인 질문 없이 수거 일시 뒤 결제 단계로 이어진다(`spec/LANGGRAPH_REVIEW.md` 1번).
- 테스트는 LLM 없이 "보고(판별 결과·도구 호출) 순서 → 단계 경로·`next`"로 쓴다. 분기 로직 전체가 LLM 없이 검증돼야 한다.

## 단계 정의는 선언형으로, 추가만으로 확장

시나리오 분기는 계속 늘어난다. **새 분기·단계를 넣을 때 디스패처·상태 엔진·기존 도구를 고치지 않고, 단계 정의를 추가하는 것으로 끝나게** 한다.

- 상태 엔진(`app/flow/engine.py`)은 업무를 모른다. 단계 정의를 읽어 "현재 단계 + 사건 → 다음 단계"를 계산하고, 허용 도구 확인과 진행 상태 문구 생성만 한다.
- **엔진은 LangGraph 상태 그래프(`StateGraph`)다.** 기동 시 단계 정의로 그래프를 한 번 만든다(단계 하나 = 노드 하나).
  - **사건 하나 = 그래프 실행 한 번**(`ainvoke`). 판별기·도구가 아무 때나 사건을 내므로, 통화 전체를 한 번 도는 그래프가 아니다. 현재 단계 노드에서 시작해, 노드가 전이(가드)를 보고 `Command(goto=다음 단계)`로 옮기고, 전이가 없으면 끝난다.
  - 진행 상태(`FlowState`: 단계·업무·복귀 정보·할 말·확정 지연·진입 시각·전이 기록)는 통화 객체가 든다. 그래프 상태(`Step`)는 지금 단계·사건·도구 이름뿐(개인정보 없음)이고, 통화 객체는 `context`로 넘긴다. 체크포인터는 쓰지 않는다(상태가 통화 객체에 있음). LANGGRAPH_REBUILD §3의 CallState 필드는 `FlowState`(stage=step, task, resume, pending, entered_ms=step_entered_ms, correcting)와 `Call`(caller, customer_type, order=slots, fail_count, agent_offered, pin_candidates, recent=recent_order, new_origin_requested, target_order, heard_rev=buffer_revision, running_ops, agent_deltas=prompt_spoken_text)에 나눠 있다.
  - `interrupt()`(답을 기다렸다가 이어 가기)는 쓰지 않는다. 도구가 어느 단계에서나 값을 기록하고, 용건이 어디서나 끼어들고, 이어 갈 때 노드가 처음부터 다시 실행돼 접수 같은 작업이 두 번 날 수 있다.
  - **노드·라우터는 async로만** 쓴다. `ainvoke`는 동기 함수를 다른 스레드에서 돌리는데 통화 객체·관제 버스는 스레드 안전하지 않다. 가드는 노드 안에서 부른다(조건부 엣지 함수로 쓰지 않는다).
  - 사건 하나로 `MAX_HOPS`번 옮겨 가면 정의 오류(`FlowError`)다(`recursion_limit`).
  - LangGraph는 분기 구조에만 쓴다. 에이전트·도구 루프(`ToolNode` 등)는 쓰지 않는다(도구 선택은 백엔드 모델이 OpenAI 안에서 한다). LLM 호출은 openai SDK로 한다(`langchain-openai`를 쓰지 않음).
- 단계 정의는 `app/flow/stages/`에 **한 흐름에 파일 하나**로 두고(`entry`·`new_order` A·`order` B·`lookup_orders` C·`qna` D), 도구처럼 자동 등록한다. **노드 이름 = 다이어그램 노드 ID**. 단계 하나가 선언하는 것:
  - 이름, 설명(관제·진행 상태용)
  - **허용 도구** 목록(도구 이름. 도구는 단계를 모른다)
  - **답 선택지와 답 처리**(`choices`, `on_answer`): 이 단계 질문에 대한 고객 답을 판별할 선택지와, 답에 따른 처리(사건). 머무르지 않는 단계·끝내는 단계는 판별하지 않는다(`listen=False`, 상태에 따라 다르면 함수)
  - **받을 항목과 순서**(항목 받는 단계일 때. 항목마다 문구 키 `field_texts`)와 **머무를 때의 질문**(`ask`, 문구 키 또는 상태를 보는 함수)
  - **전이**: `사건 + 조건(guard) → 다음 단계`(+ 그 화살표의 문구 `say`, 전이할 때 할 일 `action`). 사건은 도구나 답 처리가 내는 이름 있는 사건(`order.updated`, `pins.one`, `lookup.found`, `cancel.done`, `rag.found`, `call.ending` 등), 조건은 통화 상태·임시 주문을 보는 작은 순수 함수
  - 진입 시 할 일(`on_enter`, 예: 새 택배 진입 시 임시 주문 비우기)
- **할 말은 두 갈래**: 전이마다 붙은 말(다이어그램 화살표의 문구)을 이번 실행 경로대로 모으고(`FlowState.say`), 머무는 단계의 질문(`ask`)을 붙인다. 화살표 문구가 질문까지 하면(`asks`) 단계 질문을 덧붙이지 않는다. 질문은 그릴 때마다 상태로 다시 계산한다(예외 문구·정정 중 다시 묻기).
- **끼어드는 흐름(QnA·상담원 Hub)**: `GLOBAL_INTENT`가 질문·제한된 요청·검색 결과 사건으로 어느 단계에서나(끝내는 단계 제외) 들어오며 들어오기 전 업무·단계를 `resume`에 저장하고(이미 Hub 안이면 덮어쓰지 않음), `RESUME_TASK`가 그 단계로 고정 엣지 없이 돌아간다(돌아가면 그 단계의 질문을 다시 한다). 슬롯은 Hub에서 바꿀 수 없어(허용 도구 없음) 그대로 남는다.
- 숫자·문구(안내 문장, 요금 등)는 단계 정의에 박지 않고 서버 설정(`[flow]`)·프롬프트(`prompts/flow.toml`)에서 가져온다.
- **기동 시 검증**: 정의가 가리키는 단계·도구·문구가 모두 존재하는지, 문구의 자리표시자가 맞는지. 실패하면 기동을 멈춘다. 통과하면 그래프를 만든다. 손으로 그린 흐름도는 두지 않는다(정의와 어긋나므로). 흐름도가 필요하면 그래프에서 만든다: `engine.GRAPH.get_graph().draw_mermaid()`(노드마다 갈 수 있는 단계를 `destinations`로 적어 엣지가 그려진다). 실행하며 보려면 아래 "LangGraph Studio로 보기".
- **시나리오 테스트**: 시나리오마다 "보고(판별 결과·도구 호출·확정 지연 끝) 순서 → 기대하는 단계 경로"를 데이터로 적고 같은 테스트 함수로 돌린다(`tests/test_flow.py` `SCENARIOS`, 시각이 필요한 끼어들기는 `tests/test_sideband.py`). 분기를 추가하면 테스트 데이터 한 건을 추가한다.

단계·분기·시나리오에서 구현이 정한 것은 `spec/scenario.md`에 있다(구현: `app/flow/stages/`, 문구: `prompts/flow.toml`).

- 엔진 확장점: `enter_on`(그 사건이면 어디서나 들어옴, 들어간 단계가 같은 사건을 먼저 봄), `forward`(전이한 단계가 같은 사건을 먼저 봄, 예: A_CHOICE가 고른 업무를 HUB가 이어 받기), `subflow`+`RETURN`(복귀), `STAY`(옮기지 않고 같은 단계를 예외 문구로 다시 묻기, 그 항목이 차면 끝), `commit`(확정 지연 뒤 `COMMIT` 사건으로 옮김, 기다리는 동안 그 전이의 말을 먼저 함), `final`(끝내는 단계), 단계에 들어온 직후 `stage.entered` 사건을 한 번 더 평가(예: 다 찬 단계는 건너뜀).

- 플래그 예: 고객 유형(신규/등록/탈퇴), 업무(new_order·order·lookup·cancel), 접수한 택배들, 수거 일시, 통화 결과(백엔드 응답), 도와드리지 못한 횟수(`fail_count`)와 상담원 제안 여부(`agent_offered`), 핀 후보, 조회 결과, 취소 실행 상태.
- **백엔드에 상태 전달**: 백엔드는 `thinking.append`를 받지 않는다. 그래서 모든 도구 결과에 `state`(단계, 빠진 항목, 이번 단계에서 쓸 수 있는 도구, 다음에 할 말)를 붙이고, 상태만 읽는 도구(`get_state`)도 둔다. 판별로 바뀐 상태는 백엔드의 다음 도구 결과에서 알게 된다. 백엔드 지시문에는 "단계별로 무엇을 하는지"를 단계 이름 기준으로 적는다.
- **코드에서 강제**: 디스패처가 현재 단계의 허용 도구에 없는 호출을 거절한다(예: 취소는 `C_CANCEL`에서만, 핀 매칭은 `B_*_MATCH`에서만). 프롬프트는 안내일 뿐이다.
- **머무르지 않는 단계**: 고객에게 묻지 않고 서버가 처리만 하는 단계(`IS_REGISTERED`·`B_ORIGIN_ROUTE`·`B_LOAD_RECENT`·`B_DEST_DIFF`·`A_REGISTER_RECEIVER`·`A_PAYMENT`·`A_DONE`·`C_CANCEL_INFO`·`QNA`·`RESTRICTED_REQUEST`·`D_AGENT_AVAILABLE`·`RESUME_TASK` 등)는 들어온 직후 사건(ENTERED)으로 바로 다음 단계로 간다. 처리는 `on_enter`(async 가능)나 전이의 `action`에서 한다. 주소 보정은 노드가 아니라 `record_order`가 기록하면서 한다(`spec/address.md`).
- **음성 모델의 진행 상태도 같은 상태에서 만든다.** `thinking.append`로 보내는 "다음에 할 말 + 기록된 값"은 이 상태와 임시 주문에서 계산한다. 음성 모델과 백엔드가 같은 근원을 보게 해 서로 엇갈리지 않게 한다.
- **말하기 문구는 두 곳으로 나눈다.** 모든 단계에 같은 규칙(되읽지 않기, 번호·주소 듣기, 인사 형식, 스스로 끝내지 않기)은 `prompts/voice.md`에 한 번만 두고, 그 차례에 할 말은 `prompts/flow.toml` `[say]`에 다이어그램 문구 글자 그대로 둔다(키 = LANGGRAPH_REBUILD 표의 ID, 진행 상태에서는 따옴표로 묶음). 따옴표 없이 주는 할 일은 `[note]`. 음성 모델이 표현을 다듬을 수는 있지만 `{…}` 값은 바꾸지 않게 지시문에 적었다.
  - 받을 항목이 두 개 이상 남았으면 그다음 항목도 함께 알려 준다(`progress_then`). 기록이 한 박자 늦어도 방금 답한 것을 다시 묻지 않게.
  - 답을 고르는 질문(선택지가 있는 단계)이면 답마다 바로 이어서 할 말을 함께 알려 준다(`engine.preview`, `progress_preview`). 음성 모델은 고객 말이 끝나자마자 말을 시작해 판별(말 멈춤 대기 + 판별 약 2초)보다 앞서므로, 그사이 다음 질문을 스스로 지어 엉뚱한 것을 물었다(2026-10-31: "접수할게요" 뒤 "어디에서 보내시나요?"). 답의 사건 이름 끝(`new.order`의 `order`)이 선택지 값인 전이를 찾아, 들어갈 단계의 첫 질문(들어온 직후 전이를 따라가며 다 찬 단계는 건너뜀)을 미리 계산한다. 가는 길이 답 처리 결과에 따라 갈릴 수 있는 곳(들어온 직후 전이가 둘 이상, 넘겨 받기, 확정 지연, 같은 단계 다시 묻기·복귀)은 미리 말하지 않는다.
  - 기록된 값 중 주소록·앞 택배에서 온 번호·상세주소는 "저장됨(읽지 않음)", 발신번호와 같은 번호는 "지금 전화하신 번호"로 보여 준다(고객이 직접 불러 주지 않은 값을 읽지 않게). 고객이 다시 말하면 실제 값을 보인다.
  - 통화 정보(지시문 끝)에 등록 고객 성함과 시작 단계의 첫 질문(진입 인사)을 넣는다. 첫 진행 상태보다 인사가 먼저 나가도 맞는 첫 질문을 하게.
  - "전화번호는 이 번호로 등록해드릴까요?"에 대한 답은 판별 선택지(`use_caller`)로 서버가 발신번호를 기록한다(백엔드 모델은 발신번호를 모른다).
  - 정정 확인("받으시는 분 연락처를 … 으로 바꿀게요")처럼 한 번만 할 말은 `FlowState.notice`에 두고, 진행 상태를 보낸 뒤 지운다.
- 관제 화면에 현재 단계와 전이 기록(언제, 어떤 도구로)을 보여 준다.

## LangGraph Studio로 보기 (개발용)

전화 없이 시나리오 분기를 눈으로 따라가 보는 도구다. 운영 이미지에는 들어가지 않는다(`studio/graph.py`, `langgraph.json`, dev 의존성 `langgraph-cli[inmem]`).

- **띄우기**(`ai/`에서)
  - PowerShell: `$env:PYTHONUTF8=1; uv run langgraph dev` / bash: `PYTHONUTF8=1 uv run langgraph dev`
  - `PYTHONUTF8=1`이 없으면 한국어 Windows의 기본 인코딩(cp949) 때문에 `langgraph_api`가 자기 파일을 못 읽어 기동에 실패한다.
  - 브라우저에서 `https://smith.langchain.com/studio/?baseUrl=http://127.0.0.1:2024`(LangSmith 무료 계정 로그인). 브라우저가 로컬 네트워크 접근을 물으면 허용한다.
  - 서버는 LangSmith API 키 없이 뜬다(확인함). 공식 문서는 Studio 연결에 키가 필요하다고 하므로, 연결이 안 되면 셸 환경변수 `LANGSMITH_API_KEY`를 넣고 다시 띄운다.
- **쓰는 법**: 그래프 `call_flow`. 스레드 하나 = 가짜 통화 하나.
  1. 첫 실행은 `customer`만 넣는다: `new` 신규 고객, `saved` 주소록이 있는 등록 고객, `floors` 같은 건물 여러 층 핀, `orders` 접수한 택배가 있는 등록 고객(조회·취소), `picked` 그 택배가 이미 수거됨, `withdrawn` 탈퇴 고객. 시작 단계로 들어간다.
  2. 그다음부터 실행마다 하나만 넣는다: `answer`(결과의 `choices` 중 하나), `intent`(전역 의도, 정정이면 `slot`도), `tool` + `args`(결과의 `tools` 중 하나. `record_order`는 결과의 `example_args`를 붙여 넣으면 된다), `commit`(결과의 `pending`이 true일 때 확정 지연이 끝난 것으로).
  3. 실행하면 사건이 지나간 단계 노드가 차례로 켜지고, 결과에 단계·다음 할 말·답 선택지·허용 도구·기록된 값·지나온 경로가 나온다. 매뉴얼 검색은 가짜(질문에 "모르는"이 있으면 RAG No)다.
- **동작**: 보고 처리는 실제 코드(`call.prepare`, `listener.apply_answer`, `dispatcher.dispatch`)를 그대로 부르되, 단계 이동만 막고 사건을 모은다. 모은 사건은 실제 엔진 노드(`engine._step`)로 이 그래프의 단계 노드를 하나씩 지나가게 한다. 서버가 실행하는 도구(취소)도 사건이 다 지나간 뒤 실행한다. 판별 모델(LLM)은 부르지 않는다(답을 직접 고른다). 고객 상황과 가짜 백엔드는 테스트의 것(`tests/test_flow.py`, `tests/conftest.py`)을 쓴다.
- **한계**
  - 가짜 통화는 스레드별로 서버 메모리에 있다. Studio의 되감기·포크·상태 편집은 가짜 통화에 반영되지 않으니, 처음부터 보려면 새 스레드를 만든다. 서버를 다시 띄우면 기존 스레드도 새 통화로 시작한다.
  - 실행은 한 번에 하나만(`langgraph dev` 기본값). 사건을 모으려고 `engine.apply`를 잠시 바꾸기 때문이다.
  - QnA·상담원 Hub가 어느 단계에서나 들어가고 돌아와서 그림의 엣지가 많다(노드 42개, 엣지 약 280개). 경로는 실행할 때 켜지는 노드로 본다.
- **추적**: `langgraph.json`에서 `LANGSMITH_TRACING=false`로 고정한다. 데이터는 가짜지만 추적은 켜지 않는다.
- **테스트**(`tests/test_studio.py`): `tests/test_flow.py`의 시나리오를 Studio 그래프로 돌려 실제 흐름과 같은 경로인지 확인한다. 단계 정의를 바꿔도 Studio 쪽은 고칠 것이 없다.
