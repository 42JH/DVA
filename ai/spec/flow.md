# 통화 상태(state)와 분기

주문이 지금 어느 단계인지를 **코드가 들고 있는 별도의 상태(state)**로 관리한다. 모델의 대화 기억으로 단계를 추측하게 하지 않는다.

- **임시 주문(데이터)과 통화 상태(단계)는 따로 둔다.** 임시 주문은 받아 적은 값, 통화 상태는 "지금 무엇을 하는 중인가"(단계 + 플래그). 둘 다 통화 객체 안의 pydantic 모델이다.
- 전이는 사건으로만 코드가 일으킨다. 사건은 두 곳에서 온다: **서버의 고객 답 판별**(`app/listener.py`)과 백엔드의 **항목 기록·주문 작업 도구**. 모델이 단계를 직접 지정하는 수단은 만들지 않는다.

## 분기는 코드가 조건문으로 판단한다

LLM은 **고객 말을 정해진 형태의 값으로 옮기는 일(추출·분류)만** 하고, 그 값을 보고 어느 분기로 갈지·다음에 무엇을 할지는 **코드의 조건문**이 정한다.

- **고객 답에 따른 상태 전환은 도구 호출로 하지 않는다.** 답마다 백엔드 도구 왕복을 거치면 그만큼 상태가 늦게 바뀌고 음성 모델이 낡은 상태로 말한다. 그래서 서버가 고객 받아쓰기를 직접 듣고(말이 멈추면) 작은 모델로 판별한다(`app/listener.py`, 설정 `[listener]`).
  - 판별은 **정해진 선택지 중 하나만** 고른다: 단계가 선언한 답 선택지(`choices`, 예: `yes`/`no`, `confirm`/`correct`, 저장된 받는 곳 `dest_1`…) + 끼어드는 용건(`lookup`·`modify`·`cancel`·`handoff`·`stop`·`end`·`new_order`). 애매하면 `none`. 선택지 밖 출력은 버린다.
  - 판별 중에 단계가 바뀌었거나 더 새 판별이 시작됐으면 결과를 버린다. 판별은 통화별 잠금 안에서 반영해 도구 실행과 순서가 섞이지 않는다.
  - 한 마디에 답과 용건이 같이 있으면 답을 먼저, 용건을 다음에 반영한다.
- **백엔드 도구는 값 기록과 주문 작업만.** 이름·연락처·주소·물품처럼 자유 값은 판별로 꺼낼 수 없으므로 백엔드가 `record_order`로 기록한다. 접수된 주문의 조회·수정·취소도 도구다.
- **코드가 하는 일 = 분기.** 판별 결과는 단계의 `on_answer`가 처리해 사건을 내고, 상태 엔진이 조건(guard)으로 다음 단계를 정한다(`none`이면 그대로, 다시 묻기 등도 코드가 정함). 조건은 if/else로 읽히는 순수 함수이고, LLM 호출을 넣지 않는다.
- **다음에 할 말도 코드가 정한다.** 상태가 바뀌면 서버가 `thinking.append`로 음성 모델에 바로 알린다. 도구 결과의 `state.next`도 같은 곳에서 만든다.
- **단계가 받는 것만 허용.** 단계의 허용 도구 밖 호출은 디스패처가, 단계 선택지 밖 판별은 listener가 거절한다.
- **확인이 필요한 행동도 같은 구조.** 접수·저장·상담원 연결은 그 단계의 확인 질문에 대한 고객 답(`confirm`·`yes`)을 판별했을 때 코드가 조건(단계, 필수 항목, 발신번호)을 보고 실행한다. 수정·취소는 접수번호가 필요해 백엔드 도구(`customer_confirmed`)로 한다.
- 테스트는 LLM 없이 "보고(판별 결과·도구 호출) 순서 → 단계 경로·`next`"로 쓴다. 분기 로직 전체가 LLM 없이 검증돼야 한다.

## 단계 정의는 선언형으로, 추가만으로 확장

시나리오 분기는 계속 늘어난다. **새 분기·단계를 넣을 때 디스패처·상태 엔진·기존 도구를 고치지 않고, 단계 정의를 추가하는 것으로 끝나게** 한다.

- 상태 엔진(`app/flow/engine.py`)은 업무를 모른다. 단계 정의를 읽어 "현재 단계 + 사건 → 다음 단계"를 계산하고, 허용 도구 확인과 진행 상태 문구 생성만 한다.
- 단계 정의는 `app/flow/stages/`에 **파일 하나에 단계 하나**(또는 한 흐름)로 두고, 도구처럼 자동 등록한다. 단계 하나가 선언하는 것:
  - 이름, 설명(관제·문서용)
  - **허용 도구** 목록(도구 이름. 도구는 단계를 모른다)
  - **답 선택지와 답 처리**(`choices`, `on_answer`): 이 단계 질문에 대한 고객 답을 판별할 선택지와, 답에 따른 처리(사건). 판별하지 않는 단계는 `listen=False`
  - **받을 항목과 순서**(수집 단계일 때. 항목마다 "물을 때 할 일" 문구)
  - **전이**: `사건 + 조건(guard) → 다음 단계`. 사건은 도구나 답 처리가 내는 이름 있는 사건(`order.updated`, `order.submitted`, `place.saved`, `intent.cancel` 등), 조건은 통화 상태·임시 주문을 보는 작은 순수 함수
  - 진입·이탈 시 할 일(예: 새 주문 진입 시 임시 주문 비우기)
  - 백엔드·음성 모델에 줄 안내 한 줄(이 단계에서 무엇을 하는지)
- **시나리오 = 단계들의 조합.** 통화 시작 때 조건(신규/등록 고객, 최근 배송 유무 등)으로 시작 시나리오를 고른다. 신규·등록 고객처럼 받는 순서만 다른 분기는 항목 순서만 다른 정의로 만든다. 새 고객 유형·새 업무(배송 조회, 반품 등)는 시나리오 추가로 넣는다.
- **끼어드는 흐름**: 접수 중 "아까 주문 취소할게요" 같은 수정·취소·조회·상담원 전환은 하위 흐름으로 들어가며 돌아갈 단계 하나만 기억했다가, 끝나면 그 단계로 돌아온다. 어디서 들어올 수 있는지는 하위 흐름이 선언한다. 하위 흐름 안에서 또 다른 하위 흐름이 필요해지면 그때 스택으로 바꾼다.
- 숫자·문구(안내 문장, 요금 등)는 단계 정의에 박지 않고 서버 설정·프롬프트에서 가져온다.
- **기동 시 검증**: 정의가 가리키는 단계·도구가 모두 존재하는지. 실패하면 기동을 멈춘다. 손으로 그린 흐름도는 두지 않는다(정의와 어긋나므로).
- **시나리오 테스트**: 시나리오마다 "보고(판별 결과·도구 호출) 순서 → 기대하는 단계 경로"를 데이터로 적고 같은 테스트 함수로 돌린다. 분기를 추가하면 테스트 데이터 한 건을 추가한다.

단계·분기·시나리오는 `spec/scenario.md`에 있다(구현: `app/flow/stages/`, 문구: `prompts/flow.toml`).

- 엔진 확장점: `enter_on`+`enter_from`(어디서 들어올 수 있는지, `*`는 어디서나), `subflow`(들어온 단계를 기억했다가 `@return`, 돌아간 단계가 같은 사건을 다시 봄), 단계에 들어온 직후 `stage.entered` 사건을 한 번 더 평가(예: 다 찬 채로 돌아오면 바로 `confirming`), `order`(상황별 항목 순서), `variants`(같은 단계 안의 결과별 안내 문구 `단계.variant`).

- 플래그 예: 고객 유형(신규/등록), 이번 통화에서 접수한 주문번호들, 방금 일어난 일(접수·수정·취소·저장), 저장 제안 대상 배송지.
- **백엔드에 상태 전달**: 백엔드는 `thinking.append`를 받지 않는다. 그래서 모든 도구 결과에 `state`(단계, 빠진 항목, 이번 단계에서 쓸 수 있는 도구, 다음에 할 일 한 줄)를 붙이고, 상태만 읽는 도구(`get_state`)도 둔다. 판별로 바뀐 상태는 백엔드의 다음 도구 결과에서 알게 된다. 백엔드 지시문에는 "단계별로 무엇을 하는지"를 단계 이름 기준으로 적는다.
- **코드에서 강제**: 디스패처가 현재 단계(하위 흐름이면 그 흐름)의 허용 도구에 없는 호출을 거절한다(예: 접수는 `confirming`에서만). 프롬프트는 안내일 뿐이다.
- **음성 모델의 진행 상태도 같은 상태에서 만든다.** `thinking.append`로 보내는 "다음에 물을 것 + 기록된 값"은 이 상태와 임시 주문에서 계산한다. 음성 모델과 백엔드가 같은 근원을 보게 해 서로 엇갈리지 않게 한다.
- 관제 화면에 현재 단계와 전이 기록(언제, 어떤 도구로)을 보여 준다.
