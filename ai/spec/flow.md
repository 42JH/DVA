# 통화 상태(state)와 분기

주문이 지금 어느 단계인지를 **코드가 들고 있는 별도의 상태(state)**로 관리하고, 백엔드 위임 모델은 이 상태를 보고 분기한다. 모델의 대화 기억으로 단계를 추측하게 하지 않는다.

- **임시 주문(데이터)과 통화 상태(단계)는 따로 둔다.** 임시 주문은 받아 적은 값, 통화 상태는 "지금 무엇을 하는 중인가"(단계 + 플래그). 둘 다 통화 객체 안의 pydantic 모델이다.
- 전이는 도구 실행 결과(사건)로만 코드가 일으킨다. 모델이 단계를 직접 지정하는 도구는 만들지 않는다.

## 분기는 코드가 조건문으로 판단한다

LLM은 **고객 말을 정해진 형태의 값으로 옮기는 일(추출·분류)만** 하고, 그 값을 보고 어느 분기로 갈지·다음에 무엇을 할지는 **코드의 조건문**이 정한다. 백엔드 LLM 통제 구조 전체를 이 원칙에 맞춘다.

- **백엔드가 하는 일 = 사실 보고.** 도구는 "다음 단계로 가라"가 아니라 "고객이 이렇게 말했다"를 받는다. 인수는 자유 문장 대신 enum·bool·정해진 필드로 둔다.
  - 예: 최근 배송 질문의 답 → `answer: "yes" | "no" | "unclear"`, 마지막 확인 → `"confirm" | "correct" | "unclear"`, 고객 용건 → `intent: "new_order" | "modify" | "cancel" | "lookup" | "handoff" | "end" | "other"`, 주문 정보 → 항목별 값
  - 애매하면 `unclear`/`other`로 보고하게 한다. 추측해서 고르지 않는다.
- **코드가 하는 일 = 분기.** 디스패처가 보고된 값 + 통화 상태 + 임시 주문으로 단계 정의의 조건(guard)을 평가해 다음 단계를 정한다(`unclear`면 다시 묻기 등도 코드가 정함). 조건은 if/else로 읽히는 순수 함수이고, LLM 호출을 넣지 않는다.
- **다음에 할 말도 코드가 정한다.** 도구 결과의 `next`(무엇을 물을지·안내할지)는 단계 정의에서 만든다. 백엔드는 그것을 음성 모델에 그대로 전하고, 음성 모델은 같은 내용을 `thinking.append`로도 받는다. 백엔드 지시문에 "다음 단계를 스스로 정하지 말고, 들은 것을 도구로 보고한 뒤 결과의 `next`를 전한다"를 둔다.
- **단계가 받는 보고만 허용.** 현재 단계가 기대하지 않는 보고(허용 도구 밖, enum 밖 값)는 디스패처가 거절하고 현재 단계의 `next`를 다시 돌려준다.
- **확인이 필요한 행동도 같은 구조.** 접수·취소·저장 등은 LLM이 "실행"을 고르는 게 아니라 고객의 확인 답(`confirm`)을 보고하고, 코드가 조건(단계, 필수 항목, 본인 확인)을 보고 실행한다.
- 테스트는 LLM 없이 "보고 순서 → 단계 경로·`next`"로 쓴다. 분기 로직 전체가 LLM 없이 검증돼야 한다.

## 단계 정의는 선언형으로, 추가만으로 확장

시나리오 분기는 계속 늘어난다. **새 분기·단계를 넣을 때 디스패처·상태 엔진·기존 도구를 고치지 않고, 단계 정의를 추가하는 것으로 끝나게** 한다.

- 상태 엔진(`app/flow/engine.py`)은 업무를 모른다. 단계 정의를 읽어 "현재 단계 + 사건 → 다음 단계"를 계산하고, 허용 도구 확인과 진행 상태 문구 생성만 한다.
- 단계 정의는 `app/flow/stages/`에 **파일 하나에 단계 하나**(또는 한 흐름)로 두고, 도구처럼 자동 등록한다. 단계 하나가 선언하는 것:
  - 이름, 설명(관제·문서용)
  - **허용 도구** 목록(도구 이름. 도구는 단계를 모른다)
  - **받을 항목과 순서**(수집 단계일 때. 항목마다 "물을 때 할 일" 문구)
  - **전이**: `사건 + 조건(guard) → 다음 단계`. 사건은 도구가 내는 이름 있는 사건(`order.updated`, `order.submitted`, `place.saved` 등), 조건은 통화 상태·임시 주문을 보는 작은 순수 함수
  - 진입·이탈 시 할 일(예: 새 주문 진입 시 임시 주문 비우기)
  - 백엔드·음성 모델에 줄 안내 한 줄(이 단계에서 무엇을 하는지)
- **시나리오 = 단계들의 조합.** 통화 시작 때 조건(신규/등록 고객, 최근 배송 유무 등)으로 시작 시나리오를 고른다. 신규·등록 고객처럼 받는 순서만 다른 분기는 항목 순서만 다른 정의로 만든다. 새 고객 유형·새 업무(배송 조회, 반품 등)는 시나리오 추가로 넣는다.
- **끼어드는 흐름**: 접수 중 "아까 주문 취소할게요" 같은 수정·취소·조회·상담원 전환은 하위 흐름으로 들어가며 돌아갈 단계 하나만 기억했다가, 끝나면 그 단계로 돌아온다. 어디서 들어올 수 있는지는 하위 흐름이 선언한다. 하위 흐름 안에서 또 다른 하위 흐름이 필요해지면 그때 스택으로 바꾼다.
- 숫자·문구(안내 문장, 요금 등)는 단계 정의에 박지 않고 서버 설정·프롬프트에서 가져온다.
- **기동 시 검증**: 정의가 가리키는 단계·도구가 모두 존재하는지. 실패하면 기동을 멈춘다. 손으로 그린 흐름도는 두지 않는다(정의와 어긋나므로).
- **시나리오 테스트**: 시나리오마다 "보고(도구 호출) 순서 → 기대하는 단계 경로"를 데이터로 적고 같은 테스트 함수로 돌린다. 분기를 추가하면 테스트 데이터 한 건을 추가한다.

구현된 단계(`app/flow/stages/`, 문구는 `prompts/flow.toml`):

| 단계 | 뜻 | 가능한 일 | 다음 |
|---|---|---|---|
| `collecting_new` · `collecting_registered` | 주문 정보 받는 중. 등록 고객은 "지난번 받는 분" 질문(`recent`)이 먼저 | 기록, 저장된 배송지 찾기·쓰기, 최근 받는 분 쓰기(등록) | 필수 항목이 다 차면 `confirming` |
| `confirming` | 마지막 확인 대기 | 접수(`confirm_order`), 정정(`record_order`) | 접수 → 저장 안 된 배송지가 있으면 `save_offer`, 없으면 `after_order` |
| `save_offer` | 배송지 저장 여부 대기 | 저장 동의/거절 | `after_order` |
| `after_order` | 추가 주문·용건 확인 | 새 주문(`collecting_*`, 임시 주문은 접수 때 비움), 종료 | |
| `ending` | 마무리 인사 후 끊는 중. 어느 단계에서든 `end_call`(사건 `call.ending`)로 들어옴 | 없음 | 서버가 hangup |
| (하위 흐름) `modify` · `cancel` · `lookup` | 접수된 주문 수정·취소·조회. 수집·확인·`after_order`와 서로에게서 들어옴 | 해당 도구 | 끝나거나 `next_request(other)`면 들어온 단계로 복귀 |
| (하위 흐름) `handoff` | 상담원 전환. 어느 단계에서든 들어옴 | 전환(`transfer_to_agent`) | `ending` |

- 따로 두려던 `submitted` 단계는 없앴다. 접수 결과(`confirm_order`)의 `say`에 접수번호 안내가 들어 있다.
- 고객 용건 보고 `next_request.intent`는 `new_order · modify · cancel · lookup · handoff · other`. 통화 종료는 고객 확인이 필요하므로 `end_call(customer_confirmed)`로만 한다.
- 엔진 확장점: `enter_on`+`enter_from`(어디서 들어올 수 있는지, `*`는 어디서나), `subflow`(들어온 단계를 기억했다가 `@return`), 단계에 들어온 직후 `stage.entered` 사건을 한 번 더 평가(예: 다 찬 채로 돌아오면 바로 `confirming`).
- 고객 유형: 발신번호로 지난 주문이나 저장된 배송지가 있으면 등록 고객. 시작 때 정하고 통화 중 바꾸지 않는다.

- 플래그 예: 고객 유형(신규/등록), 이번 통화에서 접수한 주문번호들, 방금 일어난 일(접수·수정·취소·저장), 저장 제안 대상 배송지.
- **백엔드에 상태 전달**: 백엔드는 `thinking.append`를 받지 않는다. 그래서 모든 도구 결과에 `state`(단계, 빠진 항목, 이번 단계에서 쓸 수 있는 도구, 다음에 할 일 한 줄)를 붙이고, 상태만 읽는 도구(`get_state`)도 둔다. 백엔드 지시문에는 "단계별로 무엇을 하는지"를 단계 이름 기준으로 적는다.
- **코드에서 강제**: 디스패처가 현재 단계(하위 흐름이면 그 흐름)의 허용 도구에 없는 호출을 거절한다(예: 접수는 `confirming`에서만). 프롬프트는 안내일 뿐이다.
- **음성 모델의 진행 상태도 같은 상태에서 만든다.** `thinking.append`로 보내는 "다음에 물을 것 + 기록된 값"은 이 상태와 임시 주문에서 계산한다. 음성 모델과 백엔드가 같은 근원을 보게 해 서로 엇갈리지 않게 한다.
- 관제 화면에 현재 단계와 전이 기록(언제, 어떤 도구로)을 보여 준다.
