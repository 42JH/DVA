# 동시 통화

RAG 추가: BM25 인덱스/읽기용 Qdrant 클라이언트는 서비스가 공유하지만, 질문·검색 결과·위임 ID·ACK는 통화별로 관리한다. CPU 형태소 분석과 동기 검색/HTTP는 to_thread로 이벤트 루프 밖에서 처리한다. 외부 Qwen은 별도 GPU 서비스이며 GPU 내부 추론을 직렬화한다. 대기열을 포함한 지연과 동시 통화 용량은 실제 서버에서 별도로 측정한다. 새 위임이 이전 읽기 작업을 취소해도 이미 실행 중인 스레드/원격 작업을 물리적으로 중단한다고 가정하지 않는다.

한 서버(워커 1개)에서 여러 통화를 동시에 끝까지 처리해야 한다. 서버는 오디오를 다루지 않고 웹훅·sideband·백엔드 API를 기다리기만 하므로 asyncio 이벤트 루프 하나로 충분하다.

- **통화 하나 = 통화 객체 하나 + sideband 작업(task) 하나.** 통화 객체는 `session_id`를 키로 한 레지스트리에 두고, 임시 주문·진행 상태·도구 기록·발신번호를 모두 그 안에 둔다. 통화 상태를 모듈 전역 변수에 두지 않는다. 도구는 자기 통화 객체만 받는다.
- **이벤트 루프를 막지 않는다.** 백엔드 API는 async HTTP 클라이언트(`httpx2`, 시간 제한), OpenAI 호출(accept·hangup·refer)은 async 클라이언트로 한다. 동기 코드나 CPU 작업이 필요하면 `asyncio.to_thread`. 한 통화의 느린 도구가 다른 통화의 sideband 처리를 멈추게 하면 안 된다.
- **상태 그래프(LangGraph)는 모든 통화가 하나를 같이 쓴다.** 통화별 상태는 실행할 때 `context`로 넘기고 그래프에 두지 않는다. 노드는 async로만 쓴다(동기 노드는 다른 스레드에서 돌아 통화 객체와 경쟁한다, `spec/flow.md`).
- **한 통화의 실패는 그 통화에서 끝낸다.** sideband 작업의 예외는 그 통화만 정리(로그, 관제 표시, 가능하면 hangup)하고 서버와 다른 통화에 영향을 주지 않는다. 작업 참조는 레지스트리에 들고 있어 GC로 사라지지 않게 한다.
- **한 통화 안의 도구 호출은 순서대로** 처리한다(`parallel_tool_calls=false`, 통화별 잠금). 통화끼리는 병렬이다.
- **동시 통화 상한**: 서버 설정의 상한(OpenAI 동시 세션 한도 이하)을 넘으면 웹훅에서 reject(예: 486 Busy)한다. 상한 확인과 등록은 경쟁 없이 한 번에 한다.
- **공유 자원은 백엔드뿐**: 접수번호는 백엔드가 발급해 동시 접수에서도 겹치지 않게 한다(`spec/backend-api.md`). 같은 웹훅이 동시에 두 번 와도 `webhook-id`·`session_id` 기준으로 한 번만 accept한다.
- **끝난 통화 정리**: `session.closed`·sideband 종료 시 통화 객체를 닫고, 관제 화면 보관 시간이 지나면 레지스트리에서 지운다(메모리가 계속 늘지 않게).
- **관제 SSE**는 통화마다 독립적으로 보내고, 느린 관제 클라이언트가 통화 처리를 기다리게 하지 않는다(통화 쪽은 상태만 바꾸고 알림만 보낸다).
- **테스트**: 가짜 sideband 여러 개로 통화 여러 개를 동시에 돌려, 임시 주문이 섞이지 않는지, 한 통화의 도구 예외·지연이 다른 통화를 막지 않는지, 상한을 넘으면 reject되는지, 동시 접수가 서로 섞이지 않는지 확인한다(번호가 겹치지 않는 것은 백엔드 책임).
- 서버를 여러 대·여러 워커로 늘리는 건 지금 범위가 아니다. 그때는 통화 상태를 공유 저장소(Redis 등)로 옮기고 웹훅·sideband를 같은 프로세스로 묶어야 한다.
