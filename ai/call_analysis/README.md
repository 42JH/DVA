# call_analysis — 통화 불만 판정 (Jira 148, 후처리 전용)

끝난 통화의 저장된 기록(대본 · AI 동작 · 업무 결과)과 녹음으로, 고객 불만(책임 · 강도)과 AI 응대 오류 5유형(근거 없는 답변은 참고 표시: 통화 화면에는 보이지만 비율 지표에서 뺌), 통화 전체 값(용건 · 해결 여부 · 감정)을 판정한다.

## 방식: 무조건 후처리 (2026-11-05 결정)

- 통화가 **끝난 뒤** 따로 돌린다. 실시간 상담 경로에는 넣지 않는다.
  - 실시간 AI 코드(`app/` 등)를 import하지 않고, 실시간 AI도 이 폴더를 부르지 않는다.
  - AI 서버 이미지(`Dockerfile`)에 들어가지 않는다.
  - 실시간 AI에 새 값을 보내 달라고 하지 않는다. 시간 정보도 저장된 녹음으로 잰다.
- 모델 키는 실시간 상담과 다른 전용 키(`CALL_ANALYSIS_OPENAI_API_KEY`)를 쓴다.
- 대본 · 녹음 · 판정 결과는 개인정보다. 저장하지 않고, 로그 · 화면에 본문을 찍지 않고, 입력 · 결과 파일을 커밋하지 않는다.
- 실서비스 구현은 백엔드(NestJS)로 옮긴다. 이 폴더는 그 판정 원본 구현이고, 판정을 고칠 때 점수를 재는 도구다.

## 유형별 처리 — 사실은 코드가, 뜻은 모델이

| 화면 유형 | 정하는 방식 | 근거 |
|---|---|---|
| 말 끊김 `INTERRUPTION` | 코드 | AI 말이 문장 중간에 잘리고 고객이 바로 말함(고객이 끼어들어 AI가 멈춤) |
| 응답 지연 `SLOW_RESPONSE` | 코드 | AI가 말할 차례의 침묵이 녹음으로 10초 이상, 또는 3초 이상이고 고객이 "여보세요" · "왜 멈췄어"처럼 기다림을 드러냄 |
| 정보 인식 오류 `INFORMATION_RECOGNITION_ERROR` | 코드 + 모델 | 코드: 고객이 부른 번호와 AI 복창이 다름, 맞는 번호를 자릿수 틀림으로 거절, 인사에서 부른 이름 · 등록 출발지를 다시 물음. 나머지는 모델 |
| 용건 인식 오류 `INTENT_RECOGNITION_ERROR` | 모델 + 2차 확인 | 고객의 질문 · 요청 · 동의 · 거절을 놓치거나 다른 뜻으로 받음 |
| 고객 불만 `DISSATISFACTION_EXPRESSION` | 모델(3회 다수결) + 코드(고객 말 대조) | 고객이 불만을 말하거나 서비스 · 배송 쪽 잘못을 알림. 책임(`target`)을 세 질문 순서로 정함: AI가 다르게 했으면 없었나 → 규칙 자체가 불만인가 → 통화 밖 일인가. 고객 자기 사정만 설명한 것은 아님 |
| 근거 없는 답변 `UNSUPPORTED_ANSWER` (참고 표시) | 모델 + 코드(근거 구절 대조) + 2차 확인 | AI 안내가 FAQ 원문 · 업무 규칙과 **반대**이고 그 반대 근거 구절이 원문에 글자 그대로 있을 때만. 정답 표본이 4~8건뿐이라 정확도를 증명하지 못해 비율 지표로 쓰지 않음 |

- 모델: 같은 통화를 3번 동시에 판정해 2번 이상 나온 것만 남긴다(`analyze.vote`). 문제마다 대본 문장을 인용해야 하고, 대본에 없는 인용은 버린다(`analyze.check`).
- 2차 확인: 1차가 잡은 용건 인식 오류 · 근거 없는 답변은 그 장면만 보여 주고 예/아니오로 다시 묻는다(`verify.md`). 정상 응대(업무 밖 질문 거절)를 잡는 오탐을 거른다.
- 판정 프롬프트(`prompt.md` · `verify.md`)에는 평가용 통화의 문장을 넣지 않는다(과적합 방지). 예시는 규칙 문장으로만 쓴다.
- 장애 구간(검색 서버 실패): 답을 못 한 것 자체는 AI 오류가 아니다. 장애와 상관없는 AI 잘못(통화를 끊음)은 센다. 장애 중에도 고객 불만은 센다(고객 말이 기준).
- 고객 되물음(`CUSTOMER_CONFUSION`)은 판정하지만 집계에서 뺀다.

## 정확도 (2026-11-10, gpt-6-luna medium, 3회 다수결 + 2차 확인)

| 항목 (정밀도 / 재현율) | 연습용 50통화 | 처음 보는 세트 (K쇼핑 60통화) |
|---|---|---|
| 고객 불만 | 96% / 76% | 94% / 84% |
| ㄴ 책임 일치 · 강도 일치 | 100% · 89% | 83% · 97% |
| 정보 인식 오류 | 85% / 81% | - |
| 용건 인식 오류 | 79% / 92% | - |
| 말 끊김 | 100% / 100% | - |
| 응답 지연 | 100% / 86% | - |
| 근거 없는 답변 (참고 표시) | 연습용 + 보강용 80통화 합쳐 맞음 2 · 오탐 1 · 놓침 8 | - |
| 감정 일치 | 89% | 92% |
| 해결 여부 일치 | 97% | - |

- K쇼핑은 사람 상담원의 쇼핑 상담 대화라 고객 불만 · 감정만 잰다(AI 오류 · 해결 여부는 해당 없음).
- 근거 없는 답변의 놓침은 대부분 원문에 반대 근거가 없는 지어낸 말(예: 자료에 없는 운영 시간)이다. 반대 근거 구절이 있을 때만 표시하도록 좁혀서 생긴 의도된 한계다.

정답은 검수자 2명이 판정 결과를 보지 않고 각자 매겨 둘이 같은 장면만 썼다. 사람 두 명끼리 일치(천장): 불만 장면 84~90%, 책임 97~100%, 강도 96~100%, 감정 98%. 비용: 통화당 출력 약 1.2만~1.3만 토큰(입력은 대부분 캐시).

## 실행

```bash
# 서비스 (ai/ 폴더)
CALL_ANALYSIS_TOKEN=... CALL_ANALYSIS_OPENAI_API_KEY=... uvicorn call_analysis.server:app --port 8090

# 실서버 통화로 시험 — 관리자 읽기 API로 대본 · 녹음 · FAQ를 읽어 이 서비스로 보냄 (서버 변경 없음, 본문 안 찍음)
DVA_API=https://<실서버>/api DVA_LOGIN_ID=... DVA_PASSWORD=... CALL_ANALYSIS_TOKEN=... \
  python -m call_analysis.try_live 9101 9105 > run.txt
#   TRY_LIVE_CACHE=폴더 · TRY_LIVE_AUDIO=폴더: 받아 둔 <통화>.json · <통화>.wav로 같은 입력을 다시 판정

# 정답과 비교 (정답 · 결과 파일은 개인정보라 저장소 밖에 둔다)
python -m call_analysis.evaluate gold.json run.txt
```

## 판정을 고칠 때

1. 고치기 전 점수를 잰다(`evaluate`).
2. 사례 하나를 막는 예외를 프롬프트에 늘어놓지 않는다. 사실로 정할 수 있으면 코드로, 아니면 정의를 고친다.
3. 연습용으로 고치고 시험용으로 확인한다. 시험용 점수가 비슷해야 외운 게 아니다.

## 파일

- `analyze.py`: 차례 나누기, 모델 입력, 판정 · 검사 · 다수결 · 2차 확인
- `facts.py`: 코드로 정하는 사실(응답 지연, 정보 인식 오류 일부)
- `timing.py`: 녹음에서 말한 구간 · 침묵 (numpy, 토큰 없음)
- `extract.py`: 판정 결과 → 백엔드 불만 저장 형식(`complaints` · `repeatQuestionCount`)
- `prompt.md` · `verify.md`: 1차 판정 · 2차 확인 지시문
- `server.py`: 판정 서비스 `POST /analyze` · `GET /health`
- `CONTRACT.md`: 입력 · 출력 명세 (백엔드로 옮길 때도 같은 모양)
- `try_live.py` · `evaluate.py`: 실서버 시험 · 정답 채점
