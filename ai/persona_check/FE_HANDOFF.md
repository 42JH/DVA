# 페르소나 시나리오 시험: 관리자 화면 전달 사항

2026-11-11 작성. AI 상담가(페르소나) 화면을 맡은 세션에 넘기는 문서다. 시험 실행기와 판정기는 다른 세션이 로컬에서 만들고 있고, 이 문서는 화면이 알아야 할 것만 적는다.

## 0. 지금 상태

| 항목 | 상태 |
|---|---|
| 시험 실행기(가짜 고객이 AI와 음성 통화) | 로컬에서 동작. 신규 고객 접수 1개 시나리오가 접수 완료까지 감 |
| 판정기(통화가 정답대로 됐는지 채점) | 접수 시나리오용 완성. 조회, 취소, 흐름 변형은 미구현 |
| 화면이 부를 API | **없음.** 백엔드 연동 전이다. 화면은 목 데이터로 만들어야 한다 |
| 서버 배치 | 미정. AI 파트가 MR을 받아 세팅할 예정 |

아래 데이터 모양은 실행기가 지금 실제로 내는 것 기준이지만, API가 생기면 이름이 바뀔 수 있다. 화면 쪽 변환 함수 한 곳에서만 읽도록 해 두면 바꾸기 쉽다.

## 1. 기능의 목적

관리자가 페르소나를 고쳐 [통화에 사용하기]를 누르면 다음 통화부터 운영에 적용된다. 그 전에 시나리오 통화를 자동으로 돌려, 적용 중인 버전과 새 버전의 결과를 나란히 보고 적용하게 한다.

- 전화는 실행기가 건다. 사람은 시험을 시작하고 결과를 본다.
- 시험은 뒤에서 돈다. 접수 시나리오 한 통이 약 4분 30초(실측)이고, 전체를 동시에 돌리면 5~10분으로 예상한다(동시 실행은 미확인). 관리자가 기다리지 않는 화면이어야 한다.
- 시험 한 번에 음성 모델 비용이 든다(시나리오 수만큼의 통화 비용).

## 2. 화면이 다룰 데이터

### 2-1. 시나리오 목록

AI 파트 스크립트 기준 18개. ID는 아직 확정이 아니다(지금 실행기에는 `N01` 신규 고객 접수만 들어 있음).

| 묶음 | 시나리오 |
|---|---|
| 접수 (5) | 신규 고객 접수, 기존 고객 접수, 발송 정보 변경, 기존 수신자 1건 매칭, 기존 수신자 여러 건 매칭 |
| 조회 (4) | 내역 0건, 1건, 여러 건, 미등록 번호 |
| 취소 (2) | 수거 전 취소, 수거 후 취소 |
| 흐름 변형 (7) | 한 번에 여러 정보, 중간 정정, 확인 단계에서 수정, FAQ 끼어들기 후 복귀, 중도 취소, 상담원 연결 요청, 무응답 |

시나리오마다 `id`, `name`, `kind`(정상/이상 구분, 지금은 "정상"만 있음)가 있다.

### 2-2. 시나리오 한 건의 판정 (실행기가 내는 `verdict.json` 그대로)

```json
{
  "scenario": "N01",
  "name": "신규 고객 접수",
  "passed": true,
  "summary": "통과 8 · 실패 0 · 제외 4",
  "checks": [
    { "name": "접수된 택배 수", "status": "pass", "expected": 1, "actual": 1 },
    { "name": "받는 분 번호", "status": "pass", "expected": "010-2345-6789", "actual": "01023456789" },
    { "name": "물품", "status": "pass", "expected": "중형 박스 1개", "actual": "중형 박스 1개" },
    { "name": "받는 곳 상세주소", "status": "skip", "expected": "102동 1503호",
      "actual": "원 헌드레드 투 동 원 파이브 오 쓰리", "note": "주소 정보를 고정값으로 채운 환경이라 채점하지 않음" }
  ]
}
```

- `passed`: 실패(`fail`)가 하나도 없으면 true.
- `checks[].status`: `pass` | `fail` | `skip`. `skip`은 그 환경에서 볼 수 없는 항목이고 통과에도 실패에도 넣지 않는다. `note`는 `skip`일 때만 있다.
- `expected`, `actual`은 글자, 숫자, null이 올 수 있다.
- 접수 시나리오의 검사 항목 이름: 접수된 택배 수, 접수 확인된 초안 수, 보내는 분 이름, 보내는 분 번호, 받는 분 이름, 받는 분 번호, 물품, 물품 가액, 보내는 곳 주소, 보내는 곳 상세주소, 받는 곳 주소, 받는 곳 상세주소. 다른 묶음의 항목은 아직 없다.

### 2-3. 행을 눌렀을 때의 상세

통화마다 아래가 남는다. 화면 시안의 "대화 로그와 결과표가 통화 상세와 같은 구성으로 열립니다"의 재료다.

| 재료 | 모양 |
|---|---|
| 대화 | `[통화 시작부터 초, "AI" 또는 "고객", 말]`의 목록 |
| 고객이 고른 행동 | `{ at, action: say/short/free/wait/end, index, text, why }`. 고객이 대본 몇 번 문장을 왜 골랐는지. 개발 확인용에 가깝다 |
| 말하지 않은 대본 번호 | 예: `[3, 10]`. AI가 그 질문을 하지 않아 쓰이지 않은 문장 |
| 녹음 | wav 한 파일. 왼쪽 고객, 오른쪽 AI. 한 통에 약 25MB |
| 백엔드가 받은 것 | 접수 초안, 접수 완료 요청, 통화 이벤트(발화, AI 동작, 업무 결과), 통화 분석. 운영 통화와 같은 계약 모양이라 기존 통화 상세의 변환 함수를 재사용할 수 있을 것으로 본다(확인 안 함) |

### 2-4. 버전 비교

시안의 "v6 결과(적용 중) / v7 결과(새 버전) / 변화"는 두 버전의 `passed`를 비교해 만든다.

| 적용 중 | 새 버전 | 변화 |
|---|---|---|
| 통과 | 실패 | 퇴보 |
| 실패 | 통과 | 개선 |
| 같음 | 같음 | 같음 |

적용 중인 버전의 결과는 저장해 두고 재사용할 계획이라, 새 버전만 돌 때가 많다. 적용 중 버전의 결과가 아직 없는 경우도 화면에 있어야 한다.

### 2-5. 페르소나 글 검사 (통화 없는 별도 기능)

저장 전에 페르소나 글에서 문제 구절을 찾는다. 결과는 문제의 목록이다.

```json
[{ "kind": "BUSINESS", "section": "역할", "quote": "보내는 분 성함부터 묻습니다.", "other": "", "why": "질문 순서를 정하는 업무 지시입니다." }]
```

- `kind`: `BUSINESS`(업무 지시가 섞임) | `RULE_CONFLICT`(업무 규칙과 반대, `other`에 규칙 원문) | `SELF_CONFLICT`(칸끼리 모순, `other`에 맞서는 구절).
- `section`: 역할, 성격, 톤, 속도, 맞장구, 끼어들기 중 하나. 6칸과 대응한다.
- 문제 없음은 `[]`, 검사 실패는 `null`이다. 둘을 구분해 보여야 한다.
- `BUSINESS`와 `RULE_CONFLICT`는 판마다 서로 바뀌어 나온다. 화면에서 하나로 합쳐 보일지는 사용자가 아직 정하지 않았다.

## 3. 화면이 가져야 할 상태

1. 시험한 적 없음
2. 시험 중: 전체 중 몇 개 끝났는지, 시나리오별로 대기/진행/끝남
3. 끝남: 표와 요약(전체, 개선, 퇴보, 새 버전 실패 수)
4. 시험 자체가 실패함: 통화가 연결되지 않았거나 중간에 끊긴 경우. 시나리오 "실패"와 다른 상태다
5. 제외 항목이 있는 통과: `skip`이 있다는 것을 알 수 있어야 한다
6. 결과가 낡음: 시험 뒤에 페르소나를 다시 고쳤으면 그 결과는 지금 글의 결과가 아니다

## 4. 사용자가 아직 정하지 않은 것 (가정하지 말 것)

## 6. 2026-11-12 변경: 창구가 생겼고 데이터 모양이 일부 바뀌었다

위 2장보다 이 장이 최신이다. 시험 도구는 `develop-ai`에 머지됐다(!579). 서버에는 아직 띄우지 않았고 백엔드 연동도 없어서, 화면은 여전히 목 데이터로 만든다.

### 6-1. 시험 창구 (AI 서버 옆에 따로 뜨는 프로그램. 화면은 백엔드를 거쳐 부르게 된다)

| 요청 | 응답 |
|---|---|
| `GET /scenarios` | `[{ id, name, group, core }]` |
| `POST /runs` `{ scenarios?: [id], core?: bool, promptText?: 글, voiceId?, concurrency? }` | `202 { runId }`. 시나리오를 안 주면 전체, `core: true`면 핵심 묶음 |
| `GET /runs/{runId}` | 아래 묶음 상태 |
| `GET /runs/{runId}/{scenario}/verdict` | 판정 전체 |
| `GET /runs/{runId}/{scenario}/audio` | 통화 녹음(wav) |

묶음 상태:

```json
{
  "runId": "1112_090752_bd17e9", "status": "running", "total": 3, "finished": 1, "candidate": true, "voiceId": null,
  "items": [
    { "scenario": "E1", "name": "1건 조회", "group": "조회", "status": "done", "passed": true,
      "summary": "통과 7 · 실패 0 · 제외 0", "error": null, "seconds": 106, "liveSeconds": 88.0 },
    { "scenario": "H10", "name": "무응답", "group": "종료", "status": "running", "passed": null, "summary": null, "error": null, "seconds": null, "liveSeconds": null },
    { "scenario": "F1", "name": "취소 가능한 택배 취소", "group": "취소", "status": "queued", "passed": null, "summary": null, "error": null, "seconds": null, "liveSeconds": null }
  ]
}
```

- 묶음 `status`: `running` | `done` | `interrupted`(돌던 중에 창구가 꺼짐).
- 항목 `status`: `queued` | `running` | `done` | `error`. `error`는 시나리오 실패가 아니라 시험 자체의 실패(통화가 연결되지 않음)이고 `error`에 사유가 온다. 이때 `passed`는 null이다.
- `candidate`: 후보 페르소나 글로 돌렸는지(false면 서버 기본 페르소나).
- `liveSeconds`: 음성 모델 사용 시간(요금 기준). `seconds`: 준비와 판정을 포함해 걸린 시간.

### 6-3. 판정 (2-2에 더해)

`checks`에 두 종류가 섞여 온다. 모양은 같다(`name`, `status`, `expected`, `actual`, `note`).

| 종류 | name 예 | expected / actual | note |
|---|---|---|---|
| 코드 검사 | 대본 진행, 접수된 택배 수, 받는 분 번호, 물품, 보내는 곳 지역, 조회 실행, 기존 주문 상태 | 정답 값 / 실제 값 | `skip`일 때만 사유 |
| 행동 확인 | "보내는 분 연락처를 묻지 않는다"처럼 문장 | `"지킴"` / `"지킴"`, `"어김: <AI가 한 말>"`, `"판단 못 함"` | 판정 사유 한 문장(통과 · 실패에도 온다) |

- `대본 진행`이 맨 앞에 온다. 실패면 "말하지 못한 발화: [4, 5]"처럼 오고, 통화가 중간에 멈췄다는 뜻이다. 이때 뒤 항목들은 대부분 따라서 실패한다.
- `expected`, `actual`이 객체로 올 때가 있다(`기존 주문 상태`: `{ "이지은": "CANCELLED", "박서준": "PAID" }`).
- `skip` 사유는 세 가지다: 이 환경에서 볼 수 없음(주소DB 없음), 판단 못 함(그 상황이 통화에 없었거나 판마다 판정이 갈림), 진행 기록 없음.

### 6-4. 통화 시간과 실패 양상 (화면 문구 · 진행 표시에 참고)

- 시나리오 한 통은 1~5분이다(무응답 약 1분, 조회 약 1분 30초, 접수 약 4분 30초). 2통씩 동시에 도는 것까지 확인했다.
- 통화가 60초 넘게 나아가지 못하면 실행기가 끊는다. 이 경우는 `error`가 아니라 `done`이고 `대본 진행` 실패로 보인다.
- 지금까지 본 실패는 대부분 "AI가 같은 말을 되풀이하며 멈춤"이었다. 실패 사유만으로는 무슨 일이 있었는지 알기 어려워, 대화 기록을 함께 보여 주는 것이 중요하다.
